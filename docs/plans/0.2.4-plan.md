## 0. Summary

- **Goal:** read a device's configuration over SSH (and NETCONF where it is on), compare the sections tacctl manages with what tacctl would render for that device, keep a record per device, run that over many devices at once, and cache the user's password for their console session so a batch asks once. Nothing is written to a device in 0.2.4; the first push is 0.2.5.
- **Shape:** one driver interface with two transports (D60, D61); six managed sections per vendor extracted from the device text and built, on the tacctl side, from the same code as the walkthroughs (D62, D63); a line-level comparison that treats secrets as present-or-absent (D64); a rebuildable record store under `/var/lib/tacctl` (D65); `device config pull|diff|list` with batch selectors and a global concurrency cap (D66-D68); the caller's own login, never a stored account (D69); the password cache as an agent inside the user's shell process (D70).
- **Order:** the lab spike (WP11.0) runs first and in parallel with the offline packages; every offline package has a fallback that does not wait on it (§8). The Junos lab switch and the Linux test host are live-testable by the coordinator; the lab WTI is operated by the user from run sheets; Cisco IOS-XE has no lab device and stays fixture-based with the user's paste acceptance.
- **Size:** 12 packages, ≈ 10-14 sessions, ≈ 7,000-9,000 lines (Go, bats, fixtures, docs). The last two code packages (per-device SNMP overrides, D72; the rollback target, D73) are cut first if the release grows; the plan says what moves to 0.2.5 then.

## 1. Goals and non-goals

### Goals

1. **`device config pull`** (D61, D62): connect to one or many devices as the invoking user, read the running configuration, extract the managed sections, store them and a record, and print one result line per device.
2. **`device config diff`** (D63, D64): the managed sections of the last pull against the statements tacctl renders for that device today, per section, with `-`/`+` lines; `--pull` refreshes first.
3. **Per-device records and staleness** (D65, D66): when, by whom, over which transport, with what result, and the per-section fingerprints; `device config list --stale` and a `CONFIG` column in `device list`.
4. **Batch** (D67, D68): selection by names, scope, vendor or staleness; `device.config.max_concurrency` (default 8, at most 64) that `--concurrency` can lower but never exceed; per-device timeouts; a progress view; an interrupt that stops starting new devices.
5. **Transport** (D60, D61): NETCONF where it answers, the SSH CLI otherwise; `device check` shows the NETCONF state.
6. **The password cache** (D70): asked once in a console or shell session, kept in memory only, forgotten on the rules the backlog fixed; `tacctl ssh` and the pull sessions use it; the plain CLI asks once per run.
7. **The SNMP section** (D62) read from the device and compared with the scope's settings (and, with D72, the device's overrides); what is missing shows in the diff; setting it is 0.2.5's apply.
8. **Per-device SNMP overrides** (D72, backlog §3f), last and cuttable.
9. **`tacctl rollback 0.2.3`** (D73) for the new keys and fields.

### Non-goals (0.2.4)

- Writing anything to a device (`apply`, `rollback` on the device, `commit confirmed`, the revert timer): 0.2.5. The spike settles their mechanics so 0.2.5's design is not guessed.
- WTI configuration reads (D71): 0.2.6 decides from the spike's run-sheet results whether the menus script at all.
- IOS-XE reads over NETCONF (D61): the probe only; the YANG shape of `get-config` is not the CLI's and 0.2.4 would need a second extractor for no gain over the CLI read.
- Unattended pulls (a timer, a stored credential, an ssh key on devices): the never-stored rule leaves no credential a timer could use; drift detection without a person is 0.2.7's device-account work (a read-only service account proved and rotated like the others). Open question 6 of the final report.
- Device tags as a selector (the backlog's "tag"): the registry has no free tag field [V: `devreg.Device`]; scope and vendor select, names list. A tag field is a 0.3.0 format question.
- Comparing secrets by value (D64), decoding Junos `$9$` or Cisco type 7.
- Per-user `space-completion`, the request-sync queue (§0b), nss_tacplus (§4), automatic discovery (§3e): unchanged, not pursued.
- A built-in `engineer` group, moving device data into `store.yaml`: 0.3.0 (§5).

| **D70** | **The password cache: an agent inside the user's own shell process.** (1) **Where:** the long-lived process of a session is the unprivileged `tacctl shell` / `tacctl-console` loop [V: `shell.go` runs `sudo [-n] [TACCTL_CONSOLE=…] [SSH_AUTH_SOCK=…] tacctl <words>` per line]; it holds the password in a page allocated with `mmap` and locked with `mlock`, zeroed on forget, in a process marked not dumpable (`prctl(PR_SET_DUMPABLE, 0)`), and never in a Go string that the runtime copies. (2) **How it reaches a line:** the shell listens on a Unix socket in a private directory (`$XDG_RUNTIME_DIR/tacctl/` or a 0700 directory under the user's home, mode 0600), passes its path in `TACCTL_ASKPASS=<path>` on each sudo line (added to the tiers drop-in's `env_keep` beside `SSH_AUTH_SOCK` [V: `tier.EnvKeep`]), and **answers only while a line is in flight**, only to a peer whose uid is the user's or root's (`SO_PEERCRED`), and only to a request that carries the session token the shell generated at start and put in the same variable (`<path>:<token>`). The protocol has four requests: `have` (yes/no), `get` (the password, once per request), `store` (after a device accepted it), `forget`. (3) **Who asks:** the root-side `tacctl device config pull` asks `have`, then `get`; when the agent has nothing it prompts on the terminal itself (no echo), uses the password for the run, and after the **first device accepts it** sends `store` if the policy allows the tier (so "checked before it is kept" means a real target accepted it; the password is never tried against the local tacquito); a rejection by any device sends `forget` at once and the run stops with `auth-failed` for the rest (one wrong password must not lock the account out on 60 devices: the pool stops starting new devices on the first `auth-failed`). `tacctl ssh` sets `SSH_ASKPASS=/usr/local/bin/tacctl _askpass`, `SSH_ASKPASS_REQUIRE=prefer` and a dummy `DISPLAY` on the user's ssh **only when `have` is yes**; the helper runs as the user, answers a prompt only when its text is a password prompt (never a host-key or passphrase prompt), and exits 1 otherwise. (4) **Policy:** `console password-cache tiers <tier>[,<tier>]\|none` (default `none`: off for every tier; the candidates are operator, engineer, superuser), `console password-cache idle <minutes>` (default 15, 1-120) and `max <hours>` (default 8, 1-24), in `console.yaml` under `settings.password_cache` written only when set; sent on the `_console-policy` line as `password_cache=yes\|no`, `pc_idle=`, `pc_max=` (unknown fields ignored by older parsers [V: `ParseRemote`]); plain `tacctl shell` takes `--password-cache` to the same rules. (5) **Forgotten:** on exit, after the idle time without a `get`, after the maximum lifetime, on the shell line `passwd`, on `console forget` (a shell-local word, no sudo), and at once on a device's rejection. The shell prints `password cached for this session (console password-cache)` once on store and `password forgotten (<why>)`. (6) **Not covered:** `-c` and batch lines (no process persists); the plain CLI from bash, which prompts per run; root (nothing to cache). (7) **Threat model written into the usage:** root reads any process; the cache protects against other users and against the password landing in files, logs, argv or the environment. *Alternatives:* a daemon per user (systemd user service; more moving parts and a credential outliving the session); the kernel keyring (`keyctl`, session keyring; works, but it is readable by any process of the user, cannot restrict to prompts, and needs `keyutils` on every server); sudo's own timestamp (it caches the sudo password, not the network one; console users do not use sudo passwords). | **(user)** never stored, session only, askpass agent, the forget rules; lifetimes, tiers and the socket protocol recommended |

## 4. Data model

- **The device record** (D65) and the sections file: shapes above. The sections file is YAML with one key per section (`aaa: |`, …) so a human can read it and so the per-device SNMP file and the registry share one reader [V: `yamlpy`]; the JSON record file follows the seen cache.
- **Staleness** (D66): `never` (no record), `failed` (last result not ok), `differs` (any section `differs`/`missing` against today's rendering), `ok`. Computed by `device config list` and the `CONFIG` column from the stored sections; a pull updates the stored state too, so `device list` is cheap (it reads the record, never renders) and `device config list --stale` renders (it must, to see store changes); the usage says so.
- **`device show`'s block:** `Configuration: pulled 2026-10-09 14:02 by alice over netconf (hello ok), ok; sections: aaa ok, roles ok, mgmt-acl differs, snmp missing, netconf n/a, breakglass ok`.
- **The settings** (D68) in `tacctl.yaml`; the console settings (D70) in `console.yaml`; the per-device SNMP map (D72) in `devices.yaml` and its credentials file. No `store.yaml` change (0.3.0 rule, §5 of the backlog).

## 5. Concurrency model

- One pool (D67); jobs are devices; `Concurrency = min(flag, device.config.max_concurrency, len(jobs))`; the cap is 64 and superuser-only (D68).
- Each job: render (D63, pure, in the worker), probe NETCONF when `auto` and the record's probe is older than a day or absent (`--transport auto` always re-probes with `--probe`), connect, read, extract, compare, write the sections file and the record under the store lock (one lock, short critical sections: the pull text is written before the lock is taken), report. The per-device timeout (`device.config.timeout`, `--timeout`) bounds the whole job; the connect timeout inside it is 10 s; the probe's 5 s.
- The password source (D70) is shared by every worker and resolved once before the pool starts (`have`/`get` or the prompt), so no worker ever prompts; the first `auth-failed` sets `StopOnAuthFailure` (the pool starts no new device, running ones finish, the summary says why) and sends `forget`.
- The interrupt (D67): the first Ctrl-C cancels the "start" context only; a second Ctrl-C cancels the running jobs' contexts too (their sessions close; the record says `interrupted`).
- The progress view writes from one goroutine fed by a channel; workers never write to the terminal.
- Nothing is shared between workers but the password source, the records store (locked) and the read-only `Data` per scope.

## 6. Credential handling

- The login is `SUDO_USER` (D69). The password comes from the agent (D70) or from a no-echo prompt on the terminal of the root process; without a terminal and without a cached password the verb refuses (`a password is needed and no terminal or cached password is available`), exit 1. It is held in the root process as a byte slice zeroed at the end of the run, passed to `devssh` through a closure, never on argv, in the environment, in a file, in a log line or in a `--json` document.
- `store` happens only after a device accepted the password (D70); `forget` on any rejection; the agent answers `get` only while the shell has a line in flight, only once per request, only with the token, only to its user or root.
- Host keys: pinned keys from the registry only (D69); the generated `known_hosts` is for the system ssh and stays.
- The device-side secrets that a pull reads (encrypted TACACS+ keys, SNMP communities) land in the sections file (root, 0600) and in the diff output of an engineer or superuser; `--json` output carries them as the device shows them (encrypted); `device config list` never prints text.

## 10. Risks

1. **The native SSH client against real devices** (D60): prompt and paging corner cases. Mitigation: the spike runs the client against the lab switch before WP11.5 depends on it; the fake device reproduces every capture; the system `ssh` stays for interactive use.

5. **Cisco behaviour is unverified** (no lab router): the IOS extractor and fixtures are from references; the CHANGELOG says "not lab-tested"; the user's paste acceptance stays in §0b.

## 9. Amendments from the spike and the package reviews (2026-10-09)

Settled by the lab spike (`0.2.4-spike.md`) and by the security reviews of WP11.1-11.3. They amend D62, D64, D65, D70 and §6; where this section and an earlier text differ, this section wins.

- **D62 (sections).** IOS "enable secrets' presence" is dropped (Managed renders none); `ip tacacs|radius source-interface` is not classified (the operator's choice); the application of the management filter on `lo0` is not a statement but a `Note` on the `mgmt-acl` result (`filter MGMT-ACL is not applied on lo0`), because the walkthrough leaves it to the operator. The Junos read is `show configuration | display inheritance no-comments | display set`, so statements kept in groups are seen where they apply; `groups` and `apply-groups` lines are ignored.
- **D64 (comparison).**
  - Statements compare as sets, **except** the order of Junos `system authentication-order` and of the terms of each firewall filter, and the order of Cisco ACL entries (runs of one action compare as sets, because IOS reorders host entries). A reordering reads `differs` (line op `!`).
  - Secret statements compare as a count of identical elided stems, so a stray secret with the same options shows as `+`.
  - `not visible` (`?`) covers only what the device omits for the login (the TACACS+/RADIUS server `secret` statement for a non-superuser); masked values are still present and their absence is `missing`. `SecretsVisible` comes from unquoted `/* SECRET-DATA */` tokens, or from the caller.
  - A section tacctl renders nothing for lists the device's statements as informational `~` lines, state `n/a`, never counted as drift.
  - IOS shapes marked `[A]` (`aaa session-id common`, IOS-added `privilege` parent lines, `snmp-server user` absent from `show running-config`) are assumptions until a lab router confirms them.
- **D65 / §6 (what is stored).** Nothing reversible is stored: `Extract` returns normalised sections with secret values elided and the Secret marks kept; the sections file, `--json` and diffs never carry a device's encrypted keys, communities or hashes. The fingerprint hashes the normalised form, so a superuser pull and an engineer pull of the same device agree.
- **D61 / D75 (transport and spike inputs).** Junos exec channels send `exit-status` (0 even for a CLI error), so the vendor reader inspects the output for `error:` lines; NETCONF is the ssh subsystem on the ssh port; a NETCONF confirmed commit is rolled back when its session closes unconfirmed (0.2.5: keep one session from confirmed commit to confirm, or use `persist`).
- **D60 / WP11.1 (client).** One client per device job; a per-call deadline that fires during channel open or a blocked write closes that client (the Dial context is the per-device deadline). The shell reader counts prompts against sentinels sent and fails closed; `PasswordSource` must return promptly and must not prompt (the caller resolves the password before Dial); the zeroisation promise ends at the askpass boundary because the SSH library takes a string.
- **D70 (cache).** One `get` per in-flight line (a second `get` is a rejection and forgets); a repeated store of the same bytes never extends the 8 h lifetime and the pull stores only a password it prompted for; the token goes through the environment (never sudo argv) and the root side unsets it; the agent refuses to start with a tracer attached or when memory cannot be locked.
- **D70 (3), who stores (review of WP11.6).** The root side sends `store` whenever it has a client for the session's socket and the password was one it prompted for: the only sink is the invoking user's own session (the socket is the user's, the peer uid is checked on both sides, the token is the line's), so the policy gates the creation of the agent, not each store. A store never lands after a forget in the same run (one lock across the store and the forget).
- **D70 (2), the token is the line's (review of WP11.6).** The agent is shut between lines. For a line that runs an askpass-using verb (`ssh`, `device ssh`, `device config pull`, `device config diff`) and no other, the shell mints a token, puts `<socket>:<token>` in that line's sudo process environment and kills the token when the line ends; the agent answers one `get` per line and, after it, only `forget`. The residual: a process of the same user that reads ssh's or the pull's environment during the line and gets there before the one `get` of the helper or the pull. `tacctl ssh` with a cached password starts ssh as the user directly (no sudo), so the variable is never a sudo variable or argument.
