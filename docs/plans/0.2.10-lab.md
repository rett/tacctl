# 0.2.10 lab results (2026-10-15)

The NETCONF items of `0.2.10-plan.md` section 6, run on the lab switch
(Junos 25.4R1-S2.3, EX4300, one key-authenticated superuser) with raw RPCs
over `ssh -s netconf`, one session at a time. The release build's NETCONF
transport has not been run against the device: these are the device's
answers, which the fake and the transport were then corrected to. Every
change was a `zz-tacctl-*` class under `commit confirmed 1` or a plain
commit removed in the same run; the configuration (`display set`) was
compared byte for byte with a snapshot taken before the first change, and
was identical after every run. Another administrator's CLI session was open
throughout; the shared candidate was clean (its compare against the
committed configuration was empty) when the runs began.

| # | Result | Consequence |
|---|---|---|
| N1 | **Refuted.** In `<open-configuration><private/>` a `<commit><confirmed/>` is refused: `"commit confirmed" is not supported for private configuration` (error-tag `operation-failed`, severity `error`, nothing committed). `<open-configuration><exclusive/>` does not exist: `syntax error, expecting <invoke-on>`, bad-element `exclusive`. | N2 | **Corrected.** The first reading (a rollback about 5 s after the close) was the window of a one-second `<confirm-timeout>` expiring (N9), not the close. With a 600 s window tacctl was killed (SIGKILL) right after the confirmed commit: the commit stayed pending for the 70 s it was watched, `rollback in 10mins` with the `rollback pending` line, until cancelled by hand. Confirmed by the same session with `<commit><log>text</log></commit>`: no pending marker afterwards, the log kept. **The cancel that works:** in a session holding `<lock-configuration/>`, `<load-configuration rollback="1"/>` (reply `<load-configuration-results><ok/>`), the compare is exactly the inverse of the change, then `<commit><log>text</log></commit>`; the entry is a normal one, the confirmed entry has no pending line and the configuration is the one before the change. After the confirming commit the line is gone and the label stays on the entry below. | Pending is the `rollback pending` line, never `RollbackIn > 0`. The parser keeps the line out of the comment. |

## Facts the replies showed

- `<open-configuration><private/>`, `<lock-configuration/>` and
  `<unlock-configuration/>` answer with an empty `<rpc-reply>` on success:
  no `<ok/>`, no element. `<close-session/>` answers `<ok/>`.
- `<load-configuration action="set" format="text">` answers
  `<load-configuration-results><ok/></load-configuration-results>`.
- `<commit-configuration><check/>` answers `<commit-results>` with
  `<commit-check-success/>` and, outside it, `<ok/>`. A commit, confirmed or
  not, answers `<commit-results>` with `<commit-check-success/>`,
  `<commit-success/>` and the revision information, then `<ok/>`.
- `<get-configuration compare="rollback" rollback="0" format="text"/>` with
  nothing staged answers a `<configuration-output>` holding only a newline,
  inside `<configuration-information>`; with a staged change it holds the
  brace diff (`[edit system login]` and `+ class ... {`).
- A load into the shared candidate with no open private session or lock goes
  to the shared candidate; a confirmed commit then commits the whole shared
  candidate, which is why the transport reads the compare under the lock and
  refuses a candidate that holds anything.
- `<get-commit-information/>` carries the history as `<commit-history>`
  elements with `<sequence-number>`, `<user>`, `<client>`, `<date-time>` and
  a `<comment>` for the label; the transport reads `show system commit`
  through `<command>` instead, as the command line does.
- `<load-configuration rollback="1"/>` in a locked session answers
  `<load-configuration-results><ok/></load-configuration-results>`; the
  compare is then the inverse of the newest commit and a `<commit>` makes it
  a normal entry (the cancel). A session that closed or was killed left the
  confirmed commit pending (N2).
- The hello advertises `candidate:1.0`, `confirmed-commit:1.0` and
  `validate:1.0` (both the `urn:ietf:params:netconf` and the
  `urn:ietf:params:xml:ns:netconf` forms).
- The NETCONF service of the lab switch has `connection-limit 5` and
  `rate-limit 10` set (N8).

## Runs through tacctl (the release build, `--transport netconf`)

A TACACS+ superuser of the lab scope applied one harmless statement (a
login message) to the lab switch; every step was compared byte for byte with
the configuration before it.

| Run | Result |
|---|---|
| `pull`, `diff`, `plan` of the `netconf` section | The pull reads over NETCONF (`hello ok`); a `netconf` setting equal to what the device holds (`enable`, limits 5 and 10) is `ok` and plans nothing. |
| `apply --check` | `check ok [via netconf]`; the candidate was locked, loaded, compared, checked and discarded; nothing committed. |
| `apply` | Applied through NETCONF in 13 s: lock, load, compare, check, confirmed commit (`rollback in 10mins`), fresh login, confirming commit; both history entries carry the change id. |
| SIGTERM after the confirmed commit | `rolled back: interrupted; cancelled at ...`; the active cancel (`rollback 1`, commit) ran 3 s after the commit; the configuration was the one before. |
| SIGKILL after the confirmed commit | The commit stayed pending to the window's end (the device does not roll back on a closed session); the next run refuses with the id and `pending until <time>`, `device show` says `PENDING until`; cancelled by hand with `rollback 1` and a commit. |
| `--hold`, answered `no` | `rolled back: verification failed (the hold was not confirmed)`, cancelled at once. |
| `--hold`, terminal hung up | The interrupt path cancelled actively; configuration restored. |
| Another editor's staged change in the candidate | `failed: the configuration database is locked by <user>`; nothing committed. The holder is on the line after `locked by:`. |
| Another editor merely in configuration mode | The NETCONF gate does not see it (no staged change); the command-line gate refuses (`other editors or staged changes`). |
| Four checks in 13 s | One SSH login each, the NETCONF channels multiplexed on it: nowhere near the connection limit (5) or the rate limit (10 a minute). |
| A bad statement among good ones (N3) | The load is not atomic: the good statement was applied; the bad one gave two error-severity `rpc-error`s (`'bogus-permission' is not a defined permission` and `invalid value` with `<bad-element>`), the delete of an absent object a warning `statement not found`, and the reply ends with `<ok/>`. An error severity fails the load, a warning does not; the candidate was discarded. |
| `--transport netconf` with a service change | Refused with what to run instead; `cli` and `auto` take the command line. |
| Service limit changed (`connection-limit` 5 to 6, then back) | Applied over the command line with `[NETCONF verified: hello ok]`, then restored the same way; the configuration matched the one before. |
| Service disabled (`delete system services netconf`) | Applied over the command line with `[NETCONF verified: not answering]`; a raw subsystem request is refused (`subsystem request failed on channel 0`), which the transport reads as `port closed`. The pull then read over ssh and recorded `netconf: port closed`. |
| While the service was off | `--transport auto` took the command line (`[via cli: NETCONF port closed at the last read]`); `--transport netconf` failed with how to recover; the default was unaffected. |
| Service enabled again | Applied over the command line with `[NETCONF verified: hello ok]`; NETCONF answered again and the configuration matched the one before the runs. |
