**refuted** (with the change it forces on D60-D64) or **open** (what is

## (a) The configuration text

- `show configuration | display set` over an ssh exec channel, over the NETCONF
  `<command format="text">` RPC and over `<get-configuration format="set"/>`
  returned the same text: byte-identical, 564 lines, unpaged, in all three.
- Over NETCONF the reply is wrapped as `<configuration-output>` (command) or
  `<configuration-set xmlns="http://xml.juniper.net/xnm/1.1/xnm">`
  (get-configuration), with XML escaping (`&quot;`, `&lt;`).
- **Masking.** An engineer-class login gets the same statements with each
  secret value replaced by `/* SECRET-DATA */` (unquoted). Three statements
  were masked in the capture: the root authentication hash, a login user's
  password hash and the same user's ssh public key. The TACACS+ server's
  `secret` statement is not shown to the engineer at all (563 lines against
  564). A masked statement is still present, so "present, not compared"
  holds, and a masked value must never be reported as drift. An omitted one
  is not "missing": a pull as a non-superuser can say `present` or
  `not visible` for a secret statement, never `missing`; only a login that can
  see secrets (the superuser class) can say `missing`. The superuser view
  carries the real values.
- The set text carries no `deactivate` or `protect` statements in the
  capture; the extractor stays tolerant of both.
- **Exec channel exit status (checked after the devssh review).** The Junos
  exec channel sends `exit-status`, and it is `0` even for a CLI error: a
  mistyped command prints `error: syntax error, expecting <command>: ...` on
  the output and still exits 0. The exit status therefore proves the channel
  ended cleanly, not that the command was understood; the vendor reader
  inspects the output for `error:` lines.
- **Group inheritance.** With a temporary group applied (`apply-groups`),
  `show configuration | display inheritance no-comments | display set` prints
  the group's statement at its normal path (`set system login message ...`)
  and keeps the `set groups ...` and `set apply-groups ...` lines; the
  plain `display set` prints only the group form. Output is otherwise
  identical on a device with no groups (564 lines both ways). The Junos
  reader therefore uses the inheritance form, so settings kept in groups are
  seen where they take effect.
- The switch's NETCONF hello advertises `base:1.0`, `candidate:1.0`,
  `confirmed-commit:1.0`, `validate:1.0` and `url:1.0` (scheme http, ftp,
  file), and the Junos `xmlns` for the release.
- NETCONF framing is base:1.0 end-of-message (`]]>]]>`). The client sends its
  own hello advertising only `base:1.0`.

| `system services netconf ssh` present | `ssh -s <switch> netconf` answers with a hello; TCP 830 accepts | `hello ok` |

the device's ssh port (one pinned key, one firewall rule) and need not
probe 830.

## (c) Concurrency

Eight, sixteen and thirty-two concurrent sessions as one user, each running
`show configuration | display set | count`: all succeeded; wall time
1.1 s, 2.0 s and 4.4 s. No connection limit or rate limit was hit (the
switch's ssh service has none configured). D68's default of 8 stays; the
upper bound of 64 is not exercised and stays a configuration ceiling, not a
promise. The TACACS+ server logged every login; no per-source limit is
needed.

## (d) `commit confirmed` (inputs for 0.2.5)

- **CLI:** `commit confirmed 2` printed `commit confirmed will be rolled
  back in 2 minutes`; with nothing sent, the switch rolled back at expiry
  (`by root via other` in `show system commit`) and the configuration was
  identical to the pre-change one.
- **NETCONF:** `<commit><confirmed/><confirm-timeout>N</confirm-timeout>
  <log>text</log></commit>` is the working form (minutes; a `confirmed`
  *attribute* form was not needed). A following `<commit/>` in the same
  session confirms. **Constraint:** if the session that issued the confirmed
  commit closes without confirming, the switch rolls back immediately, within
  seconds, not after the timeout. 0.2.5's apply must therefore keep one
  NETCONF session open from the confirmed commit through the verification and
  the confirming commit, or use `persist`; it must not reconnect to confirm.
  `persist` was not exercised.
- `load-configuration action="set"` over NETCONF with `<get-configuration
  compare="rollback" rollback="0" format="text"/>` returns the `[edit ...]`
  diff (`+ message "...";`), usable as the pre-commit `show | compare`.
- The candidate lock (`<lock><target><candidate/>`) and its release worked;
  an apply should hold the lock for the whole transaction.
- Commit comments (`<log>`) appear in `show system commit` and are the
  natural place for the tacctl change identifier.

## (e) Class limits and accounting over NETCONF

## Junos apply mechanics (fact finding for the apply release, 2026-10-10)

Run on the lab switch over NETCONF with the admin key, in a **private**
edit session (`<open-configuration><private/>`), on `ZZ-TACCTL-*` objects
only, never committing; every run ended with `<close-configuration/>` and a
check that the shared candidate equals the committed configuration (empty
`<get-configuration compare="rollback" rollback="0"/>`). Another administrator
was logged in on the CLI during the runs, which shaped the choice of mode.

| Question | Result |
|---|---|
| Edit session type | **Private** is the safe choice for automation: its changes are invisible to every other session, `<close-configuration/>` discards them, and a dropped session cannot leave the shared candidate dirty. A shared candidate would be discarded for everyone by `discard-changes`, including another user's pending edit. |
| Loading a delta | `<load-configuration action="set" format="text"><configuration-set>` takes `set`, `delete` and `insert` lines; the reply is `<load-configuration-results><ok/>` and carries `<rpc-error>` elements beside the `<ok/>` when a statement failed. |
| A bad statement in a batch | **Not atomic.** The statements before and after the bad one are applied; the reply holds an `<rpc-error>` (severity `error`, message `syntax error` or `range: ...`, `<bad-element>`) next to `<ok/>`. An apply must treat any error-severity `<rpc-error>` in the load reply as a failed load and discard the whole candidate. |
| Delete of a node that is not there | a warning-severity `<rpc-error>` `statement not found` and `<ok/>`: idempotent, but a driver must tell warning from error. |
| Validation | `<commit-configuration><check/>` answers `<commit-check-success/>` and adds no commit to the history; a semantic error comes with `source-daemon`, `error-path` (`[edit firewall ... from]`), `bad-element` and a message (a prefix list that does not exist). Works in private mode. |
| Set of an existing node | modifies in place (keeps position); a new term goes last; `insert ... term c before term a` reorders deterministically. |
| Removing a leaf | `delete ... term b then discard` also removes the then-empty term. |
| Replace | `<load-configuration action="replace" format="text">` with `replace:` markers replaces only the tagged node (siblings are merged); a whole filter is replaced by tagging the filter. Not tried: `override`. |
| Diff | `<get-configuration compare="rollback" rollback="0" format="text"/>` gives the `[edit]` diff in brace form; `format="set"` is ignored (still brace form); `format="xml"` gives the structure with `nc:operation="create"` (and presumably `delete` and `replace`). `rollback="1"`, `"2"` compare the candidate with older commits. |
| Reading back as set lines | `<get-configuration database="candidate" format="set">` with a `<configuration>` filter gives `set` lines for a subtree; comparing sets is how a delta is computed (below). |
| Groups | a group and its `apply-groups` show in the diff as `groups` and `apply-groups`; `inherit="inherit"` (display inheritance) shows the statement at its effective place, the plain view does not. A delta against effective values must be loaded into the group when the statement lives there. |
| Contention | a second session's `<lock>` is refused with `lock-denied` naming the holder; a private session opens with a warning (`changes cannot be committed while 'configure exclusive' is active`), can load, and its `commit check` is refused with `lock-denied`. |

Computed delta, tested end to end: from the candidate's `set` lines (current)
and the wanted lines, `delete` for each current line not wanted and `set` for
each wanted line not current gave a result equal to the target as sets, in
order; the diff showed only the intended changes; re-applying the same delta
returned only the `statement not found` warning for the delete.

Protocol this supports (for the apply release): open private; read current
`set` lines of every managed subtree; compute `delete`/`set`/`insert`; load;
fail on any error-severity `<rpc-error>`; read back and compare with the
target; take the `compare` diff as the change record; `commit check`; then the
confirmed commit with the **same** session kept open (see (d) above), verify,
confirm; always `close-configuration` on any failure. Order-sensitive lists
(filter terms, authentication order) need `insert` or a whole-node `replace`.

Not tried here: the confirmed commit itself (not committing was the brief),
`override`, `commit synchronize` (single RE), and a candidate dirtied by
another user in shared mode.

## WTI: ways to configure a unit (documentation study, 2026-10-10)

The full interface reference built from this work is `wti-interface.md`.

From WTI's published artifacts for 8.10 (the firmware's MIB, release notes and
the RESTful v2 OpenAPI file) and the DSM/CPM user guide, plus the read-only
discovery above. Nothing here was changed on the unit.

| Method | Reaches | Notes |
|---|---|---|
| SNMP | ports (name, status), plugs, plug groups, the local user table (name, password, level, access flags), environment, alarms | **No** AAA, SNMP, SSH, IP tables or network objects in the MIB: not a configuration path |
| SSH text menus | every page (system `/F`, ports `/P`, network `/N`) | the only path to the per-port Direct Connect (per-port SSH, port 22nn) and IP alias; leaving a page with ESC saves it; no commit or confirm |
| RESTful API v2 (HTTPS, basic auth or token) | `aaaserver`, `ssh`, `snmpaccess`, `snmptrap`, `syslogserver/client`, `iptables`, `web`, `lockout`, `users`, `interface`, `hostname`, `dnsservices`, `timedate`, `serialports` (name, baud, parity, mode, timeouts), `staticroute`, plug and group control, `GET settings` (the configuration as XML) | needs web access (HTTPS) enabled on the unit, a local user with `accessapi` or a token; each PUT applies at once; structured replies with a status code; **no** Direct Connect or IP alias in `serialports` |

Direct Connect, as documented: per port (`/P` item 31) `On - Password` makes
the port reachable by SSH on TCP 2201 + (n - 1) for a DSM-8/CPM-800 (22nn for
the n-th port; 2301 telnet without a password, 3101 raw socket); the account
must be allowed that port and, with the Administrator command setting off at
the network port, not be an Administrator-level account. The lab unit has
Direct Connect Off on every port checked.

Apply semantics (tested on the lab unit, 2026-10-10, with the SNMP trap
managers and the disabled RADIUS page, restored afterwards): a field is
entered at a value prompt (`<text><CR>` to change, `<SPACE><CR>` to clear,
`<ESC>` to cancel; the prompt prints the accepted characters and the current
value). **The value takes effect when its `<CR>` is accepted**, not at the
ESC: a session whose ssh client was killed with SIGKILL on the page, right
after the entry and before any ESC, left the value in effect for the next
login. The configuration is written to flash only when the top-level menu
(`/N`, `/F`, `/P`) is left: the unit then prints `Saving configuration to
flash - Please wait...`; whether an interrupted session's change reaches
flash was not tested (a reboot would show it), and the rule below assumes it
does not. A driver therefore (1) treats every accepted entry as live at once,
(2) walks the whole ESC chain and waits for the save line, (3) after any
disconnect reconnects and re-reads the page, and (4) keeps the old values to
revert from.

Validation (tested the same way, trap manager 4, restored afterwards): an
entry with a character the prompt lists as not allowed (`/`, `*`, `|`) or
longer than 64 characters is refused with the line `ERROR: Invalid entry.`
printed above the current value, the prompt stays and nothing changes. There
is no semantic check: `999.999.999.999` was accepted (it is a legal domain
name) and applied like any value. A driver must validate addresses and
numbers itself before it types them, and treat `ERROR:` on the screen as a
failure of that field.

Numeric and enum fields (tested on the RADIUS page of the lab unit, a service
that is off with no host; four values were changed together and restored):
a number prompt states its range (`Enter 1 - 99`, `Enter number of seconds
(1-60)`) and refuses text, zero and out-of-range values with `ERROR: Invalid
entry.`, leaving the field unchanged; a pick is a 1-based numbered list
(`1. Off  2. On`; fallback local has three choices) and refuses any other
entry the same way. Several items changed on one page applied together when the
page was left, and a new login showed all of them; restoring them in one
session returned the page to its original values. The secret word prompt
(TACACS) prints the **current value in clear**; a driver must never log the
screen, and any capture of it has to be redacted before it is kept.

Driver rules these tests support: validate every value against the page's
declared type and range first; type it only at its own prompt; treat any
`ERROR:` line as a failed field; walk the whole ESC chain and wait for
`Saving configuration to flash`; after any unexpected disconnect assume
nothing was saved, reconnect and re-read the page, then continue or revert
from what is found.

Lock-out analysis (what to change only with out-of-band access): IP tables
(applied at once; no confirm), SSH (enable, port, password authentication),
network interface, the last local administrator, the invalid-access lockout.
Low risk: SNMP access and traps, syslog, serial port names and parameters.
Always: a `GET settings` snapshot before a change and a read-back after it,
one page per run, a second authenticated session kept open, a verified local
fallback account with fallback-local on.

## Legacy IOS 12.4 (lab 7200 emulator, 2026-10-10)

A Cisco 7206VXR emulator running IOS 12.4(15)SW (c7200-itpk9-mz), local login,
one privilege-15 user, no `aaa new-model`. Read, help and configuration probes
under the rules of the lab: the router was returned to its first configuration
and compared line by line after each pass.

**ssh.** SSH 1.99. Key exchange `diffie-hellman-group1-sha1` only, host key
`ssh-rsa`, ciphers `aes128-cbc`, `3des-cbc`, `aes192-cbc`, `aes256-cbc`, MACs
`hmac-sha1`, `hmac-sha1-96`, `hmac-md5`, `hmac-md5-96`. OpenSSH 9.x needs
`KexAlgorithms`, `HostKeyAlgorithms` and `Ciphers` appended; before this pass
`legacy-ssh` lacked the ciphers (CHANGELOG 21). OpenSSH 9.6 `ssh-keyscan` reads
no key from it (CHANGELOG 22 adds the built-in scan). One exec channel per
connection: the device closes the connection after each exec command, so the
reader uses a shell session (the 0.2.4 default for Cisco). The built-in reader
read the configuration and `Extract` parsed it (the local user lands in
`breakglass`, secret flagged).

**Privilege.** An exec channel at privilege 1 answers `Line has invalid
autocommand "<cmd>"` for a command above level 1.

**Syntax accepted** with `aaa new-model` on (the `aaa` subcommands are hidden
until it is; `radius-server` is unrecognised on this image): every statement of
the legacy rendering: `tacacs-server host <ip> single-connection timeout 5 key
<key>`, `aaa group server tacacs+ <name>` / `server <ip>`, `aaa authentication
login default local group <name>`, `aaa authorization exec|commands <n> default
local group <name> [if-authenticated]`, `aaa authorization config-commands`,
`aaa accounting exec|commands <n> default start-stop group <name>`, the
`privilege exec [all] level <n> ...` lines, both standard ACLs, `snmp-server
community <c> RO <acl>`, `location`, `contact`, `username <u> privilege <n>
secret 5 <hash>` (the hash must be a valid md5-crypt string with a 4-character
salt) and `access-class <acl> in` on the vty lines.

**What `show running-config` stores** (matters for the comparison):

| Typed | Stored |
|---|---|
| `permit 192.0.2.10 0.0.0.0`, `permit host 192.0.2.10` | `permit 192.0.2.10` |
| `privilege exec level 7 clear arp-cache` and the like | the line, plus implicit parents: `privilege exec level 7 clear`, `... clear ip`, `... undebug`, `level 1 show` |
| `privilege exec all level 7 monitor capture` | `privilege exec level 7 monitor` (no `capture` on this image) |
| `privilege exec level 7 clear mac address-table dynamic` | nothing beyond the parent (accepted, not stored) |
| the `aaa` lines | reordered (authentication, `aaa authorization config-commands`, exec, commands, accounting), a trailing space on some |
| `snmp-server community` | `snmp-server queue-length 100` appears beside it |
| `tacacs-server host ... key <key>` | the key in clear with `service password-encryption` off |

**Lock-outs found by doing it.**

1. `aaa new-model` with only `aaa authentication login default local`: every
   new ssh login lands at privilege 1 (`username ... privilege 15` applies only
   through `aaa authorization exec`), and with no `enable` secret there is no
   way to level 15 (`enable` answers `% Error in authentication`). The console
   line (`privilege level 15`) is the only way back. A block that enables AAA
   on such a device must carry `aaa authorization exec default local ...` in
   the same paste.
2. `no aaa new-model` does not put `login local` back on the vty lines: they
   keep no login method and ssh refuses the password. The back-out of
   `aaa new-model` has to restore `login local` on every vty range.
3. `configure replace <file> force` skipped the removal of `aaa new-model` in
   one pass (the line stayed): do not rely on a replace to undo it.

**Configuration replace and timed rollback.** `configure ?` offers `confirm`,
`replace`, `memory`, `network`, `overwrite-network`, `terminal`. There is no
`configure terminal revert`. `nvram:` accepted no new file (`%Error copying
... (Invalid argument)`, `archive path nvram:` fails the same way); `disk0:`
is a writable file system (the router has no flash). With `archive` /
`path disk0:<prefix>`:

- `configure replace <file> [list] [force] [ignorecase]`; the prompt is
  `Enter Y if you are sure you want to proceed. ? [no]:` and `force` removes
  it. **`list` is not a dry run**: it applies the replace and prints the
  commands per pass. The listed commands are the deletions and additions
  (`no <line>`, a submode header with its `no` children).
- `configure replace <file> force time <10-120>`: **seconds**, and `force`
  must come first (`time 2 force` is rejected at the number). The
  configuration is replaced at once and the pre-replace configuration is
  written to `<archive path><n>` (`Timed Rollback: Backing up to ...`).
- Not confirmed within the time: the router **rolls back by itself** (20
  seconds measured, 21 s after the replace), with the ssh session still open.
- `configure confirm` cancels the rollback, from the same session or from
  **another session** (30 s window, confirmed from a second login after 1 s;
  still replaced 40 s later).
- The ssh session killed after the replace: the rollback **still happens**,
  on time (the timer is the device's).
- The rolled-back file stays on disk0 (one per replace): clean them up.
- `configure replace` applies a delta (it computes the commands), so it is
  not a whole-configuration reload; whether it handles every statement
  (`aaa new-model` removal above) is per statement.
- `archive` with `log config` is part of the original configuration and is
  unrelated; `show archive` prints `Archive feature not enabled` until a
  `path` is set.

**For the paste block** (0.2.5): the confirmed-change wrapper for this IOS is
`archive` + `path <fs>:<prefix>` once, then `configure replace <file> force
time <seconds>` and `configure confirm`, with a file the person has put on
the device (the candidate configuration as a full file; the plan's delta of
lines does not map onto it) or the line-by-line paste without a timer and a
`no`-line back-out. Nothing here was run on IOS-XE.

## Changes to the plan
