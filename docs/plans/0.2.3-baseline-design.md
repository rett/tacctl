# 0.2.3 baseline commands and privileges: design and user decisions (2026-10-08)

Spec for WP10.6c (docs/plans/0.2.3-plan.md section 3b, D52). Produced by a Fable design consult after an Opus audit of the shipped baseline and the tacquito fall-through probe; the user's decisions below override the consult where they differ.

## User decisions (2026-10-08)

1. **Structure: Fable's split.** Shipped defaults get only the small safe changes (the `privileges.operator` rewrite, `terminal length|width` for readonly, `clear counters|line` for operator); the deny/permit pairs, the Junos deny sets, EN-CLASS and the engineer list stay in the opt-in preset. `group reset` restores the shipped content; `group reset --preset` the role's preset values.
2. **Junos class bits:** viewer gains `network`; operator loses `reset`.
3. **Engineers MAY configure SNMP (overrides the consult).** Do not deny `snmp-server` in the engineer's Cisco rules (remove it from the `trust` boundary used by `no`/`default`, from the `snmp-server|deny|` line, and from the `do` list where it appears) and remove `snmp` from the engineer's Junos `deny-configuration` (the reader sets for viewer and operator keep `snmp`, so those roles cannot read community strings). Recompute the engineer set sizes after the change and keep the size table test current. The walkthrough text about SNMP being pasted by a superuser is dropped; D45's engineer access to the credentials is consistent with this.
4. **The small choices, all accepted:** operator gets `clear line` and `clear counters`; engineers stay denied `reload` (no `in|at|cancel`); engineers may use `crypto isakmp|ipsec|map` and are denied `crypto key|pki|ca`; the soft-BGP-clear operator rule is a documented add-on, not shipped; `alias` is denied until the lab proves what IOS authorizes.

## Decisions on the revision (user, 2026-10-08; these override the revision below where they differ)

1. **The readonly and operator permit rules are SHIPPED defaults** (NCM `dir`/`terminal length|width`/`exit`/`logout`, operator `monitor capture`, `ssh`/`telnet` hops, single-entry ARP/MAC clears, `undebug`): they are permit-only and cannot deny anything a role has today. The deny pairs, the Junos sets and the engineer list stay in the opt-in preset.
2. **Junos: nothing is hidden from reading.** Readonly and operator carry NO reader `deny-configuration`: they see the full configuration with secrets redacted (`SECRET-DATA`, the class has no `secret` bit). "We don't need to hide the lines, just show everything with redacted secrets from readonly up."
3. **Strict nesting by visibility: the engineer must not hide what readonly and operator can see.** So the canonical engineer `deny-configuration` is EMPTY (no `system login|auth|tacplus|radius|...`, no `snmp`, no lo0 filter, no `security ...`, no management interface paths). The engineer's `deny-commands` stay (they are operational, do not hide configuration, and nest). "If we wish to further restrict then we can add non-canonical settings": a site restricts engineers by customising `group junos engineer deny-configuration` itself; WP10.6c may ship the revision's engineer set as a documented, opt-in hardening example (not canonical, not applied by the preset or `group reset`). Consequence to state in the CHANGELOG and README: with the canonical settings a Junos engineer's `EN-CLASS` bits are the only limit on configuration, so an engineer can edit `system login`, `tacplus-server` and the management filter on Junos; the Cisco rules (which hide nothing) still block the same on Cisco. The asymmetry is the user's accepted trade-off.
4. **Defaults taken from the consult for the items not put to the user (change on request):** operator `ssh`/`telnet` hops allowed; single-entry ARP/MAC clears allowed; no debug add-on shipped (documented only); `view full` at level 1 only if the lab proves the filtered backup useless.
5. **Engineers are unrestricted on Cisco too (user, 2026-10-08), so they can push tacctl's managed sections with their own login (0.2.5).** The canonical Cisco engineer list loses every configuration-mode block of the revision's trust boundary: `aaa`, `username`, `enable ...`, `tacacs`, `tacacs-server`, `radius`, `radius-server`, `line`, `login`, `password`, `privilege`, `transport`, `access-class`, `authorization`, `accounting`, `parser view`, `service password-...`, `key config-key`, the management-ACL pattern under `ip`, `ip http|ssh|...`, `crypto key|pki|ca`, `config-register`, `boot`, `license`, `event`/`kron`/`alias`/`shell`, `netconf-yang`/`netconf`/`restconf` (D53's enable path is then usable by engineers), `logging ...` protection, and the `no` and `default` rules built from that list; the `trustBoundary` constant goes away. This mirrors Junos, where the canonical engineer has no `deny-configuration`. What stays denied (the exec-level lifecycle, destructive and shell-escape commands, which nest and hide nothing): `reload`, `delete`/`erase`/`format`/`fsck`/`rename`/`mkdir`/`rmdir`, `request`/`install`/`software`/`upgrade`/`issu`, `write erase`, `copy` into running-config or flash (only the save and export forms are permitted), `configure network|memory|replace <url>`, `tclsh`/`guestshell`/`app-hosting`/`iox`/`scripting`, `debug all|aaa|tacacs|radius`, `hw-module`/`redundancy`/`switch`, and the matching `do` list. (Implementer: derive the list from the revision's engineer list minus the configuration-mode blocks above; Opus reviews it against this paragraph.) Consequences to state in the CHANGELOG and README: an engineer can change AAA, TACACS+/RADIUS servers and keys, lines, privilege levels and the management ACL on Cisco, so a mistake can lock a device out; the push (0.2.5) protects itself with the revert timer, and a site that wants a trust boundary customises the group (`group commands add ...`) or applies a documented hardening example. The earlier "push model" options of the revision are closed: engineers push with their own login for their scopes; no provisioning group, no stored push account. The nesting test is unaffected (a smaller deny list nests more easily).

The Junos sizes become: readonly `deny-commands` 112/241, operator 226/241, engineer 219/241, and no `deny-configuration` on any role; the nesting exception of the revision disappears, and `TestRolesNest` needs no exception list.

**Junos class permission bits (user, 2026-10-09): shipped in 0.2.3.** The viewer's added `network` bit and the operator's dropped `reset` bit below apply now (the first paste of the classes carries final bits); the deny sets are server-sent and need no device change.

**Class names (user, 2026-10-09, D54).** The preset's engineer class is `EN-CLASS`; the superuser stays `RW-CLASS`, and `RO-CLASS` and `OP-CLASS` are unchanged. Every class name stays behind its single source (`policy.EngineerClass`, `store.BuiltinGroups`).

## Role definitions (user, 2026-10-08) - under revision

The consult below was written before these definitions and is being revised against them; where they conflict, they win.

- **Engineers** are the users responsible for provisioning and configuring network devices.
- **Operators** troubleshoot advanced network and device issues but must not be able to make changes to devices.
- **Filtered configuration is fine on Cisco (user, 2026-10-08).** No priv-15 workaround: readonly stays priv-lvl 1 and operator priv-lvl 7; the `privileges` lists lower `show running-config` to level 1 (IOS levels are cumulative, so operator inherits it) and the output is what that level may see; whether `show startup-config` is level-filtered must be confirmed on a lab device before it is lowered. `show ip route` and `show access-list` stay out of every list (already level 1). A SolarWinds backup of a Cisco device is therefore a filtered configuration; the release notes say so plainly. Junos is unaffected: `view-configuration` gives the full configuration with secrets masked.
- **Roles nest (user, 2026-10-08): operator is a strict superset of readonly for reads**, engineer of operator, superuser of engineer, in what each permits (a lower role's explicit denies do not matter for nesting). WP10.6c adds a Go property test over the shipped defaults and the preset: with the exact tacquito emulator and a corpus of sample command lines, every command permitted to a role is permitted to the role above; the Junos side checks that each lower role's deny patterns cover everything the higher role's cover, for the sample lines.
- **SolarWinds NCM (confirmed by the user, 2026-10-08) only backs up and compares configurations; it does not deploy.** So it runs as `readonly`, never operator or engineer: nothing in the readonly rules may allow a change, a hop (`ssh`/`telnet`), debug, capture or clear; it logs in directly at the level that can read the full configuration (no `enable` step, which would use the local enable secret and skip per-command authorization). Changes to devices are made by engineers, and by tacctl's own push in 0.2.5.
- **Readonly** is primarily for monitoring systems such as SolarWinds, which uses SSH for its network configuration management (NCM) responsibilities (config backup and compare, inventory, show commands). So readonly must be able to read the full configuration (the consult's viewer denies on `show running-config`, `startup-config` and `tech-support` do not fit), and operators need configuration read access as well to troubleshoot.

## 0. Finding that changes everything else

tacquito (cmds/server/config/authorizers/stringy/command.go) appends `$` to any `match` regex that does not already end in `$` (and `^` when missing; confirmed live by the fall-through probe). So `^crypto` is really `^crypto$`. Run through an emulator of that code, the 0.2.2 engineer preset is fail-open: `no aaa new-model`, `no tacacs server TACACS`, `no username admin`, `no line vty 0 4`, `no snmp-server community ...`, `enable secret ...`, `ip ssh ...`, `ip http server`, `key config-key password-encrypt ...`, `test aaa ...`, `clear aaa ...`, `do copy tftp: running-config`, `do reload in 5` are all permitted (only the exact single-word argument is denied). `TestEngineerCiscoRules` (internal/policy/preset_test.go:81) hides this because its decide() compiles the regex without tacquito's anchors. Nothing in the shipped defaults.yaml is affected (no rule there has a match). Production (0.2.1) never ran the preset; installs that did carry the dead rules as overrides, which an upgrade does not touch (see d).

Rule for every regex: a prefix match is written `^(alts)( .*)?$`, explicitly anchored. Fall-through is confirmed; every pair below also fails closed if it were not.

## (d) Shipped versus preset, canonical, upgrade

Shipped (defaults.yaml, every install, every group without an override): the privileges.operator list above; commands.operator + clear rule; commands.readonly + terminal rule. Rule for shipped changes: no pairs, nothing that can deny a command a role has today, nothing fall-through dependent. Shipped device-side text: the RO/OP class bits in juniper.go (fresh pastes only; configured devices keep their classes until Step 1 is re-pasted, and `config juniper` should say so).

Preset (`group preset roles`, opt-in): the viewer/operator Cisco pairs, all Junos deny sets, EN-CLASS, the engineer's Cisco list, WTI override.

Canonical for `group reset` (D51): built-ins without --preset = shipped commands/privileges + BuiltinGroups priv-lvl/class + no tier/WTI/Junos overrides; with --preset = the role's preset values; engineer = the preset. Upgrade impact: server-side commands changes apply at the upgrade's re-render, but the IOS level gate makes `clear counters|line` unreachable for operators until `tacctl config cisco` is re-pasted; `terminal length` for viewers is effective at once. The privileges change is paste-only; stale `privilege exec level 7 show running-config|startup-config|tech-support|archive|access-list|show ip route` lines stay on devices until removed: the release notes list the `no privilege exec level 7 ...` lines. The engineer preset bug needs a migration: the preset writes overrides, which `tacctl upgrade` never touches, so an install that ran the 0.2.2 preset keeps the fail-open rules. Recommend: (1) `tacctl upgrade` compares commands.engineer (and the two Junos sets) with the 0.2.2 preset text and, when identical, prints a red notice naming `tacctl group reset engineer` (or `group preset roles --force`); (2) a general lint in `group commands add` and `config validate`: a match ending in a word, `)` or `\b` (no `$`, `.*`, `( .*)?`) warns "`^foo` matches only the exact argument `foo`; did you mean `^foo( .*)?$`"; (3) a CHANGELOG item stating plainly that the 0.2.2 preset's no/default/enable/ip/key/test/clear/do denies did not hold, and the release notes' "Upgrading" carries the notice and the device `no privilege` lines.

User decisions: (1) ship the privileges.operator rewrite in 0.2.3 (recommended) or keep the old list; (2) `clear line` for operators; (3) `reload (in|at|cancel)` for engineers (recommended: deny, as today); (4) engineers and `crypto isakmp|ipsec|map` (recommended: permit; deny only key|pki|ca); (5) viewer `network` bit and operator without `reset` on Junos; (6) engineers denied snmp-server/snmp despite D41/D45 (recommended: denied); (7) soft-clear rules for operators (recommended: not shipped, documented add-on); (8) `alias` denied until lab-proven.

## (A) readonly = NCM / monitoring

**Cisco:** readonly stays priv-lvl 1 and operator 7; no `tier` settings, no WTI overrides, Junos classes unchanged. `privileges.readonly` lowers `show running-config` to level 1. IOS filters a lowered `show running-config` to the commands the user's level could enter; at level 1 that is little (lab item 1). If the lab shows the filtered backup is useless, the only level-1 alternative is `show running-config view full`, which is unfiltered and shows every type-7/0 secret (user decision after the lab). `show startup-config` is believed to be a file dump that is not filtered when lowered; not shipped, lab item 2. `show version`, `show inventory`, `show interfaces`, `show cdp neighbors`, `show ip interface brief`, `terminal length 0`, `terminal width 0` are level 1 already. `dir` and `show flash:` are believed to be level 15: the server rule permits `dir` so a site may lower it (`exec all: dir`, lab item 3); not shipped. `enable` stays denied: NCM is configured without an enable step, and permitting `enable` would let any account holding the device's enable secret reach 15 (no `aaa authentication enable` in the template; a release-note item). `exit` and `logout` are permitted in case IOS authorizes them (lab item 4).

```yaml
privileges:
  readonly:
    - show running-config        # level-filtered at 1; NCM backup/compare (user: filtered is fine)
    # lab-gated, not shipped: show startup-config, "exec all: dir"
  operator:                      # level 7 inherits every level-1 line above
    - "exec all: ping"
    - "exec all: traceroute"
    - "exec all: monitor capture"
    - clear counters
    - clear line
    - clear ip arp
    - clear arp-cache
    - clear mac address-table dynamic
    - undebug all
    # lab-gated: show tech-support
  # NEVER listed: show ip route, show access-list (level 1 already; lowering moved them UP)
```

`privilege exec level 1 ...` lines are device-wide for the level, so every group at 1 gets them; each group's server rules still decide.

**Junos readonly:** bits `view view-configuration network`. NCM runs `set cli screen-length 0`, `show configuration`, `show configuration | display set`, `show version`, `show chassis hardware`, `show interfaces`; none needs `trace`, `maintenance` or `secret`. Secrets render as `SECRET-DATA` without `secret`. The reader `deny-configuration` additionally removes `system login|root-auth|auth|tacplus|radius|accounting|scripts|master|archival`, `snmp`, `event-options` from the backup. Nesting forces readonly and operator to carry the same reader set; the price is that NCM's Junos backups lack those hierarchies and compares over them are blind (user decision, below). `request support information` and `file show` need `maintenance`: unavailable to readonly and operator regardless of regexes.

**WTI:** ViewOnly (band of priv 1).

**Release-note guidance (not code):** a downloaded Cisco config carries type-7 keys. Before pointing NCM at the fleet: `key config-key password-encrypt <master>` + `password encryption aes` (type 6 for TACACS/RADIUS/ISAKMP keys and key-chain strings on recent IOS-XE), `enable algorithm-type scrypt secret` (type 9), `username ... algorithm-type sha256` (type 8); treat the NCM credential store as holding whatever stays type 7. Re-paste `tacctl config cisco` so `privilege exec level 1 show running-config` reaches the devices; NCM then stores the filtered backup, and the notes say so plainly.

## (B) operator = advanced troubleshooting, no changes

Principle: nothing that changes configuration, boots, deletes, or disrupts forwarding or control-plane sessions; everything lowered to 7 is also permitted by the server, and nothing is lowered that the server would deny, so the `local` authorization fallback gives the operator exactly the online set (that is why `exec all: copy` or `exec all: debug` must never appear in the list).

| `show running-config view full`, `show startup-config`, `show derived-config` | deny (preset pair) | unfiltered: type-7 keys |
| `show tech-support` | lab item | if filtered, lower to 7 and remove the deny |
| `debug ...` | deny all; documented add-on of exact `privilege exec level 7 debug ...` lines (`debug ip ospf adj`, `debug ip bgp events`, `debug isis adj-packets`, `debug mpls ldp session`) | broad lowering is an offline hole; `debug all`/`ip packet` kill boxes |

| `monitor capture` (IOS-XE EPC incl. `export <url>`) | allow + `exec all` lower | bounded buffer; export is data, not a device change |
| `monitor session` | unreachable | configuration |

| `test cable-diagnostics tdr` | deny | takes the port down briefly |
| `clear counters`, `clear line` | allow | statistics / hung sessions |

| `clear ip route *`, `clear ip ospf process`, hard `clear ip bgp` | deny | disrupt forwarding / sessions |

## (C) engineers = provisioning and configuring

Initial provisioning never meets these rules: a new device has no TACACS+ yet, so the AAA block is pasted over the console or a local account. The rules govern what an engineer may change afterwards through their TACACS+ login: can it lock the fleet out or blind the audit trail.

| Item | After provisioning | Reason |
|---|---|---|
| `snmp-server` (Cisco), `snmp` (Junos) | allowed (user) | engineers own the SNMP step |
| `logging host|trap|source-interface|on` | add allowed; `no`/`default` of these denied | removing one blinds the audit |
| `aaa`, `tacacs*`, `radius*`, `username`, `enable secret`, `line`, `login`, `privilege`, `ip access-list ... <mgmt ACL>`, `access-class`, `transport`, `ip http|ssh`, `key config-key`, `boot`, `config-register`, `license`, `crypto key|pki|ca`, `archive` (config mode), `event`/`kron`/`tclsh`/`shell`/`alias`, `netconf-yang`/`netconf`/`restconf` (D53), `switch`/`redundancy`/`hw-module`/`issu`, `reload`, software | stay blocked | lockout, escalation of another account, persistence/scripting path, or the audit trail; regexes can shape a command but not its values (`tacacs server X` + `address ipv4 <anything>` redirects authentication) |
| Junos `load ... terminal` | allowed (`load set|merge|patch terminal`); `load <file>` forms denied | providers paste set-lists; terminal input is checked statement by statement like `set` (lab item 8) |
| Junos `request support information`, `file list` | allowed | |

**The 0.2.5 push.** tacctl's managed sections (AAA block, servers and secrets, privilege lines, management ACL, SNMP) are the engineer's blocked set minus SNMP. Four ways to reconcile:

1. Push is superuser-only; engineers `pull`, `diff`, `--dry-run` and prepare. No widening of the standing trust boundary; device accounting names the superuser who pushed. Cost: the roadmap's "engineers for their own scopes" waits.
2. Engineers may type exactly the rendered lines (a per-install whitelist of exact-form rules generated from the templates). Cost: brittle (values per scope, template variants); the key's value cannot be checked so a wrong key locks the device out (recoverable, not an escalation); a `privilege ... level 1 configure terminal` line elevates every level-1 account.
3. A dedicated device-side push account held by tacctl. Cost: a stored device credential (against the user's never-stored stance), and lost attribution on the device.
4. Time-boxed elevation: when an engineer runs `device config apply`, tacctl adds them to a `provisioning` group that carries the whitelist of option 2, re-renders tacquito.yaml, pushes as the engineer with the confirmed-commit timer, then removes the membership. Audited by tacctl and attributed on the device, no stored credential. Cost: during the window the engineer's interactive sessions have the same rights; option 2's whitelist still has to exist.

Recommendation: option 1 for 0.2.5's first release; record option 4 as the design for engineer pushes afterwards. Either way the engineer rules in 0.2.3 stay as above.

**Engineer preset (changes to the first consult's list):** `trust` loses `snmp-server`, gains `config-register|netconf-yang|netconf|restconf|logging (host|trap|source-interface|on)`; the `snmp-server|deny|` line is removed; new lines `config-register|deny|`, `netconf-yang|deny|`, `netconf|deny|`, `restconf|deny|`; the `do` list is unchanged. 66 rules, catch-all permit.

**Junos engineer:** bits unchanged (D20); `deny-commands` 219/241:

```
^(request (system|chassis routing-engine|vmhost|security)|start|op|file (copy|delete|delete-directory|rename|archive|show|change-owner|change-permission)|clear (system login|log)|restart (chassis|management))( .*)?$
```

(`request system ...` wholesale; `request support information` stays allowed; `load` is not denied: Junos tests a pattern against the keywords of a command with each argument replaced by a placeholder, so no pattern can allow `load set terminal` and refuse `load set <file>`, as the lab showed.) `deny-configuration` 201/236 without a filter, 229/236 with a 16-byte one:

```
^(groups [^ ]+ )?(system (login|root-auth|auth|tacplus|radius|accounting|services|scripts|archival|master|ports)|event-options|security (ike|ipsec|ssh|pki)|[firewall .*<F>|]interfaces (lo0 .*filter|fxp0|em0|me0|vme))
```

Sizes for `TestRolePresetFitsAndValidates`: readonly 112/119, operator 226/119, engineer 190/201 (+28 with a 16-byte filter).

**Nesting on Junos, one known exception.** `deny-configuration` conflates write-protection with hiding, so the engineer's extra paths (`system services|ports`, `security ...`, the lo0 filter, `fxp0`) are hidden from the engineer but readable by operator and readonly. Recommended: accept as the documented exception (these paths exist to stop changes, and widening the reader set would remove `system services` and the management interface from NCM's backups). Class bits nest, `deny-commands` nest, WTI levels nest by definition.
