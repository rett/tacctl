# 0.2.5 operator audit: service-impacting commands below the engineer (2026-10-11)

Status: audit and decision proposal (Fable), for the user's rulings. Nothing
here is implemented; the change list in section 6 is what the implementer
does once the rulings in section 8 are in. Written against `feature/0.2.4`
(the worktree that removes `clear mac address-table dynamic` from the
operator defaults is confirmed by this audit and subsumed by it).

## 1. The rule and how it is applied

The user's rule (verbatim, 2026-10-11):

> clear mac-address-table (and mac address table) causes connection drops and
> service interruption so shouldn't be performed by operators. That should go
> for other service impacting commands, no operational command should allow an
> operator or lower the ability to affect service with a command.

Tightened the same day: **"As a rule, operators should not be able to
interrupt service even intermittently."**

The test applied to every command the shipped policy or the role preset lets
`operator`, `readonly` or any lower tier run, on every vendor tacctl renders:

> If running it, with ANY arguments the server rule allows, or the device's
> lowered verb allows when the server does not answer (the Cisco `local`
> fallback, and RADIUS devices always, which carry no command rules), can
> interrupt service even briefly for any host, session or flow the device
> carries or manages, or load the device enough to degrade forwarding or
> management, it leaves the operator and lower defaults; the engineer is the
> escalation.

What survives is read-only output and the few state-touching commands that
cannot interrupt anything (counter resets, stopping a debug, terminal
settings); those are classified honestly and put to the user in section 8
rather than decided silently.

Markers: **[V]** read in the code; **[S]** settled by a lab result recorded
in the plans; **[A]** IOS/Junos behaviour from knowledge, to confirm in the
lab items of section 9.

Sources read: `internal/conf/defaults.yaml` (`privileges:`, `commands:`),
`internal/policy/preset.go` (the role preset, the Junos deny sets, the
engineer rules), `internal/policy/baseline_test.go` (the corpus, the nesting
test, `localFallbackExceptions`, `TestPrivilegesArePermitted`),
`internal/devices/{cisco,juniper,wti,radius}.go` (what the walkthroughs
render), `internal/devconf/plan/ios.go` (how removed privilege lines reach a
device), `docs/plans/0.2.3-baseline-design.md` (why each item was allowed),
`docs/plans/wti-interface.md` (what a WTI level can do), `docs/plans/0.2.5-plan.md`

## 2. Mechanisms, per vendor (what can be restricted at all)

| Vendor | Device-side gate | Server-side rule | Offline / RADIUS |
|---|---|---|---|
| Cisco IOS / IOS-XE, TACACS+ | `privilege exec [all] level N <cmd>` lines from `privileges.<group>`; cumulative (7 inherits 1) [V cisco.go] | per-command `commands.<group>` rules (tacquito, regex on the arguments only) [V] | `aaa authorization commands N default group G local`: with no server answering, `local` decides, which is the level gate alone; a lowered verb runs with any arguments [S, baseline design (B)] |
| Cisco over RADIUS | the same `privilege` lines | **none** (RADIUS carries `shell:priv-lvl` only) [V radius.go, README] | always the level gate alone |
| Junos (TACACS+ and RADIUS) | the login class's permission bits, pasted in Step 1 (`RO-CLASS`: `network view view-configuration`; `OP-CLASS`: `clear network trace view view-configuration`) [V juniper.go:145-150] | `deny-commands` / `deny-configuration` sent at login from `tacctl group junos` (the preset sets them; **the shipped defaults carry none**) [V preset.go, juniper.go Step 3] | the bits are the ceiling and are final; with no server there is no login at all (no fallback to the class without the server's deny sets, unless a local user exists) |
| WTI | the access level (`ViewOnly`, `User`, `SuperUser`, `Administrator`) from the priv-lvl band or `wti-level`; the unit's Default User Access port and service lists [V wti.go] | none: a level is a fixed menu of commands [V wti-interface.md section 2] | the level is all there is |

Consequences that shape the proposal:

1. On Cisco, a server regex restricts arguments only while the server answers.
   A verb lowered by `privileges.<group>` is reachable with every argument IOS
   accepts under it whenever `local` decides, and on every RADIUS device. So
   a verb whose argument space must be restricted (ping's `repeat`, clear's
   whole-table forms) must not be lowered at all; the server rule is then a
   bound for TACACS+ devices online, and the IOS default level is the only
   bound otherwise.
2. On Junos, the shipped state (no preset applied) is **bits only**: the
   `clear` bit of `OP-CLASS` reaches every `clear` family that needs only
   `clear` permission, including `clear bgp neighbor`, `clear ospf neighbor`,
   `clear isis adjacency`, `clear security flow session`, `clear
   ethernet-switching table` [A, Junos privilege tables]. The preset's
   `deny-commands` narrow that, but the preset is opt-in and its 241-byte
   budget cannot list every disruptive family. The only lever that holds
   everywhere is the bit itself.
3. On a WTI unit nothing below a level is adjustable; the question is only
   which level the operator lands at.

## 4. Classification

Columns: **drop** = drops or resets a connection, session or adjacency;
**fwd** = changes forwarding or control-plane state; **svc** = interrupts
service of the device or of what it carries; **load** = real CPU/memory load
(degrades forwarding or management); **evid** = removes evidence (counters,
logs, buffers). "online" = the server answers and its regex applies;
"offline" = `local` fallback or RADIUS (the lowered verb with any arguments).

New preset values (POSIX ERE; sizes to be recomputed by
`TestRolePresetFitsAndValidates`, approximate here):

```
viewerDenyCommands   = ^(ssh|telnet|file|request|restart|start|load|op|test|monitor|configure|edit|clear|ping .*(rapid|interval)|show system rollback)( .*)?$        (134 of 241)
operatorDenyCommands = ^(file|request|restart|start|load|op|test|configure|edit|clear|monitor traffic|ping .*(rapid|interval)|show system rollback)( .*)?$          (131 of 241)
engineerDenyCommands = unchanged (219 of 241)
```

Nesting holds: the viewer's set covers the operator's (`monitor` whole over
`monitor traffic`; `ssh|telnet` extra).

A shipped Junos deny set (a `junos:` section in `defaults.yaml`, applied to
every install like `commands:`) would make the `ping` restriction hold
without the preset; that is a new mechanism and a ruling (8.5). Without it,
the bit removal is what the shipped state gets, and the `ping` flags are
restricted only where the preset is applied.

### 5d. RADIUS-only Cisco devices

After the change the operator's whole policy on such a device is level 7 =

### 6f. Migration for existing installs

1. **Stored `privileges.operator`.** `group privilege add` seeds the shipped
   list into the override first [V group_crud.bats:160-163], so most installs
   that ever added an entry carry the nine old lines explicitly, and
   `tacctl upgrade` never touches overrides. Proposal: at upgrade, a stored
   list **equal to** the 0.2.3 shipped nine lines is dropped (it is what tacctl
   wrote, not a choice: the `previousDefaults` reasoning); any other stored
   list that contains a removed entry gets a red notice naming the entries
   and the fix (`tacctl group privilege remove operator '<entry>'`, or
   `tacctl group privilege reset operator`), repeated by `config validate`.
   The same for `commands.operator`/`commands.readonly` through
   `previousDefaults` (6b).
2. **Devices pasted earlier** keep their `privilege exec [all] level 7 ...`
   lines. Three paths already exist: `tacctl group privilege reset operator`
   prints the `no privilege exec level 7 <command>` lines it needs
   [V testdata golden]; `device config plan` compares the `roles` section and
   emits the `no` lines before the adds [V plan/ios.go:637-651]; the release
   notes list them. The lines to remove: `no privilege exec all level 7
   ping`, `no privilege exec all level 7 traceroute`, `no privilege exec all
   level 7 monitor capture`, `no privilege exec level 7 clear line`, `no
   privilege exec level 7 clear ip arp`, `no privilege exec level 7 clear
   arp-cache`, `no privilege exec level 7 clear mac address-table dynamic`
   (and `clear counters` per 8.1). IOS 15.x leaves the command at its default
   level afterwards (`privilege exec level 15 clear counters` and the
   parents), which D106 tolerates [S]. Until a device is re-pasted or planned,
   its operators keep the old reach when the server does not answer; the
   notes say so.
3. **Junos devices** keep `OP-CLASS` with `clear` until Step 1 is re-pasted
   or the plan's `delete system login class OP-CLASS permissions clear` is
   applied; the server-sent deny sets change at the next login once the
   preset is re-applied (`group preset roles --force`, or `group reset
   operator --preset`); an install that never applied the preset gets only
   the bit change.
4. **The Cisco `local` fallback exception disappears altogether.** It existed
   only for the three `clear` entries (`localFallbackExceptions` lists exactly
   those [V baseline_test.go:336-340]); all three are removed, so the map, the
   exempt branch, the defaults.yaml comment and the README/man sentence go,
   and the invariant becomes absolute and stronger (bare and with arguments).
   No new exception is needed for any kept entry (`undebug all` and `clear
   counters` are permitted with any arguments on the server).
