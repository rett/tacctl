# tacctl 0.2.17 plan (2026-10-21)

Read `0.2.17-handoff.md` (state, working rules) first. Decisions continue
the numbering of `0.2.16-plan.md` (D231-D243). Scope chosen by the
maintainer on 2026-10-21: the audit release; widened on 2026-10-23 with
vendor detection (D260, `vendor-detection.md`) and the attended enroll
and remediation workflow (D261-D272, `enroll-workflow.md`, whose
decisions are the maintainer's and are built on here, not re-opened).
Design review: Fable, 2026-10-21 and 2026-10-23. State: planned, nothing
built; 0.2.16 is being built on `feature/0.2.16` and this plan rests on
its code as of `54435e7` (the audit) and on `feature/0.2.16` at
`938e46d` (the device verbs read for D261-D272).

## 1. Scope

The goal is compliance: every transaction recorded with who, what, when
and the result, in the syslog the server already writes to, with no
secret in any line. The read-only audit of the write paths (2026-10-21,
summarised in section 7) found one helper, `(*App).Logger`, that runs
`logger -t tacctl -p <priority>` and ignores every failure; about 35
verbs that write a line, most on success only; about 80 state-changing
verbs that write none (users, groups, scopes, sudoers, console settings,
restores, imports, install and upgrade, `log clear`, `host sync`, the
device registry setters, backends, tunables, SNMP credentials); actorless
snapshots; denials inside verbs that are not logged; lines dropped when
a signal has cancelled the context; and two argument forms that sudo's
own log records verbatim.

The release adds one audit layer under the dispatcher so that coverage
no longer depends on each verb remembering to log, and brings the verbs
that need their own detail up to one standard. No state-format change
but one optional key of `tacctl.yaml` (D249, with its rollback step) and
three keys added to the snapshot manifest that nothing reads (D252). No
new device write path, no credential, nothing scheduled or automatic
(`0.2.12-plan.md` section 2). The log is still syslog through `logger`;
where it goes from there is the site's concern (section 8 lists what
tacctl could add later, with a recommendation each).

The release also carries two device features outside the audit theme.
Vendor detection (D260, WP17.10): `device add` and `device check` read
the vendor from the device by SNMP and `device vendor <name>
--from-device` corrects a device left at `other`. It is read-only
towards the device (the SNMP credentials the name lookup already uses)
and is separable from the audit packages. The attended enroll and
remediation workflow (D261-D272; direction and settled
decisions in `enroll-workflow.md`; WP17.11-WP17.15): one verb, `device
enroll`, runs the
chain a person remembers today (scan, the host key, register, pull,
plan, and for Junos the apply review) for the addresses named or
discovered, with every trust decision made per device by a person; the
config verbs gain the selectors that pick "the devices that differ"
(`--differs`, `--name`, `--ip`) and `apply --pull` pulls first and hands
the devices that differ to the review; the apply review is answered per
device, and its scripted form is marked in the audit lines. Junos stays
the only vendor written to (0.2.9 D129); IOS, IOS-XE and WTI end at the
plan. Nothing is scheduled, no credential is stored, every device login
is the invoking user's own password asked once, and no run can reach a
sign-off without a terminal except the forms that name what a person
read on a console (`--host-key`) or confirmed in an earlier apply
(`--confirmed -y`).

## 2. Decisions

**D244 — One audit writer, no context argument.** `(*App).Logger(ctx,
priority, msg)` (`internal/app/services.go`) is replaced by an `audit`
service of the App (`internal/audit`, `App.Audit()`), made once per
process with `context.WithoutCancel` of the process context, so no line
is ever dropped because SIGINT, SIGTERM or SIGHUP cancelled `inv.ctx`
(`exec.CommandContext` will not start `logger` on a cancelled context;
the device family's `auditContext()` was the only protection, and
`ssh end` and `console end` lose their line on a hangup today). The
writer has one method for a line, `Line(priority, event string, kv
...KV)`, which builds `<event> <key>=<value>...` in the format of D245,
appends `sid=<id>` (D247) and runs `logger -t <tag> -p <priority>`
through the App's Runner as today. The 72 call sites of `Logger`, the
two of the tier gate (`internal/tier/tier.go`, which gets the writer
instead of running `logger` itself) and the console's own tag
(`internal/console`, `LogTag`, a `Tag` option of the writer) move to it.
`auditContext()` is deleted; a `go vet`-style check in `make lint`
(`tests/tools/no-private.sh`'s sibling, one grep) refuses any new
`execx.Cmd{Name: "logger"` outside `internal/audit`. The existing lines
keep their words and keys (D254): only the transport changes.

**D245 — The line format.** Every line is `<event words> key=value ...`
with keys from one fixed vocabulary (the table of `docs/security/
audit.md`, generated into the manual page), in a fixed order per event.
A value is written as it is when it is non-empty and holds only
`[A-Za-z0-9._:/@+-]`; otherwise it is Go-quoted (`strconv.Quote`:
spaces, quotes, control characters and non-UTF-8 escaped, so a line is
always one line and a collector can split on spaces outside quotes); an
empty value is `-`. A value longer than 64 bytes is cut and ends in
`...` (`console.LogValue` does this today and becomes the shared
function). The central lines (D249) carry a format token `v=1` as their
first key, so a collector's parser can pin itself to a version and a
later change of the vocabulary bumps it; the older per-verb lines do not
get the token (their format is already in the manual page and in
sites' filters). Priorities: `auth.info` for an action, `auth.notice`
for the weighty ones (D249 lists them: `log clear`, every whole-state
replacement, install/upgrade/uninstall, `group edit <g> tier` and
`priv-lvl`, `config sudoers`, `console system-shell|tiers|user`, the
apply and onboard approvals as today), `auth.warning` for every DENY,
FAIL, mismatch and for a `cmd end` whose result is not `ok`. The tag is
`tacctl` for every line of a tacctl command and `tacctl-console` for the
console session's own lines (unchanged: the commands a session runs are
`tacctl` processes under sudo and carry `console=<session>`).

**D246 — The actor.** The central lines carry `user=<SUDO_USER>`, which
the gate has verified against `SUDO_UID` before any verb runs
(`tier.VerifyCaller`), `uid=<SUDO_UID>`, and `origin=sudo`; a process
with no `SUDO_USER` (a root shell, a script run as root) is
`user=root uid=0 origin=root`, which the docs name as the one case
where the log holds no login identity, as sudo's log does not either.
`tty=<pts/n>` comes from the terminal the command runs on (the
`terminalLine` hook exists), `-` when none; `console=<session>` is the
console marker (`TACCTL_CONSOLE`) when set, as `tacctl ssh` writes it
today. The per-verb lines keep `by=` and `user=` as they have them
(D254); nothing is renamed.

**D247 — The session id.** Every invocation gets `sid=<8 characters of
[a-z0-9]>` from the App's random source (`Knobs.Rand()`, so a test's
lines are stable), made before the gate runs; the writer appends it to
every line of the process, the gate's DENY lines included. It ties the
`cmd start`, the detail lines, the `cmd end` and the snapshot (D256) of
one command together, and `tacctl ssh` and the console keep their own
`session=` beside it. A collision is harmless (two commands share a
word; the timestamps and pid separate them); the id is for grep, not a
key.

**D248 — When `logger` fails.** The writer notices a `logger` that could
not be started (not installed, exit 127) or that returned non-zero (the
syslog socket refused: journald down), and prints once per process, on
stderr, `[WARN] The audit line was not written (logger: <reason>); the
command continues.` so an operator's terminal and a script's stderr
show it. Nothing else changes without D257: the line is lost, as every
line is lost today, silently. A missing `logger` on a machine that has
tacctl installed is a packaging fault (`util-linux` provides it on every
supported distribution); the install's preflight gains the check (one
line in `install`'s requirements, as `ssh` and `flock` are checked).

**D249 — The class table and the central lines.** A table in
`internal/cli/audit.go` classifies every command of the tree by the
words the gate sees (`cmd sub`, or `cmd` alone for `install`,
`upgrade`, `uninstall`, `rollback`, `passwd`, `status`, `version`,
`hash`, `shell`, `phase`): `read` (no central lines: lists, shows,
checks, scans, the completion helpers, the shell itself, which runs
each line as its own sudo process), `action` (a verb that changes state
or logs in somewhere every time it runs: `user add`, `host sync`,
`ssh`, `log clear`, ...) and `mixed` (a word that is a read or a write
by its later arguments: `scope secret` is `show` or `set`, `device
snmp`, `scope block`, `user scope`, `console *`, `device config`,
`breakglass`, `config allow`, `config mgmt-acl`, ...). An entry also
says `weight: notice` for the verbs D245 lists and names the positional
secret to redact (D252). The dispatcher (`prelude`, after the gate and
preflight, before `run(args)`) writes for an `action`:

    cmd start v=1 sid=<id> user=<u> uid=<n> origin=sudo tier=<t>
      tty=<tty> console=<session|-> cmd="user add"
      args="alice ops --scopes core --hash <redacted>"

and, where the exit status is decided (the one function `Main` and the
test harness share, `exitCode`'s caller), for every invocation that
wrote a start line:

    cmd end v=1 sid=<id> user=<u> cmd="user add" result=ok status=0
      duration=0.312s snapshot=<id|->

`result` is `ok` (status 0), `failed` (any other status that is not one
of the next), `denied` (`tier.ErrDenied` or the typed in-verb denial of
D251), `interrupted` (130) or `aborted` (a panic: a deferred function in
the same place writes the end line with `status=2` and re-panics, so a
crash of tacctl's own code leaves an end line too). `duration` is
seconds with millisecond precision, from the start line to the end
line; `snapshot` names the snapshot or snapshots the command took
(`Snapshotter.Take` reports its id to the writer; `-` when none was
taken or the newest was current). A `mixed` verb gets the same pair, but
its start line is written by the first write choke point it reaches
(`storeApply`/`applyWith`, `store.Mutate` through them, `deviceWrite`,
`consoleWrite`, `Conf().Set*`, `snmpcred.Save`, `Snapshotter.Take`,
`hosts.WriteScript`, `policy` blocks writers, the lifecycle `Env`),
through `Audit.Touch()`, before anything is written: a `mixed` verb that
only read writes nothing to the log. `Touch` is idempotent. A `read`
verb that reaches a choke point is a classification bug: the line is
written all the same with `class=unexpected` added, and a `-tags
testknobs` binary (every Go test) panics there, so the test suite finds
it. A verb with no entry is treated as `action` (the safe side) and the
classification test (D255) fails until the entry is added, so a new verb
is covered from the day it exists. A signal that cancels the context
ends the verb with `ui.ErrInterrupted` and the end line says
`result=interrupted status=130`; a SIGKILL or a power loss leaves a
start line with no end line, which the docs explain: the command did not
finish, the snapshot named by the start line's `sid` (D256) holds the
state before it, `config validate` says what the files are now.

**D250 — Dedupe with the lines that exist.** The verbs that log well
today (device config apply, onboard, pull, plan, diff, collect, shapes
seed, ssh, the console session, host provisioner rotate, breakglass,
host enroll/unenroll/rename/forget/target, block set/remove, ...) keep
every line they write: those lines carry what the central pair cannot
(per-device results, the approval, counts, from/to), and sites may
filter on them. The central pair is written for them too, with no
exception, so `grep 'cmd end'` lists every transaction. The rule for a
verb's own lines from now on: a verb line must say something the central
pair does not (the object, a count, a before/after, a per-item result);
a line that would only repeat verb, actor and result is not written.
`tacctl ssh`'s `ssh start`/`ssh end` and the console's `console
start`/`console end` stay (session detail: device, login, lines, the
reason of the end); the ssh session therefore has four lines, accepted.

**D251 — Denials inside verbs.** The ~25 refusals that read `'tacctl
<verb>' is the superuser's. Nothing was changed.` and the scope-filter
refusals (an engineer naming another scope's device or secret) return a
typed error, `*deniedError{Cmd, Sub, Reason string}` (`reason=superuser`
or `reason=scope`), which unwraps to what each site returns today
(`usageErr`'s `ExitError` or `ui.ErrReported`), so every message and
exit status stays as it is and the tests of those texts pass untouched.
The dispatcher sees it where it decides the status and writes

    cmd DENY v=1 sid=<id> user=<u> uid=<n> tier=<t> cmd="scope secret"
      args="core set <redacted>" reason=superuser

at `auth.warning`, and the end line says `result=denied`. The gate's own
`tier DENY` lines keep their words (`reason=sudo-user-mismatch`, the
cap reasons) and gain `sid=`; a collector matches `DENY` for both.

**D252 — Redaction.** `args=` is the command line after the words of
`cmd=`, each word as D245 quotes and caps it, with these values replaced
by `<redacted>`: the value of a flag whose `Flag` has `Secret: true`
(`--hash` of `user add` and `user passwd`); the positional the class
entry names (`scope secret <s> set <value>`: the word after `set`;
`hash <password>` is `read` and writes no line, but its entry names the
word all the same, so a future line cannot leak it); and nothing else.
Free text is logged: `breakglass hold --reason` is why a device was
taken out of AAA and is the field an auditor asks for; the docs say that
whatever is typed there is in the log (and in sudo's log, which records
the whole command line regardless). The console's `console DENY ...
first=<word>` logs the first word only when it is a verb of tacctl or
of the console (then it says what was attempted: `bash`, `vi`, `scp`
are not and read `first=- len=<n>`), so a password typed at the console
prompt never reaches the log. The invariant is tested (D255): a test
runs every verb that takes a secret, with a marker value in each
position, through the fake runner and asserts the marker is in no
`logger` argument of the whole run.

**D253 — Detail lines.** The verbs below write a line of their own
beside the central pair, at the priority of their class, because the
pair does not say what changed. Keys reuse the vocabulary of D245; a
value is a name or a count, never a secret, hash or password.

- `user add name= group= scopes=`, `user remove name=`, `user passwd
  name= source=prompt|hash|generated` (the admin form; the self-service
  `passwd` lines stay), `user disable|enable name=`, `user rename
  from= to= uid=<carried|->`, `user move name= from= to=`, `user scope
  name= op=add|remove|replace scopes=`.
- `group add name= priv-lvl=`, `group remove name=`, `group edit name=
  key=tier|priv-lvl|wti-level|junos-class|... from= to=` (one line per
  key changed; `tier` and `priv-lvl` at `auth.notice`), `group commands
  name= op= count=`, `group privilege` the same, `group preset name=
  preset=`.
- `config sudoers op=install|remove file=`, `config sudoers tiers` the
  same; `console set key=system-shell|tiers|user|forwarding|
  agent-forwarding|ssh-escape|password-cache|idle-timeout|
  space-completion from= to=`.
- `backup restore id= pre=<snapshot> keep-uids=yes|no legacy=yes|no`,
  `store import source=<file|->`, `store rollback`, `install branch=`,
  `upgrade from= to= branch=`, `uninstall` (the latter three from
  `internal/lifecycle` through the App's writer; `lifecycle.Host` gets
  it), `rollback target=` (exists; gains `result=`).
- `scope secret set scope= source=set|generate`; `config snmp`, `scope
  snmp`, `device snmp`: `snmp set kind=community|v3-user|clear|port|
  timeout|... scope=|device=`.
- `secret-read kind= name=` for every caller, not only a restricted one
  (`completion_names.go` calls it for readonly, operator and engineer
  today): `scope secret <s> show`, `scope snmp <s> show --reveal`,
  `device snmp <d> show --reveal`, `config snmp show --reveal`, `store
  show` (`kind=store`), `config dump`, `backup diff` (`kind=snapshot`),
  `device config show|plan` and the `config cisco|juniper|wti`
  walkthroughs (`kind=walkthrough name=<scope>`); `config linux script`
  writes a file holding a scope's secret: `secret-export scope= file=`.
- `host sync name= target= created= updated= renamed= removed=
  remove-home=yes|no result=` per host (the counts `recordRun` has),
  plus the failed enroll and unenroll (`result=failed reason=`), and a
  batch `host move` summary `host move scope= moved= failed=`.
- `device sync devices=<name,...>` (the first 20 names, then `+<n>`),
  `holdCarry` on `device rename`: `breakglass hold-move from= to=`.
- Scope and policy: `scope add|remove|rename|default`, `scope prefixes
  op= scope= cidr=`, `scope protocols|vendor-attrs|devices|auth-method|
  exec-timeout|tacacs-group|radius-group|aaa-order|mgmt-acl|netconf
  scope= from= to=`, `config allow|deny op= value=`, `config mgmt-acl
  op= value=`, `backend enable|disable id=`, `config render backends=`,
  `config <tunable> from= to=` (loglevel, listen, metrics,
  password-age, bcrypt-cost, password-min-length, secret-min-length,
  branch, devices, cisco source-interface), `config linux uid user=
  uid=`.
- The device registry setters: `device set name= field= from= to=`
  (address, hostname, vendor, port, description, location, legacy-ssh,
  config-syntax, netconf, stale-days, notice), `device add|remove|
  rename|import` with counts.

`log clear` gets no line of its own: its class weight is `notice`, so
the start line is the "before" record and the end line the "after",
both at `auth.notice` (the backlog's own rule: destroying the AAA logs
stays a superuser act, and now a recorded one).

**D254 — The existing lines gain `result=` and their failure paths.**
The success-only lines (host enroll, unenroll with `--force`
distinguished, rename, forget, target; breakglass hold, release,
remove-record, hold-move; rollback; device sync; block set/remove; scope
breakglass; staging; group reset; section reset; device hostkey; device
config forget; linux engineer-sudo; console provision/deprovision) are
written on the failure path too with `result=failed reason=<short
word>`, where the reason is the class of error, never its text
(`reason=script`, `reason=store`, `reason=race`, `reason=lock`). The
lines with no actor (`uid-map renumbered`, `uid-range set`, the two
`hostkey-mismatch` lines, `console policy ... unusable`) gain `by=`;
`scope staging done` stays actorless and the docs say it is the sweep's
own line. `passwd.go`'s `(self-service)` becomes `source=self`. No
existing key is renamed and no line removed, so a site's filter keeps
matching.

**D255 — The tests.** (1) `audit_class_test.go` walks the command tree
(`newRoot`, every `*Specs` map) and fails for a `cmd [sub]` with no
class entry, and for an entry that names no command (stale). (2) Golden
lines per class: one `action` verb, one `mixed` verb read then written,
one `read` verb, through the fake runner: the exact `cmd start`, `cmd
end`, the absence of lines for the read, the sid shared by every line of
the run, `snapshot=` naming the id the run took. (3) The failure and
interruption paths: a `storeApply` that fails after its snapshot ends in
`result=failed status=1 snapshot=<id>`; a context cancelled during the
verb (the `interruptSource` hook) ends in `result=interrupted
status=130` and the `logger` call is made (the fake runner records it
although the invocation's context is done); a panic in a verb (a test
hook) leaves `result=aborted`. (4) The backstop: a test verb classified
`read` that calls `storeApply` panics in the test binary. (5) The
no-secret scan of D252, which also runs the whole corpus of existing
secret-bearing verbs (`config snmp community --stdin`, `scope snmp
v3-user`, `device snmp`, `passwd`, `user add --hash`, `scope secret
set`, `hash`). (6) `logger` missing and `logger` failing: the one stderr
warning, the command's own status unchanged. (7) The denial line for an
in-verb refusal and for the gate's. (8) The tests that count `logger`
calls today (62 assertions in 39 files) are moved to a helper
`auditLines(r) []string` and `auditLine(r, prefix)`, and assert on
content; a count assertion is kept only where the count is the point.
(9) The man test gains the generated audit block (D259). Bats:
`tests/integration/audit.bats` runs a write verb and a denied verb as
`tester` with `logger` replaced by a stub on `PATH` that appends its
arguments to a file, and checks the pair, the sid and the redaction on a
real binary.

**D256 — The snapshot manifest records who and what.** `Manifest`
(`internal/snapshot/manifest.go`) gains `"sid"`, `"user"` and
`"command"` (the `cmd=` words of the start line, no arguments) beside
`tacctl_version`, `created` and `rendered`; the Snapshotter gets them
from the App's writer. Nothing in tacctl reads a manifest (the only
reference in Go is the writer; `backup list`, `diff` and `restore` go by
the directory names and the state files), 0.2.16 does not either, and a
restore of a snapshot from an earlier release has no such keys and needs
none, so the format change is one-way safe and needs no rollback step.
`backup list` is unchanged; showing the actor there is an option
(section 8).

**D257 — `audit.strict` (WP17.6, separable).** A key of `tacctl.yaml`,
`audit: {strict: false}` by default. With `strict: true`, an `action` or
`mixed` verb whose start line could not be written (D248) is refused
before any write: `The audit line cannot be written (logger: <reason>)
and audit.strict is set; nothing was changed.`, exit 1; a `read` verb
runs. The end line's failure cannot be acted on (the change is made) and
is the D248 warning. The key is one leaf under a new top-level mapping;
the schema refuses keys it does not know (`conf/schema.go`), so
`rollback 0.2.16 --apply` drops the `audit` mapping and says so, as the
converters of the earlier rollbacks do for their keys (the implementer
confirms the refusal on a 0.2.16 binary first and notes it in the
rollback's text). Listed under CONFIGURATION KEYS and in
`docs/cli/tunables.md`. Recommended, because without it "every
transaction recorded" is a best effort; the default is off so that a
server whose journald is restarting does not refuse the command that
fixes it.

**D258 — Secrets off the command line (WP17.7, separable).** sudo's own
log holds `COMMAND=/usr/local/bin/tacctl scope secret core set
<value>` and `... user add alice ops --hash <bcrypt>`, and `ps` shows
them while they run; tacctl cannot change what sudo logs, so the
mitigation is a form that carries no value in argv: `scope secret <s>
set` with no value prompts once without echo (a terminal) and `--stdin`
reads one line from standard input (a script), as `config snmp
community` does (`readSecret`); `user add`/`user passwd --hash -` reads
the hash from standard input, the `-` of `device import -`. The argv
forms stay (scripts use them) and `docs/cli/scope.md`, `docs/cli/
user.md` and the manual page say they are recorded by sudo and visible
in `ps`, and name the quiet forms. The `tacctl shell` runs every line
through sudo and is the same case.

**D259 — The documentation.** `docs/security/audit.md` (new; the index
of `docs/security/README.md` and the Security row of `README.md`): what
is recorded and what is not, the three central lines and the field
table, the detail lines by family, the redaction rule, the actor and
the `origin=root` case, the session id and how to correlate (the start
line, the end line, the snapshot's manifest, sudo's log), what a start
line without an end line means, the `logger` failure and `audit.strict`,
and forwarding in general terms (the facility is `auth`, the tags
`tacctl` and `tacctl-console`; a collector matches the program name;
one rsyslog and one journald example with `example.net` names). The
manual page gets `.SH AUDIT LOG` after TIERS: the same content in man
form, and a generated block (`make man`, `man_gen_test.go`) listing
every `action` and `mixed` verb with its weight, from the class table,
so the page cannot drift from the code; the per-verb mentions scattered
through the page stay and say the same. The CHANGELOG items: one per
user-visible WP.

**D260 — Vendor detection (WP17.10, separable).** Design and rationale
in `vendor-detection.md`. `DetectVendor(objectID, descr) (vendor,
reason)` in `internal/snmp` maps sysObjectID (1.3.6.1.2.1.1.2.0) and
sysDescr (1.3.6.1.2.1.1.1.0) to `cisco`, `juniper` or `wti`; the SNMP
getter gains the two reads, with the stub, the test agent and
`_snmp-agent --sysobjectid --sysdescr`. Enterprise 9 alone never maps to
`cisco` (ASA, NX-OS and IOS XR share it): the sysDescr must start
`Cisco IOS Software` or `Cisco IOS XE Software`; anything ambiguous
prints what was read and offers nothing. `wti` and `juniper` are offered
once a lab capture of each is a fixture. The surfaces: `device add`
prints the detection, warns when `--vendor` disagrees, and at a terminal
asks one `y/N` to register with the detected vendor, folded into the
`device add <address>` question; when no name can be discovered it asks
for one at a terminal (the usual name rules) instead of refusing, and
refuses as today without a terminal. `device check` gains a `Vendor` row
and `vendor_detected` in `--json`; `device check --all` is the report of
devices at `other` whose detected vendor is supported. `device vendor
<name> --from-device [-y]` reads now and writes after a `y` or `-y`, and
refuses an ambiguous read. `device discover --probe` contacts each
listed address by SNMP and fills the suggested `device add` lines with
`--vendor` and the name found; without `--probe` discover reads logs
only. A vendor tag that disagrees with the detected vendor is a `device
notices` kind. A vendor change marks the device's pull record `needs
pull`, so `diff` and `plan` say to pull again instead of comparing a
record of the old vendor's shape. `device vendor --from-device` is
classified as an `action` verb in the D249 table and writes the D253
device line like `device vendor`. Nothing is written to a device and no
credential is added; every read is started by a person.

*Review of D260 against the code (2026-10-23, `938e46d`).* The design
stands; the implementer of WP17.10 settles these gaps, each verified by
reading the code: (1) `deviceSpecs["vendor"]` has no flags
(`device.go`): `--from-device` and `-y` are added to the spec, the
`deviceVerbs` row and `deviceOptions`, and the setter branches as
`location --from-device` does (`deviceSetter`,
`deviceLocationFromDevice`). (2) `--probe` on `device list` is a TCP
connect to the ssh port (`deviceOptions["list"]`, operator-gated by
`scanAllowed`); D260 gives the same word an SNMP meaning on `discover`.
Recommended: `discover --snmp` (the flag says what is read), else the
two meanings are documented side by side. (3) `device add --pull`
refuses before anything is read unless `--vendor` names a readable
vendor (`deviceAddPullCheck` runs first in `deviceAddWith`); for the
detected vendor to feed `--pull`, the vendor part of that check moves
after the detection and its question, the tier and login parts stay
first. (4) `snmp.Config.Get` sends one varbind per request
(`client.go`; `SysName` and `SysLocation` are two exchanges): two more
OIDs are two more round trips per device unless a `System(ctx, addr)`
read with four varbinds is added, with the test agent (`agent.go`,
`_snmp-agent`) answering all four; `device check --all` (16 in flight,
`checkSysNames`) is where the difference shows. (5) The "needs pull"
mark needs no record field: `Record.Vendor` is kept by every pull and
apply (`recordSuccess`, `writeApplied`), and `store.Sections(name,
vendor)` parses the sections file in the family of the vendor it is
asked for (`readSections`), so today a vendor change silently re-reads
the old file in the new family; the rule `rec.Vendor != e.Vendor` in
`staleness()` and `configStateOf()` yields `StalePull` with its own text
(`NeedsPullText` is the Cisco-syntax case and gets a sibling). (6) The
notice kind: notices are computed from the registry and the seen cache
(`devreg/notices.go`, `notices_scan.go`), never from a live read, so
the detected vendor must be kept somewhere for the kind to exist; the
seen cache already keeps per-device scan results (`Seen.RecordKeyScan`)
and gets a `detected: {vendor, at}` written by `device add`, `device
check` and `discover --probe`, which `device notices` reads. Not
verified: that `device show` warns on a tag against the vendor today.

**D261 — `device enroll`: grammar and help.** A new verb of the
registry family, beside `onboard` and `collect` (0.2.9 D130: a verb
that logs in before or at registration sits under `device`):

    tacctl device enroll <address>... | --discovered
        [--host-key SHA256:<fp>] [--vendor cisco|juniper|wti]
        [--name <name>] [--legacy-ssh] [--json]

Superusers only (no `tier.Rules` row, `deviceVerbAllowed("device",
"enroll", tier.Superuser)` as `collect`), the invoking user's own login
(`configLogin`; no `--login`: a device that has no TACACS+ login yet is
`device onboard`'s). The addresses come from the arguments (normalised
and deduplicated as `collect.args` does) or, with `--discovered`, from
`Resolver.Unregistered(false)`, the addresses `device discover` lists
that authenticated; the two forms do not mix. `--host-key`, `--vendor`
and `--name` are for one address (a list is answered at the terminal,
device by device) and are the only way a run without a terminal gets
past the questions; `--legacy-ssh` registers every device of the run
with the legacy algorithms (a device that answers only those is detected
as `collect.scan` detects it and registered so without the flag). Usage
row in `deviceVerbs` after `collect`, option lines in
`deviceOptions["enroll"]`, a paragraph in `deviceRegUsage`'s text, the
spec in `deviceSpecs["enroll"]` (`MaxArgs: -1`, `Args: []string{""}`,
`--discovered` `Alone`), the completion kinds from it, `help_text.go`'s
family block. No `-y`, no `--accept-all`, no `--trust`, nothing that
answers a host-key question for a list.

**D262 — Each host key is accepted by one person for one device.** The
new helper `acceptHostKey(addr, port, vendor, name string, offered
[]devreg.HostKey) (devreg.HostKey, hostKeyAnswer)` in
`device_hostkey.go` prints the keys as `echoKeys` prints them
(`HostKey.Display()`: the algorithm label and the SHA256 fingerprint),
the vendor's console command (`devreg.VerifyHint(vendor)`, the
detected vendor's when D263 read one, every vendor's line otherwise)
and asks once: `Type the fingerprint shown on the console of
192.0.2.10 (sw1) to accept it, or press Enter to skip the device: `.
The answer, trimmed, with or without the `SHA256:` prefix, must equal
the fingerprint of one offered key (`devreg.MatchFingerprint`); that
key alone is pinned, exactly as `device add --host-key` pins it (the
registration of D264 passes `--host-key <fp>` and the offered keys as
`trusted` into `deviceAddWith`, so `deviceAddReport` prints the other
offered keys as "offered, not pinned (unverified)" with the `device
hostkey <name> accept` line that pins them after a check). An empty
answer skips the device (`skipped: not accepted`); any other mismatch
refuses it (`refused: the fingerprint typed matches no key offered`),
with no second try: the fingerprints are printed again in the refusal
and the address is run again when the typo is found. There is no
accept-all, no trust on first use and no form that answers for several
devices; without a terminal the one form is `--host-key` for one
address, the key read on the device's console, matched the same way.
Every answer is an audit line at `auth.notice`, before any login uses
the key:

    device enroll hostkey user=<u> addr=192.0.2.10 device=sw1
      alg=ssh-ed25519 fp=SHA256:<fp> result=accepted|skipped|refused
      source=typed|flag

(`sid=` from D247 ties it to the run's `cmd start`; a fingerprint is a
public value and passes the no-secret scan of D255.) Why the
fingerprint typed back and not `y`: the project's strongest answer form
is a value the person must have looked at (the hold's device name,
D124; the apply's name), and a fingerprint is what the console shows;
`y/N` was `collect`'s one question for a whole list, which this
decision ends. A shorter confirmation (the last characters of the
fingerprint) is an open question for the maintainer (handoff).

**D263 — Vendor and name from the device, a question for what cannot
be read.** For each address the SNMP read of D260 (sysName,
sysObjectID, sysDescr, the scope's credentials through
`snmpConfigFor`) runs beside the host-key scan, as `device add` runs
`lookupNameHint` beside `deviceAddKeys` (one goroutine per address, the
result awaited at the question). Then, at the terminal, after the key
is accepted, one registration question per device: `Register
192.0.2.10 as 'sw1' (juniper, the device says so)? [y/N] `, the name
lower-cased and checked as `collect.names` checks it
(`devreg.ValidateName`, `res.CheckName`, taken in this run). What the
read did not give is asked: `Vendor of 192.0.2.10 (cisco, juniper or
wti; Enter skips the device): ` and `Name to register 192.0.2.10 as: `,
each answered once and checked with the usual rules (a generic name is
refused with `devreg.GenericRefusal`'s text and the device skipped:
`enroll` has no `--allow-generic`); an enterprise-9 answer without the
IOS sysDescr (D260) prints what was read and asks, so an ASA is never
registered as `cisco` by a default. `--vendor` and `--name` (one
address) answer the questions ahead and are what a run without a
terminal gives when the read fails; a detected vendor that disagrees
with `--vendor` is a warning, the flag wins, as in `device add`. A
device whose vendor stays unknown is skipped (`skipped: the vendor
could not be read or given; register it with: tacctl device add <name>
192.0.2.10 --vendor <vendor>`): `enroll` never registers a device as
`other`, because every later step of the chain needs a vendor.

**D264 — The chain: order, state and partial failure.** One run has
four stages, and every address is independent of the others.

1. *Identity and registration, one address at a time, in the order
   given.* Refused before any question (one row, the run goes on): an
   address already registered (`registered already as 'sw1': tacctl
   device config pull sw1`), an address no scope's prefixes cover
   (`m.LookupAddr`), a scope the caller is not a member of
   (`loginProblem`), a break-glass hold (`holdAt`, `holdRefusal`), a
   scan that reads no key (`scanDevice`, with the legacy second try of
   `collect.scan`). Then D262's acceptance, D263's registration
   question, and the registration itself through `deviceAddWith([]
   string{name, addr, "--vendor", v, "--no-lookup", "--host-key", fp,
   ("--legacy-ssh")}, offered)`: the registry write (`deviceWrite`, the
   known_hosts regenerated, the snapshot `deviceWrite` takes), the D253
   `device add` line and the central pair's `snapshot=`. A registration
   that fails (a name taken meanwhile, the registry lock) is a row
   `not registered: <reason>`. From here the device exists whatever
   happens next: nothing of stage 1 is undone by a later failure, and
   the summary says what each device still needs.
2. *The pull, once for every device registered.* The password is asked
   once here (`inv.hooks.newDevicePasswords(inv)`, D70; the cache
   applies as for a pull), after every identity question and before the
   first login, then `runPull(pullBatch{entries: registered, ...})`
   reads them in the 0.2.4 pool with the pull's view, lines and audit
   lines; a device whose pull fails is `registered, pull failed:
   <reason> (tacctl device config pull sw1)`. `pullBatch` gains a
   password source so stage 4 reuses the same string (D268 needs the
   same field).
3. *The plan, for every device pulled.* The plan of `device config
   plan` from the fresh record, printed as `plan <names>` prints it
   (the cover page for several devices); `deviceConfigPlan` is split so
   that `planEntries(entries []devreg.Entry, planOptions)` can be
   called with the entries in hand (today the verb parses, selects and
   prints in one function of 400 lines; the split is the one refactor
   of this package). A WTI unit's checklist and an IOS paste region
   are the end of the chain for those vendors.
4. *The offer, Junos only.* The Junos devices whose plan has changes
   are named and one question is asked: `Run the apply review for sw1,
   sw2 now (the plan is checked on each device, then each is confirmed
   on its own)? [y/N] `. `y` hands them to `applyCtl.run2` with an
   `applyRun` built as `deviceConfigApply` builds it and the stage-2
   password; the review of D265 follows, device by device. `n` ends
   the run with the devices registered, pulled and planned: `tacctl
   device config apply sw1,sw2` is printed as the next step. With
   `--json`, or without a terminal, the chain ends at the plan and one
   line says so; `--json` prints the pull's and the plan's objects as
   those verbs print them, then one object of the run (D272 lists it).

Interrupts: Ctrl-C during stage 1 ends the questions (the devices
already registered stay, the rest are `not tried: interrupted`); in
stages 2 and 4 the batch's two-stage interrupt applies
(`batchInterrupts`, 0.2.4 D68 and 0.2.9 D138); exit 130. Exit status:
0 every address was enrolled (registered, pulled and planned; declining
the offer or a plan with no change is 0), 1 any address was refused,
skipped or failed at any stage, 2 wrong arguments or a terminal needed
and absent, 130 interrupted. The summary is a table (`ADDRESS NAME
VENDOR KEY PULL PLAN RESULT`) and, under it, the next step of every
device that did not reach the end.

**D265 — The apply review is answered per device.** `applyCtl.review`
keeps its display: the groups by shape with the statements once per
group (`reviewStatements`), the notes (`reviewNotes`), the devices left
out. The one question becomes one question per device to apply, in
Phase B's order (the order `selectApply` returns: registry order, at
most `--max`, so no device beyond `--max` is asked about): for each,
one line `sw1  shape 3f2a1b (confirmed on sw-lab-2), 2 set, 1 delete`
and `Type the device name to apply to sw1: `. The name typed back
approves the device; anything else declines it (`skipped: not approved
(the answer typed is not its name)`), with no second try, and the next
device is asked; an end of input declines every device not yet asked.
Phase B then runs over the approved devices exactly as today: the
canary per shape (the first approved device of each shape), `--pause`,
`--concurrency`, `--no-canary` and `--hold` are untouched, because the
questions are all answered before Phase B starts; `--hold` adds its own
`OK` after the fresh login, so a held device has two answers, before
and after, which is the point of `--hold`. The grouping stays the
display so identical changes are read once; the answer is per device
so that no device is applied on the strength of a count. Exit status:
a declined device is a person's choice, not a failure: the run exits 0
when every approved device applied and at least one was approved, 1
when none was approved (today's `declined` rule, kept) or any approved
device failed, rolled back or is pending. `--json`: one object per
device with `"phase":"review"`, `"status":"approved"|"declined"` and
`"mode"` (D266) on standard output, the review text on standard error
as today. `device onboard`'s review (one device, its name typed back)
is already this and gains only the `mode=attended` key. Why not ask
each device's question just before its Phase B job: with
`--concurrency` above 1 and the canary, the questions would interleave
with the progress lines of running devices, and a run of twenty devices
would hold the terminal for its whole duration; the answers up front
keep the review one sitting.

## 3. Candidates weighed

**A flag on each `Spec` instead of a table (D249).** `Spec` is per
sub-verb and already exists, but the gate and the sudoers rules speak in
`cmd sub`, several families parse their own words after that and some
verbs have no `Spec` at all (`install`, `rollback`). One table keyed as
the gate keys, with a test that it covers the tree, is the smaller
change and reads as one policy. Reusing `tier.Rules` was weighed: it
says who may run a verb, not whether the verb writes (`device scan` is
an operator row and writes a cache; `scope secret` is one row for a read
and a write). Not chosen.

**Logging every invocation, reads included.** Sudo already logs every
command line with its user and tty; a tacctl line for every `device
list` would double the volume of the busiest, least interesting lines
(the shell's completion helpers run one per keystroke). Not chosen; a
site that wants every invocation has sudo's log, and `audit.all` is an
option of section 8.

**The central lines only at the end (no intent line).** One line per
command, but a command killed mid-write leaves nothing, which is the
case an auditor asks about. Chosen: the pair.

**A local append-only file beside syslog.** Tamper-evident storage is a
collector's job and a second place to look; section 8 keeps it as an
option. Not chosen for this release.

**Fail closed by default (D257).** The compliance-standard behaviour,
but a tacctl whose first run on a half-installed machine refuses
everything because `logger` is not there yet, or a server whose journald
is restarting, is worse than a warning the operator sees. Chosen:
strict exists and is off by default.

**Dropping the ssh and console session lines in favour of the central
pair (D250).** They carry the device, the login and the end reason;
removing them changes what sites filter on. Chosen: keep, four lines
per session.

**Redacting `--reason` (D252).** The free text is the audit's purpose
for a hold; sudo logs it anyway. Chosen: logged, documented.

**The session id in the host records and apply records.** `LastSync`
and the apply records are overwritten or per-device; the snapshot is the
one artefact that outlives the command and that a restore names. Chosen:
the manifest only.

**A verb of its own for "pull, select, apply" (D268).** `device
remediate --scope lab` reads well, but it would be `apply --pull
--differs` with a second name, a second usage block and a second man
entry for the same transaction; the enroll-workflow decision names the
flags. Not chosen.

**`device enroll` built on `device collect --register` (D261).**
`collect` already scans, shows keys, logs in and registers; a flag
chain (`--register --pull --plan`) would get there. But `collect`'s
read is a Junos `show version` before registration (a login on an
address nobody registered, which the registry otherwise forbids), its
one question covers a whole list, and its table is a report, not a
chain's progress. `enroll` registers first (after the person's two
answers), then pulls through the ordinary verb with a pinned key, so
no login is ever made against an unregistered address: fewer special
paths, and `collect` stays what it is. Chosen: a verb of its own, and
`collect`'s acceptance follows (D270).

**Asking each apply question just before the device's commit (D265).**
Closest to "confirm what you are about to do", but it interleaves with
running devices' progress under `--concurrency` and holds the terminal
for the run's whole length. Chosen: every answer before Phase B.

**One review question for a `device enroll` run (the count typed
back).** The enroll-workflow decision rules it out: each device is
verified on its own. Not chosen.

**Pinning every offered key in `enroll` after one fingerprint is typed
(D262).** `device add` without `--host-key` pins all; `collect` pins
all. The person compared one fingerprint, so one key is what they
verified; the others are listed and pinned after a check with `device
hostkey accept`, as `device add --host-key` already does. Chosen: one
key.

**`--pull` on `apply` implying `--differs` (D268).** It saves four
characters and makes the flag mean two things; Phase A already ends a
device that needs nothing as `no change`. Chosen: `--pull` pulls, the
selectors select.

## 5. Ordering and dependencies

WP17.1 first: everything else writes through it. WP17.2 next: the table,
the pair and the backstop are the release's substance, and the
classification test from then on catches every verb the later WPs touch.
WP17.3 before WP17.4, so the no-secret scan runs over every detail line
as it is added. WP17.4 is the largest and is built family by family,
each family its own gated unit and commit (identity and groups; access
grants and console; whole-state and lifecycle; secrets; hosts and
devices; the `result=` fixes). WP17.5 any time after WP17.1. WP17.6 and
WP17.7 are separable and last among the code packages; either can be
dropped from the release without touching the others. WP17.10 is
separable and independent of the audit packages (it only needs its
verbs classified in the D249 table); built after WP17.7.

The workflow packages follow, in this order and with these
dependencies. WP17.11 (the selectors) depends on nothing of this release
and can be built in parallel with the audit packages in its own
worktree; WP17.12 (`apply --pull`) needs WP17.11 for the filters it
applies after the pull. WP17.13 (the per-device review, `mode=`) needs
WP17.1 for the writer that carries the new key and WP17.2 for the
vocabulary it extends, and is otherwise independent of the selectors.
WP17.14 (`device enroll`) needs WP17.10 (the vendor and name read, with
the review note's items (3) and (4) settled), WP17.13 (the review it
hands its Junos devices to) and WP17.2 (its class entry and the central
pair its lines sit under); it is the largest of the five and is built
last among the code packages. WP17.15 needs WP17.14's helper only. The
base of the release is the audit packages (WP17.1-WP17.5) and vendor
detection (WP17.10); the workflow packages stand on it and never the
other way round. WP17.8 and WP17.9 last.

## 6. Risks

- Volume and cost: an `action` verb now runs `logger` twice (a few
  milliseconds each); `host sync` of ten hosts runs it twelve times;
  `device config apply` of many devices adds two to its per-device
  lines. Nothing runs `logger` in a loop over keystrokes (the completion
  helpers and the shell are `read`). Accepted; measured once in the
  container matrix.
- The 62 test assertions that count `logger` calls (D255 8) are the
  largest mechanical change; moving them to the content helpers is done
  in WP17.1 before any new line exists, so a later failure is a real
  one.
- The backstop panic (D249) fires in every Go test for a misclassified
  verb, which is the point; it must never fire in the release binary
  (the `testknobs` tag guards it, as the other knobs are guarded).
- `Touch` from `internal/app`, `internal/snapshot`, `internal/hosts`,
  `internal/policy` and `internal/lifecycle` needs the writer reachable
  without an import cycle: `internal/audit` imports only `execx` and
  the standard library, and every package takes the writer as a field
  or a function, never by importing `cli`.
- D251 changes the type of ~25 errors; each site's message and status
  are pinned by tests today, which is the regression net.
- D256 adds keys to a file that nothing reads; the risk is only that
  something outside tacctl parses manifests. The keys are additive and
  sorted, as the format has always been.
- The gate's DENY line is written before the model is read in some
  paths; the sid is made before the gate, so no ordering issue, but the
  writer must not need the model.
- Sites that already filter the existing lines see new `sid=` on them;
  a key appended at the end breaks no prefix match and the release
  notes say so.
- The release is now three themes. If it must shrink, the cut order is:
  WP17.15 (`collect`/`onboard` acceptance) first, then WP17.14 (`device
  enroll`, the largest package; the selectors, `--pull` and the
  per-device review stand without it and are the remediation half of
  the workflow), then WP17.12 and WP17.11 together, then WP17.13, then
  WP17.7 and WP17.6 as section 5 says; the audit packages WP17.1-WP17.5
  and vendor detection WP17.10 are the base and are not cut. A cut
  package's decisions stay in this plan marked deferred, as
  `apply-deferred.md` did for 0.2.5.
- The per-device review changes the one answer of `apply` that scripts
  and operators know; `--confirmed -y` keeps working unchanged, and the
  attended form asks N names instead of one count, which is the
  decision's intent. The bats and Go tests that type the count are
  rewritten with WP17.13, before anything else depends on the review.
- `device enroll` registers a device as soon as its two answers are
  given (D264 stage 1): a run interrupted or failed later leaves
  registered devices, by design, and the summary names each one's next
  step. The alternative, registering only at the end, would mean a login
  against an unregistered address (what `collect` does and `enroll`
  avoids) or a second scan.
- `acceptHostKey` asks for a 43-character fingerprint with no retry; a
  typo costs a second run of the address. The shorter confirmation is an
  open question of the handoff; the code keeps the matching in one
  function so the rule can change without touching the callers.
- The split of `deviceConfigPlan` into `planEntries` (D264 stage 3) is
  the one refactor of a 400-line verb that the plan tests pin by output;
  the diff corpus and `device_config_plan_test.go` are the net.
- `pullBatch` gains a password source shared by a pull, a check and an
  apply of one run (D264, D268): the string lives in one `applyRun` as
  today and is zeroed at the end as `deviceConfigApply` zeroes it; the
  review of WP17.12 reads that path.
- WP17.14 depends on WP17.10's lab captures only for `wti` and
  `juniper` being offered as detected vendors; without them `enroll`
  asks for the vendor (D263), so the package does not wait for the lab.
- The D260 review note found that a vendor change re-reads a device's
  stored sections in the new vendor's family today; item (5) fixes it
  as part of WP17.10 and the fix is needed before `enroll` registers
  detected vendors on devices that have records.

## 7. The audit this plan rests on

Read-only, 2026-10-21, against `54435e7`. Findings used above: one
helper and two direct `logger` callers; no logging in any shared
writer; ~35 verbs logged, mostly success only; ~80 state-changing verbs

## 8. Options beyond this release, with a recommendation

- **`tacctl log audit [--since ...] [--sid <id>]`**: reads `journalctl
  -t tacctl -t tacctl-console` and prints the lines of one sid or
  period; operator-level like the other `log` reads. Cheap (the `log`
  family exists) and the natural way to answer "what happened"; the
  one tacctl-side reader of the log. Recommended for the release after
  this one, once the format of 0.2.17 has settled.
- **`backup list` showing `user` and `command` from the manifest**:
  one column; changes a pinned output. Recommended with `log audit`.
- **`audit.all`**: the central pair for `read` verbs too. Doubles the
  volume for what sudo already records. Not recommended.
- **A local append-only file** (`<state>/audit.log`, 0600, written
  beside syslog): survives a journald outage and a collector gap, but
  is a second store to protect, rotate and reconcile. Not recommended
  while the site runs a collector; worth it only where none exists.
- **A hash chain over the lines** (each line carries a digest of the
  previous): tamper evidence on the local copy; it belongs in the
  collector, where the lines of every host meet. Not recommended.
- **Remote shipping from tacctl** (`logger -n <host>`, TLS): the
  forwarder's job (rsyslog, journald's upload, the site's agent); tacctl
  would gain a network dependency and a credential. Not recommended.
- **`device add` without `--host-key` pinning every offered key**
  (D270): the registration path's own trust model, older than the
  workflow; moving it to a typed fingerprint changes every `device add`
  and the bats that drive it. Recommended for a later release once
  `enroll` has shown the question works for operators.
- **`collect` and `onboard` left with one `y/N`** if WP17.15 is cut:
  acceptable for a release, not for long (two trust models). The
  recommendation stands (D270).
- **A short confirmation for the fingerprint** (the last eight
  characters, as some consoles show them): less typing, a smaller
  space to match against; a decision for the maintainer (handoff).
- **`enroll` for a blank device** (`--login <local-user>`, the onboard
  path inside the chain): one verb for both cases, but two passwords
  and two trust questions in one run; `device onboard` stays the verb
  for a blank device. Not recommended for now.
- **An IOS write path** so that `enroll` ends at an apply for Cisco
  devices too: the deferred questions of `apply-deferred.md` section
  5.3 stand; not for this release.
- **`device enroll --json` offering the apply**: the apply's objects
