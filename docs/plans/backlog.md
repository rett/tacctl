# tacctl backlog: work filed for after 0.2.0

**Decision (user, 2026-10-03):** 0.2.0 is the Go rewrite with functional equivalence to 0.1.16 and nothing else. Everything below waits until 0.2.0 is released. Each item records where its design lives and why it was deferred. Nothing here may be started on `feature/go-rewrite`.

## 0. Roadmap after 0.2.2 (user, 2026-10-08): 0.2.x, one release per major phase

Planned 2026-10-08; **solidified 2026-10-09 with the 0.2.4 plan** (`0.2.4-plan.md`, D60-D76; the rows below were rewritten then, the earlier wording is kept where it still holds). 0.2.8 is released (2026-10-13); 0.2.9 is released (2026-10-14); 0.2.10 and 0.2.11 are released (2026-10-15); 0.2.12 is released (2026-10-16); 0.2.13 is released (2026-10-16: parallel `internal/cli` tests, `0.2.13-plan.md`); 0.2.14 is released (2026-10-18: holds that follow `device address` and cover hosts, `host rename|forget`, host state in snapshots, lower-case names, the UID carried by `user rename`, `0.2.14-plan.md`); 0.2.15 is released (2026-10-19: restore vs host lock, `--keep-uids`, `host sync`/`host check` for several hosts, `config validate --json` and `--fix-names`, `0.2.15-plan.md`; state: `0.2.15-handoff.md`). Each release follows the git-flow procedure in `0.2.2-plan.md`.

**Transport: NETCONF with SSH fallback (user, 2026-10-08).** Device configuration (0.2.4 read, 0.2.5 apply) goes through one driver interface with two implementations: NETCONF over SSH (tcp/830; Junos first, IOS-XE where `netconf-yang` is on) and the SSH CLI (every vendor, nothing to enable). An unmanaged statement under a managed hierarchy stays kept and listed. *Resolution:* device > scope > default > built-in is kept; per object (the vendor-native key: community string, client-list name, trap-group name); a device block's object replaces the scope's of the same key whole; the default level carries nothing that names a client or a target. tacctl's own community, `TACCTL-SNMP` and its v3 names stay in the structured settings and a block that names them is refused. *Decided:* (2) engineers read a block elided for their scopes, setting is superuser-only, `--reveal` is logged `secret-read kind=block`; (3) a `delete`/`no` line in a device block means "not managed on this device" (kept), never "must be absent"; (4) `trap-options source-address` and IOS `trap-source` were refused in a block until the parked per-device source address (this section, "Source address for AAA and SNMP") existed; they are accepted in 0.2.7 as one device-specific value (an interface or an address the devices of a scope share, noted by `check` at the scope level; a device's own block states another), replaced in place by the plan, and the parked source-address idea stays about the AAA and SNMP client addresses themselves; (5) adoption opens the system's configured editor on the adopted text; (6) the blocks release goes before the device accounts (0.2.7 and 0.2.9; moved up from 0.2.8 on 2026-10-12). *Editing:* `tacctl scope block <scope> <vendor> edit <block>` opens the file in the configured editor: `$VISUAL`, else `$EDITOR`, else `editor`, else `vi`. It follows `visudo`/`sudoedit`: the editor runs as the INVOKING user on a private 0600 copy in a 0700 directory (never as root: an editor's shell escape must not be a root shell), the file is installed only after `check` passes (token lint against the block's allow-list, the TACCTL names refused, the objects that become owned and the statements that carry a secret listed, the diff against the file in force, optionally `--against <device>` showing the plan it would make), after a confirmation, a config snapshot and one atomic write. A failed check offers to re-open the editor. `adopt <device> <block>` reads the device's hierarchy with the caller's login, drops what tacctl renders itself and the per-device identity statements (`snmp name`, `engine-id`), and opens the result in the editor as the draft to prune. Superuser only, and the console's `system-shell` rule applies (default tiers: superuser). Caveat to document: an editor may write swap or backup files beside its working copy (the private directory is where they land, and it is removed afterwards); a block that holds a community is a poller's credential on this host and in the snapshots. *More blocks (requested 2026-10-12):* a `system` block per vendor for the device's own system settings. Junos: `system login message`, `system domain-name`, `system domain-search`, `system time-zone`, `system name-server <addr>` (the statement is singular on Junos), `system ntp server <addr>` (also `boot-server`, `source-address`, `authentication-key`, the last a secret typed only where the device lacks it). IOS: `banner login`, `ip domain name`, `ip domain list`, `clock timezone`, `ip name-server`, `ntp server` (the keys of `ntp authentication-key`); built in 0.2.7, not lab-tested. Semantics to decide before building: each statement is an object (set when missing, extras kept and listed as unmanaged); an exclusive list ("the name servers are exactly these", extras removed) is the declared-ownership idea rejected above and is only ever an explicit per-statement marker, never the default. These statements are outside the planner's AAA/roles/SNMP/management-filter domain, so the plan section list, the apply helper's region allow-list (it permits `system authentication-order|tacplus-server|radius-server|accounting|login class|login user` today and would need `login message`, `domain-name`, `domain-search`, `time-zone`, `name-server`, `ntp`) and the walkthrough's Step 0 comment lines (`ip domain name`, `no ip domain lookup`, NTP) are all touched: the block replaces those comment lines for a scope that has one. *Sizing (Fable):* the extract-time labels first (0.2.7), then the `snmp` block for Junos (4-6 sessions), device-level blocks and IOS (3-4), the `system` block and later names (per block). *Rejected:* a keyed fingerprint of other communities' strings; adoption from stored pulls; named structured profiles as the general mechanism; declared ownership; cross-vendor translation; retiring `config snmp` or `device snmp`.

- **Deny-by-default management filter for Junos (considered 2026-10-12; parked, not scheduled).** *Finding:* the standard filter (`permit-mgmt`, `deny-mgmt`, the SNMP terms, a final `default-accept`) restricts ssh, NETCONF and SNMP only. A site that runs a deny-by-default `lo0` filter (one `then accept` term from a prefix list, everything else dropped by the implicit discard) cannot be expressed: naming tacctl's filter the same as the site's makes the plan delete the site's terms (the filter object is owned whole, `junos.mgmt-acl.filter`) and the device becomes accept-by-default for everything but ssh, NETCONF and SNMP. *Today's workaround:* clear the scope's permit list (`scope mgmt-acl <scope> clear`, and the global list empty), so the section reads `n/a` and the device's own filter is listed as kept. *Options weighed:* (a) a per-scope `scope mgmt-acl <scope> mode ssh-only|strict` (recommended): `strict` renders one term accepting every protocol from the permit list (the server's address stays first, so the existing refusal of a filter that would not permit the tacctl server still holds) and no `default-accept`, with the plan's report listing the traffic that stops (NTP, syslog, DHCP, SNMP sources outside the list), a per-scope opt-in because a scope with routing protocols would lose them, lab-verified first; (b) a free-form `firewall` configuration block (the site's filter and `policy-options prefix-list` in Junos form), which needs the planner and the lock-out guard to understand arbitrary filters, the larger job. *Not decided; no release chosen.*

- **WTI RESTful API as a second transport (considered 2026-10-12; tabled while the ssh reader is sufficient).** *Idea:* enable web access on a unit over ssh (once, by a person), read `GET /api/v2/config/settings` over HTTPS with `device.config.transport` `auto|rest|ssh` (as NETCONF sits beside the ssh CLI on Junos), and fall back to the ssh menu reader when HTTPS is not reachable. *For:* one structured read with no pty, pager or menu scraping, clear status codes, no final-ESC flash risk. *Against:* enabling web is a write to a guarded setting and the backlog rule is never to switch it on and off per change; whether a TACACS+ user can authenticate to the API is not known (a local API user or token would be a credential no person types, which is the service-account question of 0.2.9); a certificate is needed (none installed on the lab unit); the ssh reader is required anyway for the fallback and for per-port direct connect, which the API lacks. *Kept open by design:* the 0.2.7 reader sits behind a small terminal interface so a REST transport could be added without touching compare or plan. *Experiments not run:* enabling web on the lab unit, an API user, a 443 IP tables line, `GET` of the settings, a TACACS+ user against the API, what a partial PUT does. Revisit when per-device web access is wanted for another reason.

## 3b. Juniper authorization from the server (0.2.2 candidate, filed 2026-10-05)

**Request (user, 2026-10-05):** send Juniper users' command and configuration permissions from the server, as attributes, instead of only the login class.

- **Today:** a Juniper login gets only its class: `local-user-name` in tacquito's `junos-exec` service (TACACS+), `Juniper-Local-User-Name` (RADIUS). `tacctl group commands` rules reach Junos only as the class's `allow-commands`/`deny-commands` lines that `tacctl config juniper` prints for each device (`internal/devices/juniper.go`).
- **Proposal:**
  - TACACS+: the same `junos-exec` service also carries `allow-commands`, `deny-commands`, `allow-configuration`, `deny-configuration` (or the `*-regexps` variants where Junos has them).
  - RADIUS: the matching Juniper VSAs (Juniper-Allow-Commands 2, Juniper-Deny-Commands 3, Juniper-Allow-Configuration 4, Juniper-Deny-Configuration 5), set in post-auth beside `Juniper-Local-User-Name`, only for scopes that send Juniper attributes.
  - Rendered from the group's command rules (the same regexes `config juniper` builds), and from a new per-group configuration rule set (`tacctl group config-access <group> allow|deny <regex>`, stored like the command rules), which tacctl does not have yet.
  - The device-side class lines stay as the fallback for logins when the server is unreachable; `config juniper` says which source is authoritative.
- **Open, to settle by a live check on the lab Juniper switch first** (run sheet kept outside the repo):
  1. How Junos combines server-sent values with the class's own: override or merge, for allow and deny, commands and configuration; what `show cli authorization` reports.
  2. Length: a TACACS+ value is at most 255 bytes, a RADIUS VSA 253; today's per-class regex joins every rule into one expression. Which Junos releases accept the `*-regexps` (list) variants.
  3. Behaviour over both protocols, and the Junos release on the lab switch.
- **Live check on the lab Juniper switch (2026-10-05; EX4300, Junos 25.4R1), TACACS+:**
  - Junos applies server-sent values: after a new login `show cli authorization` lists them under "Individual command authorization" (allow/deny regular expression, allow/deny configuration regular expression).
  - `deny-configuration "^system"` blocked system edits for a class with `permissions all`.
  - `allow-commands-regexps` (the list form) is accepted on 25.4.
  - **An argument longer than 255 bytes makes the login fail**: the limit is TACACS+'s for the whole `name=value` argument, so a `deny-commands` value may be at most 241 bytes and a `deny-configuration` value 236 (a 247-byte `deny-commands` value is a 261-byte argument; tacquito logs `unable to marshal packet; invalid arg length. valid range [2-255], found [261]` and Junos `PAM_TACPLUS_SEND_AUTHOR_FAIL`). An oversized value locks the group out of every Juniper device of the scope. tacctl must check each rendered argument's length and refuse the change (naming the group and the length), never send it.
  - The switch's classes carry only `permissions view` / `permissions all`, no local regexes: on such devices the server is the only source of command rules, and the permission bits decide which commands exist at all (an operator without `view-configuration` has no `show configuration`, whatever the regex says).
  - Still open: whether a server value replaces or joins a class's own allow/deny lines (the lab classes have none); whether Junos accepts the same attribute twice (splitting long rule sets); RADIUS (VSAs 2-5) not yet run.
- **Not in 0.2.1:** it changes what devices are told at login; 0.2.1 is at its release gate.

## 3c. Device authorization from the server: Cisco, Junos and WTI (0.2.2, filed 2026-10-05; planned in `0.2.2-plan.md`)

**Status (2026-10-08): shipped.** 0.2.2: `group junos`, `group edit <g> wti-level`, per-level Cisco authorization, the `group commands remove` selector and `add` placement, privilege modes. 0.2.3: every command regex rendered whole (`^(?:regex)$`), the match lint, the baseline rules and privileges of the four roles, the role preset rewritten, `group reset`. What stays open is the lab acceptance (§0b) and `--match` regexes that cannot contain a comma.

**Request (user, 2026-10-05):** one interface for command permissions across vendors, with no permissions hardcoded on devices; Cisco keeps its privilege levels. Extends §3b. A worked scheme for four roles (viewer, operator, engineer, superuser) on all three vendors, and the lab run sheet that tests it, are kept outside the repo.

- **How tacquito evaluates command rules** (read in its source, `cmds/server/config/authorizers/stringy/command.go`):
  - Rules are tried in order. A `*` rule decides at once, wherever it stands; a rule with another name is skipped; a rule without `match` decides; a rule whose regexes all miss falls through to the next rule, so a deny with `match` followed by a permit of the same name works.
  - Every `match` regex is anchored at both ends (`^` and `$` added when missing) and tested against the arguments joined by spaces, without the final `<cr>`. A regex therefore has to cover the trailing arguments itself: `--match '^crypto'` matches `show crypto` only, not `show crypto pki certificates`; write `--match '^crypto( .*)?'`.
- **Cisco (TACACS+): privilege levels stay; the server decides each command.**
  - IOS checks both: the privilege level decides which commands exist, `aaa authorization commands <level>` asks the server about each one. Configuration commands are sent as ordinary commands (`interface ...`, `hostname ...`), so one rule set covers both modes.
  - `config cisco` emits `aaa authorization commands` and `aaa accounting commands` for levels 1, 7 and 15 only, while `group add|edit` accepts 0-15: commands at any other level in use are never sent to the server. Emit one line per level in use.
  - Emit `aaa authorization config-commands` explicitly (IOS's default once `aaa authorization commands` is set, per Cisco's reference; the line makes it certain), and offer `aaa authorization console`.
  - A role that configures (engineer) has to be priv-lvl 15: configuration commands are level 15, and lowering them needs a `privilege configure` line per command and submode on every device. The server's rules are then the only thing separating it from superuser; the `local` fallback makes it a superuser while the server is unreachable (document it).
  - Over RADIUS Cisco IOS has no per-command authorization; nothing changes there.
- **Junos:** the classes keep permission bits only; the server sends `deny-commands` and `deny-configuration` (no `allow-*` values, so the question of how allow and deny combine never arises). Junos regexes are POSIX ERE over the whole command line, Cisco's rules are a command word plus RE2 over the arguments, and the deny sets of the two differ in content (Cisco `aaa`, `username`; Junos `system login`, `system tacplus-server`). So the attributes are a per-group Junos rule set of their own under the `group` verbs (for example `tacctl group junos <group> deny-commands|deny-configuration add|remove|list <regex>`), not a translation of `group commands`. Each value is checked when it is set: its `name=value` argument must fit TACACS+'s 255 bytes (RADIUS: 253 bytes for the value).
- **WTI:**
  - The unit has no per-command authorization; it takes one of four access levels from priv-lvl (bands 0-4 ViewOnly, 5-9 User, 10-14 SuperUser, 15 Administrator) or from `WTI-Super` (0-3) over RADIUS. WTI's documents: Administrator has all ports, features and configuration menus; SuperUser all ports and operating features and may view but not change the configuration; User only status and the ports enabled for it (over TACACS+: Default User Access); ViewOnly status only.
  - Because the WTI level comes from the Cisco priv-lvl, an engineer at 15 is an Administrator on WTI units and can change their users and AAA settings. Proposal: a per-group WTI level (`tacctl group edit <group> wti-level auto|viewonly|user|superuser|administrator`, `auto` = today's bands). RADIUS: set `Tacctl-WTI-Super` from it. TACACS+: a `wti_exec_<group>` service named `wti` with its own priv-lvl, and the walkthrough sets the unit's Service Name back to its factory `wti`; groups without an override keep working through patch 0001's fallback to the `shell` values.
  - Ports and outlets: TACACS+ carries no port lists. RADIUS has `WTI-Port-Access` (42), `WTI-Plug-Access` (43), `WTI-Group-Access` (44) in WTI's dictionary, one character per port or outlet, so the value depends on the model; not pursued (per-unit Default User Access lists instead).
- **tacctl gaps found on the way:**
  - `group commands remove <group> <name>` drops every rule of that name, so one rule of a deny/permit pair cannot be removed alone; it needs a selector (`--match`) or an index.
  - `group commands add` always appends before the catch-all; a rule cannot be placed before an existing one.
  - `group privilege add` emits `privilege exec level N <cmd>` only; `privilege exec all level N <cmd>` (a whole command tree) and `privilege configure level N <cmd>` cannot be expressed.
  - `--match` regexes cannot contain a comma (the rule line form splits on it).
- **Lab results so far (2026-10-05):**
  - Junos (TACACS+): logins with `deny-commands` and `deny-configuration` values sent from the server work for permission-only classes once each `name=value` argument is at most 255 bytes (the largest tried: 251); at 257 and 261 bytes the login failed.
  - WTI (TACACS+): User-level logins reach the ports turned On under Default User Access, as `config wti` now instructs (0.2.1 item 59).
  - Junos role tests (EX4300, 25.4R1), classes with permission bits only: `show cli authorization` lists the server's values; `deny-commands` refused the listed operational commands (`ssh`, `file`, `request`, `start shell`, `load`); `deny-configuration` refused `set system login`, the same under `set groups <name>`, `set system services` and `set snmp`, while `set interfaces`, `set protocols ospf` and `set system host-name` were accepted. A command refused by a regex disappears from the CLI (`syntax error`), like one the permission bits leave out.
  - **`deny-commands` does not cover the path after `show configuration`:** the viewer and operator read `show configuration system login` and `system tacplus-server` although their `deny-commands` named them; Junos treats that path as configuration.
  - **`deny-configuration` hides hierarchies from reading, for every class** (automated run, 31 checks, all as expected): with `deny-configuration "^(groups [^ ]+ )?system (login|root-auth|tacplus|radius|accounting)"` the viewer and operator (no `configure` bit) got `error: permission denied: login` / `tacplus-server`, the hierarchies vanished from `show configuration | display set` (0 matching lines; 516 lines against the superuser's 571), and other hierarchies stayed readable. So the viewer and operator sets keep only operational commands in `deny-commands` and put configuration paths in `deny-configuration`.
  - Junos reports a command hidden by a regex or by missing bits as `error: unknown command: <word>` or `error: permission denied: <word>`; a refused `set` is a `syntax error` at the denied keyword.
  - **A per-group WTI level works over TACACS+** (WTI unit, Service Name `wti`): the unit asks `service=wti protocol=tcp`; tacquito answered the engineer, whose group carried a `wti` service with priv-lvl 12, `priv-lvl=12` (SuperUser) while Cisco and the `shell` service keep 15, and answered the operator, whose group has no `wti` service, `priv-lvl=7` through patch 0001's fallback to the `shell` values. Accounting records carry `service=wti` too.
  - `deny-configuration` also hides a hierarchy from reading for a class that has `configure`: in configuration mode the engineer got `tacplus-server` as a missing parameter of `show configuration system`.
  - Routing secrets do not need `secret-control`: the engineer (`routing-control`, no `secret`/`secret-control`) set `protocols bgp group <g> authentication-key`, and `show | compare` showed it as `/* SECRET-DATA */`. Engineers can therefore rotate routing keys on Junos as on Cisco, without seeing them.
- **To settle on lab devices before building:** that tacquito's denies hold for priv-lvl 15 commands and in configuration mode (IOS-XE); how IOS reports `do <cmd>` in configuration mode; the Junos deny sets with permission-only classes (including `set groups ... system login`); that a WTI unit with Service Name `wti` sends `service=wti` and takes the priv-lvl of a `wti` service (SuperUser from 12 while Cisco gets 15).

## 3d. Fully qualified device names (filed 2026-10-05)

  - Several devices sending the same short NAS-Identifier raise the ambiguous-NAS-ID notice; it is correct, and the remedy is a fully qualified host name on the device (or the notice acknowledged).

## 3h. Version-gated statements and device facts (filed 2026-10-12)

A bootstrap check of a Junos 11.4 switch refused `set system login
idle-timeout`: before the statement existed at `[edit system login]` the
timeout is set only under a login class. The device's own load and
`commit check` caught it before anything was committed, and the helper
script now falls back to the per-class form for a first-time plan. Two
pieces of tacctl itself were open; both are built in 0.2.8:

- **Record the release, model and serial of each device (built in
  0.2.8).** Keep what a device reports about itself as
  read-only facts with the time they were read: the OS release string
  (Junos `set version` in the pull, IOS and WTI from the version output
  and page the pull already reads, so no extra login), and the model and
  serial number (SNMP `sysDescr` and the vendor serial objects, or one
  more `show` command in the same pull session: `show chassis hardware`,
  `show inventory`). They are kept with the last-pull record, not in
  `devices.yaml`, replaced on every pull, and shown by `device show`
  (and `--json`) and as a release column of `device config list`. A
  WTI unit shows its firmware version; whether it exposes a serial is
  open.
- **Consumed by 0.2.9 (D144):** the apply never rewrites a plan; a gated refusal at `commit check` names the gate and asks for a second run.
- **A short table of version-gated statements, learned from refusals
  (built in 0.2.8; the first row is `system login idle-timeout`).**
  One row per statement: the first release that takes it, and the
  fallback the walkthrough and the plan render for older releases. The
  first row is `system login idle-timeout` (fallback: one
  `system login class <C> idle-timeout <N>` per template class; with no
  stored release the current form is rendered, as today). A row is added
  only when a real device refuses a statement, with a fixture of the
  refusal; there is no model or version matrix, because the device's check
  already refuses what it cannot take.

## 3i. Device reports (proposal, filed 2026-10-29; not scheduled)

A report is a saved, dated document about the registered devices, made on demand from data tacctl already holds or reads on the operator's word. Proposal only; nothing here is decided.

- **Verbs:** `tacctl device reports generate --type <type> [--scope <scope>] [--vendor <vendor>] [--format text|csv|json|pdf] [--name <name>]`, `list`, `show <report>`, `rename <report> <new>`, `remove <report>`. Names carry the date (`inventory-20261028`).
- **Contents by type** (a short catalogue, one row per device): inventory (model, serial number, hardware revision, chassis members), software (release, the version-gate state of backlog 3h), chassis alerts, uptime, licence status, notices and host-key state, configuration state (the `device config list` states: ok, differs, never, failed). Further filters by scope, vendor, the user that generated it and the age of the data.
- **Source:** the pull records and the device facts already stored (no login). `--pull` reads the devices first, as `device config pull` does, with the operator's own password and no stored credential; a report is never scheduled and no device is contacted by a timer.
- **Storage:** the invoking user's home, `~/reports/devices/`, mode 0600. A dotted user has no Linux account and no home: decide where their reports go or whether they get the verb at all.
- **`show <report>`:** the date and time, the user, the exact command line that generated it, the filters, the age of the oldest datum, the size, and an example `scp` line to download it (generic host: `scp alice@tacctl.example.net:reports/devices/<file> .`).
- **Open points:** a PDF needs a vendored pure-Go writer (the build has no network, `vendor/`), so the first format could be text, CSV and JSON; the tier of each verb (read-only reports for operators, `--pull` for engineers); retention and a size cap; whether a report may carry the SNMP location and description (no secret, hash or community string in any report); the new verbs need completion, man page, docs page and a CHANGELOG item like any other.

## 3j. Filed 2026-10-29 for 0.2.23 and later (designs, nothing built)

- **Lockdown on enrolled hosts (0.2.23).** `emergency lockdown` closes TACACS+
  and RADIUS logins on devices but not an ssh key login or a forwarded port on
  a Linux host (`lockdownResidual` in `internal/cli/emergency.go`). Design: a
  static sshd drop-in on each host, named to sort first, with `Match Group
  <lockdown group>` setting `PubkeyAuthentication no` and `AllowTcpForwarding`,
  `AllowStreamLocalForwarding`, `X11Forwarding` and `AllowAgentForwarding` to
  `no`; enabling a lockdown changes group membership through `host sync`, the
  drop-in is checked with `sshd -t` and `sshd -T -C user=...` (a host without
  the `Include` of `sshd_config.d` fails open) and removed to lift. Exclude
  superusers, the provisioner account and the running user; end live sessions
  separately; a host unreachable at `disable` keeps the drop-in. The server's
  own console drop-in needs the lockdown block before the tier blocks. The
  script protocol of `internal/hosts` and `client-remove.sh` carry it.
- **Naming a device from its configuration (0.2.23).** For a device SNMP
  cannot name, an opt-in registers it under a random provisional name with a
  common prefix, reads the host name from the first pull and takes it over
  (`takeName`), lower-cased. A name that is registered with a different pinned
  host key is a conflict; with the same key it is the same device seen from
  another address and the address update is offered, never applied alone.
  Writing a host name to a device goes through the apply review (Junos) or a
  paste-ready line (others); `system host-name` has no render path yet.
- **`device clone` and `rename --replace` (0.2.23).** `device clone <old>
  <new> [--staging <bench-ip>]` copies a device's intent (blocks, SNMP
  settings and credentials, plain fields; not the pull record, host keys,
  acknowledged notices, hold, address or name) and registers it at a bench
  address with the existing scope staging `/32`. A rename with `--replace`
  (a distinct flag name: `device import --replace` exists) removes the
  original after a snapshot and confirmation, shows and clears its hold,
  moves the replacement to the original's address, which ends the staging.
  `renameDevice` must carry the staging line; engineers may clone within
  their own scopes, so the clone is audited and the tiers sudoers gain a row.
- **SNMPv3 user pool (0.2.23).** Today a level (config, scope, device) holds
  one setting and `v3-user` sets the version to v3 for everything below it.
  Design: the version stays a per-level setting; each level keeps a pool of v3
  users and a default user or none; adding a user changes nothing; a device on
  v3 uses its own user, else its scope's default, else the config default; the
  pool a device picks from is its scope's users plus the config's. A level on
  v3 with its one user keeps both on upgrade, the user becoming its default.
  The credential files change shape: a rollback step.
- **An email address on users (0.2.23).** An optional `email` field validated
  as a plain address, set by superusers (`user add --email`, `user email`),
  shown by `user show` and `--json`, never in audit lines, no SMTP. The store
  changes: a rollback step that removes it or refuses while one is set.
- **Several addresses per device.** The registry holds one `address`, the AAA
  identity, in about 40 places. Keep it as the management address and add a
  list of further addresses (AAA source addresses, loopbacks), unique across
  devices and hosts, used for log attribution, holds and known_hosts. An
  opt-in `device scan` option reads the host key of unknown log addresses and
  raises a notice on the one device that pins it; accepting asks whether the
  new address becomes the management one. A source-address change by apply
  must be a registered address of the device inside its scope's prefixes
  (else AAA fails). Older builds refuse unknown `devices.yaml` keys.
- **Multiple shared secrets for phased roll-outs.** TACACS+ has no message
  authentication, so two secrets for one address cannot be told apart
  without a daemon patch. Mechanism without one: a scope holds labelled
  secrets with one primary; a device (or host) selects one; the render emits
  an extra provider per non-primary secret with the `/32` of its devices; the
  new secret is made primary and the old removed when no device uses it. Check
  first which provider tacquito takes when a `/32` and the scope prefix both
  match and whether FreeRADIUS picks the most specific client.
- **The logging release.** A small hardened built-in logging server
  (standard library, reproducible, auditable) writing to local files, a local
  logger or a remote server over TCP or UDP, with a disk spool bounded by
  size, age and free space, per-scope targets, RFC 5424 with a tag per stream
  and an optional collector or relay for replica servers; rsyslog or another
  forwarder only as an opt-in plugin with a stated disclaimer. Plan it with
  the replica and failover work.
- **Replica and failover.** Several server addresses, a manual failover pair,
  primary and backup, mirror and sync per site or scope, possibly corosync;
  nothing is built.
- **Completion single source, phase 2.** Move the flags and words family by
  family into `Spec`/`Flag` and generate the usage rows; after the feature
  work of a release so it conflicts with nothing.
