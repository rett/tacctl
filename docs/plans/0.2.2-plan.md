## 0. Summary

- **Goal:** one interface for command permissions across Cisco, Junos and WTI, with nothing hardcoded on the devices beyond privilege levels (Cisco), permission bits (Junos classes) and port lists (WTI). The server tells each device what the group may do: Cisco keeps `aaa authorization commands` per level (now for every level in use), Junos receives `deny-commands` / `deny-configuration` at login (TACACS+ `junos-exec`, RADIUS VSAs 3 and 5), WTI receives a per-group level (TACACS+ `wti` service, RADIUS `WTI-Super`).
- **Plus:** the four `group commands`/`group privilege` gaps found on the way (§3c), fully qualified device names (§3d), a role preset (viewer / operator / engineer / superuser) that is opt-in, and a fourth tacctl tier, `engineer` (D18, WP9.14), which the preset assigns.
- **No state-format change.** Everything new lives in `tacctl.yaml` under two new key families (`junos.<group>.*`, `wti_level.<group>`), rendered into `tacquito.yaml` and the FreeRADIUS files like `commands.<group>` is today. `store.yaml`, `devices.yaml` and the registries are untouched, so 0.2.2 → 0.2.1 is a checkout plus one `tacctl upgrade` (§4.4 says exactly what a rolled-back 0.2.1 does with the new keys).
- **Size:** 12 packages, ≈ 10–12 sessions, ≈ 6,500 lines (Go + bats + docs), one live-acceptance session on the user's machine, then the release gate as in 0.2.1 (§4.14 of the console plan, amended for 0.2.2).

## 1. Goals and non-goals

### Goals

1. **Junos rule sets from the server (§3b):** per group, `deny-commands` and `deny-configuration` sets, stored in `tacctl.yaml`, rendered into the group's `junos-exec` service (TACACS+) and into `Juniper-Deny-Commands` / `Juniper-Deny-Configuration` in post-auth (RADIUS), each value checked against the protocol limit when it is set and again when it is rendered.
2. **Per-group WTI level (§3c):** `tacctl group edit <g> wti-level …`, rendered as a `wti` service with its own `priv-lvl` (TACACS+) and as `Tacctl-WTI-Super` (RADIUS); groups without it keep today's bands.
3. **Cisco AAA block (§3c):** `aaa authorization commands <L>` and `aaa accounting commands <L>` for every privilege level in use, `aaa authorization config-commands` explicit, `aaa authorization console` offered; a lockout guard for a level whose groups have no rules.
4. **The four tacctl gaps (§3c):** `group commands remove` selects one rule; `group commands add` can place a rule before another; `group privilege` can express `exec all` and `configure` (optional package); the comma restriction stays (deferred, §2).
5. **Role preset (§3c, lab fact 6):** `tacctl group preset roles`, opt-in, idempotent, never a forced default change.
6. **Fully qualified device names (§3d):** names up to 253 characters, the name-mismatch notice accepts the registry name's first label, the ambiguous-NAS-ID notice names the remedy.
7. **Walkthroughs:** `config cisco|juniper|wti` say what the server now sends and what stays on the device.
8. **Tests, docs, diff corpus, release notes** as in 0.2.1; a live acceptance on the lab devices reusing the permcheck approach (§9).

### Non-goals (0.2.2)

- `allow-commands` / `allow-configuration` from the server: the lab classes need none (permission bits decide what exists; `deny-*` removes), and how Junos merges a server-sent allow with a class's own is still open [L]. The data model leaves room (§4.1), nothing renders them.
- Splitting an over-long Junos set over two attributes (`*-regexps` list form, or the same attribute twice): whether Junos accepts it is open [L]; 0.2.2 refuses the change instead (§4.3).
- WTI port and plug lists over RADIUS (`WTI-Port-Access` 42 …): model-dependent, not pursued (§3c).
- Cisco per-command authorization over RADIUS: IOS has none (§3c).
- Merging `linux-hosts` into the device registry, any device data inside `store.yaml`: 0.3.0 (§5 of the backlog).
- Fully qualified **host** names (`host enroll --name`): the host name is also the scope name `linux-<name>` (`internal/cli/host.go:335,399`), whose pattern has no dot and 32 characters (`internal/conf/schema.go:57`); the FQDN already travels as the entry's `Hostname` (`internal/devreg/resolve.go:109-120`), which `nameMatches` accepts [V]. Decision D13.
- A comma inside `group commands add --match` (0.2.1 item 7 refuses it): the rule-line form `name|action|m1,m2` of `internal/policy/policy.go:104-134` is 0.1.16's; replacing it is a refactor of `policy`, `cli/group.go` and `devices/juniper.go` with no user-visible gain the Junos lists do not already give (they are stored as native lists). Deferred, decision D9.

## 4. Data model

### 4.1 New `tacctl.yaml` keys (exact)

```yaml
junos:
  <group>:
    deny_commands:        [<ERE>, ...]   # each item one POSIX ERE over the whole command line
    deny_configuration:   [<ERE>, ...]   # each item one ERE over the configuration path
    # allow_commands / allow_configuration: reserved, refused in 0.2.2 (D1)
wti_level:
  <group>: viewonly | user | superuser | administrator   # absent = auto (today's bands)
```

- Schema (`internal/conf/schema.go` wildcards): `{"junos.", Rule{Type: TypeJunosRegexList, Depth: 2}}` and `{"wti_level.", Rule{Type: TypeEnum, Values: [viewonly user superuser administrator]}}`. `RuleFor` already splits the trailing segments by depth (`:137-153`); group names have no dot (`names.MatchGroup`), so `junos.<group>.<attr>` resolves. The new list type: every item a string, compiles as a Go regexp (`names.ValidateRegex`, `names.go:185`), contains no `(?` (not POSIX ERE — Junos would refuse it [A, checked in WP9.12]), is non-empty; the attribute is one of the two deny keys (an allow key: "allow_* is not supported in this release"); the joined value fits the limit (§4.3). `config set-list junos.operator.deny_commands …` therefore works as an escape hatch with the same checks (`conf/write.go:102`).
- Policy API (`internal/policy/junos.go`, new): `JunosSet(c, group, attr) []string`, `WriteJunosSet(c, group, attr, items)` (empty → `Unset`, and `junos.<group>` removed when both are empty), `JunosValue(items) string` (the join), `JunosArg(attr) string` (`deny-commands` / `deny-configuration`, the wire names), `JunosLimit(attr) int` (255 − len(arg) − 1), `JunosProblem(attr, items) string` ("" or the refusal text). `internal/policy/wti.go` (new): `WTILevel(c, group) (level string, override bool)`, `WriteWTILevel`, `WTIPrivLvl(level) int` (band floors), `WTILevelOf(privlvl int) string` reusing `radius.WTISuper` so the bands cannot drift (as `devices/wti.go:589-595` does today).
- Defaults: none (`defaults.yaml` unchanged, so `config defaults` output and its goldens do not move). The README documents the keys under "Configuration tunables".

### 4.2 Validation and messages

- `group junos <g> deny-commands add '<regex>'`: shape (regex compiles, no `(?`), duplicate ("already present; no change"), then the length of the **resulting** joined value:

  ```
  [ERROR] Group 'operator': deny-commands would be 247 bytes; the limit is 241
          (TACACS+ carries 'deny-commands=<value>' in one argument of at most 255 bytes,
          and Junos refuses the login when it is longer).
          Shorten a pattern or remove one: tacctl group junos operator deny-commands list
  ```

  exit 1, nothing written.
- Render (`tacacs.Render`, `radius.Render`): the same check over the merged view (a hand edit or a `config set-list` of an older binary); a failure is a `rendered.Error` ("cannot render: group 'operator': deny-commands is 247 bytes; the limit is 241 …"), so no backend ever receives an oversized value [L: an oversized value locks the group out of every Juniper device of the scope].
- `config validate` lists the same problem through the schema type.
- WTI level: enum only.

### 4.3 The limit, exactly

`len("deny-commands=") = 14` → value ≤ 241; `len("deny-configuration=") = 19` → value ≤ 236 (backlog §3b, confirmed on the lab switch: 251-byte arguments log in, 257 and 261 fail). RADIUS: a Juniper VSA string is ≤ 253 bytes, so the TACACS+ limit is the only one enforced; the message names TACACS+. Lengths in bytes (`len(s)`), since both protocols count bytes.

### 4.4 Migration and rollback

- **Upgrade 0.2.1 → 0.2.2:** no migration. `tacctl upgrade` re-renders (`RenderAll`): `tacquito.yaml` is byte-identical for a model without Junos sets or WTI levels (the renderer adds nothing for a group without them — a golden test pins this); the RADIUS conf and dictionary change once (D15) and FreeRADIUS restarts once.
- **Rollback 0.2.2 → 0.2.1** (checkout, `tacctl upgrade`): `store.yaml` untouched; `tacquito.yaml` and the RADIUS files are re-rendered by 0.2.1 without the new values (devices lose the server-sent sets and WTI overrides, nothing else); the new keys stay in `tacctl.yaml`, where 0.2.1 ignores them for rendering, lists them as `unknown config key` in `config validate`/`config show` (`config_report.go:266`), and **refuses `backup restore` of a snapshot whose `tacctl.yaml` holds them** (`backup.go:450-455`). The release notes' "Rolling back" section says: remove the keys first (`tacctl group junos <g> clear`, `tacctl group edit <g> wti-level auto` on 0.2.2; or delete the two sections by hand) if a restore on 0.2.1 is needed. The same held for `linux.*` between 0.2.1 and 0.2.0.
- **Readback and `store import`:** the importer learns the two tacctl-owned additions (a `wti` service; `deny-commands`/`deny-configuration` set_values of `junos-exec`) and records them as notes, not drops (§6.3); `store import --replace` of a `tacquito.yaml` keeps ignoring them with a note naming `tacctl.yaml` as their home (as it does for command rules, which `lifecycle/legacy.go:362` migrates only in the legacy path).

### 5.1 `tacctl group junos` (new sub-family)

```

tacctl group junos <group> deny-configuration list|add|remove|clear [<regex>]
tacctl group junos <group> list                       both sets, with byte lengths
tacctl group junos <group> clear                      both sets (confirms)
```

Usage block (`help_text.go`, new `"group-junos"` entry, added to `cases.tsv` and the usage goldens):

```
tacctl group junos — per-group Junos rules the server sends at login

Usage:
  tacctl group junos <group> list                                    Show both sets and their sizes
  tacctl group junos <group> deny-commands list                      Show the set
  tacctl group junos <group> deny-commands add '<regex>'             Add a pattern
  tacctl group junos <group> deny-commands remove '<regex>'          Remove a pattern (exact text)
  tacctl group junos <group> deny-commands clear                     Drop the set (confirms)
  tacctl group junos <group> deny-configuration list|add|remove|clear
  tacctl group junos <group> clear                                   Drop both sets (confirms)

Each pattern is a POSIX extended regular expression Junos tests against
the whole command line (deny-commands) or the configuration path
(deny-configuration). The set is sent as one value, the patterns joined
with '|'; a set may not exceed 241 bytes (deny-commands) or 236
(deny-configuration), the TACACS+ argument limit. deny-commands does not
cover 'show configuration <path>': put paths in deny-configuration, which
also hides them from reading. The class on the device keeps only its
permission bits ('tacctl config juniper').

Sets live under junos.<group> in {{overrides}}; tacquito.yaml's
junos-exec service and the RADIUS policy are regenerated from them.
```

Output examples:

```

Junos rules for group 'operator' (class OP-CLASS)
--------------------------------------------------
  deny-commands        1 pattern    44 of 241 bytes
    ^(ssh|file|request|start shell|load)( .*)?$
  deny-configuration   1 pattern    67 of 236 bytes
    ^(groups [^ ]+ )?system (login|root-auth|tacplus|radius|accounting)
  Sent at login over TACACS+ (junos-exec) and RADIUS (Juniper VSAs) to the
  scopes that serve Juniper devices.
```

### 5.9 `tacctl host show <name>` (WP9.15)

`tacctl host show <name> [--all] [--json] [--check]`, for an enrolled host (`device show` stays the entry point for devices; it keeps finding hosts too). Sections, in order:

- **Connection:** target, port, identity (`(missing)` when the key file is gone), server, method; `this server (enrolled --local)` for the tacctl server itself.
- **Scope:** the registered scope; the scope that answers the host's address today and the prefix it matched; the drift warning `host list` gives, with its `tacctl host move <name>` fix; a staging /32 still pending for it (`scope staging`).
- **Address:** the recorded address; the previous one and when it changed.
- **Host keys:** the pinned keys with their `SHA256:` fingerprints and the command that shows them on the host.
- **Sightings:** last and first seen, by which user over which backend, the NAS-Identifier it sends.
- **Notices:** the open ones with their remedies and a count of the acknowledged ones; `--all` lists those too, marked, as `device show --all` does.
- **Accounts:** the tacctl users the next sync makes there: name, tier, UID, groups (`tac-users`, plus `tac-superuser` for superusers; all five groups on the server); disabled users counted, not listed.
- **Last sync** (new record): when, by whom, the result (ok, or failed and the reason), the client script protocol it ran, and the accounts it created, updated and removed. A host not synced since the upgrade: `not recorded (before 0.2.2)`.
- **Host facts** (new record, from that sync's session): OS name and version (`/etc/os-release`), sshd version, the PAM module in use (`pam_tacplus` or `pam_radius_auth`, with its version), `useradd`'s UID range from `login.defs`.

The two new records live in `StateDir/hosts/<name>.json` (one file per host, written atomically by `host enroll`/`host sync`, removed by `host unenroll`, renamed with the host; never read for any decision, only shown). A failed sync records its failure too.

`--check` logs in read-only, as `host target` tests a login (the invoking user's ssh; a terminal for a password), and compares the host with what tacctl would make it: the tac groups and their GIDs, each tacctl account's UID, primary group and home mode, the PAM files tacctl manages (present, and the same text the client script writes), the client script protocol installed, and the host's keys against the pins. It changes nothing. Each difference is one line with the command that fixes it (usually `tacctl host sync <name>`); exit status 1 when there is one, 0 when the host is as it should be. Without a terminal and with a password login it fails with the same message `host sync` gives.

`--json`: every field above (and the `--check` findings under `check`), for scripts.

### 5.10 The device's own name at `device add` (WP9.17, D28)

`device add <name> <address>` reads `sysName.0` (1.3.6.1.2.1.1.5.0) from the address before it registers the device, next to the host-key scan, and compares it with what was given:

```
$ tacctl device add core-sw1 192.0.2.10 --vendor juniper
  The device calls itself 'sw1.site-a.example' (SNMP sysName).
  ! That is not the name given or its --hostname: add --hostname sw1.site-a.example, or register it as sw1.site-a.example.
```

- A match (the name, the `--hostname`, or either's first label, case-insensitively, the same rules as `nameMatches`) prints the sysName line only. A mismatch is a warning, not a refusal; the add goes ahead.
- No SNMP configured, no answer within the timeout (default 2 s, one retry), or an empty sysName: one info line (`No SNMP answer from 192.0.2.10; no name hint.`) and the add goes ahead. If a scan has recorded a NAS-Identifier for the address, that is shown instead, labelled as such.
- `--no-lookup` skips it (scripts, devices without SNMP).
- `device add <address>` with no name: the sysName (lowercased, checked with the name rules of §5.8) is offered as the name, and used only after a `y` at a terminal; without a terminal, or without an answer, it is refused with the usage line. The add's other checks (generic names, duplicates, address) apply to the offered name unchanged.
- `device check <name>` gains a `SNMP name` row (the sysName, `match` or `differs`), and `--json` a `sysname` field; nothing is stored or raised as a notice in 0.2.2.
- WTI units answer sysName with their Site ID; a generic one (`WTI`, `Switch`) is shown but never offered as a name (the generic-name rule).

Configuration:

- Non-secret settings in `tacctl.yaml`: `snmp.version` (`v2c`|`v3`, no default: unset means no lookup), `snmp.port` (161), `snmp.timeout` (seconds, 1..10, default 2), `snmp.v3.auth` (`sha`|`sha256`), `snmp.v3.priv` (`aes128`).
- Secrets in `StateDir/snmp.yaml` (0600, like the store; never printed): the v2c community, or the v3 user name and the auth and priv passphrases. `tacctl config snmp community` and `tacctl config snmp v3-user <user>` prompt without echo (or read stdin with `--stdin`); `tacctl config snmp show` prints the version, port, timeout and `community: set`/`not set`; `tacctl config snmp clear` removes both; `tacctl config snmp test <address>` does one GET and prints the answer or the reason (timeout, wrong community shows as a timeout on v2c, `unknownUserName`/`wrongDigest` on v3).
- Superuser only (it is a credential for every device); `device add` reads it as the tier that may add devices already does, through tacctl, never handing the secret to the caller.

Implementation: `internal/snmp` (BER encode/decode of one GetRequest/GetResponse, v2c; v3 with engine discovery, key localisation per RFC 3414, HMAC-SHA-96 / HMAC-SHA-256-192 and AES-128-CFB per RFC 3826), from the standard library only; Go tests against RFC test vectors (key localisation) and a fake UDP agent; `device add` gets the lookup through an interface so the bats run against a stub agent (a small Go test helper bound to 127.0.0.1).

## 11. Risks and mitigations

1. **Readback coupling.** The render refuses itself if the importer drops the new content (`readback.go:93-95`). 9.2 changes both sides in one package with a golden that renders, reads back and compares; a fixture with the new content runs the full `store import` path too.
2. **A long value locks a group out of every Juniper device of a scope** [L]. Enforced at set time, at render time and in `config validate` (one function, three callers); the acceptance pins 241/242 exactly.
3. **Cisco lockout from a new per-level authz line** for a group without rules. D16's guard; the `SeedSiblings` auto-seed stays. The CHANGELOG says the AAA block must be re-pasted and what the guard comment means.
4. **WTI units configured with Service Name `shell`** (every unit set up with 0.1.x–0.2.1) silently ignore overrides. The walkthrough, the `wti-level` command's warning and the release notes say so; `tacctl log tail` shows `service=shell` from such a unit, which the verify lines point out.
5. **Patch 0001 is what serves groups without an override on `wti` units.** It is part of every tacctl build (`patches/README.md`); the acceptance checks the operator's fallback [L already].
6. **Custom Cisco templates** keep the hardcoded accounting lines; `config templates` reports the stale copy; release notes say to re-copy.
7. **Junos ERE vs Go RE2.** tacctl validates with Go's regexp (as `commands` does); a pattern Junos refuses but Go accepts is possible (`(?` is caught; back-references are refused by Go, not Junos). The acceptance runs the preset's sets; the usage says "POSIX ERE".
8. **RADIUS dictionary attributes** `Juniper-Deny-Commands`/`-Configuration` must exist in the package's `dictionary.juniper` on Debian and RHEL families [A]: the container run of 9.3 checks both (`radius/run.sh` already runs `ubuntu-noble` and a RHEL family).
9. **Rollback restores.** A 0.2.1 `backup restore` refuses a 0.2.2 snapshot with the new keys (§4.4); the release notes say how to clear them first.
10. **Scope creep on the preset's content.** The run sheet is the user's; 9.8 takes the sets as given, generic words only; `tests/tools/no-private.sh` runs on the Go table.
11. **Cisco not lab-tested** (fact 5). If no IOS-XE device is available for 9.12, the Cisco items ship as "designed from Cisco's references, not lab-tested" in the CHANGELOG (the precedent is the WTI RADIUS walkthrough), and the backlog keeps the open questions (`do <cmd>` in configuration mode; denies at level 15 in configuration mode).
