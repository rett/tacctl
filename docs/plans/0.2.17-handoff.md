# tacctl 0.2.17 handoff (2026-10-21)

Read `docs/plans/backlog.md` section 0 (the roadmap) with this note.
`0.2.17-plan.md` holds this release's scope and decisions (D244-D272,
WP17.1 to WP17.15), `0.2.16-plan.md` (D231-D243) the release before it.
The direction of the workflow half is `enroll-workflow.md`; its
decisions are the maintainer's and are not re-opened.

## State

0.2.15 is released (tag `0.2.15`, 2026-10-19). 0.2.16 is being built on
`feature/0.2.16` (its handoff has the state); 0.2.17 branches from
`develop` once 0.2.16 is merged and tagged, as every release does.

0.2.17 is planned, nothing built. Scope chosen 2026-10-21: the audit
release. One writer that no signal can silence and that reports a
`logger` failure (WP17.1); a class table over every command with a
central `cmd start` / `cmd end` / `cmd DENY` pair for every
state-changing verb, a backstop in the write choke points, and a test
that every verb is classified (WP17.2); redaction and a no-secret test
(WP17.3); the detail lines of the verbs that need them and the
`result=` and failure paths of the lines that exist (WP17.4); the actor,
command and session id in the snapshot manifest (WP17.5); `audit.strict`
(WP17.6, separable); `scope secret set` and `--hash` without the secret
on the command line (WP17.7, separable); the `docs/security/audit.md`
page and the AUDIT LOG section of the manual page (WP17.8).

Vendor detection (D260, WP17.10, `vendor-detection.md`) was added to
this release on 2026-10-23: `device add`, `device check`, `device
vendor --from-device` and `device discover --probe` read the vendor from
the device by SNMP; a lab capture of a WTI unit and a Junos and an IOS
device is wanted as fixtures before `wti` and `juniper` are offered.
Separable, like WP17.6 and WP17.7. The plan's review note under D260
lists six gaps found against the code (the `vendor` spec has no flags,
`--probe` already means a TCP probe on `device list`, `device add
--pull` checks `--vendor` before any read, one SNMP varbind per request,
the "needs pull" rule from `Record.Vendor`, where a detected vendor is
kept for the notice kind); WP17.10's implementer settles them.

The attended enroll and remediation workflow (D261-D272, WP17.11 to
WP17.15, `enroll-workflow.md`) was added the same day, in place of a
0.2.18 release: `device enroll <address>... | --discovered` runs scan,
a host-key acceptance typed per device (no `-y`, no accept-all, no
trust on first use; `--host-key` for one address is the only form
without a terminal), vendor and name from the device with a question
for what cannot be read, register, pull, plan, and for Junos the offer
of the apply review; `--differs`, `--name` and `--ip` join the
selectors of `device config pull|diff|plan|apply|list`; `apply --pull`
pulls first; the apply review is answered per device by its name, and
`--confirmed -y` stays for superusers, marked `mode=scripted` in the
lines. Every host-key acceptance is an audit line with the person, the
device, the algorithm, the fingerprint and the `sid=`. Junos is the
only vendor written to. The plan recommends that `collect` and
`onboard` accept keys the same way (WP17.15, separable). The dependency
order and the cut order are sections 5 and 6 of the plan: the audit
packages and vendor detection are the base, the workflow packages stand
on them.

The plan rests on a read-only audit of the write paths made 2026-10-21
against `54435e7` (`0.2.17-plan.md` section 7). The 0.2.16 work in
progress touches `internal/hosts`, `internal/cli/{backup,linux,user}.go`
and `internal/snapshot`; WP17.1's mechanical change of the `Logger` call
sites is made after 0.2.16 is merged, not against the half-edited files.

Excluded by decision: a local audit store of tacctl's own, a hash chain,
remote shipping, logging the read verbs (section 8 of the plan keeps
them as options with a recommendation each). No new device write path,
no credential, nothing scheduled or automatic.

Direction: every operation is started by a person; tacctl holds no device
credential and runs nothing on a schedule (`0.2.12-plan.md` section 2).
The log is syslog through `logger`; where it goes from there is the
site's concern, and no repo file describes any installation's collector.

## Decisions the maintainer may want to overrule

- D257 `audit.strict` ships, default off. The alternatives: default on
  (fail closed from the first run), or no key at all (the D248 warning
  only, no rollback step).
- D252 `--reason` is logged as typed. The alternative: redact it and
  lose the hold's justification from the log.
- D250 the ssh and console session lines stay beside the central pair
  (four lines per session). The alternative: exempt session verbs from
  the pair.
- D246 a root shell logs `user=root origin=root` with no login identity.
  The alternative, refusing a root shell for write verbs, is a policy
  change outside this release.
- WP17.7 is small but changes two verbs' argument forms; it can be left
  for a later release without affecting the rest.
- D262 asks for the whole fingerprint typed back, once, with no retry.
  The alternatives: the last eight characters (less typing, a smaller
  space to match), or one retry after a mismatch.
- D265 exits 0 when some devices were declined and every approved one
  applied. The alternative: any declined device is exit 1, as the one
  declined review is today.
- D264 registers each device as soon as its two answers are given, so a
  run that fails later leaves registered devices. The alternative,
  registering at the end, needs a login against an unregistered address
  or a second scan.
- D270 recommends that `collect` and `onboard` move to the typed
  fingerprint (WP17.15). The alternative: leave their `y/N` for this
  release.
- The D260 review recommends `discover --snmp` over `--probe`, because
  `device list --probe` is a TCP connect. The alternative: keep
  `--probe` and document the two meanings.

## Open questions

- Should `audit.strict` default to on for a new install (`tacctl
  install` writes the key) and off on upgrade? The plan says off
  everywhere.
- Is one `cmd` line per key enough for `group edit` with several keys,
  or should the pair be one and the detail lines several (the plan:
  several detail lines, one pair)?
- The `first=` rule of the console DENY line (a verb of tacctl or the
  console, else `-`): is a word list in `internal/console` acceptable,
  or should the console ask the policy for the verbs?
- The fingerprint answer of D262: the whole `SHA256:` value as the
  console prints it, or a shorter confirmation, and is one retry after
  a typo acceptable?
- Should `device enroll` register a device whose vendor cannot be read
  or given as `other` and stop there (the device exists, the chain
  ends), or skip it as D263 says (nothing registered, the `device add`
  line printed)?
- Should the apply offer at the end of `enroll` (D264 stage 4) be made
  with `--json` too, the question on standard error as the review is,
  or is ending at the plan right for a scripted call?
- Is one snapshot per registration (what `deviceWrite` takes today) fine
  for an `enroll` of many addresses, or should the run take one snapshot
  before its first write?

## Working rules

- Model routing: Opus reviews, Sonnet and Haiku implement, Fable decides
  important design questions. Subagents never commit; the coordinator
  reviews, merges, renumbers CHANGELOG items and commits.
- Commit when appropriate (a coherent unit of work that has passed its
  gates); ask before pushing, and push only the branch being worked on;
  merges into `develop` and `master`, tags and releases only when the
  user says so. No Claude attribution in commit messages.
- No private names (hosts, addresses, users, home paths, domains) and no
  description of any installation's state, deployment or log collector
  in repo files or commit messages: use roles ("the dev server", "the
  collector") and `example.*`, `192.0.2.x`.
- Never act against the production host and never connect to a
  production device: prepare the files and let the user apply them.
- Every user-visible change gets a numbered CHANGELOG item and updates
  `man/tacctl.1` and the matching `docs/` page in the same change.
- No secret, hash, password or community string in any log line, test
  golden or doc example; the no-secret test of D255 is a gate.
- Gates: build, gofmt, `go vet`, `make lint`, Go tests (`internal/cli`
  needs `setsid -w ... < /dev/null`, a scratch `GOCACHE`), bats as the
  invoking user, the diff corpus against the previous release, the
  container matrix, `groff -k -ww`; the `test` workflow on the pull
  request. Tests sandbox host paths, and a test must not read a path of
  the machine it runs on. A test that needs the process environment, the
  lock wait or a package-wide registry calls `serial(t)` first; the
  others run in parallel (`hooks_test.go`).
- A release: `docs/releasing.md`. The release branch is pushed and a pull
  request opened to `master` so the Go tests run before the tag;
  `release-reproducible` runs on the tag by `workflow_dispatch`.
