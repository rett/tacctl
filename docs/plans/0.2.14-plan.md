# tacctl 0.2.14 plan (2026-10-17)

Read `0.2.14-handoff.md` (state, working rules) first. Decisions continue
the numbering of `0.2.13-plan.md` (D166-D174). Scope review: Fable,
2026-10-17.

## 1. Scope

A short release. No state-format change, no new device write path, no new
credential. Scope decided 2026-10-17 (D175-D178), widened the same day
(D182-D202).

| WP | Item | User-visible |
|---|---|---|

| 14.2 | A break-glass hold on an enrolled Linux host (design: D179-D181) | yes |
| 14.3 | The action pins are bumped once the newer release is two weeks old | no (CI) |
| 14.4 | Backlog hygiene: the lock bullet, the hold and queue bullets, the roadmap rows | no |

## 2. Decisions

| # | Decision | Status |
|---|---|---|
| D175 | `device address` on a held device moves the hold. The new address passes the checks a new hold passes (not loopback, not a listener of the server, not an enrolled host's address, not held by another record, covered by a scope); one line names both addresses and asks to confirm (`-y` skips it); one write of the registry and the record, one render, one restart. A refused address refuses the whole change ("Nothing was changed."). A failed restart reports `NOT restarted` and exits 1, as `breakglass hold` does. Releasing first is the wrong answer in the case this is for: it re-answers the old address. | decided |
| D176 | A hold on an enrolled Linux host is built (the earlier proposal to close it was not taken). The mechanism is the device hold's: `breakglass_hold.<name>` in `tacctl.yaml`, the address carved out of every scope by the renderers. The refusal "a host is never held" goes; the checks that stay are the server's own address, loopback and the machine tacctl runs on. The design is D179-D181. | decided |
| D177 | No request-sync queue. It is dropped from the backlog as not pursued; if it comes back, it starts from a fresh design. | decided |
| D178 | Action pins are bumped in one batch at the start of a release, only for releases two weeks old, with the `test` and `release-reproducible` workflows green on the pull request as the proof. First candidate: `upload-artifact` 7.0.2 (eligible 2026-10-21), so WP14.3 runs on or after that date. | decided |
| D179 | What a held host loses and keeps. A hold makes the server answer no login and no sudo check for the host's address; the host's local administrator and its console still work, which is the point. `host sync` and `host show --check` refuse for a held host and name the hold (since, by, reason) and the release command, as `device config pull` does for a held device; nothing is attempted over ssh. | decided |
| D180 | The shape of the record and the listings: the same record as a device's (since, by, reason, address); `breakglass list|status|hold|release` name hosts and devices alike; `host list|show` and `status` mark a held host; a host enrolled again under a new name is a separate host, and the record under the old name is an orphan. A name that is both an enrolled host and a registered device is refused as ambiguous, naming both, and nothing is changed. | decided |
| D181 | The tier rule: holds and releases are superuser-only, as for devices; an engineer sees the holds of the hosts of their own scopes in `breakglass list` and `host list|show`. | decided |
| D182 | `tacctl host rename <old> <new>` is superuser-only (host deployment is the superuser's); engineers keep `list|show`; no new `tier.Rules` row. It is local only: the remote host records no registry name, so nothing is sent over ssh. | decided |
| D183 | One name rule for hosts and devices. A new host name passes the registry's shape (`reHostName`) and the device reserved words (`devreg.ValidateName`: a host can no longer be named `all`), flat, with no `--allow-generic` on a rename. It is refused when any host or device is equal to it ignoring case (naming the holder); `host enroll` gets the same check (today `Web1` and `web1` can both be enrolled and share one pin record). `old == new` says "already has that name"; a rename that changes only the spelling is legal. | decided |
| D184 | Leftovers under the new name (a pin, a record or a staging entry from an earlier enrolment with no registry line) are listed and replaced after a confirmation (`-y` skips it); declining changes nothing. A leftover break-glass hold under the new name is always refused: only `breakglass release` removes a hold. | decided |
| D185 | The registry functions (`Remember`, `Replace`, `Forget`) take the existing `.hosts.lock` flock internally, so enroll, target, provisioner, scope rename, rename and forget serialise with no caller change and no format change. The rename also takes `LockHost(old)` without waiting: a running rotation refuses it. | decided |
| D186 | The rename sequence. After every refusal (nothing changed): a snapshot; the registry line renamed in place; one `devreg.Mutate` renames the pin, address history and acknowledgement (known_hosts is regenerated), and if it fails the registry line is renamed back and the command says nothing was changed. Then, each a warning naming the leftover and the fix: the record (`Records.Rename`), the staging entries, the hold (`holdCarry`; a held host is not refused, a rename does no ssh), the seen-cache key; then the log line `host rename old= new= by=`. | decided |
| D187 | Existing duplicates are found by `config validate` and `host list` (two names equal ignoring case; a host named like a device; two hosts with one recorded address; a pin, record, staging entry or hold with no registry line) and repaired by a new local-only `host forget <name>`: it drops the registry line, the pin, the record and the staging entries, runs nothing over ssh and is refused for a held host. `host unenroll --force` is not the repair: it runs the removal script on the machine the surviving registration shares. No `host merge`. | decided |
| D188 | A snapshot holds `linux-hosts`, `hosts/` (the records), `staging` and `linux-uids`. Not the provisioner lock files or the caches (`devices-seen.json`, `known_hosts`, the device-config files). Modes as the rest (files 0600, directories 0700). | decided |
| D189 | `linux-hosts` is written to every 0.2.14 snapshot, empty when there is no registry, so its presence says that the snapshot knows the hosts. The manifest does not change. This is not a state-format change: the live files keep their formats, and 0.2.13 ignores the new entries. | decided |
| D190 | The snapshot dedupe compares these entries too; otherwise a registry-only change followed by a store change would be deduped against a snapshot holding the old registry. | decided |
| D191 | `host enroll` (just before the registry write, after the script succeeded), `host move`, `host unenroll`, `host rename` and `host forget` take a snapshot first; `host sync` does not (its record is informational). | decided |
| D192 | Restore. A snapshot without `linux-hosts` (0.2.13 or older) leaves the registry, records, staging and ledger alone. One with it puts `linux-hosts` back whole, makes `hosts/` match (a record it lacks goes), puts `staging` back or removes it, and puts `linux-uids` back as it was (the maintainer's choice; the pre-restore snapshot makes it undoable). A restore of the ledger can forget a number a host already holds, so the note before the confirmation names every user whose number the restore drops or changes. | decided |
| D193 | Order and lock: inside the restore's apply lock, after the render and the `devices.yaml`, known_hosts, console, snmp and blocks restores, then `linux-hosts`, `hosts/`, `staging`, `linux-uids`. The pre-restore snapshot holds the live host files. | decided |
| D194 | No reconciliation. Pins, holds and the registry of one 0.2.14 snapshot come from one moment and restore consistent; an older snapshot can leave a registry line without a pin (the next `host sync` pins as at enrolment) or a hold without a host (an orphan, D180). A note before the prompt and after says which hosts come back and which go, and that the hosts themselves are unchanged. | decided |
| D195 | A restore touches no host. What drifts is named in the note: a line that comes back for a host `unenroll` cleaned (`host sync`, `host show --check`, `host unenroll` again); a line that goes for a host enrolled since (`host enroll` again, or `host unenroll --force` after that). | decided |
| D196 | `backup diff` adds `linux-hosts`, `staging`, `linux-uids` and each record of the union, each only where one side has it; `backup list` is unchanged. `restore --legacy`, `store rollback` and `rollback <release>` are untouched. | decided |
| D197 | The scope offer. After the host checks pass and before any write, when the host's scope is `linux-<old>`, no other host uses it, the store has it, `linux-<new>` does not exist and the scope-rename checks pass, the rename asks whether to rename that scope too. Otherwise one line says why the scope stays. If left, the end prints `tacctl scope rename linux-<old> linux-<new>`. | decided |
| D198 | The question: "Scope 'linux-<old>' is this host's own (no other host uses it). Rename it to 'linux-<new>' too? [y/N]". Re-enrolling the renamed host without `--scope` would default to `linux-<new>` and move it, so keeping the convention is the useful answer. | decided |
| D199 | `--yes` answers both questions yes; no new flag. | decided |
| D200 | Not one transaction. Both questions come first; the host rename runs whole; then the scope rename runs (the body of `scope rename` factored out and shared, with its own snapshot, so there are two undo points). A scope first would leave the old host in `linux-<new>` if the host rename failed. | decided |
| D201 | If the scope step fails the host stays renamed in `linux-<old>`, a valid state: "Host renamed. Scope 'linux-<old>' was NOT renamed: <reason>; the host keeps it. Retry: tacctl scope rename linux-<old> linux-<new>." Exit 1. | decided |
| D202 | `host list` gets `--json` and a recorded-address column; `host show` says "no record under this name" in place of "not recorded (before 0.2.2)" for a host with no record. | decided |

## 3. Candidates weighed

**A hold that follows `device address` (WP14.1).** The refusal is a few
lines in `internal/cli/device.go` (the address change under a hold) and the
rename already carries a record (`holdCarry`, `internal/cli/breakglass.go`).
The difference from a rename is that the address is what the renderers carve
out of every scope, so the move needs the render and the restart of each
backend and the address checks of `holdCheck` on the new address. Touches
`device.go`, `breakglass.go` (a move beside the carry), `docs/cli/device.md`,
`docs/cli/breakglass.md`, the man page, about six tests. One session.

**A hold for an enrolled Linux host (WP14.2).** About two sessions. The
mechanism itself is unchanged (a hold is `breakglass_hold.<name>` in
`tacctl.yaml`; the address resolves through the registry), but the refusal
for hosts (`serverOwnAddress`, `holdCheck`), the orphan and JSON helpers
(`holdOrphan`, `holdJSONOf`), the way-in text by vendor, the `host`
listings and `status` all assume a device. A held host loses `host sync`
and `host show --check` and, by D179, sudo through TACACS+ for everyone but
the local administrator, so the lock-out reasoning of the device hold
applies to the host's own text.

**A request-sync queue.** Dropped (D177).

**Left as documented.** The restart that follows a render sits inside the
apply lock; a failed restart leaves the new files and the old daemon, and
the reports say so. Undoing the render would restart a daemon on the old
files and can fail again, which leaves less than now.

## 4. Gates

Each WP: build, gofmt, `go vet`, `make lint`, the Man tests and the
`internal/cli` run green before the next starts. WP14.1: a test for each
refusal of the new address; a test that a failed restart leaves the registry
and the record on the new address with exit 1 and `NOT restarted`; a bats
case that holds a device, changes its address and reads the rendered files;
the diff corpus shows only the address line and the hold comment moved; the
container matrix (`fresh`) observes the render. WP14.2: a held host is
refused by `host sync` and `host show --check` with the reason, listed in
`host list|show` and `status`, and a record whose host is no longer
enrolled at its address is an orphan; the container matrix `hosts` runner
observes the carve-out on a real client. WP14.3: both
workflows green on the pull request and the release notes name the new pins.
At release: bats, the diff corpus against 0.2.13, the container matrix, and
the `test` workflow on the release pull request.
