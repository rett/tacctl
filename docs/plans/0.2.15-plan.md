# tacctl 0.2.15 plan (2026-10-18)

Read `0.2.15-handoff.md` (state, working rules) first. Decisions continue
the numbering of `0.2.14-plan.md` (D175-D206). Scope chosen by the
maintainer on 2026-10-18; design review: Fable, the same day. State:
planned, nothing built.

## 1. Scope

A follow-up release to the host work of 0.2.14. No state-format change, no
new device write path, no new credential, nothing scheduled or automatic
(`0.2.12-plan.md` section 2). Every item is either a hardening of a 0.2.14
verb, a machine-readable or batch form of an existing read, or a fix.

WP15.0 is the release-start step of D178 (the action pins), not built now.
The others are built in the order of section 4, each its own gated unit.

- WP15.0  The action pins are bumped at release start (D178, D225). CI only.
- WP15.1  Small fixes: the client script's `check_ids` and `rename_account`
          wording, the `host sync` help line and docs, the `host list`
          footer counts the Names findings about hosts (D222).
- WP15.2  `device config apply --hold`: an answer typed before the first
          question is taken; the bats flake of `device_apply.bats` #13 is
          explained and closed (D223, D224).
- WP15.3  `backup restore` refuses while a host's provisioner lock is held
          (D207, D208).
- WP15.4  The snapshot dedupe ignores the volatile parts of the host
          records; the pre-restore snapshot compares everything (D209-D211).
- WP15.5  `backup restore --keep-uids` (D212, D213).
- WP15.6  `host sync <name>...`: several hosts in one run (D214, D215).
- WP15.7  `host check <name>... | --all [--json]`: read-only (D216-D218).
- WP15.8  `config validate --json` (D219-D221).
- WP15.9  `config validate --fix-names` (D226-D230).
- WP15.10 Backlog, roadmap and handoff hygiene; the release gates.

## 2. Decisions

**D207 — `backup restore` refuses while a host is locked.** Today the
restore takes the apply lock and the registry lock (`Registry.Lock`,
`backup.go`), but not the per-host provisioner lock
(`hosts.LockHost`, `<state>/locks/host-provisioner-<name>.lock`, taken by
`host provisioner rotate`, `host rename` and `host forget`). A rotation
running through a restore ends with `Registry.Replace` of its new login,
which waits 30 s for the registry lock and either fails
(`ErrRegistryBusy`) or writes over the line the restore just put back; the
release notes list this as a known limit. The restore now tries
`LockHost` without waiting for every name of the union of the live
registry and the snapshot's `linux-hosts`, after the registry lock and
before the pre-restore snapshot, and holds every lock until the host files
are back (the same `defer` scope as the registry lock). One busy lock
refuses the whole restore, nothing changed:

    Snapshot <id> was not restored: '<name>' is locked by another tacctl
    command (a rotation, rename or forget of it is running). Nothing was
    changed. Run this again when it has finished.

Only a snapshot that knows the hosts (`snapshot.KnowsHosts`) takes the
locks: a 0.2.13 snapshot touches no host file. Lock order is safe: the
restore holds the registry lock and tries the host locks without waiting,
so a rotation that holds its host lock and waits for the registry lock is
never waited for; the restore lets go and refuses. A name the snapshot's
registry holds but no command would lock (the host is gone) is locked all
the same: it costs a lock file and keeps a `host enroll` under that name
out while the line comes back. Lock files are 0600 under a 0700
directory, as `LockHost` makes them.

**D208 — One wording for a busy host lock.** The three refusals that read
`Another rotation of '<name>' is running; nothing was changed.` (`host
provisioner rotate`, `host rename`, `host forget`) become the D207 text
without the snapshot clause: `'<name>' is locked by another tacctl
command (a rotation, rename, forget or restore of it is running); nothing
was changed. Run this again when it has finished.` A restore is now a
holder too, and a rename blocked by a restore must not be told a rotation
runs. The tests that assert the old text change with it.

**D209 — What is volatile in a host record.** The records under `hosts/`
(`hosts.Record`, `record.go`) hold three entries. `last_sync` (at, by,
command, ok, reason, protocol, created/updated/removed) and `facts` (at,
OS, sshd, PAM modules, login.defs range) are written by every `host
enroll` and `host sync` (`recordRun`, `host_show.go`), carry a timestamp
each time, and nothing reads them to decide anything: they are what `host
show` prints. `provisioner` (at, by, old, new, auth, old_removed) is read
back by `rotate --remove-old` to find the login a rotation replaced, so a
restore that changes it changes what the next rotation does. The pins,
the recorded address and its history are not under `hosts/` at all
(`devices.yaml`), and the scope, method, target and port are the registry
line (`linux-hosts`). So: volatile = `last_sync` and `facts`, whole;
meaningful = `provisioner`, and everything outside `hosts/`.

**D210 — The dedupe compares the records on their meaningful part.**
`Snapshotter.current` (`snapshot.go`) decides whether the live state
equals the newest snapshot. `sameRecordsDir` compared the records byte for
byte, so a `host sync` (which takes no snapshot) made the next
snapshot-taking command take a new snapshot even when nothing it would
put back had changed: a re-enroll of a registered host, a `host move
--all` that moves nothing, a `scope block set` of the same text, each
after a sync, consumed one of the 30 kept. Now a record counts as equal
when both sides have the same `provisioner` entry (both absent, or equal
field by field); a record present on one side only counts as equal when
its only content is volatile (no `provisioner`); the rest of the
comparison (registry, `staging`, `linux-uids`, `store.yaml`, `tacctl.yaml`,
`devices.yaml`, console, SNMP, blocks) stays byte-exact. The snapshot
that is taken still copies the records whole: nothing in a snapshot
changes, only when one is skipped. `backup diff` is unchanged: it prints
each record where the sides differ, volatile or not, so a diff can show a
`last_sync` the dedupe ignored; `backup restore` is unchanged: it puts
the snapshot's records back whole.

**D211 — The pre-restore snapshot compares everything.** The snapshot
`backup restore` takes first is what undoes the restore. With D210 it
could be skipped while the live records differ from the newest snapshot's
`last_sync`, and the undo would then put back older sync information. The
Snapshotter gets an `Exact bool` (set by `restoreSnapshot` for its
`snapshotFirstID` call, cleared after): with it, `current` compares the
records byte for byte as before. Everywhere else the D210 rule applies.
`host enroll`'s own pre-registry snapshot is not exact: the record it
would preserve is the one the enrolment rewrites.

**D212 — `backup restore <id> --keep-uids`.** The ledger `linux-uids` is
left as it is; the registry, records and staging come back as D192 says.
Before the question the ledger line of the hosts note is replaced by
`The UID ledger (linux-uids) is kept as it is (--keep-uids): the restored
users keep the numbers they have now; a restored user with no line gets
one at the next sync.` and no drop/change note is computed. After the
restore the same line is the warning that replaces the ledger note. The
pre-restore snapshot is taken as always and holds the live ledger
(unchanged by this restore). A snapshot that does not know the hosts
(0.2.13 or older) never touches the ledger: `--keep-uids` is accepted
and one line says `This snapshot does not know the hosts: the ledger
stays either way.` `--keep-uids` with `--legacy`, or without a store, is
a usage error (`--keep-uids is for a snapshot restore: an old-style
restore never touches linux-uids.`). The flag joins `backupSpecs` and
the `config restore` alias. The log and `backup diff` do not change.

**D213 — When to use it, in the docs.** The ledger note of D192 exists
because a host may already hold a number the snapshot's ledger forgets.
`--keep-uids` is the answer when the snapshot is wanted for its users,
groups, scopes or devices and the hosts have synced since: the live
ledger is the one the hosts agree with. The docs say that, and that a
user the snapshot brings back who has no live line is numbered afresh at
the next sync (`renumberUIDs`, as for any new user), while a live line of
a user the snapshot lacks stays, as after `user remove`.

**D214 — `host sync <name> [<name>...]`.** Several names run in one
command with the semantics of `--all` per host (`syncOne` in registry
order of the names as typed, `renumberUIDs` once, `exit 1` when any
failed, the rest still run). Every name is checked before the first host
is touched: an unknown name refuses the run (`No enrolled host named
'<name>'. See 'tacctl host list'.`), a name given twice counts once, and
`--all` with a name is a usage error (`Give names or --all, not both.`).
`hostSpecs["sync"]` becomes `MaxArgs: -1`; completion offers host names
at every position (the last kind of `Spec.Args` repeats past the end,
`completion.go` line 290, a one-line rule the other `MaxArgs: -1` verbs
with one kind can share). The usage line becomes `tacctl host sync
<name>... | --all [--allow-uid-mismatch] [--remove-home]`.

**D215 — A held host among the names.** Typed names are deliberate: a
held host among them refuses the whole run before anything is attempted,
with `hostHeldErr` (the hold, since, by, reason and `tacctl breakglass
release <name>`), as `host sync <name>` does today; `--all` keeps skipping
a held host with its warning (`hostSkipHeld`). The alternative, skipping
a typed held host with a warning and going on, hides a refusal inside a
batch that exits 0 when the rest succeed; the person can drop the name.
(The maintainer may prefer the skip: section 3.)

**D216 — `host check <name>... | --all [--json]`.** A read-only check of
several hosts: for each, what `host show <name> --check` does
(`hostCheck`, `host_check.go`: a login as the invoker, the groups, GIDs,
accounts, sudo groups, PAM files, script protocol and ssh keys against
the pins), with no record written (`host show --check` writes none
either) and nothing changed on any host or here. Superuser only, with the
refusal of `host show --check` for an engineer: `'host check' logs in to
each host over ssh, which is the superuser's; 'tacctl host list' and
'tacctl host show <name>' show what tacctl recorded.` A held host is
skipped with the `hostSkipHeld` warning, named or not: a check is
read-only, there is nothing to refuse the person. The server's own host
(`--local`) is checked as `host show --local-name --check` checks it (no
ssh). Names and `--all` follow D214 (every name checked first, `--all`
with a name is a usage error, no hosts enrolled is `No hosts enrolled.`).

**D217 — The output and exit status of `host check`.** Per host, in
order, after the `Checking <name> at <target> (read-only)...` line
`hostCheck` prints on stderr:

    web1: as tacctl would make it.
    web2: 2 difference(s):
      - alice has no account. Fix: tacctl host sync web2
      - /etc/pam.d/sshd is not the text tacctl wrote there. Fix: ...
      <the notes of --check, indented, when any>
    web3: skipped: break-glass is held on it since ... (tacctl breakglass
    release web3)
    web4: could not be checked: the read-only run as root on <target>
    failed (see above); nothing was compared.
  4 host(s): 1 as tacctl would make it, 1 with differences, 1 not checked,
  1 skipped (held).

Exit 1 when any host has a difference or could not be checked; 0
otherwise (a skipped held host is not a failure, as for `host sync
--all`). An interrupt ends the run after the host in progress (exit 130).
The engineer's sudoers rule does not change (superuser only).

**D218 — `host check --json`.** A JSON array on standard output, `[]`
with no host, and everything else on standard error (`hostCheck` already
has the `toStderr` mode for this). One object per host, in order:
`name`, `target`, `state` (`ok`, `differences`, `failed`, `held`),
`differences` (`text`, `fix`; empty unless `differences`), `notes`
(strings), `error` (the reason when `failed`, else `""`), `breakglass`
(the hold as in `host show --json`, only when `held`). The exit status is
D217's. The same shape serves `host show --check --json` today under
`check`, so a reader of one reads the other.

**D219 — `config validate --json`: the report is collected, then
printed.** `configValidate` (`config_report.go`) prints each finding as it
goes and counts the errors. It is refactored into a collector that
appends `validateFinding{Section, Level, Text, Fix, Backend, Hosts}` in
the order the text report prints them, and two printers: the text one
reproduces today's lines byte for byte (the diff corpus `config.txt`
against 0.2.14 is the proof: zero differences but for the items of this
release), the JSON one prints the object of D220. The lines that are not
findings (`Store: valid`, `Rendered config: up to date`, the three
counts, `Configuration is valid.`) stay text-only. What the report writes
around itself (the model's complaint through `reportModelError`, the
store's `tacctl store:` lines, the drift blocks of `set.DriftLines`) goes
to standard error with `--json`, so standard output is the JSON alone;
the drift becomes one finding per drifted artifact from `set.CheckDrift`
(section `drift`, with the artifact path in `text`).

**D220 — The schema.** One object:

    {
      "valid": false,
      "errors": 1, "warnings": 3,
      "mode": "store",                      // or "legacy"
      "counts": {"users": 12, "groups": 3, "scopes": 4},   // null when
                                                           // unreadable
      "backends": ["tacacs", "radius"],     // the enabled ones, [] when
                                            // they cannot be read
      "findings": [
        {"section": "overrides", "level": "error",
         "text": "scope.default: ... ", "fix": ""},
        {"section": "linux_hosts", "level": "warning",
         "text": "the hosts 'Web1', 'web1' are one name ignoring case ...",
         "fix": "tacctl host forget <name> drops ...",
         "hosts": ["Web1", "web1"]},
        {"section": "rendered", "level": "error", "backend": "radius",
         "text": "clients.conf is out of date with the store", "fix":
         "tacctl config render"}
      ]
    }

`section` is a stable token, one per label of the text report: `store`,
`yaml` (legacy mode), `overrides` (tacctl.yaml), `command_rules`,
`structure` (the `Error:` lines of the model), `scope_default`,
`linux_hosts`, `names`, `breakglass`, `breakglass_hold`, `config_blocks`,
`operator_policy`, `group_settings`, `orphan_settings`, `orphan_files`,
`leftovers`, `backends` (the enabled list cannot be read), `rendered`,
`drift`, `vendor_attrs`. `level` is `error` or `warning` exactly as the
text report colours it (red is an error and counts; yellow is a warning).
`fix` is the command when the finding carries one apart from its text
(`hostFinding.Fix`, `caseFindings`, the holds' release line, the render
line); else `""`, and the text is the line as printed. `backend` and
`hosts` are present only where they apply. A restricted caller gets the
same view as in text (no `names` or `linux_hosts` findings). The schema
is documented in `docs/cli/config.md` and the man page as the other
`--json` shapes are, field by field.

**D221 — Exit status and tier of `--json`.** Exit 1 when `errors > 0`,
else 0, the JSON printed either way: that is the text report's rule and
the rule of `host show --check --json` (JSON, then exit 1 on
differences). Warnings alone exit 0. `config validate` is the operator's
(`tier.Rules`: `Sudoers: "config validate"`, an exact match), so the row
gains `config validate --json` as `host list --json` gained its entry in
0.2.14, `tacctl upgrade` rewrites the drop-in, and the generated TIERS
block of the man page follows (`make man`). `--json` with `--fix-names`
is a usage error.

Built differently (WP15.8): with `--json` the store's lines, the drift
blocks and the `backends` complaint are findings only and are not repeated
on standard error (the model's complaint is the one line that goes there).
`level` is `error` only for what counts toward the exit status, so `valid`
and `errors` agree: a break-glass hold with no registered device and the
hold defects other than a missing address are warnings in the object though
the text report colours them red. The object counts each drifted file as an
error, where the text report counts a drift block as one.

**D222 — Small fixes.** (a) `check_ids` in `config/linux/client-install.sh`
prints `Nothing was changed. Options:` after `rename_accounts` has run,
which can have renamed accounts in this very run; the line becomes `No
account was created or removed (an account renamed above keeps its new
name). Options:`. (b) `rename_account` prints `UID <uid>` from its
argument, the assigned number, while on a host still on an earlier range
the account has the previous range's number until `renumber_previous`
runs later in the same run; it prints the account's number as `getent`
shows it after `usermod -l`, and when that differs from the assigned one
adds `, renumbered to <uid> later in this run`. The script protocol stays
6 (no header field changes; a message changes). (c) The `sync` line of
`hostVerbs` (`host.go`), the host usage in `help_text.go`, `docs/cli/
host.md` and the `host sync` paragraph of the man page say `Push account
adds, renames, deletions, expiries and tier changes` and that a renamed
user's account is renamed with its UID and home (CHANGELOG 0.2.14 item
10 describes it; the verb's own line did not). (d) `hostFindingsFooter`
counts `hostFindings()` only; the `Names:` findings about hosts
(`caseFindings`, those with `Hosts` set) are hosts' findings too and are
counted in the footer and listed under the host's `findings` in `host
list --json`. The footer text does not change. The tests of 0.2.14 item 7
that count findings are updated.

**D223 — The flake of `device_apply.bats` #13, diagnosed.** The test
types `example-sw1\nOK\n` into a pty with `printf | script -qec`, so both
lines sit in the pty before tacctl reads any. The review's answer is read
with `Prompter.Ask` and the hold's answer with `Prompter.ReadLine` on the
same `bufio.Reader`, which reads both lines from the pty in one read.
`holdFunc` (`device_apply.go`) starts the reader goroutine at the first
question (`holdOnce`) and then drains the channel with a non-blocking
`select` to drop a line typed before the question. The goroutine's first
`ReadLine` returns `OK` from the buffer with no system call, so whether
its `lines <- line` is delivered before the drain's `select` runs depends
on scheduling: usually the drain runs first and the answer is taken; under
load the goroutine wins and the drain discards the answer, the timer
fires (`the hold: the window ran short` after the window, or `no answer`
when the input ends) and the change is rolled back, so the second half of
the test exits 1. The first half (`no`) is exposed the same way, where a
lost answer prints a different reason than the one the test asserts.
That explains a failure in a full run and a pass alone.

**D224 — The fix: lines are stamped with the question they answer.** The
reader goroutine hands over `(line, asked)` where `asked` is the number
of questions opened at the moment the line was read (`r.holdAsked`,
incremented by `holdFunc` before it starts or wakes the reader). A line
stamped with an earlier question is dropped (an answer that came after a
device's own timeout is not the next device's); a line stamped with the
current question is the answer. The first question therefore never drops
anything: nothing came before it, and an answer typed ahead for the first
device is taken, deterministically. The drain loop goes. A unit test in
`internal/cli` (parallel; beside the test that sets `applyHoldWait` in
`device_apply_run_test.go`) feeds `OK\n` before the first question and
expects it taken, and feeds a late answer to question one followed by
question two and expects it dropped. The bats test is unchanged: it was
right. The documented behaviour (`--hold`: a line typed before the
question is dropped) is reworded in `docs/cli/device.md` and the man page
to say "before the question for that device, after the device before it
was answered or timed out".

**D225 — The action pins (WP15.0).** D178 stands: the pins are bumped in
one batch at release start, only for releases two weeks old, with the
`test` and `release-reproducible` workflows green on the release pull
request as the proof, and the release notes name the new pins. The
candidate is `actions/upload-artifact` 7.0.2 (eligible 2026-10-21;
`release-reproducible.yml` line 66). `actions/checkout` 7.0.1 and
`actions/setup-go` 7.0.0 are checked for a release that is two weeks old
on the day the step runs. Not built now.

**D226 — `config validate --fix-names`: superuser only, after the
report.** The flag prints the usual report first, then offers each
`Names:` finding whose fix is determinate (the lower-case spelling, not
`<new>`) one at a time. It renames, so it is the superuser's: an operator
(whose sudoers entry is the exact `config validate` and `config validate
--json`) and an engineer are refused with `'config validate --fix-names'
renames devices, hosts, users and scopes, which is the superuser's.`
(`tierGate().Caller`). It needs a store (`requireStore`). It is refused
with `--json` (D221).

**D227 — Each rename is the existing verb.** The question is `Rename
<kind> '<Old>' to '<old>'? [y/N]:` (`Prompter.Confirm`, so a piped `y`
works as for every other question; no terminal is required); `-y`/`--yes`
answers every question yes. On yes the verb body runs in-process with the
names as arguments: `deviceRename([old, new])`, `hostRename([old, new,
"-y"?])`, `userRename([old, new])`, `scopeRenameCheck` then
`scopeRenameRun`. Each prints what it prints when typed, takes its own
snapshot (one undo point per rename, as D200 chose for `host rename`),
carries what it carries (the device's configuration records, SNMP
override, blocks and hold; the host's pins, record, staging, hold and the
offer of its own `linux-<name>` scope; the user's UID line and the
"renamed at the next sync" note; the scope's keys, hosts and staging).
`-y` is passed to `host rename` only when the person gave `-y`: without
it, `host rename` asks its own questions (a leftover under the new name,
the scope offer) after ours, as when typed. The findings are read again
after each rename, so a scope a host rename carried is not offered twice,
and a rename that another rename made possible is offered.

**D228 — Order.** Devices, then hosts, then users, then scopes, the order
`caseFindings` already returns (sorted within a kind). Hosts before
scopes because a host rename may carry its scope; users before scopes for
no dependency reason, only so the per-host account rename note of `user
rename` comes before the scope lines. Within a kind, alphabetical.

**D229 — Conflicts and refusals.** A name whose lower-case spelling is
taken by another name of its namespace (the `<new>` fixes: two hosts
`Web1` and `web1`, a user `Alice` beside `alice`, a device and a host
equal ignoring case) is not offered; one line: `'<Old>' is not offered:
'<old>' is taken; pick a name: tacctl <kind> rename <Old> <new>` (for two
hosts equal ignoring case the line adds `, or tacctl host forget <name>
drops the stray registration`). A rename the verb refuses (a generic
device name, a device registered under the new name since the report, a
name taken meanwhile) prints the verb's refusal, counts as failed, and
the loop goes on with the next: one failure does not stop the rest, as
each rename stands alone with its own snapshot. A declined question
prints nothing beyond the verb's absence and counts as declined.

**D230 — The summary and the exit status.** The run ends with `Names:
renamed N, declined N, not offered N, failed N.` and, when a user was
renamed and hosts are enrolled, one `tacctl host sync --all` line (the
verb prints its own per user; the closing line is for the batch). Exit 1
when the report had errors (as `config validate` exits), when a rename
failed, or when a name was not offered: with `-y` a script learns that
names remain. A decline is the person's choice and does not fail the run
(as the other confirmations). The log lines are the verbs' own.

## 3. Candidates weighed

**A held host typed by name in `host sync a b c` (D215).** Refuse the run
(chosen) or skip the host with the `--all` warning. Refusing keeps the
one-name form's contract and makes the batch's exit status mean what it
says; skipping is friendlier for a long list typed from a script. The
maintainer decides; the code is one branch either way.

**`host check` with names, or `--all` only (D216).** The loop takes a
name list for `--all` anyway, so names cost the D214 checks and nothing
else, and give `host check web1 web2` a home beside `host sync web1
web2`. Chosen: names and `--all`.

**A per-section status in `config validate --json` (D220).** The text
report prints `valid` or `up to date` for a section with no finding; the
JSON leaves those out. A `sections` list (`{"name": "store", "status":
"ok"}`) would let a reader tell "checked and fine" from "not applicable"
(no blocks, no hosts, legacy mode). Not chosen: the findings plus `mode`
and `backends` say the same with less to keep in step; it can be added
later without breaking a reader.

**Ignoring the records entirely in the dedupe (D209, D210).** Simpler
than comparing the `provisioner` entry, but a restore that rolled back a
rotation's record would then be deduped against a snapshot that lacks
the rollback, and `rotate --remove-old` reads that record. Not chosen.

**A terminal requirement for `--fix-names` (D227).** `device config apply
--hold` demands a terminal because it waits for a person in another
terminal; a rename question is an ordinary confirmation, and the host
verbs take a piped `y`. Not chosen.

**Dropping `--fix-names` from the release.** It is the largest item and
the only one that writes through four verbs from one command. It is kept
because it reuses the verbs whole (no new write path) and the 0.2.14
`Names:` warnings otherwise ask the person to type every rename; a
server with many legacy names is the case it is for. If the release runs
long, WP15.9 is the one to defer: nothing else depends on it.

**Left as documented.** `host sync` takes no snapshot (D191), so the
record churn of D210 is the only trace a sync leaves in the snapshot
comparison. The ledger keeps having no lock of its own.

and the `internal/cli` run green before the next starts (`setsid -w ...

`serial(t)` first, every other test `parallel(t)` (`hooks_test.go`).
Every user-visible WP: a numbered CHANGELOG item under `## 0.2.15`,
`man/tacctl.1` (the prose by hand; `make man` for the generated blocks:
the flags of a `Spec` and the TIERS table are checked by

## 6. Risks

- The `configValidate` refactor (WP15.8) touches a 360-line function
  whose text output is pinned by bats, the corpus and the Man tests; the
  collector must reproduce every line in order, colour and spacing. The
  corpus run against 0.2.14 is the gate; the refactor is done before the
  JSON printer, as its own commit, so the corpus can be run on it alone.
- D210 changes when a snapshot is skipped. The risk is a skipped snapshot
  that someone wanted; D211 covers the restore's own, and every other
  taker changes something outside `hosts/` or changes nothing worth a
  snapshot. The tests enumerate the cases.
- D207 adds up to N lock files for N hosts at restore time under
  `<state>/locks`; `LockHost` creates the directory. A restore of a
  snapshot with hundreds of hosts opens hundreds of descriptors for its
  duration; well under any limit, noted here.
- WP15.9 runs four verbs from one command; a verb that prompts (`host
  rename`) does so after our question. The tests type the sequence; the
  docs show one full exchange so the person knows what to expect.
- D222 (b) changes a line the script tests pin; the protocol does not
  change, and a host synced with the old script prints the old line until
  the next sync writes the new one (the script is sent each sync).
