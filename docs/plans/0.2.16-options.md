# Two ideas not scheduled: a design round (2026-10-21)

Neither item below is in the scope of 0.2.16 or any release. Each is
written as the questions a plan would have to answer, with the pros and
cons as read from the code today and a recommendation; the decision is the
maintainer's. The constraints that hold for both: every operation is
started by a person, tacctl holds no device credential and runs nothing on
a schedule; nothing here changes a state format.

## 1. A per-device source address or interface for AAA and SNMP

Backlog section 0b, "Source address for AAA and SNMP" (parked 2026-10-10;
its open questions were not answered).

### What exists today

- Junos: the walkthrough prints a commented example under the server
  statement (`#   set system tacplus-server <server> source-address
  10.0.0.1`, `internal/devices/juniper.go`; the same for `radius-server`),
  nothing is rendered, and the planner keeps a `source-address` leaf the
  device has under tacctl's server (`plan/owned.go`, the `Kept` note of the
  server row). The shape masks it as "the device's own management
  address" (`plan/shape.go`), so a fleet whose devices differ only there
  already confirms as one shape. `snmp trap-options source-address` is an
  unmanaged row the plan leaves alone (`plan/simulate.go`); `system ntp
  source-address` is a `system` block statement (0.2.7).
- Cisco: a per-scope setting exists, `cisco.source_interface.<scope>`
  (`tacctl config cisco source-interface <scope> [<interface>|none]`, the
  D119 of the paste release): it renders `ip tacacs|radius
  source-interface <ifc>` and is an owned single-valued row
  (`ios.aaa.source-interface`); with no value set the device's own line is
  dropped from the comparison (`devconf/compare.go`) and the plan reports
  a policy gap. `snmp-server trap-source` is accepted in an IOS `snmp`
  block as a device-specific value (backlog 0b, decision (4) of the
  blocks round).
- WTI: no source setting (one management interface).
- The registry (`devreg.Device`) has no field for it, and the loader
  refuses an unknown key (`device '<name>': unknown key`), so an earlier
  binary refuses a `devices.yaml` that carries a new key.
- The server sees the device's source address: scope matching, the
  per-prefix secret and the "address changed" notice follow it. A source
  outside the scope's prefixes makes the device unknown to the server.

### The questions

**Q1. What is the value, per vendor?** Junos takes an address (`tacplus-
server`/`radius-server ... source-address <addr>`; `snmp trap-options
source-address <addr>`); Cisco takes an interface name (`ip tacacs|radius
source-interface <ifc>`; `snmp-server trap-source <ifc>`). One field with
a vendor-shaped value (an address for Junos, an interface for Cisco,
refused for WTI), as `config-syntax` is Cisco-only today.

**Q2. Is a per-device field needed at all for Junos, or is the registered
address the source?** The address tacctl registers for a Junos device is
the address the server sees from it, which is what a `source-address`
pins. A per-scope switch (`source-address: registered`) would render
`source-address <device.Address>` for every Junos device of the scope with
no per-device data; a device behind NAT (the registered address is not an
interface of the device) is the exception and needs an explicit value or
`none`. *For:* no new per-device state for the common case; the value
can never be outside the scope's prefixes. *Against:* a NAT'd device
would be rendered a source address it does not own, so the switch must be
per scope and off by default, with the explicit per-device value as the
override; two mechanisms instead of one.

**Q3. Where does it live and who sets it?** A device field in
`devices.yaml` (`source: <value>`), set by `tacctl device source <name>
<value>|none` and shown by `device show`, superuser-only as `device
location`, `device netconf` and `device snmp` are; engineers read it. A
Junos address is refused when no prefix of the device's scope covers it
(the device would stop being answered); a Cisco interface name is
checked for shape only (`cisco.source_interface` has a rule already,
`TypeInterfaceName`), since tacctl does not know the interface's address.

**Q4. What renders and compares it?** The walkthrough (`config juniper
--name <device>`, `config cisco --name <device>`, `device config show`)
prints the statement in place of the commented example; `devices.Managed`
carries it in the `aaa` expected section, so the pull compares it (`!`
when the device sources from elsewhere, `-` when it has none) and the plan
sets it (ModeSingle, replaced in place: the row exists for Cisco and is
`Kept` for Junos today, so the Junos row changes from kept to owned only
when a value is rendered). With no value: today's behaviour, unchanged
(Junos kept, Cisco dropped from the comparison, the policy gap).

**Q5. SNMP in the same change?** `snmp trap-options source-address` and
`snmp-server trap-source` go into the `snmp` expected section the same
way, from the same field, when the device's SNMP is rendered at all. The
0.2.7 blocks already accept both as device-specific values inside a
block; a device that has one in its block and a registry value would have
two sources of truth, so the block statement would be refused when the
field is set (as a block naming tacctl's own community is refused).

**Q6. Which side wins?** tacctl's, when set: the device's other value is
`!` and the plan replaces it. When not set, the device's own is kept (Junos)
or ignored (Cisco), as today.

**Q7. Migration?** None in the file version: a new optional key. But the
0.2.15 binary refuses the key, so a `tacctl rollback 0.2.15` target would
have to strip it (the D91/D143 pattern), or the release notes say that a
rollback after `device source` was used needs the key removed by hand.
That is the one cost that is not "none".

### Smallest useful first slice

Junos AAA only: the `source` field, `device source <name> <addr>|none`,
rendered in the walkthrough and the `aaa` expected section, compared and
planned; `device show` and `device list --json` show it; no scope switch,
no SNMP, no Cisco. Size: about 2 sessions (the field and loader with its
validation and the `names`/`validate` checks; the rendering and the owned
row flip; `device show`; docs, man, CHANGELOG, goldens, corpus markers;
the rollback target). The SNMP trap source and the Cisco per-device
interface are a second slice of about one session each; the per-scope
`registered` switch is a third, if Q2 says yes.

### Risks

- A wrong Junos source address makes the device unknown to the server.
  The apply's fresh-login verification catches it and the device rolls
  back; a paste by hand does not, so the walkthrough's note says to keep
  the first login open (it does for the AAA block already). The scope
  prefix check at `device source` time removes the common mistake.
- The planner's Junos server row changes from kept to owned when a value
  is rendered: a device whose own `source-address` differs from tacctl's
  gets a replace, which is the point, but the review must show it as a
  change of the login path (class A, D81), not as SNMP.
- The rollback target (Q7) is a lifecycle change for one key.

### Open questions for the maintainer

1. Is Q2's "registered address is the source" the common case on the
   Junos estate, or is NAT common enough that only the explicit field is
   worth building?
2. Junos only first, or Cisco per-device interface in the same slice
   (the per-scope setting exists; is a per-device exception needed)?
3. SNMP trap source in the first slice or later?
4. Is a rollback target for the new key wanted, or a release-notes line?

## 2. `device config rollback` from the device's history (D86)

`apply-deferred.md` D86 (deferred 2026-10-10; kept deferred by D129 in
0.2.9 and by 0.2.10). The 0.2.9 and 0.2.10 apply changed what D86 rests
on, so the questions are asked again against the code.

### What exists today

- Apply over the Junos command line (0.2.9) and NETCONF (0.2.10, opt-in):
  a plan loaded in an exclusive session, `commit confirmed` with tacctl's
  comment (`tacctl apply <id> by <user>`), the fresh login as the user, the
  landed compare (`show configuration | compare rollback 1`), the read
  back, the confirming `commit`. Superusers only, Junos only. Cisco and WTI
  are refused by apply.
- The record (`devconf.Applied`): `id`, `kind` (check or apply), `result`,
  `via`, `shape`, `sections`, the counts, `commit` (the confirming
  commit's sequence number and time), `pre` (per section, the fingerprint
  of the text before the change). The last apply only; no copy of the
  pre-apply text (D85: the device's history is the record, and a copy
  could restore no secret).
- The driver already reads the history (`show system commit`,
  `CommitEntry`, `History`), the pending banner, and compares against
  rollbacks (`RollbackCompare`, `show configuration | compare rollback n`)
  to settle an unknown outcome; its cancel path loads the inverse of its
  own commit (`rollback 1`, checked by compare) and commits it. What it
  does not read: the text of a rollback as `set` lines (`show
  configuration rollback n | display set`), the one read a rollback from
  history needs; the lab item L6 of the deferred plan is still open, and
  the fake device (`fakedev`) does not answer it.
- The transport's guarantees: nothing but allowed statements and apply
  words is typed; every commit is confirmed; the confirming commit is typed
  only in the session that committed; a text the parser does not know
  fails.

### The questions

**Q1. What does a rollback write?** As D86 says: not Junos `rollback N`
(it undoes everyone's later changes), and not a stored inverse (no secret
could be restored, a second source of truth). The target is the text of
the rollback entry before tacctl's commit, found in `show system commit`
by the comment that carries the record's `id` (never by sequence number:
others' commits shift it), read as `set` lines, filtered to the applied
sections; the delta is the planner's, against the current read, under the
ownership rule (nothing outside the sections, extras kept); the write is
the apply transaction with the comment `tacctl rollback <id> by <user>`,
the fresh login, the landed compare, the confirming commit. The record
gains `kind: rollback`. A later change inside the sections is undone and
listed (`also undone`, from the diff between the rollback text and the
current read); outside them, untouched.

**Q2. Which transport?** Both, through the same transport interface: the
read of the rollback text is one more `show` on the CLI and one more RPC
on NETCONF (`<get-rollback-information>` or the command RPC; L6 decides
the form the lab switch answers), and the write is the apply path that
already exists for each. A device whose apply was `via: netconf` can be
rolled back over the CLI and the other way round: the history is the
device's, not the transport's.

**Q3. Read-only against writes.** `device config rollback <name> --check`
is read-only: it logs in as the person, reads the history and the current
configuration, reads the rollback text, computes and prints the delta and
the `also undone` list, and types nothing but `show` commands (the Reader
of the driver, which cannot commit). Without `--check`, the write is
reviewed first (the plan printed, the question), then the transaction.
`--yes` answers the question, as for apply; `--check` has no question.

**Q4. The safety model.** The apply's: the confirmed commit and the fresh
login as the user are the rollback's own proof (a rollback that breaks
the login path rolls back by itself); the lock-out guards of the planner
apply to the computed delta as to any plan (the authentication order is
never left empty, the server statement is never deleted); the per-device
lock of `device-apply/locks`; a pending commit of anyone fails the
transaction before the discard. New refusals, before anything is typed:
no apply in the record; the last apply was `no change` or `check`; the
entry with the record's comment is not in the history any more (Junos
keeps 50; the way forward is `apply`); the device has a pending confirmed
commit. The reviewed text must say that a rollback returns the sections
to their pre-apply content, not to today's rendering: `device config
diff` reads `differs` again afterwards by design, and the next `apply`
reapplies.

**Q5. Who, and with what credential?** Superusers, with their own login
and password as for apply (D69); the password cache answers it as it
answers apply. No stored credential, no service account, nothing run
unattended: the person types the command and answers the review. One
device per command, or `--id <id>` for every device whose record carries
that apply's id (what a batch apply wrote), with the canary and
`--max-failures 1` of apply.

**Q6. Secrets.** Superusers see the rollback text whole, so a `secret`
statement the pre-apply text had is restored by value from the device's
own history (never stored by tacctl; it passes through the transaction
masked in every output, as apply's secrets do). No `--secrets` flag is
needed while apply is superuser-only.

### Smallest useful first slice

`device config rollback <name> --check` alone: the history search by
comment, the rollback text read (the L6 form settled on the lab switch
first, as a read-only spike with `show system rollback` and `show
configuration rollback n | display set`), the filter, the delta and the
`also undone` list printed as a plan with every secret elided, exit
status as `plan --exit-code` (2 when a rollback would change something,
0 when the sections are already as they were, 1 for a refusal). Nothing
is written to a device. Size: about 2-3 sessions (the read on both
transports, the fake device's `show configuration rollback n | display
set` with a history of entries, the verb, the tier row and sudoers
drop-in, docs, man, CHANGELOG, a corpus marker, the lab spike). The write
is a second slice of about 2 sessions: the driver takes a plan whose
target is the historical text (the state machine is unchanged), `kind:
rollback` in the record, `device config list`'s `APPLIED` column, the
bats cases through the knob verb, a lab acceptance under `commit
confirmed` with a `zz-tacctl-*` change on the lab switch.

### Risks

- L6 is unsettled: the form in which a Junos release prints a rollback as
  `set` lines, and whether NETCONF has an RPC for it, is written from the
  references. The check-only slice is where it is settled, with no write
  at stake.
- The comment search depends on tacctl's own comment surviving in the
  history; a device whose `system commit` settings drop comments, or an
  operator's `commit` that reuses the sequence, would not be found and the
  verb refuses, which is the safe side.
- A rollback restores pre-apply content that today's rendering has moved
  on from (a community since rotated): the device is then `differs` until
  the next apply. The review says so, but a person who expects "undo the
  last apply and stay current" is surprised once.
- Running the write slice adds a second verb that commits to devices;
  its tests are the apply's harness and the fake device, which already
  model the confirmed commit, the banner and the history.

### Open questions for the maintainer

1. Is the check-only slice worth shipping on its own (a read that shows
   what a rollback would type, as `apply --check` shows an apply), or
   only with the write?
2. One device per command only, or `--id` for a batch apply's devices in
   the first write slice?
3. Lab time for L6 on the lab switch (read-only; `show system rollback`
   and `show configuration rollback n | display set`), before any of it
   is planned?
4. Should the record keep more than the last apply (D85 keeps one), so a
   rollback can name an apply before the last? Today's answer is no; it
   is the reason the verb rolls back the last apply only.
