# tacctl 0.2.16 plan (2026-10-21)

Read `0.2.16-handoff.md` (state, working rules) first. Decisions continue
the numbering of `0.2.15-plan.md` (D207-D230). Scope chosen by the
maintainer on 2026-10-21; design review: Fable, the same day. State:
planned, nothing built.

## 1. Scope

A small release that closes what 0.2.15 left open and hardens two paths of
the host work. No state-format change (the 0.3.0 format work is excluded
by decision), no new device write path, no new credential, nothing
scheduled or automatic (`0.2.12-plan.md` section 2). One item changes
locking (WP16.5) and is designed in full here; the others are fixes.

WP16.0 is the release-start step of D178 and D225, now eligible. The rest
is built in the order of section 5, each its own gated unit.

- WP16.0  The action pins: `actions/upload-artifact` 7.0.2 (D231). CI only.
- WP16.1  `config validate` refuses extra positional arguments (D232).
- WP16.2  `config validate --fix-names`: a host rename whose carried scope
          is refused counts as renamed; the scope is not offered again in
          the same run (D233, D234).
- WP16.3  `host enroll` checks the device namespace again after the
          script has run, under the device registry's lock (D235, D236).
- WP16.4  The rendered backend comment says `host` for a held host (D237).
- WP16.5  A lock for the UID ledger `linux-uids` (D238-D242).
- WP16.6  A precise bats assertion for the snapshots of `host forget`
          (D243). Tests only.
- WP16.7  Backlog, roadmap and handoff hygiene; the release gates.

## 2. Decisions

**D231 — The action pins (WP16.0).** D178 stands. `actions/upload-artifact`
7.0.2 was published 2026-10-07 and is two weeks old today; its tag
resolves to commit `cf430e030ddbb5b0abf93d22962f4752f3646cd9` (read from
the GitHub API on 2026-10-21; the implementer reads it again and compares).
`actions/checkout` 7.0.1 (2026-07-20) and `actions/setup-go` 7.0.0
(2026-07-16) are the newest releases of their repositories and stay. The
one line that changes is `release-reproducible.yml` line 66; `test.yml`
does not use `upload-artifact` and is checked, not changed. Proof: the
`test` workflow green on the pull request of the feature branch, and
`release-reproducible` (it runs on `workflow_dispatch` only) dispatched on
the feature branch with the previous release tag as its input before the
merge, then on the release tag as every release does. The release notes
name the pins. No CHANGELOG item (CI only, as WP14.3 and WP15.0).

**D232 — `config validate` takes no positional argument.**
`configSpecs["validate"]` (`config.go` line 55) has `MaxArgs: -1`, so
`config validate extra` runs the report and ignores the word. It becomes
`MaxArgs: 0`: `Parse` then returns an `ArgCountError` whose text is the
one every other bounded verb prints, `Unknown argument: '<word>'`, exit 1,
and the report does not run. The flags stay (`--json`, `--fix-names`,
`-y`). Nothing else of the spec changes, so completion is unchanged;
`shell_view_fixes_test.go` lists the `MaxArgs -1` verbs that take none
and loses `validate` from that list if it names it. The corpus
(`tests/diff/corpus/config.txt`) runs `config validate` with no argument
and is unaffected.

**D233 — A host rename whose carried scope is refused is a rename.**
`host rename Web1 web1` with the scope offer answered yes renames the host
first and the scope after; when `scopeRenameCheck` or `scopeRenameRun`
refuses (the new scope name exists, its SNMP credentials file or blocks
exist under the new name, an invalid name), D201 leaves the host renamed
in its old scope, prints `Host renamed. Scope 'linux-Web1' was NOT
renamed: <reason>; the host keeps it. Retry: tacctl scope rename
linux-Web1 linux-web1.` and exits 1. `--fix-names` reads that exit as a
failed rename (`fixNames`, `exitCode(err) != 0`) and, because the findings
are read again after each rename, then offers `linux-Web1` on its own,
where the same check refuses it for the same reason. Both are wrong: the
host was renamed, and the second refusal is a repeat the person can do
nothing about in this run. Now the host counts as `renamed`; the scope is
added to the names not offered in this run, with one line in place of the
offer:

    'linux-Web1' is not offered: its rename was refused with the host's
    (<reason>); retry: tacctl scope rename linux-Web1 linux-web1

It is counted under `not offered` (the summary line keeps its four
counts), and the run exits 1 as D230 says for a name not offered: a script
learns that a name remains, and the person has the command. The scope is
left out only in this run: the next `--fix-names` offers it again, and a
refusal that something in between has cleared (the credentials file
renamed by hand) then succeeds.

**D234 — How the loop learns it.** `hostRenameScopeFailed`
(`host_rename.go`) prints what it prints today and returns a typed error
(`*hostScopeKeptError{Old, New string; Reason error}`) that unwraps to the
`exit(1)` it returns today, so `host rename` typed directly prints and
exits exactly as before (the tests of D201 pass untouched). `fixNames`
checks for it with `errors.As` before the exit-code test: on a match it
counts `renamed`, marks `scope/<Old>` as seen, and prints the D233 line
when the scope would next be offered (the line replaces the question). The
scope offer that `host rename` makes when a scope keeps its name because
other hosts use it (`OtherHostsUse`, a warning and exit 0) is not this
case: the host rename counts as renamed, the scope is then offered on its
own, and `scope rename` renames it with its hosts. The `-y` run of the
`name_fix_test.go` fixture gains the case; the scope's SNMP credentials
file under the new name is the refusal the fixture provokes (the one
refusal of `scopeRenameCheck` a lower-case rename can meet).

**D235 — `host enroll` checks the device namespace again before it writes
its line.** `hostEnroll` (`host.go`) runs `hostNameCheck` (a read of
`devices.yaml` without a lock, then `devreg.CheckHostName`) before it
resolves the target, builds the script and runs it on the host, which can
take minutes; the host-against-host rule is held again under the host
registry's lock by `RememberNew` (0.2.14), the device-against-host rule is
not. A `device add <name>` that completes while the script runs leaves a
host and a device with one name, which `breakglass hold` refuses as
ambiguous and `config validate` reports. The second check goes where `host
rename` puts its own (`host_rename.go` lines 129-135): after the registry
line is written by `RememberNew`, in a `devreg.Mutate` of `devices.yaml`
that finds the name and writes nothing (`f.Find(name)`; the pins are
written by `PinKeys` later, as today). `Mutate` holds `.devices.lock`,
which `device add` holds while it reads the enrolled hosts and writes, so
either the device was registered before and the mutate sees it, or `device
add` starts after and sees the registry line. No lock is nested: the
registry's lock is released by `RememberNew` before the mutate, as in
`host rename`. Only a new name is checked (`enrolled` false); a
re-enrolment or `host move` keeps the host's own name.

**D236 — What a conflict leaves.** The registry line is removed again
(the undo of `hostRenameUndo`, by name), so the registry is as before the
command; no record, no pins, no facts are written, no `host enroll` log
line. The host itself keeps what the script installed: the accounts of the
scope, the PAM and sudo files, the server's address. It authenticates
through this server as long as the scope's prefixes cover its address (the
registry line is a name for tacctl's own commands, not what the server
answers), and nothing on it refers to the name. The message, exit 1:

    A device named '<name>' (<address>) was registered while the client
    script ran; a host and a device cannot share a name. The script
    already ran on the host; the registry was not changed. Enroll it
    under a name of its own: tacctl host enroll <target> --scope <scope>
    --name <other>

The re-run is the ordinary enrolment (the script is idempotent) and takes
the pins and the record then. The snapshot taken before the registry
write stands (nothing in it is wrong). The pre-script check stays: it
refuses early what it can see, and the late check is for what it cannot.

**D237 — The hold comment names a host as a host.** The two renderers
(`internal/render/tacacs/render.go` `holdComment`, `internal/render/
radius/hold.go` `holdComment`) print `(device <name>)` for every hold
because `conf.Hold` carries a name and no kind; a hold on an enrolled host
(0.2.14, D176) is stored the same way. The word is decided from the host
registry: `Render` of both backends gains the set of enrolled host names
(read once by the backend from `Paths.LinuxHosts` with
`hosts.LoadRegistry`; a missing or unreadable registry is the empty set,
never an error: a comment decides nothing), and a hold whose name is an
enrolled host reads `(host <name>)`. The comment is part of the rendered
file, which `config validate` compares with a fresh render, so the word
must change only when a render follows: it can, because a held host
cannot be forgotten (D187), unenrolled or enrolled over, and `host rename`
carries the hold and renders; `backup restore` puts both files back and
renders. A hold whose name is neither (an orphan, a `config validate`
finding) keeps `device`. The alternative, a `kind` leaf on the hold record
in `tacctl.yaml`, is a schema key an earlier binary refuses and needs a
rollback target for one word; not chosen. The two goldens hold devices
only and do not change; `docs/devices/break-glass.md` line 77 says the
old wording and is corrected.

**D238 — The UID ledger gets a lock of its own.** `linux-uids` is read and
written by more commands than its comments say. Writers: `host sync` and
`host enroll` (`renumberUIDs`, then `WriteScript`, whose `ScopeUsers`
allocates a number for every user that has none, `UIDs.For`, an append),
`config linux script` (the same), `config linux uid <user> <uid>`
(`Holder`, then `Assign`, a replace), `user rename` (`moveUID`, `Rename`,
a replace, under the apply lock), `backup restore` (the whole file, under
the apply and registry locks), `config linux uid-range` (`RenumberTo`).
Readers that decide something: `WriteScript` (`Recorded`, `inactiveUIDs`:
the numbers sent to the host), `hosts.Removed` (which accounts a host
deletes), `user rename` (`Lookup` before the move), `config linux uid`
(the holder check), `backup restore` (the ledger note), the snapshotter
(the copy into a snapshot, and the comparison that decides whether one is
taken). Readers that only display: `user list` and `user show`
(`userUID`), `config linux uid` with no argument, `host show --check` and
`host check` (the comparison report), `backup diff`. Today no lock covers
any of this: two `host sync` runs that meet a new user both compute the
same next number (`For` is a lookup, a scan and an append) and the user
gets two lines or two users one number; `config linux uid`'s holder check
and its write are two steps; and `user rename`'s move beside a sync is
"before or after", as its comment says. The lock is one `flock` on
`<state>/.linux-uids.lock` (0600, beside `.hosts.lock` and
`.store-apply.lock`; created on demand; it goes with the process), taken
by `hosts.UIDs.Lock()` (returning the unlock) and `WithLock`, and held by
every writer and every deciding reader for its read-modify-write window
and nothing longer. The display readers take no lock (D241).

**D239 — The windows.** Each holder takes the lock, does its ledger work
and lets go before it does anything else, so no holder waits on a host,
a person or another lock while it holds the ledger:

- `renumberUIDs` (every caller): lock, `RenumberTo`, unlock.
- `WriteScript` (`host enroll`, `host sync` per host, `config linux
  script`): lock around the whole build (`ScopeUsers`, `Recorded`,
  `inactiveUIDs`), unlock before the script file is written and before
  `RunScript`. A `host sync` of ten hosts takes it ten times, each for
  milliseconds; the ssh run never holds it.
- `hosts.Removed` (`homesToDelete`): lock around its reads.
- `config linux uid <user> <uid>`: lock from the holder check to the end
  of `Assign`.
- `user rename` (`moveUID`): lock around `Lookup`, `Rename`, `Lookup`,
  inside the apply lock the writer already holds.
- `backup restore`: lock around the ledger's `backupPut` or its removal
  in `restoreHosts`; nothing with `--keep-uids`.
- The snapshotter: lock around its copy of `linux-uids` into the
  snapshot; the comparison (`sameHosts`) reads without it (a torn read can
  only make the files differ, which takes a snapshot, the safe side).

**D240 — Lock order and the wait.** The ledger lock is the innermost lock
of tacctl: no holder takes any other lock while it holds it, and no holder
takes it while waiting on anything but the lock itself. The orders that
exist today stay: the apply lock before the registry lock (`backup
restore`), the registry lock before the per-host locks (the restore tries
them without waiting), the registry lock before the records lock (the same
file), the registry lock released before `.devices.lock` (`host rename`,
D235). The ledger lock sits after all of them, so there is no cycle: a
holder of the ledger lock is never waiting, and whoever waits for it waits
for a holder that will let go in milliseconds. The wait is the registry
lock's (`registryLockWait`, 30 s, polled every 20 ms, `LOCK_EX|LOCK_NB`),
and the variable is shared: `SetLockWait` sets the wait of both locks, so
the tests have one seam (`shortLockWait`, `serial(t)`). The refusal after
the wait is `ErrLedgerBusy`: `the UID ledger (linux-uids) is locked by
another tacctl command; try again in a moment (waited 30s)`, printed by
the command as the registry's is, exit 1, nothing changed by the command
that gave up (every holder takes the lock before its first write of the
ledger; `user rename` has written the store by then and reports the move
as failed with the snapshot to restore, as it does for any error of
`moveUID`). A lock held for 30 s means a holder died inside its window,
which `flock` does not allow (the lock dies with the process); the wait is
a backstop, not a path.

**D241 — Every write of the ledger is atomic; display reads take no
lock.** `For` appends one line with `O_APPEND` today; it becomes a
read-modify-write through `writeAtomic` (the whole file replaced by
rename), as `Assign`, `Rename` and `RenumberTo` already are. With that,
a reader without the lock sees the file before or after a write, never a
part of one, and a line is never torn; so `user list`, `host show
--check`, `host check`, `backup diff` and the listing of `config linux
uid` read as today. The documented sentence of `user rename` ("a `host
sync` reading it at the moment of the rename sees the file before or
after", `docs/cli/user.md`, the man page) becomes: a `host sync` builds
its script from the ledger under the ledger's lock, so it sends the names
as they were before the rename or after it, never a mix; an account
created under the old name is renamed at that host's next sync.

**D242 — What `backup restore` does with the ledger.** Unchanged in
effect: the whole file comes back (or goes, when the snapshot has none)
in `restoreHosts`, now under the ledger lock (D239); `--keep-uids`
touches it not at all. The ledger note before the question
(`restoreLedgerNote`) is read without the lock and before the person
answers; a sync that allocates a number in between is not in the note.
The warning after the restore (D212: the same comparison, live against
snapshot) is computed from the pre-restore snapshot's copy of the ledger,
which the snapshotter took under the lock, against what was restored; so
what the person is told after the restore is exact, and the undo (the
pre-restore snapshot) holds the ledger as it was at the moment of the
copy. A snapshot that does not know the hosts takes no ledger lock.

**D243 — The `host forget` snapshot assertion (B3).** `host.bats` "host
forget: a registration is dropped locally" asserts `-gt $before` for the
snapshot count after two forgets, weakened in 0.2.15 because the second
forget is deduped by D210. The precise statement of what D210 promises:
after `host forget ghost --yes` the count is `before + 1` and the newest
snapshot holds `hosts/ghost.json` and a `linux-hosts` with `web1` (the
undo of the forget); after `host forget web1 --yes` the count is still
`before + 1`, because the live state differs from that snapshot only by a
record present on one side with volatile content alone, which D210 counts
as equal, and the newest snapshot still holds the `web1` line (the undo
of the second forget is the first forget's snapshot). The test asserts
exactly that: two `-eq` counts and the three files, with the comment
naming D210. No code changes.

## 3. Candidates weighed

**Counting the refused scope as `failed` (D233).** The host rename did
not fail and the scope rename was not attempted on its own; `failed`
would make a script re-run something that cannot succeed as it stands.
`not offered` says what is true: a name remains and the person has the
command. A fifth count (`kept`) was weighed and not chosen: the summary
line is pinned by tests and docs, and `not offered` already means "a name
remains, here is the command".

**Checking the device namespace before the script under the lock, and
holding it through the run (D235).** It would hold `.devices.lock` for
minutes and block every `device` command for the duration of an
enrolment; a second check after the run costs one read. Chosen: the
re-check, as `host rename` does.

**A `kind` on the hold record (D237).** One leaf in `tacctl.yaml` would
make the renderer independent of the registry, at the price of a schema
key an earlier binary refuses and a rollback target. The registry read is
free and cannot drift while a hold stands (the held host cannot be
forgotten or unenrolled). Chosen: the registry.

**The ledger under the registry lock (`.hosts.lock`) instead of a lock of
its own (D238).** It would spare a file, but the registry lock is held
by `backup restore` through the whole host restore and by `Records.Update`
while a record is rewritten, and `user rename` (which holds the apply
lock) would then take the registry lock inside it, an order that exists
nowhere today and that `backup restore` takes the other way round (apply,
then registry). A lock of its own, innermost, needs no new order. Chosen:
its own.

**A shared lock for readers (`LOCK_SH`).** Readers would not block each
other. Not chosen: every holder holds for milliseconds, the display
readers take no lock at all (D241), and one kind of lock is easier to
reason about and to test.

**Locking the display readers too.** Safe but unneeded once every write
is atomic (D241); `user list` would take the lock once per user. Not
chosen.

**Refusing a restore whose ledger changed while the person answered
(D242).** Safe but harsh for a number allocated in the seconds of a
question. Not chosen: the warning after the restore is exact and the undo
holds the ledger as copied.

## 6. Risks

- D240 asserts an order between locks that no code enforces. The
  statement "the ledger lock is innermost" is checked by reading every
  holder (D239 lists them) and by the `host_test.go` hook test; a future
  holder that takes another lock inside the ledger lock breaks the
  argument, so the `Lock` doc comment says the rule and names D240.
- `For` becoming a whole-file rewrite (D241) changes the ledger's inode on
  every allocation, as `Assign` and `Rename` already do; a hard link or an
  open descriptor someone keeps on the file (nothing in tacctl) would
  stop following it. Noted, accepted.
- D237 reads the host registry at render time: a registry edited by hand
  while a hold stands makes the comment drift until the next render,
  which `config validate` reports as any drift. The 0.2.14 name rules
  make such an edit unlikely; accepted.
- D235 adds a `devreg.Mutate` to every new enrolment; it writes nothing
  (the bytes do not change) and waits on `.devices.lock` as `PinKeys`
  already does. The hook that the test uses to register a device between
  the script and the write must not leak into the release binary: it is
  a test hook of `hooks_test.go`'s kind.
- WP16.5 touches `backup restore` again (`restoreHosts`, the warning);
  the restore tests of 0.2.15 (`backup_hosts_test.go`,
  `backup_hosts_fixup_test.go`) are the regression net and must pass
  unchanged apart from the new cases.
