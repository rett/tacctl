# tacctl 0.2.11 lab sheets: NETCONF limits and a competing commit

Two runs that 0.2.10 did not make (`0.2.10-lab.md`, N4 and N8). They run
on a lab switch only, one at a time, each with its own approval. Nothing
here changes code unless a result says so (last section).

## What the code does

- One `apply --transport netconf` opens **three SSH logins** (the check:
  one login with the read, gate and held sessions; the apply: the same and a
  second login for the verification) and several NETCONF sessions as
  channels of them; `pull` is one login, `apply --check` one. The sessions
  are subsystem requests on the SSH port (22); port 830 is not used.
- A batch never holds the same device twice and runs devices one at a time
  unless `--concurrency` says otherwise.
- `auto` falls back to the command line only when the SSH dial succeeded and
  the NETCONF login or hello failed. A refused dial fails the device under
  every setting. A refusal after the login never falls back; a refused
  verification login cancels the change.
- Another editor's **commit** between the gate and the lock is not refused.
  Staged work and held locks are. The apply continues when the delta
  recomputed after the review is the same; a delta that differs ("the device
  changed since the review"), a foreign pending confirmed commit and the
  compare of what landed with the delta are what stop a harmful case.
- Nothing paces or retries a refused session.

## Results (2026-10-15, Junos 25.4R1-S2.3, limits 5 and 10)

Every apply was compared with the saved configuration, which was identical
after the cleanup; nothing was left pending. The second session was a
separate login as the lab's own account, never the operator's open session.

| Run | Result |
|---|---|
| N8.1 one apply over NETCONF | `applied [via netconf]`; the device logged three accepted logins for it |
| N8.2 five applies inside a minute (A and B alternating, the last four in 60 s) | all applied; no session was refused |
| N8.4 seven raw NETCONF sessions held at once on the SSH port (22) | all seven got a hello, though the connection limit is 5 |
| N8.4 the same seven on port 830 | five got a hello; the sixth and seventh were closed with no hello |
| N4.1 an unrelated commit at the review prompt | the apply proceeded and applied; both commits in the history |
| N4.2 the same statement committed at the review prompt | `failed: the device changed since the review`; nothing committed by tacctl |
| N4.3 staged change | settled in 0.2.10: refused at the gate |
| N4.4 a commit inside the pause (`TACCTL_TEST_APPLY_PAUSE=gate:14`) | the apply continued and applied; both commits present, nothing pending |

Consequences: the connection and rate limits bound the service's own port
(830), not the SSH subsystem the transport uses, so no apply was refused and
the transport needs no pacing on this release; the `auto` fallback on a
refused login could not be provoked by the limits (the 0.2.10 run with the
service disabled covers it). A commit between the gate and the lock is
tolerated and harmless: the landed compare proves exactly the delta landed.
Not run: another Junos release; the rate limit on port 830.

## Setup (both sheets)

- The lab scope has the NETCONF service enabled with the connection limit 5
  and the rate limit 10 that the device has, so the pull reads `ok`.
- A harmless delta that toggles: two variants of a block statement (the
  login message), so every apply has exactly one statement to change.
- A saved copy of the device's configuration before the run, and a second
  command-line session left open for `rollback 1` and `commit` if a
  confirmed commit is left pending. Every commit is tacctl's own confirmed
  commit (the default window); nothing else on the device is changed.
- After every step: `device config pull --diff` is empty, the device's
  `show system commit` has no `rollback pending`, and the configuration is
  identical to the saved copy.

## N4: another editor's commit during an apply

Window 1 is the review pause between the check and the apply: a person
commits from a second session. Window 2 is the milliseconds between the gate
and the lock, which only a test build can hit (below).

| Step | Run | Pass | Record |
|---|---|---|---|
| 1 | At the review prompt the second session commits an unrelated statement (a `zz-tacctl-*` login class), then answers | The apply proceeds (the recomputed delta is equal), `applied`; both commits are in `show system commit` | The device's words and the timing |
| 2 | As 1, but the second session commits the very statement tacctl is about to set | `failed: the device changed since the review`, or `no-change` when the recomputed delta is empty; nothing committed by tacctl | Which of the two |
| 3 | As 1, but the second session stages a change and stays in configure mode | The apply fails at the gate: the database is locked by that user, or modified by a staged change | Unchanged from 0.2.10 |
| 4 | Test build with `TACCTL_TEST_APPLY_PAUSE=gate:<seconds>` (a knob that pauses between the gate and the open); the second session commits an unrelated statement inside the pause | The apply continues and lands: `applied`, both commits present | Whether a refusal on a newer commit than the read's first entry is wanted |

## What each result changes

- A device text with no mapping: a mapping in `internal/devapply/errors.go`
  and the matching fake knob; no new write path.
- A rate-limit refusal at the verification login that cancels a good change:
  consider one retry after a short wait for that dial only.
- A downgraded NETCONF state: fix where the probe is recorded.
- Always: the session budget in the user documentation ("one apply opens up
  to seven NETCONF sessions over three logins; a rate limit below 7 refuses a
  single apply, below 14 a second one within a minute; `apply --check` opens
  three, `pull` one"), and the N4 and N8 rows of `0.2.10-lab.md` settled.
- A newer-commit refusal in the gate only if step 2 or 4 shows a harmful
  case; the landed compare already proves that exactly the delta landed.
- `auto` as the default transport stays a later release's decision; these
  runs are its input.
