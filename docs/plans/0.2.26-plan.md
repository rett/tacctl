# tacctl 0.2.26 plan (2026-11-06)

State: scope chosen by the owner 2026-11-05 (device reports, with serial
numbers and chassis members), designs mapped on the 0.2.25 code, nothing
built. Branch `feature/0.2.26` (or smaller features) from `develop` at the
0.2.25 merge. Decisions continue the numbering of the earlier plans (the
0.2.23 plan ended at D315): D316 and up. A decision the owner has not made is
marked "default" and stands until overruled; the owner's own decisions are
marked "owner, 2026-11-05".

The proposal this plan builds is `backlog.md` section 3i ("Device reports",
filed 2026-10-29); the stored facts it extends are `docs/plans/backlog.md`
section 3h (built in 0.2.8) and `internal/devconf/facts.go`.

## 1. Scope

A report is a saved, dated document about the registered devices, made on
demand from what tacctl already stores about them. This release adds the
reports and the data they need that tacctl does not store yet: the members of
a chassis.

| Item | What |
|---|---|
| Chassis members | A good pull also reads the members of a Junos virtual chassis or a Cisco stack and stores them as read-only facts: id, role, model, serial number, software release, status, priority |
| Reports | `tacctl device reports generate|list|show|export|rename|remove|prune`; text, CSV and JSON; four types: inventory, members, software, config |
| Storage | A report is a file of the user's own home, `~/reports/devices/`, mode 0600 |
| Superusers | List, show, export, rename and remove other users' reports, every access audited |
| Rollback | `tacctl rollback 0.2.25` is a new target (D331) |

Out of the release (`backlog.md` 3j and below): chassis components (power
supplies, fans, line cards, PICs, optics; 0.2.27, D319 leaves room for them),
PDF, chassis alerts, uptime and licence status (each needs a device command
tacctl does not run), scheduled reports, `generate --as <user>`.

## 2. Decisions

### What a report holds

D316. (owner, 2026-11-05) Serial numbers and detailed chassis member
information are part of the first release of reports, not a later one. The
inventory report carries the serial number of every device; the members report
has one row per chassis member.

D317. (default) Four report types, all made from the stored records, so no
device is contacted unless `--pull` is given:

| Type | One row per | Columns |
|---|---|---|
| `inventory` | device | name, address, vendor, scope, model, serial, release, members (a count), location, description, pulled (date) |
| `members` | chassis member | device, member id, role, model, serial, release, status, priority, pulled |
| `software` | device | name, vendor, model, release, pulled |
| `config` | device | name, scope, the `device config list` state (`ok`, `differs`, `never`, `failed`), pulled, applied |

A device that was never pulled is a row with empty facts and `pulled` empty
(`never`); it is not left out, because a report that hides a device hides the
gap. The members report lists a standalone device as one member (id `-`, role
`-`) built from its model and serial, so every device with a serial appears in
it. Further types (chassis alerts, uptime, licence status, notices and
host-key state) wait for the data they need, and so does the `software`
report's version-gate state (`backlog.md` 3h): the column is added when the
version gates exist, because nothing could fill it before and an empty column
in every format says nothing (it was in the first draft).

D318. (owner, 2026-11-06 for the columns; the rest is default) No secret, hash
or community string is in any report. The inventory report has two more
columns, `location` and `description`: the registry's own fields of the device
(`device location`, `device description`), free text an operator wrote, empty
when none is set. The members, software and config reports do not carry them.
Text that came from a device or an operator (model, serial, release, member fields, location, description) is shown as
the record keeps it: control, bidirectional and C1 characters replaced by `?`
(`cleanFact`). A CSV cell that starts with `=`, `+`, `-` or `@` is written with
a leading `'` so a spreadsheet does not run it; the JSON and text formats need
no such step.

### Chassis members

D319. (owner, 2026-11-05 for the depth; the shape is default) The pull's
record gains `members`, a list read only by reports and `device config show`,
rebuilt on every good pull (a pull that read none leaves the list empty, never
the old one, as `Release`, `Model` and `Serial` do):

```
members: [{id, role, model, serial, release, status, priority, components}]
```

Every field is a short string except `priority` (an integer, 0 when the vendor
prints none). `role` is `master`, `backup`, `linecard` or `member`; a role a
vendor prints that is none of these is kept in `status`. `components` is
reserved: it is a list of `{kind, slot, model, serial, status}` that 0.2.26
never writes and never reads, but a JSON report already carries each member's
`components` as an empty list, and the text and CSV reports ignore it, so
adding power supplies, fans, line cards and optics in 0.2.27 changes the
report files by rows and not by format. At most 32 members, each field at most
`maxFact` (100) bytes, as for the other facts. The key is derived data: an
older release's decoder must ignore it (the builder checks the parser, as D314
did for `interfaces`); if it does not, the rollback strips the key.

D320. (owner, 2026-11-05 for the commands) A Junos device's members are read
with two more commands after the pull, best effort in the same session:
`show virtual-chassis status` (member id, role, priority, status and the
mastership) and `show chassis hardware` (the `FPC` rows: model and serial
number of each member). The first gives the set and the roles, the second the
model and serial, joined by the member id (`fpc1` and `1` are the same
member); `show version` already read per member (the `fpc0:` blocks, 0.2.25)
gives each member's release. A device without a virtual chassis (the command
is refused, prints `error: ... not applicable`, or lists one member) has no
members and is reported as one (D317). Two routing engines are not members:
they are components (0.2.27). A cluster (SRX) is out of scope.

D321. (owner, 2026-11-05 for the commands) A Cisco stack is read with `show
switch` (switch number, role `Master`, `Member` or `Standby`, priority, state,
version) and `show inventory` (the `Switch N` entries: `PID:` the model, `SN:`
the serial number). A device that is no stack (`show switch` is refused or
lists one switch) has no members. A device the vendor table does not know (WTI
and others) has no members and is reported as one when it has a serial (it has
none today).

D322. (default) The reading of the members is best effort like the other
facts (`facts.go`): a refused command, a class that may not run it, an old
release that does not know it and an output that is not what the command
prints leave the list empty and never change the pull's result or its exit
status. The commands run inside the facts limit (`hooks.factsLimit`) and only
for a vendor with a reader. Each reader has fixtures from real captures (the
names replaced from the examples table, `docs/development/README.md`), and
one fixture per layout seen: two members, three or more (the layout the
0.2.25 known limit lacks), a master that prints its own label, a member that
is not present, a standalone device.

### Where the data comes from

D323. (owner, 2026-11-05) Reports are generated from the stored records with
no login. `generate --pull` first reads the devices as `device config pull`
does, with the operator's own password and no stored credential (the engineer
tier, the devices the user's scopes cover), then generates. A report is never
scheduled and no timer contacts a device. Every row carries the date of the
pull its facts came from, and the header of a report states the age of the
oldest datum (owner, 2026-11-06: no warning line for old data; the dates are
the information).

### Files, names and storage

D324. (owner, 2026-11-05 for the place; the rest is default) A report is a
file of the generating user's home: `~/reports/devices/<type>-<yyyymmdd>.<ext>`
(`inventory-20261106.csv`; a second one on the same day gets `-2`), the
directory mode 0700, the file mode 0600, created by tacctl as the user (the
user's own uid; nothing runs as root for it). `--name` replaces the type and
date part. Next to it lies `<name>.<ext>.meta`, a JSON file of mode 0600 with
what `show` prints: the date and time, the user, the exact command line, the
filters, the age of the oldest datum, the size, the format and the schema
number. A file in the directory with no `.meta` is a file the user put there:
`list` shows it as `other`, `show` says so, and nothing deletes it. Every user
has a Linux account and a home (D334: no user name has a period), so there is
no other place for a report.

D325. (default) Formats: `text` (aligned columns, the default), `csv` (RFC
4180, a header line, UTF-8, `\n`) and `json` (one object: `schema`, `type`,
`generated`, `oldest_data`, `filters`, `columns`, `rows`; `filters` is an
object with the keys `scope` and `vendor`, each only when given, `{}` for
none). A report is written to the home with the
format's extension; `generate --stdout` prints it instead and stores nothing.
PDF would need a vendored pure-Go writer (the build has no network) and is
out of this release.

D326. (owner, 2026-11-06 for the settings; the defaults are default) Limits
are settings: a global value and a per-user override. The global ones are
`reports.max_size` (default 10 MiB per report; a fleet of 20000 devices fits)
and `reports.max_count` (default 100 reports per user), set by a superuser
with the other settings of `tacctl config`. A superuser can give one user an
override of either (`tacctl user reports-limit <user> max-size|max-count
<value>|clear`, listed by `user show`); the override wins over the global value
for that user and `clear` returns the user to it. `0` means no cap. A
`generate` over the cap is refused with the `remove` line and names the
setting by its key in `tacctl.yaml` (`reports.max_size`, with an underscore,
like `device.config.max_concurrency`) and the command that changes it;
nothing deletes a report by age unless a user runs `prune` (D333). The
override is a field of the user record, like the email of 0.2.23: it needs the rollback step of D331. Names are
`[A-Za-z0-9._-]`, at most 64 bytes, no leading dot; `rename` refuses to
overwrite.

### Who may do what

D327. (owner, 2026-11-05) Reading from stored data is read-only tier work:
`generate` (without `--pull`), `list`, `show`, `export`, `rename` and `remove`
of one's own reports are open to the read-only tier and above. `generate
--pull` is the engineer tier. A report holds only the devices the generating
user's scopes cover (a superuser: all). The tier table
(`internal/tier`) gets the verbs; the usage rows, completion, the man page and
the tier tests follow.

D328. (owner, 2026-11-05) A superuser reaches the reports of other users:
`list --user <name>` and `list --all-users`, `show <user>/<report>`, `export
<user>/<report> --out <file>` (a copy into the superuser's own home or the
path given), `remove <user>/<report>` and `rename <user>/<report> <new>`.
Every cross-user access writes one audit line with who, whose and which report
and never the contents (`internal/audit`). A report that holds devices the
superuser's scopes would not cover is still readable: he is a superuser.

D329. (owner, 2026-11-05) Not wanted: `generate --as <user>`. A user generates
for himself; a superuser already generates for every scope. No verb writes a
report into another user's home.

D330. (default) `export` exists so a report can leave the server by the
user's own means (`scp alice@tacctl.example.net:reports/devices/<file> .` is
printed by `show`); tacctl sends nothing anywhere itself.

### Rollback, docs and tests

D333. (owner, 2026-11-06) `tacctl device reports prune --older-than <age>
[--yes]` removes the user's own reports older than an age: `<n>h`, `<n>d` or
`<n>w` (no default; the age is always given). It lists what it would remove
(name, type, generated date, size) and asks once, like `remove`; `--yes` skips
the question and `--dry-run` only lists. The age is that of the report's own
`generated` date in its `.meta` file; a file with no `.meta` (listed as `other`)
is never removed, and neither is anything outside the report directory. A
superuser can add `--user <name>` or `--all-users`; each other user whose
reports are pruned gets one audit line (who, whose, how many reports, never
names or contents), as for D328. Nothing prunes by itself: no timer and no
setting; D326's limits are what stops a directory from growing.

D334. (owner, 2026-11-06) A user name with a period is not tolerated anywhere:
"We need to completely remove dot username support, no dots allowed at all in
usernames." 0.2.20 and 0.2.21 allowed one, and 0.2.22 to 0.2.25 only read a
stored one (`config validate` reported it, `user rename` still ran from it,
`rollback` and the password verbs had notes for it). 0.2.26 removes all of
that: every verb refuses a name with a period with `Username must contain only
letters, numbers, underscores and hyphens (a period cannot be part of a Linux
account name).`, the store and `console.yaml` validate the name strictly, and the
tolerance in `config validate`, `rollback` (every target), the password verbs,
`config linux uid` and the renderer is gone. Existing users are converted, not
refused: **`tacctl upgrade` renames them** (the owner's answer), each period
becoming `_` (`alice.smith` is `alice_smith`), after a snapshot it names, with
the store record, the UID line and the console settings, and with a note to
tell the people to log in with the new name. A new name that is taken (a user
of the name, a second name that becomes it, a break-glass local user of the
user's scopes) gets a random suffix (owner, 2026-11-06: "Random suffix is
fine for collisions."): `_` and four lowercase letters or digits
(`alice_smith_k3x9`), drawn again until the name is free of every user, every
other new name of the run and the break-glass users, cut before the suffix
when the name would pass 32 characters; the first of two names that meet keeps
the plain name, and the line says `(alice_smith was taken)`. Only a new name
that is no user name at all, a `console.yaml` or ledger that cannot take the renames (checked before the snapshot), stops the upgrade before any change; the renames are journalled in `upgrade-renames` so that an upgrade that stopped after the store is finished by the next, and a dotted key of `console.yaml` no rename covers is dropped, named. So a report
always goes to the user's home (D324 has no fallback). `backup restore` and
`backup recover` read a snapshot that holds such a user (the snapshot the
upgrade takes first can): the snapshot's store is validated with the period
allowed and nothing else relaxed, the restore renders nothing (the renderer
refuses the name) and says to run `tacctl upgrade`, and a recovery skips the
user.

D331. (default) `tacctl rollback 0.2.25` is a target. It removes the `members`
key from the records only if the 0.2.25 decoder does not ignore it (a test
decodes a 0.2.26 record with the 0.2.25 reader code to decide), leaves every
report file alone (they are the user's files; the 0.2.25 release has no
`reports` verb) and says so in its next steps, takes no snapshot unless it
removed the key, and ends with `tacctl upgrade --branch 0.2.25`. Per-user overrides (D326) are a
stored-file change: `rollback 0.2.25` drops the field and the two global
settings unless the 0.2.25 reader ignores the keys (the same test), needs
`--yes` when a user has an override (like the emails of 0.2.23) and lists what
it drops. Every older
target also removes the key (like the other pull-derived keys) and its note
says reports stay in the home.

D332. (default) Every verb gets completion, a usage block, `help`, a man
page entry, a page `docs/devices/reports.md`, a CHANGELOG item and a row in
the tier table; the one-line descriptions follow the style ratchets
(`TestStyleRatchets`). The planning documents say what a report type holds.

## 4. What the owner supplies

Real captures, with the names replaced from the examples table (host name,
users, serial numbers `SN000001` and up, addresses, locations); the model,
release lines and layout stay as printed. One file each, or a paste:

1. Junos virtual chassis of two or more members: `show virtual-chassis
   status`, `show chassis hardware`, `show version | no-more`. A three-member
   (or larger) chassis is the one the 0.2.25 limit lacks.
2. A Junos device that is no chassis: the same three commands (a baseline).
3. Cisco stack: `show switch`, `show inventory`, `show version`.
4. A Cisco device that is no stack: `show switch` (its refusal) and `show
   inventory`.
5. The same commands on an older release, if one is in the fleet (EX 12.3,
   IOS 12.2), for the old layouts.

No capture is needed for the report files themselves.

## 5. Decided by the owner, 2026-11-06

- No warning line for data older than a number of days (D323).
- The inventory report carries the registry's location and description (D318).
- A standalone device is one row of the members report (D317).
- The limits are settings, global with a per-user override (D326).
