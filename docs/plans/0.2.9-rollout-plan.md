## 0. Summary

- **Goal:** what the helper does by hand and by shell becomes four tacctl
  verb families that share one transaction: `device config apply` (with
  `--check`), `device config shapes` (with `shapes seed`) (one reviewed plan
  checked on the device, committed under a confirmed commit, proven by a fresh login, compared with what landed,
  read back, confirmed; and the batch by confirmed shape), `device onboard`
  (a blank device with only a local account, in one sitting), `device
  collect` and `device sync` (a read of addresses that are not registered
  yet, then the registry filled from what the devices say), and the one-shot
  `--login <local-user>` of `device config pull|diff|plan` that the backlog
  recommends. Junos over the ssh command line is the first and only
  transport of the release; NETCONF apply (`apply-deferred.md`) stays
  deferred and plugs in later as a second implementation of the same
  interface (D129).
- **Shape:** one transaction driver over `devapply.Transport` with
  `Confirms()` (D129); the Junos CLI transport holds one exclusive session
  from `configure exclusive` through the verification to the confirming
  `commit` (D131); the planner of 0.2.5 is the only source of statements
  (D133: the allow-list tripwire is derived from its ownership tables, not
  kept by hand); every check of the helper that a machine can make is made
  by the machine, and what remains for a person is one review of every
  device, grouped by shape, with one typed answer (D134); shapes are a typed
  function of the planner's delta and become the canary's rule (D135);
  records in `/var/lib/tacctl`, never raw device output and never a secret
  (D138).
- **What pulls against safety, for the user to confirm** (§12): the trust
  of a blank device's host key before its local password leaves the server
  (one question before any login, or `--host-key`), the human proof that
  every login class still lands after an AAA change (automatic by default,
  an opt-in hold), and the truth about a pending confirmed commit over the
  command line (the device rolls back at expiry, not when tacctl dies;
  the record says `pending until <time>`).
- **Size:** 13 packages, ≈ 14-18 sessions, ≈ 9,000-12,000 lines with tests
  (`0.2.9-execution.md`). Cut order in §11.

## 1. Goals and non-goals

### Goals

1. **`device config apply`** (D130, D131): one or many Junos devices, the
   plan of each checked on the device, reviewed once, committed under a
   confirmed commit, verified, confirmed; one line per device and a summary,
   as the pull prints them.
2. **`device config apply --check`**: the check phase alone (the helper's
   `rollout --check` and `batch --check`): the device loads the plan,
   `commit check` runs, the candidate is discarded, the shape is recorded.
3. **Shapes, seed, the batch by confirmed shape** (D135, D139): `device config
   shapes`, `device config shapes seed`, `device config apply --confirmed`.
4. **`device onboard`** (D136): a blank device with a local account brought
   to a TACACS+ login in one run, with the local password asked once and
   never stored.
5. **`--login <local-user>`** on `device config pull|diff|plan` (D136): the
   backlog's recommendation, so a device that has no TACACS+ yet pulls as
   empty sections and the ordinary planner makes the first-time region.
6. **`device collect`, `device sync`** (D137): the helper's collect, register
   and sync, without python.
7. **Records, locking, interrupts** (D138): what moved from the helper's run
   directory and what did not.
8. **Tests without a device** (D142): the fake device learns a Junos
   configure model over the command line; golden transcripts; bats.
9. **`tacctl rollback 0.2.8`** (D143).

### Non-goals (0.2.9)

- NETCONF apply (D129: the interface is built so it plugs in; nothing of it
  is implemented), `device config enable-netconf` (D93), `device config
  rollback` from the device's history (D86): all stay in `apply-deferred.md`.
- Cisco and WTI applies: refused with the reason (`Confirms()` false; the
  §5.3 unknowns of the deferred plan stand; WTI has no candidate).
- Engineers: the verbs are the superuser's (D141); the seam of D87 is kept
  in the driver (a class pre-flight input) and nothing uses it.
- Writing `breakglass`, `netconf`, the lo0 application, `system
  root-authentication`, `system services`, `interfaces`, `groups`,
  `apply-groups`, any `system login user <name> authentication` (D133):
  never, whatever flag is given.
- A per-device commit script, `commit synchronize`, `load override`,
  `configure exclusive` left to a person, key-based device logins (the
  helper's `ROLLOUT_AUTH=key`: `devssh` authenticates with a password or
  keyboard-interactive and nothing else [V: `auth.go`]).
- Unattended applies (a timer): they need a credential no person types
  (0.2.10's service account).

### D129. The transport interface; the Junos CLI first; D77 amended

**`devapply.Transport`** (§5) carries `Vendor()`, `Confirms() bool`,
`LocalAddr()`, `Identity()` (the reported hostname and release),
`Pending()` (whether a confirmed commit is waiting), `Login()` (the class
and permission bits of this login), `SharedDirty()`, `Open(mode)`,
`Load(line)`, `Compare()`, `Check()`, `CommitConfirmed(minutes, comment)`,
`Confirm(comment)`, `Cancel()`, `Discard()`, `LandedCompare()`, `Close()`.
**The first implementation is the Junos command line** over one `devssh`
shell session (D131). `Confirms()` is true for it when the login's class
may configure and commit (from `show cli authorization`, L1 [S]) and the
device is Junos; a Cisco device is `failed: apply is not available for
Cisco devices in this release`; a WTI unit `unsupported`. The driver
(`devapply.Driver`, §3) is written against the interface and never
against the CLI, so the NETCONF transport of `apply-deferred.md` §5 can be
added without a change to the driver: its `Open` is
`<open-configuration><private/>`, its `Load` the `load-configuration`
RPC, its `Confirm` the `<commit/>` on the same session, and its confirm
semantics (the session-close rollback) are a property the transport
reports (`RollsBackOnClose() bool`), which the driver uses only to word the
record (D132).

### D130. The verb tree

A family of its own under `device`, beside `device config` and `device
block`:

```
tacctl device config apply  (<name>... | --all | --scope <s> | --vendor juniper | --stale)
                             [--check]
                             [--section <list>] [--secrets]
                             [--concurrency N] [--timeout <s>] [--max-failures N]
                             [--server ...] [--source ...] [--json] [--exit-code]
tacctl device config apply  (<selection>) [the check's options]
                             [--yes] [--confirmed] [--max N] [--pause <s>]
                             [--no-canary] [--hold]
tacctl device config shapes [--show <hash>] [--json]
tacctl device config shapes seed   <name> [-y]
tacctl device onboard <address> [--name <name>] --login <local-user>
                             [--host-key SHA256:<fp>] [--legacy-ssh] [--check]
                             [--section <list>] [--json]
tacctl device collect <address>... | --discovered  [--login <user>]
                             [--register] [--legacy-ssh] [--json]
tacctl device sync   (<selection>) [--apply] [--overwrite] [--json]
tacctl device config pull|diff|plan ... --login <local-user>
tacctl device add <name> <address> ... --pull
tacctl device location|description|address|config-syntax <name> <value> [--apply]
```

**Why the verb sits under `device config`:** `device config` is the
managed configuration read and plan (`show`, `pull`, `diff`, `plan`,
`list`, `forget`); `apply` is the step that follows `plan`, the same
planner's statements typed by the tool instead of pasted by a person, so the
chain reads `pull`, `diff`, `plan`, `apply`. It is the one write under the
word: it is the superuser's, it takes the review prompt and the confirmed
commit, and `--check` stops before the commit (the tier note of `device
config` says so). `onboard`, `collect` and `sync` are registry acts that log
in, so they sit directly under `device` like `add` and `discover`. **Why `apply --confirmed` and not
a `batch` verb:** the batch is the same transaction with one difference,
the gate (only shapes confirmed on another device, the rest skipped); a
flag says that, a second verb would duplicate the options and the man
page. The helper's `rollout --check` is `device config apply --check`;
its `status` is the
`APPLIED` column of `device config list` and the `Configuration` row of
`device show` (D85's shape); its `archive` is dropped (D138: no raw output
is kept). **Output shape:** the pull's per-device line and summary [V:
`device_config_view.go`], the phases of D84 in the line (`checked`,
`committed, verifying`, `confirming`), the result words of §3.2; `--json`
one object per device and phase. **Exit status** (the batch's [V:
`batch.Exit*`]): 0 every device applied, checked or had no change; 1 any
device failed, rolled back or is pending; 2 wrong arguments, or with
`--exit-code` a check that found a change; 130 interrupted.
*Alternatives:* everything under `device config` (above); a top-level
`apply` family (the act is a device's); `device onboard` as `device add
--onboard` (one verb would hold a registration, two passwords and a
transaction behind one flag).

### D131. The CLI transaction: one exclusive session, held

The Junos transport opens one `devssh` shell session (the shell channel
with the prompt detector [V: `cli.go` `openShell`], which 0.2.9 teaches the
configure-mode prompt: `^\S+@\S+[>#] $` after a `[edit...]` line, and the
`{master:0}` lines a switch prints before each prompt are already dropped
[V: `read`]) and keeps it from `configure exclusive` to the confirming
`commit`, while a second connection makes the fresh login of the
verification. The steps, each a method of the transport and a state of
§3.1:

1. **Pre-flight** over an exec channel, as the pull: `show version` (the
   reported hostname against the registry: the name, its first label, or
   the registry's `hostname` field or its first label, the tolerance of
   backlog §3d; another name is `failed: calls itself '<x>'`), `show
   system commit` typed in a shell session, whose prompt carries the
   pending marker (the line `# commit confirmed will be rolled back in N
   minutes` before the `{master:0}`/`[edit]` line of every session while a
   commit is pending [L2]; entry 0's `rollback in` label is not one, a
   `commit check` confirms without an entry): `failed: a confirmed commit
   is pending until <time>; nothing was sent`, because a `commit check`
   from any session confirms it [L2]), `show cli authorization` (the class;
   `Confirms()`).
2. **Read**, as the pull (the record's pull part is refreshed), and the
   delta recomputed; in Phase B a delta that is not the reviewed one is
   `failed: the device changed since the review` (D83).
3. **Gate** (`SharedDirty`): a throwaway shared `configure`, `show |
   compare | no-more`, `exit`; `Users currently editing the configuration`
   or any `+`/`-` line or `changed but not committed` is `failed: other
   editors or staged changes` [S: L5; the helper's `staged_gate`]. The gate
   reads and owns nothing: an exclusive session's `exit` would discard a
   stranger's staged work, so the dirtiness is read before exclusive is
   taken.
4. **Open**: `configure exclusive` only (a private session refuses `commit
   confirmed` [L5]); any text but the warning, `Entering configuration
   mode` and the configure prompt fails closed (`locked by <user>`, the
   holder parsed from `error: configuration database locked by:` and the
   next line; `database modified`) [L1].
5. **Load**: every statement of the delta on its own `Run`, so an error is
   attributed to its line; the planner's lines carry the secret values
   (D80) and the transport's command log elides them. Any line of the error
   table (§5, the helper's `ERROR_WORDS` as data, matched per statement
   output and never against a `show | compare`) is `failed: load: <stmt>:
   <msg>` after `rollback 0` and `exit`. The one tolerated answer is
   `warning: statement not found` to a `delete` (idempotent [S]): counted,
   shown in the review, never a failure.
6. **Compare**: `show | compare | no-more`; the text is parsed (§5
   `CompareText`); empty is `no change` (`rollback 0`, `exit`, nothing
   committed, the record refreshed).
7. **Check**: `commit check` must print `configuration check succeeds`
   [S: the helper]; anything else is `failed: check: <msg>` after the
   discard. **`check` ends here**: `rollback 0`, `exit`; the record is
   `checked`, with the shape (D135).
8. **Confirmed commit**: `commit confirmed N comment "tacctl rollout <id>
   by <user>"` with N = `device.apply.confirm_timeout` (D140). Required
   text: `configuration check succeeds`, `commit confirmed will be
   automatically rolled back in N minutes unless confirmed`, `commit
   complete`, and the banner in the prompt after it [L1]. Any other text:
   the state is read before it is named (D132).
9. **Verification** on a second connection, as the invoking user (in
   `onboard` as the user's own TACACS+ name, D136): a fresh login through
   the device's own login path; `show system commit` with the banner
   (pending, entry 0 tacctl's commit); `show cli authorization` (the class
   lands); the **landed compare** `show configuration | compare rollback 1
   | no-more` in operational mode [L3], normalised (D135; a `/* SECRET-DATA
   */` value compares by structure; a statement the delta does not explain
   fails and is never quoted) and equal to the compare of step 6; the
   **convergence read**: the pull's read command on the same session, the
   sections compared: every planned section must lack nothing (`-` lines
   are `verification failed: <section> still lacks <stmt>`). A refusal of
   the fresh login is a verification failure, never a rejected password
   (D82 reused: the password worked a minute before; the cache is not told
   to forget and the batch does not stop for it). The optional `--hold`
   (D134, Q2) sits here.
10. **Window rule**: the confirm needs at least 60 s left of the window
    (the helper's 45 s); with less, nothing is typed and the device rolls
    back (`rolled back: the window ran short`).
11. **Confirm**, in the held exclusive session: `commit comment "tacctl
    apply confirm <id> by <user>"` must print `commit complete`. The
    exclusive lock held since step 4 is what keeps a stranger's staged work
    from riding along and a stranger's `commit check` from confirming for
    us; the helper's before-confirm gate is therefore not repeated. If the
    held session was lost meanwhile the confirm is **not** made from a new
    session: the device is left `pending until <time>` (D132) and the line
    says so.
12. **Record**: `show system commit` over the second connection (no
    banner; the entry above tacctl's commit is the confirm), the record
    `applied`
    with the shape, the commit sequence and time, the sections, the counts
    (§6); both sessions closed.

**Cancel** (`Cancel()`): every failure after step 8 types `rollback 1` and
`commit comment "tacctl rollout cancel <id>"` in the held session, which
commits the previous configuration and ends the pending commit at once
**[L2]**, only when the prompt after `rollback 1` still shows the banner
and its compare is the inverse of the commit; the fallback is the device's
own expiry, which the record then says. **Why exclusive:** a private
session refuses `commit confirmed` **[L5]**, and only an exclusive
session refuses cleanly when anyone has the configuration open and keeps
everyone out until the confirm. **Why not a session per step** (the
helper's way: a session for the check, one for the apply, one for the
confirm): the lock between them is lost, and the confirm must then be
gated again against a candidate that may have changed, which is a race
the helper acknowledges. *Alternatives:* the private session of D78 (the
refusal above; a stranger could confirm with `commit check`); no held
session and a re-dial for the confirm (the race); `load set terminal` for
the load (every line answered at the end: no attribution; the helper's L2
note); NETCONF (D129).

### D132. The truth about a pending confirmed commit over the CLI

Over NETCONF a dropped session rolls back at once [S]; over the CLI the
device rolls back at expiry and only at expiry [S: spike (d)], and any
`commit` or `commit check` by anyone confirms it. So the driver never
claims "nothing committed" without reading: after any failure between the
confirmed commit and the confirm, `show system commit` is read in a shell
on the second connection (or a re-dial) with the banner of its prompt, the
only pending marker [L2]: no banner and entry 0 unchanged from the
pre-flight is `failed: nothing was committed` (the helper's "NOTHING WAS
COMMITTED" rule); the banner with tacctl's commit at entry 0 is `pending
until <time>` with the record `result=pending until=<time>`; no banner
with tacctl's commit still at entry 0 is `applied by someone else's
commit` (a `commit check` confirmed it and left no entry; recorded
`applied`, reason given); `by root via other` directly above tacctl's
commit is rolled back (expired); a read that fails is `unknown: check the
device; the window ends at <time>`. A record that
says `pending` makes `device config list` and `device show` say so in red
until the next verb that touches the device reads `show system commit`
and settles it (`rolled back at <time>` or `applied`); `device config apply
check|apply` of that device is refused until then with the reason (a
`commit check` would confirm it); the operator's text says **do not type
`commit` or `commit check` on the device before <time>**. The second
Ctrl-C after the confirmed commit (§7) tries the cancel of D131 before
leaving the device pending. *Alternatives:* the NETCONF property promised
for the CLI (false); a `persist`-style design (the CLI has none); refusing
every apply on the server while any device is pending (the helper's
`.pending` rule: only the device itself is at risk from a `commit check`,
so only it is refused).

### D133. Lock-out guards reused, and the allow-list derived from the planner

D81's guards stand as 0.2.5 built them [V: `plan/junos.go` `lo0Check`,
the never-emitted list of D97, the authentication order never empty]. Two
additions. **(1) `--from` is filled by the driver** with `LocalAddr()` of
its own TCP connection (new on `devssh.Client`, D81 (3)), so the planner's
filter guard decides for the address tacctl really connects from, with no
flag; the fresh login after the commit is the proof for the same address.
**(2) The allow-list tripwire** of the helper's `check_region`, generalised
and derived: `plan.CheckRegion` [V: `emit.go`] already refuses anything
but `configure private`, `set|delete|insert`, comments and the wrapper
lines, but it accepts `set` of any hierarchy [V: `junosStatementOK`]. 0.2.9
adds `plan.Allowed(vendor, line) error`, computed from the ownership
tables [V: `owned.go`] and `PlanOrder` [V: `plan.go`]: a statement is
allowed when its path lies under a hierarchy some owned row of a planned
section names, or is one the renderer of that section emits (the sections'
`Lines`), and is **refused** whatever the tables say when it touches
`system root-authentication`, `system services`, `interfaces`, `groups`,
`apply-groups`, `system login user <x> authentication`, `system login user
<the invoking login>`, `system login user root`, or deletes a whole
hierarchy or object the rendering names (`delete snmp`, `delete system
login class <c>` of a rendered class, `delete system tacplus-server`, the
helper's `denyobj`). The driver runs `Allowed` over every line before the
first `Run` and the test `owned_test.go` gains one case per row proving
the row's statements pass and the never-list fails: when a release adds an
owned row (0.2.7 added the system block and had to touch the helper's
regex by hand, B9), the tripwire follows by construction. The helper's
hard-coded class names (`RW-CLASS`, `super-user`) are replaced by "a
rendered class" from the input. *Alternative:* port the helper's three
regexes as they are (a second hand-kept list that drifts, which is what
the tripwire exists to catch).

### D135. Shapes: a typed function of the delta; the canary's rule

**What a shape is.** `plan.Shape(d Delta) (hash string, lines []string)`:
the delta's lines in `PlanOrder`, each secret value elided (already so in
`Line.Shown()` [V]), each device-identity value masked to `<v>` by rule
(`snmp location|contact|description`, `system host-name`, `system login
message`, the community and trap-group labels `<secret:N>`/`<other:N>`
kept as labels), sorted within a section (a Junos release prints
hierarchies in another order, the helper's lesson, and the delta's own
order is the paste order, which is not identity), the section names
included; the hash is SHA-256 of that text, shown as 12 hex characters.
Two devices that need the same change have the same shape; the shape is
what a batch trusts a confirmed apply for. The planner emits one
`delete` per extra statement of an owned object [V: ModeWhole, "every
statement under it ... is deleted"], so the lines say exactly what is
removed and the shape is as specific as the helper's compare-based one.
**Why over the delta and not over `show | compare`:** it is pure, it is
known before any login (`shapes` groups devices from their records with no
device contacted), it needs no parsing of brace text, and it is what the
person reviewed. **The landed check** is a separate, same-device equality:
`plan.CompareText.Parse(text)` turns a `show | compare` or `show system
rollback compare` output into blocks (`[edit path]`, `+`/`-`/`!` lines,
the `{master:0}` prefix and the `uid N;` line dropped, the helper's rules)
sorted by path, and the landed text must equal the checked text (`what
landed is not the change the check showed` otherwise); a test over the
lab captures proves two devices with one shape give one normalised
compare **[L3]**. **Two hash generations:** the helper carried its first
hash beside its second; 0.2.9 stores, per shape, the masked lines and an
`algo: 1`, so a later masking rule re-files every stored shape from its
lines instead of carrying two hashers. **The store:** `/var/lib/tacctl/
device-apply/shapes.json` (0600 root; `{hash: {algo, lines, confirmed:
[{device, at, by, id}], seeded}}`); no secret is in it (values elided), it
is state like the pull records (not in snapshots, listed by `rollback
0.2.8`). **`seed <name>`** records the shape of the device's last `check`
record as confirmed by a person's word (`seeded`), for a device applied
and verified by other means. **The helper's shapes are not migrated:** its
hashes are over compare text, 0.2.9's over delta lines; an installation
that used the helper gets each shape confirmed again by one reviewed
`apply` (one per shape, not one per device), and `shapes` shows which are
new. **The canary (D84 answered):** the shape *becomes* the canary's rule:
in `apply`, the first device of each distinct shape runs alone to
completion (through confirm or rollback) and the devices of that shape
follow only when it applied; `--no-canary` starts them all; `--confirmed`
runs only devices whose shape is confirmed already (the helper's batch)
and skips the rest with `unknown shape <h>: review and apply it by hand
first`. *Alternatives:* the compare-based shape (above); a shape per
section (a batch would mix changes nobody reviewed together); the helper's
hashes recognised (two hashers forever for a format tacctl never wrote).

### D136. Onboard and the one-shot local login

**`--login <local-user>`** on `device config pull|diff --pull|plan
--pull`: the device login is that account instead of the invoking user.
Refused unless the caller is a superuser (the flag's own gate inside an
Engineer verb, as `forget` is [V: `deviceConfigNeeds`]), unless the device
is in the registry with a pinned key, and unless its scope answers it
(`LookupAddr`, the hold's rule); refused with `--all`/`--scope`/`--vendor`
(one device per local login). **The password travels** exactly as the
0.2.4 password does up to the cache and never into it: `askpass.Prompt`
on the tty into a `[]byte` [V]; `terminalPasswords` with the cache client
nil (never `Have`, never `Store`: `Accepted` is a no-op for a local login),
the `PasswordSource` closure hands the string to `devssh` once
(`passwordMemo` clears it at the single send [V]); `Done()` zeroes the
bytes [V: `askpass.Zero`]; the zeroisation promise ends at the string the
ssh library takes, as the 0.2.4 handoff says. Audit: `auth.info device
config pull user=<caller> device=<name> login=local:<account>`. **Root**:
`--login root` is accepted for `onboard` and for `pull|diff|plan --login`
of a device whose record has never pulled as a TACACS+ login; the shell
channel then runs the CLI as the remote command (`devssh.WithCommand("sh -c
'PATH=$PATH:/usr/sbin:/usr/bin:/sbin:/bin; exec cli'")`, the helper's
csh wrapper, fixed text) because root's login shell on Junos is csh **[L4:
the prompt and echo of a `cli` started this way without a pty]**.

**`device onboard <address> --login <local-user>`**, one run:

1. **Identity.** The host keys are scanned [V: `ScanHostKeys`] and shown
   with fingerprints. With `--host-key SHA256:<fp>` the matching key is
   pinned (the `device add` rule); without it, interactively, **one
   question before any login**: `Trust these keys and send the local
   password of '<user>' to 192.0.2.21? [y/N]` (Q1); without a terminal and
   without `--host-key` the run is refused. A key that differs from a
   pinned one (a re-run) is a refusal (`devssh` ErrHostKey [V]). The ssh
   banner is read on the dial (`Client.ServerVersion()` [V]); a handshake
   that fails on algorithms is retried with the legacy set and the device
   is registered `--legacy-ssh` [A: `devssh` tells that failure apart,
   WP14.1].
2. **Pre-flight** as the local account: `show version` (Junos, hostname,
   release), `show system commit` (no pending commit), `show configuration
   system | display set | match "tacplus-server|radius-server"`: a server
   present is `refused: the device already has a TACACS+ or RADIUS server;
   it is reached by the normal flow (device add, device config pull)`, the
   only blocker (backlog: SNMP, classes, a community are never blockers).
3. **Name and registration.** `--name`, else the reported hostname, else
   (a generic name, `devreg.IsGeneric` [V]) a prompt for one. `device add
   <name> <address> --vendor juniper [--legacy-ssh]` through the same code
   (the keys of step 1 pinned; the key the login used must be among them,
   `devreg.CrossCheckKeys` [V]). The device's own `snmp location`, `system
   host-name` (+ `domain-name`), `snmp description` fill the registry's
   empty fields through `device location|hostname|description` (the
   helper's bootstrap; a set field is never replaced). A device registered
   by an earlier onboard whose record never pulled as TACACS+ is taken
   again (the helper's `reuse` rule); any other registered address is
   refused with the normal flow named.
4. **Pull as the local account** (step 2's session, the pull's read
   command): the record is written with `login=local`; the sections read
   `missing` for everything tacctl renders.
5. **Plan** by the ordinary planner: the complete first-time region, the
   same compare, owned rows, labels, back-out; D97's refusals apply; the
   device-specific values the rendering needs come from the registry
   fields just filled (backlog's "prompted at plan time" is answered by
   step 3's prompt for a name and the device's own values as defaults; a
   blank value renders the walkthrough's placeholder and the plan lists it
   as unfilled, as today). `set system host-name` is **not** emitted
   (tacctl renders no host-name statement [V: no owned row]; the registry's
   `hostname` field carries the device's name and D131's identity check
   accepts it): a renamed device is the person's step, listed in the
   report.
6. **Check** (D131 steps 3-7) as the local account; `--check` stops here
   (registered, nothing committed).
7. **The review** (D134), then **the user's own TACACS+ password** is asked
   (the ordinary path, cache allowed: it is the invoking user's).
8. **Commit** as the local account; **every session after it is the TACACS+
   login** (with `authentication-order tacplus` the local account is
   refused while the server answers): the fresh login, the landed compare,
   the convergence read, the record; then the confirm in the held local
   session. A fresh TACACS+ login that fails rolls the change back and
   leaves the local account as it was (the bootstrap rule). The local
   account is probed once more after the verification, informationally
   (`the local account still logs in` / `is refused while the server
   answers: expected`).
9. **Break-glass users** with placeholder hashes are never in the first
   plan (D79; the walkthrough's step), and the plan never touches the
   local account (D133).

*Alternatives:* a `--blank` rendering path (rejected by the backlog: two
plan generators); parsing the walkthrough (the helper's fragile part);
storing the local password (never); `onboard` without the register step
(a device must be in the registry for `--login` to be allowed at all).

### D138. Records, state, locking, interrupts, a dead tacctl

**Records** (`devices-config.json`, version 1, fields added, 0.2.8's
reader ignores them): `applied` becomes D85's set: `at`, `by`, `id`
(`tacctl-<yyyymmddThhmmssZ>-<4 hex>`, in the commit comments), `kind`
(`check`, `rollout`, `onboard`, `seed`), `result` (`checked`, `no-change`,
`pending`, `applied`, `rolled-back`, `failed`, `unknown`), `reason`,
`until` (a pending window's end), `shape`, `sections`, `set`, `delete`,
`insert` (counts), `commit` (entry 0's sequence and time after the
confirm), `pre` (per section, the fingerprint before). The pull part is
refreshed by every read the transaction makes. **The shape store** (D135).
**Per-device lock**: `device-apply/locks/<name>.lock`, `flock` for the
transaction (`another apply is running on <name>`); the records store's
own lock [V: `Store.Lock`] around each record write as the pull does. One
writer per server is not enforced: two superusers on two devices are
fine; the same device is refused. **What is not stored:** raw device
output (the helper's `raw/`), the plan text (recomputed; `Delta.Equal`
between the phases is the helper's sha256), the review (one run), any
password, the compare texts (only their normalised equality is judged;
the shape lines are the record). **Snapshots and backups:** `/var/lib/
tacctl` is outside every snapshot [V: `snapshot.go` holds store, tacctl,
devices, snmp, blocks]; `backup restore` leaves the records; `device
forget` removes a device's apply record with its pull record. **Modes:**
the records 0600 root in `/var/lib/tacctl` (0711) as today.
**Interrupts** (§7): the first Ctrl-C stops starting devices and lets a
running transaction finish (through confirm or rollback: a finished
transaction is a known state); the second cancels: before the confirmed
commit `rollback 0` and `exit` are typed on the way out (a short grace,
best effort; the exclusive lock dies with the session anyway), after it
the cancel of D131 is tried and otherwise the device is `pending until`
with the hold's PENDING line printed to stderr (the helper's
`PENDING_MSG`). **A dead tacctl** (SIGKILL, the host): before the
confirmed commit nothing is committed and the exclusive lock is released
with the session; after it the device rolls back at expiry unless someone
commits; the record stays at `committed, verifying` and the next verb that
touches the device reconciles it (D132). *Alternative:* a journal file per
apply (a second store for the same key; `log search` has the audit
lines).

### D139. Concurrency and the batch

Phase A (`check`) runs in the 0.2.4 pool (`min(--concurrency,
device.config.max_concurrency, N)` [V: `PoolSize`]): checks are
independent (each is its own exclusive session on its own device). Phase
B's default concurrency is **1** (the helper's serial batch): an apply is
a write under a window and a person watches one device at a time;
`--concurrency N` raises it to at most `device.config.max_concurrency`,
with the canary by shape of D135 first. `--max N` (default 5) caps the
devices applied in one `--confirmed` run, `--pause <s>` (default
`device.apply.pause`) waits between them, `--max-failures` defaults to 1
(D84), `StopOnAuthFailure` stays for the first login. The password is
resolved once before Phase A (D70); the fresh logins use the same string.
`batch.Options` gains `Canary` (the index set of first-of-shape jobs),
`Pause`, and `Event.Phase` text (`checked`, `committed, verifying`,
`confirming`), `Summary.RolledBack` and `Pending`. *Alternatives:* the pool
for Phase B by default (D84's reading: a fleet applied eight at a time
with a 10-minute window each is a wall of pending commits if the server
blinks); no `--max` (the helper's limit exists for a reason: a batch is
watched).

renders the per-class form for a release older than the row's), so the
plan is right before the device is touched and the convergence read
compares against the same form. What 0.2.9 consumes from 0.2.8 [A: 0.2.8
is not built; the names are the backlog's]: `Record.Release` (the Junos
`set version` line of the pull), the gate table (`devices.VersionGates`:
statement, first release, fallback renderer), and the rule that a device
with no recorded release is rendered the current form. The apply adds
one thing: a **check failure whose only error is a gated statement** (the
fake's `version-gate` knob) is reported `check: <stmt> is refused by this
release (<release>): the gate table renders the per-class form once the
release is recorded; the pull of this run recorded it: run the check
again`, so a device onboarded before its release was known converges on
the second run without a hand edit. *Alternative:* the helper's in-place
rewrite (it rewrote a reviewed plan and re-signed it itself: the review
was bypassed for the new lines).

## 3. The transaction

### 3.1 State machine (one device; `check` stops after CHECK)

```
PREFLIGHT  exec: show version, show cli authorization; shell: show system commit
  │        name mismatch ─────────────▶ FAILED "calls itself '<x>'"
  │        banner in the prompt [L2] ─▶ FAILED "a confirmed commit is pending until T"
  │        Confirms() false ──────────▶ FAILED "cannot commit as this login/vendor"
READ       the pull's read; record refreshed; delta recomputed (Phase B: must
  │        equal the reviewed one) ───▶ FAILED "changed since the review"
ALLOW      plan.Allowed over every line ▶ FAILED "statement outside the planner's
  │        domain" (a tacctl bug: nothing was sent)
GATE       shared configure; show | compare; exit
  │        editors or staged ────────▶ FAILED "other editors or staged changes"
OPEN       configure exclusive (no private mode [L5])
  │        any text but the prompt ──▶ FAILED "locked by <user>" / "database modified"
LOAD       one Run per statement; error table ▶ rollback 0; exit ▶ FAILED "load: ..."
COMPARE    show | compare | no-more ▶ empty ▶ rollback 0; exit ▶ NO-CHANGE
CHECK      commit check ▶ not "configuration check succeeds" ▶ discard ▶ FAILED
  │        ── check ends: rollback 0; exit; record "checked", shape ──
COMMIT-C   commit confirmed N comment "tacctl rollout <id> by <user>"
  │        text ≠ "will be automatically rolled back in N minutes unless confirmed",
  │        or no banner after it ▶ READ-STATE (D132)
  │        (from here the device runs the new configuration under the timer)
VERIFY     second connection, fresh login as the user (onboard: the TACACS+ name)
  │        show system commit (banner; entry 0 = ours); show cli authorization;
  │        show configuration | compare rollback 1 ≡ COMPARE's text (normalised);
  │        the read command; sections lack nothing; [--hold: the typed OK]
  │        any failure ▶ CANCEL (rollback 1; commit) [L2] ▶ ROLLED-BACK,
  │        or expiry ▶ PENDING-UNTIL
WINDOW     < 60 s left ▶ nothing typed ▶ ROLLED-BACK "the window ran short"
CONFIRM    held session: commit comment "tacctl rollout confirm <id>"
  │        session lost ▶ PENDING-UNTIL; text ≠ "commit complete" ▶ READ-STATE
RECORD     show system commit on the second connection; record "applied"
```

### 3.2 What the device and the record look like after each exit

| Exit | Device | Record `applied` | Line |
|---|---|---|---|
| FAILED before OPEN | untouched | `failed`, reason; the pull part refreshed when READ ran | `failed: <reason>` |
| FAILED at LOAD / CHECK | untouched; candidate discarded (`rollback 0`, `exit`) | `failed: load: ...` | `failed: load: <stmt>: <msg>` |
| NO-CHANGE | untouched | unchanged (the last apply stands); pull refreshed | `no change` |
| CHECKED | untouched; candidate discarded | `checked`, `shape` | `checked: shape <h> (<n> set, <m> delete)` |
| READ-STATE: nothing committed | untouched | `failed`, reason | `failed: nothing was committed (<text>)` |
| ROLLED-BACK (cancel worked) | as before; two history entries (ours, the cancel) | `rolled-back`, reason | `rolled back: verification failed (<why>)` |
| PENDING-UNTIL | the new configuration until T, then the device's own rollback, unless someone commits | `pending`, `until`, reason | `PENDING until T: do not type commit or commit check on the device; <why>` |
| APPLIED | the target; entry 0 carries the confirm comment | `applied`, counts, `commit`, `shape`; the shape store gains the device | `applied (aaa,snmp: 7 set, 2 delete) [tacctl-...-3f2a]` |
| UNKNOWN | not readable after the failure | `unknown`, `until` | `unknown: check the device; the window ends at T` |
| First Ctrl-C | a running device finishes its transaction; nothing new starts | as the exit reached | `interrupted: N not started` |
| Second Ctrl-C / SIGTERM | before COMMIT-C: `rollback 0`, `exit` typed best effort; after: CANCEL tried, else pending | `interrupted` or `rolled-back`/`pending` | `interrupted` |
| tacctl killed, the host dies | before COMMIT-C: nothing committed, the lock dies with the session; after: pending until T | the last written state; reconciled on the next run (D132) | — |

Nothing in 0.2.9 can leave a device with a change that no timer and no
record knows about: every commit is a confirmed one with tacctl's comment,
every confirm is read back, and a record that says `pending` stays red
until a read settles it.

## 11. Risks

1. **The transport leaves a confirmed commit pending that something else
   confirms.** Mitigation: the exclusive lock from OPEN to CONFIRM, the
   cancel path, the truthful `pending until` and its red state, the
   refusal of `check|apply` on a pending device, the fake's `commit.drop`
   and the lab items (5), (6).
2. **A line outside the planner's domain reaches a device.** Mitigation:
   `Allowed` derived from the tables with a test per row, `CheckRegion`,
   the command-log assertion, Opus's review of the driver.
3. **A text the parser does not know.** Mitigation: fail closed; L1's
   captures; the fake's texts replaced by captures; the state read before
   it is named (D132).
4. **The local password of a blank device goes to the wrong box.**
   Mitigation: `--host-key`, the one question before any login (Q1), one
   attempt per device, the refusal without a terminal.
5. **Size.** Cut order: `device sync` (the preview table stays as
   `collect`'s), then `device collect` (`device add` + `pull --login` do
   the job by hand), then `--hold`, then the APPLIED column (the show row
   stays). Not cuttable: the transaction, the review, the verification,
   the records, shapes with `--confirmed`, `onboard`, `--login`, `rollback
   0.2.8`.
6. **Shared files** (`device.go`, `device_config*.go`, `tier.go`, docs,
   goldens): serialised in the execution plan.
7. **The 0.2.8 facts are not built yet.** Mitigation: D144 names what it
   consumes; WP14.3 carries a stub (`Record.Release` empty: the current
   form) until 0.2.8 merges into `develop` before `feature/0.2.9` starts.
