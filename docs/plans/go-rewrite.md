## 0. Summary of the recommendation

1. **Strangler, not big-bang.** A Go binary becomes the front door on day one and delegates every command it does not yet own to the untouched bash implementation (`bin/tacctl.sh`, same process environment, same on-disk state). Commands are cut over family by family; the bats suite stays green throughout because delegated commands behave exactly as before. The bash tree is deleted in one package at the end (Phase 4). Justification in §4.
2. **The existing bats suite is the black-box contract — after it is completed.** One harness switch (`TACCTL_IMPL=bash|go`) points `TACCTL_BIN_SCRIPT` at either implementation; ~674 of 1373 tests already drive only the CLI [V §2.2] and run against the Go binary unchanged once the binary reproduces output, exit codes, file modes and external-command behaviour. Several verbs have **no** CLI-level test today (`hash generate|commands`, `user verify`, `config branch|defaults`, the auto-generated-password path, `install|upgrade --branch`, top-level `help`) [V §2.2]; WP0.2 writes characterisation tests for them against bash **before** anything is cut over, so the contract has no blind spots. The ~700 tests that call bash functions are ported to Go unit tests package by package as each package lands, and deleted with the bash tree. Byte-identical goldens (tacquito.yaml, store.yaml, model JSON, device configs, FreeRADIUS files) are the parity proof for rendered artifacts; a differential runner compares both implementations on a command corpus (bash side = the `0.1.16` tag), and a read-only shadow run compares them on the dev server's live state.
3. **Architecture:** one Go module `github.com/rett/tacctl`, cobra command tree with per-command argument parsing that reproduces today's messages, `gopkg.in/yaml.v3` for decoding (what tacquito itself uses [V `/opt/tacquito-src/go.mod`]) plus a small purpose-built PyYAML-compatible emitter for the two files tacctl writes, `golang.org/x/crypto/bcrypt`, an `execx.Runner` abstraction with PATH lookup so the suite's PATH stubs keep working, `go:embed` for templates, unit files, patches and the two Linux client scripts (which stay bash: they run on the enrolled hosts), the backend contract as a Go interface with the TACACS+ and RADIUS modules behind it and `tacacss` reserved.
4. **Distribution:** built on the host from the `/opt/tacctl` clone with the Go toolchain tacctl already installs (1.26.2), vendored dependencies (no network at build), `-trimpath`, version stamped from `git describe`; a real binary at `/usr/local/bin/tacctl`; `bin/tacctl.sh` survives as a ~80-line **self-healing** bootstrap shim: whenever it runs (the 0.1.16 upgrader execs it after a pull, *or* `/usr/local/bin/tacctl` still points at it because the upgrader took the `--branch` path that skips the exec, §5.2) it builds the binary if it is missing or stale, installs it and execs it. On build failure it never touches the installed binary and prints the exact recovery recipe; there is no silent half-state. Rollback to 0.1.16 is a checkout plus the symlink, and `tacctl upgrade --branch` does it on its own when the target tree is a bash release.
5. **Phases:** 0 scaffold and test kit → 1 core packages (parallel) → 2 backend spine and command cut-over → 3 devices, hosts, lifecycle → 4 retire bash, completion, docs, parity proof → 5 live acceptance on the dev server and the test client and release gate. About 31 subagent sessions (§10; Revision 1 said 26 — two packages were split because they covered more than one session of dense bash).
6. **Interactive shell mode** is not scheduled; §8 weighs it and Decision 13 asks the user. The committed design only keeps the door open (commands runnable in-process from a cobra tree).
7. **Test runtime is managed, not hoped for.** The bash suite takes 55 minutes serially; the bash tree does not change during the campaign, so the bash-mode suite runs only when harness or bats files change, and `bats --jobs` (needs GNU `parallel`, Decision 19) cuts the wall clock on the 4-core the dev server (§6.1).

## 2. Parity strategy

### 2.1 Harness switch

`tests/helpers/setup.bash:7` is the single indirection, today an **unconditional** `export TACCTL_BIN_SCRIPT="${TACCTL_SRC}/bin/tacctl.sh"` [V], and 1303 lines in 41 files use the variable — 869 as `run "$TACCTL_BIN_SCRIPT" …`, 34 as `$("$TACCTL_BIN_SCRIPT" …)`, ~45 inside `bash -c 'echo y | "$1" …'` pipes, all plain executions that work for a compiled binary [V subagent grep]. WP0.1 changes line 7 to:

```bash
: "${TACCTL_IMPL:=bash}"            # Phase 4 flips the default to go
case "$TACCTL_IMPL" in
  go)   TACCTL_BIN_SCRIPT="${TACCTL_SRC}/dist/tacctl"; export TACCTL_BASH_IMPL="${TACCTL_SRC}/bin/tacctl.sh"; export TACCTL_TREE="${TACCTL_SRC}" ;;
  bash) TACCTL_BIN_SCRIPT="${TACCTL_SRC}/bin/tacctl.sh" ;;
esac
export TACCTL_BIN_SCRIPT
```

`dist/tacctl` is `make build` output (gitignored). `TACCTL_BASH_IMPL` is where the Go front door delegates not-yet-owned commands during the campaign (default `/opt/tacctl/bin/tacctl.sh` when unset). `TACCTL_TREE` is the source/deploy tree the binary treats as "its" checkout — bash derives `PROJECT_DIR` from the script's own location (`bin/tacctl.sh:52-55`) and tests assert it (`backend_cli.bats:295-301` expects `install build ${TACCTL_SRC}`; the `Using template:` lines embed it) — the Go rule is: `TACCTL_TREE` if set, else `<dir of executable>/..` when that contains `go.mod`, else `/opt/tacctl` (`DEPLOY_DIR`). `tacctl_source_lib` keeps sourcing `bin/tacctl.sh` for white-box tests until those are gone.

### 2.5 Differential runner and shadow mode

`tests/diff/run.sh <corpus>` (WP0.2): for each line of a corpus file (a `tacctl …` command with optional stdin), runs both implementations against two copies of the same fixture state (fresh `TACCTL_*` tmp dirs, same PATH stubs, same `LANG`/`TZ`, `TACCTL_SKIP_SUDO=1`), normalises (ANSI strip, timestamps `\d{8}_\d{6}_\d{3}` → `<TS>`, generated secrets/passwords → `<RANDOM>`; on the Go side via the test knobs of Decision 17, on the bash side via stubbed `date`/`openssl` producing the same values), and diffs stdout, stderr, exit code and the resulting state directory tree (`find -printf '%P %m %s\n'` plus file contents). Corpora: `tests/diff/corpus/{users,groups,scopes,config,backup,store,devices,hosts}.txt`, written per cut-over package from the integration tests' command lines **plus the error paths** (unknown sub, missing arg, bad value, closed stdin, `n` to a prompt) — the differential runner is the cheapest place to catch exit-code and stderr drift, so every corpus has at least as many failing lines as succeeding ones. The bash side is **always the `0.1.16` tag** (`--against 0.1.16`, the runner checks the tag out into a temp dir once per run and uses its `bin/tacctl.sh`), never the working tree, so a corpus result does not depend on which bash files a package happened to touch. The runner is the per-package acceptance tool ("corpus X shows no unexplained diff") and the Phase 4 proof ("all corpora, 0.1.16 tag vs Go").

**Shadow mode on the dev server** (read-only, Phase 5): with the live state, run the read-only verbs under both implementations and diff: `status`, `backend list|status`, `user list|show <u>`, `group list|commands list <g>|privilege list <g>`, `scope list|routing|show <s>|lookup <ip>`, `config show|validate|dump|get …|listen show|loglevel|metrics show|sudoers show|cisco|juniper|wti [--protocol radius]|linux uid`, `host list`, `log tail|failures|accounting`, `backup list|diff`, `store show`, `store import --check <live tacquito.yaml>`, `version`. Secrets appear in `scope show`/`config cisco` output — the diff stays on the dev server and is deleted after. Mutating shadow runs happen on a **copy** of `/etc/tacctl` + `/etc/tacquito` + the raddb in a tmp dir with `systemctl` stubbed, never on the live state.

### 3.2 CLI framework: cobra, with our own argument parsing on the leaves (Decision 2)

- **Why cobra:** shell completion for bash/zsh/fish through the `__complete` protocol with `ValidArgsFunction` for live names [V search: cobra completions and `ValidArgsFunction`], a command tree that a future interactive shell can reuse (§8), wide familiarity for the implementing agents. Man pages are *not* generated from it (Decision 4).
- **Why not cobra's flag parsing on leaves:** tests pin today's messages (`Unknown argument: 'x'`, `Unknown flag: '--x'`, `Unknown option`, family usage blocks, `scope` no-sub exit 0 vs `user` exit 1). pflag's errors and cobra's usage output differ. So leaf commands set `DisableFlagParsing: true` and call `args.Parse(spec, argv)` where `spec` lists positionals and flags (`--hash <v>`, `--scopes <csv>`, `--force`, `-y|--yes`, `--backend <id>`/`--backend=<id>`, …). The same `spec` feeds `ValidArgsFunction`, so completion and parsing have one source of truth. Root sets `SilenceUsage`, `SilenceErrors`, and a `SetHelpFunc` per family that prints today's usage block (`lib/dispatch.sh:198-245`, `users.sh` "User Commands", …) and exits with today's code.
- **cobra defaults that must be switched off** (each one would silently change the contract of §1.2): the auto-generated `help` command (`root.SetHelpCommand(&cobra.Command{Hidden: true})`) and `completion` command (`CompletionOptions.DisableDefaultCmd`, replaced by our own `completion` with the sudo bypass below), the `-h/--help` flags (leaves have `DisableFlagParsing`; the root and family nodes get `DisableFlagParsing` too so `tacctl --help` and `tacctl user --help` reach our dispatcher and produce today's "usage, exit 1"), "Did you mean" suggestions (`DisableSuggestions`), cobra's own `Args` validation and error text, `TraverseChildren`. A family node with no sub-command runs the family's own `RunE` (usage + the family's exit code from §1.2: 0 for `scope|host|store|hash`, 1 for the rest). A table test in `internal/cli` runs every family with no args, with `help`, with `-h` and with an unknown verb and asserts stdout/stderr/exit against §1.2.
- **Hidden commands:** `_completion-names` (as today, runs preflight and the tier gate), `_phase <backend> <install|upgrade|uninstall> <phase> [tree]` (new; drives one lifecycle phase for container drivers and tests; §2.3), `__complete` (cobra's). `__complete` and `completion` run **without the sudo re-exec and never open `/etc/tacctl`** (the completion script runs as the invoking user); live names come through the existing bridge `sudo -n tacctl _completion-names <kind>` exactly as `config/tacctl.bash-completion:49-51` does today [V], invoked from `ValidArgsFunction` through the runner.
- **Exit model:** `type ExitError struct{Code int; Err error}`; `cli.Main` maps `nil`→0, `*ExitError`→its code, any other error→1 after printing `[ERROR] <msg>` to stderr. Packages return `backend.ErrRefused` (3), `backend.ErrAdopt` (10, internal), `lifecycle.ErrFlipStopped` (20) etc. as typed errors so the mapping lives in one table (`internal/cli/exit.go`) and a test enumerates it against §1.2.

### 3.3 YAML (Decision 5)

- **Decoding — decided 2026-10-03 (user, "most future-proof"):** tacctl's own files (`store.yaml`, `tacctl.yaml`) are read with `internal/pyyaml` (written in WP1.3 as `internal/conf/pyyaml`, moved with `internal/py` in WP1.4c), the port of PyYAML 6.0.1's reader/scanner/parser/composer and SafeConstructor order: the same acceptance and the same error text as 0.1.16, no external dependency, and a reader that matches the `yamlpy` writer. Constructs tacctl never writes (aliases, merges, non-string keys, `!!set|omap|pairs|binary`, time-of-day timestamps, ints beyond 64 bits) are refused with position (§3.9). yaml.v3 stays only for files tacquito reads (the legacy `tacquito.yaml` importer and the equivalence check), because tacquito itself uses it. The paragraph below is the Revision 2 analysis, kept for the record.
- **Decoding (Revision 2 text):** `gopkg.in/yaml.v3` (v3.0.1). It is the library tacquito loads `tacquito.yaml` with [V `sudo grep /opt/tacquito-src/go.mod`: `gopkg.in/yaml.v3 v3.0.1`, imported only in `cmds/server/loader/yaml/yaml.go:17`], so the importer and the equivalence check read the daemon's file exactly as the daemon does. The go-yaml repository was archived in April 2025 and v3 receives only security fixes [V web search]; that is acceptable for a decoder of two small, tacctl-written formats, and `goccy/go-yaml` remains the fallback if a defect is hit [A: evaluate only if needed]. Dates: PyYAML turns an unquoted `password_changed: 2026-10-01` into `datetime.date`, which `store_normalize` folds back to a string (`store.sh:400-442`); **yaml.v3 does the same for an `interface{}` target — `2026-10-01` decodes to `time.Time` [V: probe program against the module cache on the dev server]**, so `store.Normalize` formats `time.Time` as `2006-01-02` (dates are only unquoted in hand-edited or legacy files; PyYAML itself writes them quoted, `'2026-10-01'`). Also verified: yaml.v3 reads `0123` as the octal int 83 and `yes` as the string `yes` for untyped targets, both the same as PyYAML's YAML 1.1 resolver [V].
- **Encoding:** a purpose-built emitter `internal/yamlpy` for the two files tacctl writes, because the store fixtures pin PyYAML's bytes (§1.3) and because today's operators see those files. Scope of the emitter: mappings with string keys, sequences, scalars (string, int, bool, null); block style by default; **flow style for a collection whose members are all scalars when `FlowLeaves` is set** (PyYAML `default_flow_style=None`, used for store.yaml); never fold lines (`width=4096` for the store; tacctl.yaml values are short, but the emitter still implements PyYAML's width-80 folding rule for plain scalars to be safe); 2-space indent; block sequences **not** indented relative to their key, as PyYAML emits them (`  permits:\n  - 10.0.0.0/8`; see `/etc/tacctl/tacctl.yaml` on the dev server [V]), which is also where `yaml.v3`'s encoder differs (it indents the dash, and has no option not to) and why its encoder is not used.
  **The quoting decision is ported, not re-invented.** PyYAML's rule is `Emitter.analyze_scalar` (~150 lines of flag computation) combined with the implicit `Resolver` regexes (bool/int/float/null/timestamp/merge/value), and it has corners a from-memory rule misses — a probe on the dev server [V PyYAML 6.0.1]: `'1e3'` stays **plain** (`1e3`, YAML 1.1 floats need a dot), `'1.0'`, `'0123'`, `'0x1f'`, `'1_000'`, `'2026-10-01'`, `'yes'`, `'~'`, `'null'`, `'True'`, `'='`, `'1:2'` are single-quoted, `::1` is plain in block context but `'::1'` in flow, `x,y` plain in block but quoted in flow, `it's` is **plain** (an apostrophe inside a word needs no quoting), `+abc`/`-x`/`a|b`/`a>b`/`$2b$…` plain, `tab\there` double-quoted with `\t`, and **non-ASCII is escaped as `"\xFC"`** (`safe_dump` has `allow_unicode=False`). WP1.1 therefore transliterates `analyze_scalar` and the resolver regexes from `/usr/lib/python3/dist-packages/yaml/{emitter,resolver}.py` line by line, and the emitter returns an error (never guesses) for a scalar outside the verified domain — invalid UTF-8, control characters other than tab and newline, leading/trailing newlines — so a quoting corner can at worst refuse a write, never corrupt one. **Non-ASCII is written with PyYAML's escapes** (`\xFC`, `\u2026`, `\U0001F511`, `\_ \N \L \P`; decided 2026-10-03 on Fable's advice — 0.1.16 carries non-ASCII secrets to the daemons by design and refusing them would strand hosts that hold one), pinned by corpus cases `n01`–`n04`.
  **Write-time self-check (cheap insurance):** every `store.Write` and `conf.Write` parses the bytes it is about to rename into place with the reader of those files (`internal/pyyaml`, since WP1.4c; yaml.v3 before) and compares the result with the in-memory structure; a mismatch aborts the write with an internal error. This bounds the blast radius of any emitter bug to "the command fails", which is the right failure mode for a file holding secrets and hashes.
  **Verification:** a corpus test (`internal/yamlpy/testdata/*.json` → expected `.yaml`) generated once from PyYAML 6.0.1 by `tests/tools/pyyaml-corpus.py` and committed, plus `make test-pyyaml` that re-runs the generator and diffs when `python3-yaml` is present (the dev server has it); the three store fixtures and `golden/tacctl.overrides.yaml` are the integration check. The emitter is ~400 lines plus ~150 lines of ported analysis and the riskiest single piece of parity (§11).
  **Exit ramp (decided at the end of WP1.1, not later):** if the corpus is not byte-clean within one session, the alternative is adopted immediately rather than iterated on — Go writes with yaml.v3's encoder (`SetIndent(2)`, explicit `Style` on leaf collections for flow), the three store fixtures and `tacctl.overrides.yaml` are regenerated once by the Go code and reviewed, and the parity proof for the store becomes **semantic** (parse both files, compare structures; the differential runner gains a `--yaml-semantic` switch). Cost of the ramp: one noisy `backup diff` the first time 0.2.0 rewrites a 0.1.16-written store (every line changes style once), which the release notes would explain; rollback to 0.1.16 is unaffected because PyYAML reads any valid YAML. Decision 5 records both.

### 3.4 Hashing (Decision 6)

`golang.org/x/crypto/bcrypt` (`GenerateFromPassword(pw, cost)` with `cost` = `bcrypt.cost` from tacctl.yaml, clamped 10..14 as today, `conf.sh:1044-1072`). Go emits the `$2a$` prefix [V `x/crypto@v0.45.0/bcrypt/bcrypt.go:57-58`: `majorVersion='2'`, `minorVersion='a'`]; python-bcrypt 3.2.2 emits `$2b$` [V probe on the dev server; `users.sh:25-29`; `hash.bats:146-150` checks `^\$2b\$10\$`]. `$2a$` and `$2b$` denote the same algorithm for passwords tacctl accepts (≤72 bytes; `validate_password_strength` enforces a minimum, and the Go code adds the 72-byte maximum because `GenerateFromPassword` returns `ErrPasswordTooLong` above 72 bytes [V `bcrypt.go:85-97`]; python-bcrypt silently truncates, so a >72-byte password is the one input where 0.1.16 and 0.2.0 differ — §3.9 lists the new, explicit refusal). tacquito's authenticator uses the same package (`golang.org/x/crypto v0.52.0`, `cmds/server/config/authenticators/bcrypt/bcrypt.go:22` [V `sudo grep`]). **Recommendation:** rewrite the prefix to `$2b$` on generation so stored hashes, `user show` (`Hash type: $2b$12$`), the RADIUS `Crypt-Password` lines and the hash tests stay as they are; verification accepts `$2a$`, `$2b$`, `$2y$` as today (`users.sh:49,55`, `store.sh:121`). Cross-checks in the acceptance phase: a Go-generated hash is verified by `python3 -c 'import bcrypt…'` in `make test-pyyaml`'s sibling `make test-crypt`, by tacquito on the dev server (TACACS+ login) and by FreeRADIUS (`radtest`, libxcrypt), see WP5.1. `tacquito-hashgen` keeps being built and installed for parity (`tacacs.sh:2633-2644`) though tacctl never calls it [V].

Random values: `crypto/rand`; secrets keep today's shapes (`openssl rand -base64 24` → 32 base64 chars; `-hex 16` → 32 hex; generated passwords `-base64 18` → 24 chars) so the length checks and the `Generated secret:` lines are unchanged.

### 3.5 Privilege, tier gate, prompts

- **Re-exec:** `cli.Main` reproduces `bin/tacctl.sh:37-47`: not root, `TACCTL_SKIP_SUDO!=1`, first arg ∉ {`hash`, `__complete`, `completion`} (the last two are new, §3.2) → `syscall.Exec(sudoPath, …)` with `SSH_AUTH_SOCK=…` inserted as a sudo command-line assignment for `host` exactly as `:43-44` does (and for `shell` if §8 is ever adopted). `umask(077)` first thing (`:48`). The command path passed to sudo is `os.Executable()` (symlinks resolved): for the installed binary that is `/usr/local/bin/tacctl`, which is what the sudoers rules name (`dispatch.sh:263,402`; sudo matches command path by basename then inode [A], so a path to the same file matches either way); bash passes `$0`, which through the symlink and `secure_path` is also `/usr/local/bin/tacctl`. `sudo` is found via `exec.LookPath` (the two `completion.bats` stubs of `sudo` rely on PATH lookup).
- **umask and modes:** with `umask 077` every `os.WriteFile(path, data, 0644)` yields 0600. Rule for all packages: **create, then `os.Chmod` to the intended mode** (0640/0644/0440/0750/0755 per §1.2/§2.2), never rely on the mode argument; `os.Chown` to `tacquito:tacquito` is best-effort as today (`chown … 2>/dev/null || true` at 24 sites), resolving the uid with `os/user.Lookup` — pure-Go `/etc/passwd` parsing under `CGO_ENABLED=0`, which is correct because the account is created locally by `useradd` [V `tacacs.sh` account phase].
- **Signals and children:** `signal.NotifyContext(SIGINT, SIGTERM, SIGHUP)` at the top; packages take the context and clean staging dirs on cancellation (bash's `trap EXIT` does that today, §1.6). While a child that owns the terminal runs (`ssh -t`, the tacquito load-smoke, `diff --color`), the parent ignores SIGINT and returns the child's exit status, as bash's `wait` does; a child's exit 130 is passed through (`host` relies on the remote `trap 'exit 130'`).
- **Tier gate:** `tier.Caller()` = `dispatch.sh:38-61` verbatim (SUDO_USER, `id -nG` via the runner, name regex, `model.UserPrivLvl`), `tier.Permits(tier, cmd, sub)` = the table at `:70-90` (note: `help` is **not** in the allow-list, so a tier user running `tacctl help` is denied before reaching the usage — reproduce), `emit_tier_sudoers` text byte-identical (`tiers.bats` checks the two against each other; a Go test keeps doing so, and `golden/sudoers.tiers` pins the bytes). Denials log through `logger` as today. The tiers file is **not** rewritten on upgrade (the installed one on the dev server predates the `backend list|status` lines [V]) — parity, not a bug to fix here.
- **Prompts:** `ui.Confirm(prompt) bool` reads a line from **stdin** (never `/dev/tty`: 40 tests feed `<<< "y"`, 33 pipe `echo y |`, 7 use `< /dev/null` [V]); EOF/closed → false; the yes-set is per call site (`^[Yy]` vs exactly `y|Y`, see §1.2 notes) and the parser spec records which. `ui.Password(prompt)` implements `read_password_masked` (`users.sh:100-122`): `read -rsn1` on stdin, so a raw-mode byte loop with `*` echo and backspace when stdin is a terminal (`golang.org/x/term`), plain line read otherwise, prompt on stderr; EOF or empty → the auto-generate path where today's code has it (`users.sh:161-180`), including the `Generated password:` line on stderr.
- **Preflight:** `app.Preflight()` = the 0.1.16 rule (store present, or legacy `tacquito.yaml` present when there is no store; Decision 11d) minus the `python3 -c "import bcrypt"` check, which is the one remaining deviation (§3.9).

Without the tag the three variables are not read at all, so a production binary has no clock override, no RNG override and no fault injection reachable from the environment — a cheaper guarantee than arguing that sudo's `env_reset` would strip them. `TACCTL_SKIP_SUDO` stays an ordinary env check (it is harmless as root and the tests need it). The knobs are read in `internal/app/knobs_testknobs.go` only and listed in `tests/README.md` as test-only.

`ip -4 route get 1.0.0.0` stays exec: the stub's `src 10.0.0.42` feeds eight device goldens and dozens of assertions in six files, and it is the correct way to ask the kernel. `id -nG` stays exec for the tier gate (NSS-correct, 26 stubbed tests). `logger` stays exec (audit lines; `tiers.bats:135` asserts the call).

## 4. Strangler vs big-bang

**Recommendation: strangler by command family behind a Go front door, with the bash tree kept untouched as the oracle until Phase 4.**

Why the code allows it:
- Every tacctl invocation is a separate process and all shared state is on disk (`store.yaml`, `tacctl.yaml`, `rendered.json`, snapshots, registry files); the in-process caches (`_TACCTL_CFG_CACHE`, `_TACCTL_MODEL_CACHE`) never cross an invocation [V `conf.sh:122-125`, `model.sh:35-61`]. So a Go process that owns `user *` and a bash process that owns `scope *` can alternate on the same state with no coordination beyond the file formats — which the goldens pin byte for byte.
- The bash dispatch is a flat `case` on the first word (`bin/tacctl.sh:111-208`); delegation is "`syscall.Exec` `$TACCTL_BASH_IMPL` with the same argv and the **unmodified** environment" — exec, not a child process, so stdin, the tty, signals and the exit code are bash's own and nothing in Go sits between the operator and a prompt. The Go front door runs the sudo re-exec once (bash then sees EUID 0 and does not re-exec; in tests `TACCTL_SKIP_SUDO=1` is inherited), runs **no** preflight and **no** tier gate for a delegated family (bash runs `enforce_tier` itself, `:109`, and `preflight` per the dispatch), so a delegated command behaves exactly as 0.1.16 down to its `get_version` (bash resolves it from its own tree). Delegation resolves `TACCTL_BASH_IMPL`, else `/opt/tacctl/bin/tacctl.sh`; if that file is missing or is the shim (0.2.0 tree), the front door prints `[ERROR] command not available in this build` and exits 1 — the campaign state in which that can happen is a dev checkout without `TACCTL_BASH_IMPL`, never an installed host.
- Hazard: both implementations write the same files during the campaign. The only coupling that matters is `rendered.json` (sha of rendered artifacts) and the store/tacctl.yaml bytes; both are byte-pinned by goldens before any command is cut over (Phase 1 acceptance), so bash reading a Go-written store or Go re-rendering a bash-rendered `tacquito.yaml` is a no-op (`render_check` → `current`). If the yamlpy exit ramp of §3.3 is taken, the two implementations still read each other's files (both are valid YAML) but the first Go write restyles the store; the campaign then adds "store restyled" to the explained-diff list of the differential runner.

Why not big-bang: the bash tests cannot validate a half-written Go tree, so weeks of work would have no end-to-end signal; subagent sessions need a green suite as their acceptance criterion; and a long-lived branch with nothing runnable makes review impossible for the user. The strangler gives each cut-over package a crisp acceptance: "`TACCTL_IMPL=go` passes `tests/blackbox.list` with these families no longer delegated, and corpus X shows no unexplained diff".

Order of the strangler is dictated by the coupling: nothing can be cut over before `store`/`model`/`conf`/renderers exist in Go (Phase 1) and `StoreApply` plus the two backend modules' render/service verbs exist (Phase 2.1-2.3), because every mutating command ends in `store_apply` and every read command starts in the model. Hence Phase 1 and 2.1-2.3 are pure library work with Go tests and goldens, and the first visible cut-over is Phase 2.4.

What stays delegated longest: `install`, `upgrade`, `uninstall`, `host *`, `config linux *`, `config cisco|juniper|wti`, `backend enable|disable`, `store rollback` (Phase 3). The front door removes delegation in WP4.1 and `delegate.go` is deleted.

## 5. Distribution and the upgrade path

### 5.1 How 0.2.0 is built and installed (Decision 7)

- **Build on the host from `/opt/tacctl`** with the Go toolchain tacctl already installs for tacquito (`GO_VERSION="1.26.2"`, `tacacs.sh:60`; `/usr/local/go/bin/go`). Command (one recipe, in `bin/tacctl.sh --build <out>` and called by both `make build` and `internal/lifecycle/build.go`): `cd "$TREE" && umask 022 && GOTOOLCHAIN=local GOFLAGS=-mod=vendor CGO_ENABLED=0 GOCACHE="${GOCACHE:-/root/.cache/go-build}" /usr/local/go/bin/go build -trimpath -ldflags "-s -w -X main.version=$(git describe --tags --always --dirty)" -o "$OUT.new" ./cmd/tacctl && chmod 755 "$OUT.new" && mv -f "$OUT.new" "$OUT"`. Vendoring means no network and no module proxy trust at upgrade time (today's tacquito build, by contrast, pulls modules from `proxy.golang.org` into `/root/go/pkg/mod` with `GOTOOLCHAIN=auto` [V `go env` as root] — unchanged by this plan); `GOTOOLCHAIN=local` prevents a toolchain download and fails fast with a clear message if the host Go is older than `go.mod` requires; `-trimpath` plus a fixed toolchain gives reproducible binaries (same tree → same bytes), which `tacctl version --long` lets the user verify. **Cost on the host:** first build compiles cobra, yaml.v3 and x/crypto from vendor — on the order of 30-90 s on the dev server's 4 cores and ~100-200 MB in `/root/.cache/go-build` [A: measured in WP0.1 and written into the README's upgrade section]; later builds reuse the cache. Build cache files inherit `umask 022` from the shim; the old process's `umask 077` (`bin/tacctl.sh:48`) is inherited by the exec'd shim [V], which is why the shim resets it.
- **Why not GitHub release binaries now:** the repo has no release pipeline or signing today [V `gh release list` empty]; the host already has the toolchain; the clone is already the update channel (`cmd_upgrade` pulls it, `lifecycle.sh:627-669`). Release binaries (with checksums, built by CI) are a sensible 0.2.x follow-up and Decision 7 asks.
- **Layout after 0.2.0:** `/usr/local/bin/tacctl` is a real binary (today a symlink to `bin/tacctl.sh`); `/opt/tacctl` stays the clone (source for upgrade, for the man page and for `bin/tacctl.sh`); `/etc/tacctl`, `/etc/tacquito`, raddb, logs unchanged. The sudoers aliases keep `/usr/local/bin/tacctl` (`dispatch.sh:263`).
- **Fresh install on a clean host:** README one-liner becomes `sudo bash -c 'git clone https://github.com/rett/tacctl.git /opt/tacctl && /opt/tacctl/bin/tacctl.sh install'`. The shim installs Go if missing (today's steps from `tacacs.sh:2571-2608`: `wget` of the amd64 tarball, `.sha256` fetched from the same origin and compared, `tar -C /usr/local`; it **never removes a newer Go** — today's install does (`:2580`), and `upgrade` never touches Go at all [V `:2929-2942` checks only `-x`]), builds the binary, execs `tacctl install`, which does everything else (`cmd_install` logic ported: deps, clone/patch/build tacquito, service account, seed, units, completion, man). amd64 stays hard-coded as today; §11 lists arm64 as out of scope.

### 5.2 Crossing from 0.1.16 (bash) to 0.2.0 (Go)

What the bash `cmd_upgrade` does [V `lifecycle.sh:584-768` at 0.1.15; **refreshed in WP0.1 against the `0.1.16` tag, where it is `:680-863`: 0.1.16 changed this flow at the exec (item (g), below), the 0.1.15 numbers below map to 0.1.16 in `docs/plans/go-rewrite-refs.md`**]: `--branch` parse (`:586-592`) → `backends_run upgrade preflight` (`:596`; tacacs requires `/usr/local/go/bin/go` to exist, `tacacs.sh:2929-2942`) → `ensure_safe_directory` → `state_migrate` (`:617`) → **tacquito `upgrade build` (`:624`, network: `git fetch` of tacquito, rebuild, `tacquito.bak` kept)** → `cd /opt/tacctl; git checkout -- .` (`:633`) → if `--branch`: `git fetch --tags --force; git checkout <b> || git checkout -b <b> origin/<b>` (`:642-650`) → `git fetch --tags --force` (`:651`) → `LOCAL=$(git rev-parse HEAD)`, `REMOTE=$(git rev-parse '@{u}')` (`:656-657`) → **only if `LOCAL != REMOTE`:** `git pull --ff-only` (`:662`) and then **if `git diff --quiet $LOCAL HEAD -- bin lib` fails: `exec "${DEPLOY_DIR}/bin/tacctl.sh" upgrade`** (`:672-675`, `--branch` is not passed on, nothing is exported) → otherwise `normalize_deploy_perms` (`chmod -R a+rX /opt/tacctl`, `:685`), `ensure_dependencies` (`:688`), `chmod 755 bin/tacctl.sh; ln -sf /opt/tacctl/bin/tacctl.sh /usr/local/bin/tacctl` (`:692-693`), `upgrade config`, `files`, templates, `finish`.

Three facts about that flow decide the design [V subagent walk + own reading]:

- **(F1) The `--branch` path can skip the hand-over — closed in 0.1.16 (Decision 18g).** 0.1.16 records `START_MANAGE=$(git rev-parse HEAD)` *before* the branch switch (`lifecycle.sh:741` at the tag) and re-execs whenever `git diff --quiet "$START_MANAGE" HEAD -- bin lib` fails (`:781-784`), pull or no pull. A host on 0.1.16 therefore always hands over to the new tree's `bin/tacctl.sh` (the 0.2.0 shim) on `upgrade --branch <go branch>`, and WP5.1 takes that single path. What follows is the 0.1.15 behaviour, which a host still on 0.1.15 or older would show if it upgraded straight to 0.2.0 — the case the shim's self-healing is kept for. At 0.1.15, `LOCAL` is read *after* the branch switch. When the branch is new to the clone, `git checkout -b <b> origin/<b>` leaves `LOCAL == REMOTE`, so there is no pull, no `git diff`, **no exec**: the running 0.1.16 process finishes the upgrade against the Go tree — `chmod 755 bin/tacctl.sh` (fine: the shim exists), `ln -sf` (now points at the shim), `upgrade files` (the unit files are still in the tree, §3.7), templates, `finish`. The binary is never built in that run; the **next** `tacctl` invocation runs the shim. This is exactly the path WP5.1 takes (`upgrade --branch feature/go-rewrite` or `--branch develop` when the local `develop` is already at the remote). Revision 1 assumed the exec always happens.
- **(F2) Nothing rolls back.** If the exec'd process fails, `/opt/tacctl` stays at the new HEAD, `/usr/local/bin/tacctl` points (or will point) at the new `bin/tacctl.sh`, and the old process is gone. Revision 1's "the 0.1.15 symlink keeps working" was wrong: the symlink target is the *new* `bin/tacctl.sh`, and the bash `lib/` is no longer in the checkout.
- **(F3) A rebuilt tacquito is not restarted across the re-exec — closed in 0.1.16 (Decision 18h).** At the tag, `upgrade build` treats "sources up to date, patches applied, binary present **and `tacquito.bak` present**" as a binary built before the re-exec that is not running yet: `SKIP_BUILD=false`, `TACQUITO_PREBUILT=1`, the summary's old commit from `TACCTL_UPGRADE_TACQUITO_FROM`, which the building run exports (`tacacs.sh:2980-3000` at the tag); `finish` then restarts and can roll back to the `.bak` (`:3093-3096`). This is parity for the Go upgrade. The 0.1.15 bug, for the record: the old process rebuilds tacquito (`:624`) *before* the pull; the exec'd process finds `LOCAL == REMOTE`, patches applied and the binary present, sets `SKIP_BUILD=true` (`tacacs.sh:2966-2968`), and `finish` restarts only on units/flip/config change (`:3068-3069`); `tacquito.bak` stays because it is removed only after a restart (`:3076`). The code comment at `:2961-2965` describes the opposite order.

Consequences:

**The shim** (`bin/tacctl.sh` in 0.2.0, ~80 lines, shellcheck-clean, idempotent, callable with any tacctl argv):

1. `set -euo pipefail; umask 022`. Must run as root for anything but `--build`; it is (0.1.16 execs it as root; the symlink case re-execs under sudo exactly as `bin/tacctl.sh:37-47` does today, so `tacctl status` typed by an operator the morning after an F1 upgrade still works).
2. Determine its tree `T=$(dirname "$(readlink -f "$0")")/..` and the installed binary `B=/usr/local/bin/tacctl`. **Fast path:** if `B` is a regular file (not a symlink) and `"$B" version --long` reports the commit `git -C "$T" rev-parse HEAD` → `exec "$B" "$@"`. This makes the shim a no-op forwarder once the binary is current, so an operator running `/opt/tacctl/bin/tacctl.sh …` by habit (the README one-liner, muscle memory) does not rebuild every time.
3. Ensure the toolchain: `/usr/local/go/bin/go` present and `go version` ≥ the `go` line of `$T/go.mod`; else install `GO_VERSION` as `_tacacs_install_build` does (`tacacs.sh:2571-2608`, with the checksum); never remove a newer Go.
4. Build with the §5.1 recipe into `$B.new`. **On failure:** print `[ERROR] tacctl 0.2.0 could not be built (see above). The installed command is unchanged.` followed by the recovery recipe `sudo git -C /opt/tacctl checkout 0.1.16 && sudo tacctl config branch <previous branch>` (the previous branch is `git -C "$T" rev-parse --abbrev-ref @{-1}` when the checkout was a branch switch, else `master`), and exit 1 **without touching `$B`**. Whether `$B` is still a 0.1.16 symlink (F1 before the `ln -sf`, or a never-upgraded host) or already a Go binary (a later upgrade failing), it keeps working; only in the F2 case (`ln -sf` already executed, build failing) is the host without a working `tacctl` until the recipe is run — and every subsequent `tacctl` invocation re-runs the shim, re-fails identically and re-prints the recipe, so the state is loud, not silent. Decision 20 asks whether the shim should run the recipe itself.
5. On success: `mv -f "$B.new" "$B"` (atomic; replaces the symlink), then `exec "$B" "$@"`.
6. `--build <out>` is the dev/Makefile entry (build only, no install, no root), so the harness and the deploy share one recipe; `TACCTL_DEV=1` of Revision 1 is dropped.

For the cross-over argv `upgrade`, the Go `upgrade` then continues from wherever 0.1.16 stopped: it re-runs `state_migrate` (idempotent), `backends upgrade preflight|build` (tacquito "up to date"; **the Go `upgrade build`/`finish` reproduce 0.1.16's F3 rule: `tacquito.bak` present with the sources up to date means a binary that is not running yet, so `finish` restarts — and can roll back — exactly as 0.1.16 does**, with no new input for the no-change case), deps, `upgrade config`, `files` (installs the generated completion, man page, templates per the 0.1.16 manifest rule, logrotate), `finish`. Running `tacctl upgrade` again right after is a no-op (0.1.16 item (c), enforced by test in both implementations).

**0.1.16 companions (Decision 18) — both shipped in 0.1.16** (see F1 and F3 above; the recommendation as written:) (g) read `LOCAL_MANAGE` **before** the `--branch` checkout (move `:656` above `:642`), so a branch switch always counts as "management scripts changed" and the exec happens — F1 disappears for hosts upgrading from 0.1.16, and the shim's self-healing is then only a safety net; (h) fix F3 in bash by exporting a marker (`TACCTL_UPGRADE_REBUILT=1`) before the exec and honouring it in `_tacacs_upgrade_finish`, or by the same mtime rule — optional, since the Go side handles it anyway. If (g) is declined, nothing in this plan changes; WP5.1 simply observes the F1 path.

**Go-side self-update** (`lifecycle.Upgrade`): `LOCAL` is taken before any branch switch (the (g) rule); after `git pull --ff-only`, if `git diff --quiet $LOCAL HEAD -- cmd internal vendor go.mod go.sum bin config patches` fails or the binary's commit ≠ HEAD: rebuild via the shim recipe (`bin/tacctl.sh --build`), then `syscall.Exec` the new binary with `upgrade` (mirrors `:672-675`; a guard env `TACCTL_UPGRADE_REEXEC=1` prevents a loop if the remote keeps moving). If the pulled tree has no `go.mod` but has `lib/core.sh` (a bash release, i.e. `tacctl upgrade --branch master` while master is 0.1.16, or a deliberate rollback), the Go upgrader prints `Target branch is a bash release of tacctl; handing over.`, runs `chmod 755 bin/tacctl.sh; ln -sf /opt/tacctl/bin/tacctl.sh /usr/local/bin/tacctl`, and execs `/opt/tacctl/bin/tacctl.sh upgrade`. State formats do not change in 0.2.0 (`store.yaml` stays `version: 1`, `tacctl.yaml` keys unchanged, `rendered.json` unchanged, registry lines unchanged, the 0.1.16 template manifest unchanged), which is what makes both directions safe (Decision 10).

## 8. Interactive shell mode — an open question, not planned work

The user asked whether a `tacctl shell` is practical. It is **not** in any phase or work package below and the release gate does not depend on it; this section gives the trade-offs for Decision 13.

**What it would be (recommended scope if adopted):** `tacctl shell` (not bare `tacctl` on a TTY — that prints usage today and scripts depend on exit 1) opens a prompt `tacctl> ` where lines are tacctl commands without the prefix; tab completion of sub-commands, flags and live names (users, groups, scopes, hosts, backends, listeners) from the same command tree and the same `_completion-names` provider; history in `~/.local/state/tacctl/history` of the sudo-invoking user (0600); `help`, `exit`/`quit`, Ctrl-D. **Not** a network-device-style context (`scope lab` then `show`): every tacctl verb already names its scope explicitly, a mode would duplicate every command's argument handling and invite "which scope am I in" mistakes with secrets involved.

**How it would sit on the existing model:**
- *Privilege:* one sudo re-exec at `tacctl shell` start (same as `host`, carrying `SSH_AUTH_SOCK`); the whole session runs as root. The tier gate is then **re-evaluated per command** from the same `SUDO_USER` (cheap: `id -nG` + one model read), so a user disabled or demoted mid-session is denied from the next line; the sudoers tier aliases would need `tacctl shell` in `TACCTL_RO` for tier users to start it, and the per-command gate remains the real control (as today, `dispatch.sh:9-11`). Audit: the same `logger` lines per command; add one `shell start/stop` line.
- *Execution:* the simplest robust form is **one child process per line** (`/proc/self/exe <args>` with the tty inherited): Ctrl-C reaches the child's process group and cancels the command, not the shell; `log tail` and other streaming verbs behave as today; prompts and masked passwords work because the child owns the tty; exit codes are shown (`[exit 3]`). In-process execution would be faster but needs every command to be cancellable through a context and to never call `os.Exit` — a cheap discipline worth keeping anyway (see constraint below), but the child-process form avoids any new failure mode.
- *Store locking/caching:* nothing changes; each line is an invocation like today.
- *Non-TTY:* `tacctl shell < script` runs the lines in order, stops at the first non-zero exit and returns it (useful for batch provisioning); `echo y |` style prompt feeding works line by line only in that mode because stdin is shared — documented.
- *Libraries:* `reeflective/console` + `reeflective/readline` (cobra-native menus and completion derived from the command tree [V web search]) is the fit if the tree is cobra; `chzyer/readline`, `c-bata/go-prompt`, `peterh/liner` are lighter but their maintenance status is uncertain [A] and completion would be hand-wired. A pty-based test (`creack/pty`) drives the prompt, completion and Ctrl-C in CI.

**Costs:** ~1,000-1,500 lines plus tests; 3-4 subagent sessions; one more dependency cluster to vendor and keep patched; a second entry point to document (README, man, sudoers tiers); a security review of running an interactive root shell-like loop (argument injection is not a concern because lines are tokenised by the same parser, but history files must not capture secrets typed as arguments — `scope secret set <value>` would land in history; mitigation: do not record lines containing `secret set`, `--hash`, or treat history as opt-in).

**Pros:** faster iteration for operators doing many changes, completion without installing the bash completion file, batch mode. **Cons:** small user base for the feature today, root-level long-lived session, more surface to keep at parity, delays a release whose point is parity.

**Recommendation:** defer to 0.2.x. The only constraint it places on 0.2.0, and which §3.2 already adopts for other reasons: the command tree is cobra and every command is runnable in-process through `cli.Run(ctx, args, stdio) error` without `os.Exit`, so a shell can be added without touching the commands. **This awaits the user's decision (Decision 13).**

- **Never run anything against the production host.** Live checks only on the dev server (this machine) and `client`, only in WP5.x, snapshot first, throwaway accounts `gotest*` removed afterwards.
- **Do not `git commit` or `git push`** (Decision 12 decides who commits and when); stop at the working tree and report a file-by-file summary, the list of bats tests ported/deleted/rewritten, and the lint/test commands run with their results.
- `make lint` must exit 0 and the tests must be green at the end of every package: `go test -race ./...`, `TACCTL_IMPL=go make test-blackbox`, and `TACCTL_IMPL=bash make test` **only when the package touched the harness, the Makefile, `bin/tacctl.sh` or a `.bats` file** (§6.1; otherwise say so in the report); no test left failing or skipped; a package that cannot reach green reports why instead of weakening a test.
- Line references in this plan into `users.sh`, `scopes.sh`, `core.sh`, `conf.sh`, `lifecycle.sh` are 0.1.15 numbers marked [refresh @0.1.16]; WP0.1 writes the refreshed table into `docs/plans/go-rewrite-refs.md` and every later package reads from the `0.1.16` tag (`git show 0.1.16:lib/users.sh`), never from the working tree.
- Parity rule: a test failing against the Go binary means the Go binary is wrong unless §3.9 says otherwise; proposing a new §3.9 item is allowed and goes in the report for the user.
- Go: `gofmt`, `go vet`, `golangci-lint` clean; no `os.Exit` outside `cmd/`; no `os/exec` outside `internal/execx`; no `os.Getenv` outside `internal/paths` and the knobs; every exported function in a package touched gets a test or a reason.
- **Worktrees (the stale-commit hazard).** The last effort created agent worktrees from a stale commit and half-rewired packages could not run in parallel [V: two worktrees at `09580ee` still exist, plus the three `fix/0.1.16-*` worktrees of the current release work]. Rules: (1) the user (or the coordinator) removes stale worktrees before the campaign (`git worktree list`, `git worktree remove --force <path>`, `git branch -D worktree-agent-*`), and the 0.1.16 worktrees once 0.1.16 is merged; (2) a package marked "worktree: safe" is started only after every package it depends on is **merged into `feature/go-rewrite`**, and the worktree is created from that merged HEAD — the hand-off states the expected `git rev-parse --short HEAD` and the agent runs `git rev-parse --short HEAD` and `git merge-base --is-ancestor 0.1.16 HEAD` before working, stopping if either fails; (3) packages marked "main tree" run alone; (4) parallel packages own disjoint files (listed in each package); the shared files `internal/cli/root.go`, `Makefile`, `tests/helpers/setup.bash`, `tests/blackbox.list`, `go.mod`/`vendor/` are owned by exactly one package at a time (named below; a package needing a new dependency asks for it in its report, and the next main-tree package vendors it); (5) a package that needs a file it does not own writes the change into its report instead of editing it; (6) a worktree package runs `make build` into its **own** `dist/` (the harness uses `TACCTL_SRC`, so two worktrees never share a binary).
- **Secrets.** No package commits, prints into a report, or leaves in a scratch file any real secret from `/etc/tacctl` or a dev host; shadow-diff output stays on the dev server and is deleted. Test fixtures use the existing placeholder secrets only.
- Executor suggestions follow the precedent: Opus for design-sensitive or safety-critical packages, Sonnet for well-specified ports. Each package is sized for one session.

## 11. Risks, and assumptions to verify

### 11.1 Risks (with mitigation)

1. **PyYAML byte-compatibility** (store.yaml fixtures, `tacctl.yaml` style). Mitigation: WP1.1 ports PyYAML's own scalar analysis instead of approximating it, the corpus is generated from the real PyYAML and re-run on every change where python3 is present, the emitter refuses scalars outside tacctl's domain, every write is parsed back before it is renamed into place, and the exit ramp (yaml.v3 encoder + regenerated goldens + semantic parity) is decided at the end of WP1.1 — never by weakening a test, and never later than that.
2. **Hidden `set -e` semantics.** Bash aborts a command midway where Go would continue (or vice versa), e.g. a failing `logger` or `chown … || true`. Mitigation: every `|| true` and every unguarded command in a ported function is classified in the port (best-effort vs fatal); the differential corpora include error paths and catch exit-code drift.
3. **The cross-over on a live host.** Two paths exist (§5.2 F1: exec into the shim, or the bash upgrade finishing against the Go tree with the build deferred to the next call), nothing in 0.1.16 rolls back, and the symlink ends up pointing at the shim either way. Mitigation: the shim is self-healing and idempotent, never touches `/usr/local/bin/tacctl` until the build succeeded, and prints the recovery recipe on failure; 0.1.16 item (g) removes F1 for hosts upgrading from it (Decision 18); the WP3.3d container rehearsal exercises both paths and the failure cases before the dev server; WP5.1 repeats them live with the failure rehearsal on a copy first; rollback is a checkout plus a symlink and is itself tested (WP5.1 step 5).
3b. **The tacquito restart gap across the re-exec** (§5.2 F3; closed in 0.1.16). Mitigation: the Go upgrade reproduces 0.1.16's `tacquito.bak` rule; a Go test and WP5.1 step 2 check `tacquito.bak` is gone after the cross-over.
4. **ssh/sudo/tty plumbing for `host`** (`sudo -u $SUDO_USER -H env SSH_AUTH_SOCK=…`, ControlMaster, `-t` vs `-T`, remote `trap`). Mitigation: the Go runner builds the same vector; `host.bats` pins it; WP5.2 exercises the test client with an agent-held key exactly as the user does.
5. **Exec-stub expectations in the suite** (~20 tests) and tests that inspect bash source. Mitigation: listed in §2.3/§3.6, rewritten once, documented in `tests/README.md`.
6. **Go toolchain on the host.** Every host that runs tacctl already has `/usr/local/go` because tacquito is built from source there (`tacacs.sh:2571-2608`; `upgrade preflight` requires it to exist, `:2929-2942`, but never checks or upgrades its version [V]). The shim checks the version against `go.mod` and installs 1.26.2 when missing or too old, never removing a newer one. Risk is a host where `/usr/local/go` was removed by hand or is offline: the shim installs it (needs `wget` and network, as the tacquito build already does) or fails loudly with the recipe. amd64 only, as today.
7. **Reproducibility and supply chain.** Vendored deps are reviewed once (`go mod vendor` diff, module list with versions and licences in WP0.1's report); `go mod verify` is a gate item; `GOTOOLCHAIN=local` prevents silent toolchain downloads; `-trimpath` gives identical binaries from identical trees; `tacctl version --long` shows the commit; golangci-lint is pinned by version and its install command printed, never run by `make`. The tacquito build keeps pulling modules from the network as today — out of scope, noted in the CHANGELOG as unchanged.
8. **Parallel packages and stale worktrees.** Rules in §9.0; shared files have a single owner per phase; `go.mod`/`vendor/` are main-tree-only; Phase 1 is the only phase with three-way parallelism and its packages create new directories only; every worktree verifies its base commit before working.
9. **Scope creep.** Everything that is not parity is in §3.9 or deferred (release binaries, shell mode, arm64). The release gate measures parity, not features. The 0.1.16 items are parity by definition.
10. **Time.** 28 sessions plus contingency; the renderers and lifecycle have the most hidden detail. The strangler keeps a shippable state at every package boundary, so the campaign can pause without a broken `develop` (feature branch, Decision 12). The test-runtime rules of §6.1 keep a package's verification under ~30 min.
11. **golangci-lint availability.** Not installed on the dev server [V]. `make lint` pins a version and prints the install command; the user installs it once (`curl -sSfL https://golangci-lint.run/install.sh | sh -s -- -b "$(go env GOPATH)/bin" v2.x` [A: current v2 line, pick the latest at WP0.1]). Until then `make lint-go` with `gofmt`+`go vet` is the minimum and the gate requires the full lint.
12. **Secrets in argv and logs (pre-existing, unchanged, stated so nobody "fixes" it mid-campaign).** `scope add --secret <v>`, `scope secret <s> set <v>`, `user add --hash <h>` put the value on the command line, where `ps` and **sudo's own log line** (`/var/log/auth.log` records the full argv of every sudo command) can see it; the Go re-exec through sudo keeps that exactly as today. Go's `logger` audit lines carry names only, as bash's do (`users.sh:492-694`, `linux_hosts.sh:956,1051` [V]). A `--secret-file`/stdin form is a 0.2.x candidate, not a 0.2.0 change. Child-process argv never carries a secret (the Go test over the exec recorder, §2.3).
13. **Test knobs in a root binary.** Closed by the build tag (Decision 17): the installed binary has no knob code; the harness binary does and says so in `version --long`.
14. **Parallel bats hides an ordering bug.** `--jobs` could mask a test that depends on a previous test's side effect only when run serially — the reverse (flaky under parallel) is the real risk. Mitigation: WP0.1 runs the bash suite both ways once and records both results; the gate's final run (WP4.3) is serial.
15. **Cobra defaults leaking into the contract** (`help`, `completion`, `-h`, suggestions, arg validation). Mitigation: §3.2's switch-off list and the family table test in WP0.1, which fails the moment a default reappears.
16. **Characterisation tests written against bash behaviour that 0.1.16 then changes.** WP0.2 runs after 0.1.16 is tagged and tests the tag; any later 0.1.17 behaviour is out of the parity baseline by definition.

### 11.2 Assumptions to verify [A]

1. ~~bcrypt prefix and 72-byte limit~~ **[V in Revision 2]**: `x/crypto/bcrypt` emits `$2a$` (`bcrypt.go:57-58`), returns `ErrPasswordTooLong` above 72 bytes (`:85-97`); tacquito's authenticator uses the same package (`x/crypto v0.52.0`). Still to confirm in WP1.2: `CompareHashAndPassword` accepts `$2b$` and `$2y$` inputs (it parses the minor version byte; `$2y$` [A]).
2. ~~yaml.v3 and bare dates~~ **[V in Revision 2]**: an unquoted `2026-10-01` decodes to `time.Time` for an `interface{}` target; `store.Normalize` formats it `2006-01-02`.
