## 0. Scope

In:

1. A NETCONF service setting for Junos devices: `enable`, `disable` or
   `leave`, per scope with a per-device override (D145-D148).
2. Apply over NETCONF as the second transport of D129: `device config check`
   and `apply` and their shapes and batch run over NETCONF where the device
   offers it, with the driver unchanged (D149-D151).

Out (not in 0.2.10):

- `device config rollback` from the device's commit history (D86 of
  `apply-deferred.md`; **(user)**, stays deferred; the records keep what it
  needs).
- Device accounts, break-glass rotation and unattended drift detection:
  **on hold**, their rows stay in `backlog.md` section 0.
- IOS and WTI apply, ASA (`asa-deferred.md`).
- Anything on the NETCONF transport for `onboard`, `seed` and `collect`
  writes: a blank device has nothing enabled yet, so they stay on the command
  line (D150).

## 1. Decisions

### D145. The setting: three states, layered

`netconf` is a per-scope state with a per-device override, layered as the
SNMP settings and the blocks are (device value, else scope value, else the
default):

| State | Rendered and planned | Compared |
|---|---|---|
| `leave` (default) | nothing | nothing (today's behaviour) |
| `enable` | `set system services netconf ssh`, or the statements of the limits that are set (a limit's statement creates `ssh`, and the device prints no bare `ssh` beside it) | the statements, as any section |
| `disable` | `delete system services netconf` | the subtree is absent (D146) |

Verbs (superuser, as the other settings; names settled with the man page):

- `scope netconf <scope> [show | enable | disable | leave]`, with
  `--connection-limit <n>` and `--rate-limit <n>` on `enable` (1 to 250
  [A: the Junos reference, no lab run]; `none` removes one).
- `device netconf <name> [show | enable | disable | leave | clear]`;
  `clear` removes the override.

The value lives where the SNMP overrides live [V: `scopes` and `devices`
stores]; a scope with no value reads as `leave`. Cisco and WTI devices:
`enable`/`disable` on a scope is accepted (the scope may mix vendors) and
applies to Junos devices only; a per-device value on a non-Junos device is
refused with the reason (`netconf-yang` is not designed, WTI has none).

*Alternatives:* a boolean (cannot say "do not touch", which is every
device's state today); a flag on `apply` (hides a decision in a run; the
state belongs to the scope as every managed section does).

### D146. Rendering and comparing an absence

Today the `netconf` section is rendered commented and `Managed` leaves it
out [V: `devices/managed.go`]. With `enable` the section carries the
statements above and is a normal section (pull, diff, plan, apply, backout
by the existing rules). `disable` is the first managed **absence**: the
section is `Section{Name: "netconf", Absent: true}`; the comparison reports
a `+` line for every statement the device has under `system services
netconf` (so `diff` says `differs`), and the planner emits
`delete system services netconf` as one statement, the only whole-subtree
delete of a hierarchy outside tacctl's ownership tables (D147). A device
that already lacks the subtree is `ok`. The pull's NETCONF probe result
(`hello ok`, `port closed`) is unchanged and independent.

### D147. The allow-list admits exactly these statements

`plan.Allowed` (D133) gains, and only for a device whose effective state is
not `leave`:

- state `enable`: `set system services netconf ssh`, `set system services
  netconf ssh connection-limit <n>` and `... rate-limit <n>` (n a whole
  number, 1 to 250), each only when the rendering holds that statement;
- state `disable`: `delete system services netconf`, only when the rendering
  expects the hierarchy to be absent.

The delete of a limit is **not** admitted (WP15.1 narrowed the first draft
of this list): a limit the setting states none of is the device's own and is
kept, and a limit with another value is replaced in place by its `set`.

Everything else under `system services` stays refused whatever the tables
say (`ssh`, `web-management`, `telnet`, `netconf traceoptions`, a port,
`rfc-compliant`, ...): the generated `owned_test.go` case for the row proves
the passes and the never-list, as D133 requires. A statement under
`system services netconf` is always typed over the command line (D148), so a
`disable` never cuts the session that carries it.

### D148. A change to the NETCONF service always goes over the command line

The confirmed commit is held on the session that makes it and proved by a
fresh login (D131, D82). `delete system services netconf` ends the service
the verification and, over NETCONF, the held session depend on; `enable` has
no NETCONF to run on. So a delta containing any `system services netconf`
statement runs over the Junos command line whatever the transport setting
says (D150), and its verification is:

- `enable`: after the confirmed commit, a fresh ssh login as the user with
  the `netconf` subsystem and a `<hello>`; a refused hello is a failed
  verification and the window rolls it back (D132, as the 0.2.9 fresh login
  does);
- `disable`: after the confirmed commit, the fresh login over the ordinary
  command line (the AAA path) must succeed, and a NETCONF probe must now
  answer `port closed` or `no hello`; a hello still answering is a failed
  verification (the statement did not take effect).

A delta that mixes the NETCONF statements with other sections is one
transaction over the command line (D131 already types any statement set).
The record's probe field is updated from the verification's result, so
`device check` and the next apply see it at once.

*As built (WP15.4b):* `Input.VerifyService` runs in the driver's
verification after the fresh login's class check and before the landed
compare; its error fails the verification (`the NETCONF service: ...`) and
the existing rollback path takes it. The probe is `devapply.ProbeNetconf`
(a fresh dial, then the subsystem and hello): `ErrNoSubsystem` is `port
closed`, `ErrProtocol` is `no hello`, and every other error (the dial, the
login, a timeout, a session closed before the hello) is a failed proof, not
a pass; whether a real Junos device that has had the service deleted
answers one of the first two words, and not a closed session, is item N6.
The probe is made on its own login rather than through the verification's
fresh login, which is the command line's. The record's probe is written
only when the change is applied (`keep`), from the proof; a failed proof
says what the record's probe stays. The line and the JSON carry the proof
(`NETCONF verified: hello ok|not answering`, `service_proof`). The fake
device follows its committed configuration with `netconf.follow` and keeps
answering after a delete with `netconf.disable.noeffect`. A NETCONF
transport words the "no pending commit" reason from its history
(`NoPendingWord`); the command line's words are unchanged.

### D149. The NETCONF transport

`devapply.JunosNetconf` implements `Transport` over `devssh.NetconfSession`
[V: `internal/devssh/netconf.go`], so the driver is untouched. Mapping:

| Transport method | NETCONF |
|---|---|
| `Confirms()` | the hello advertises `candidate:1.0` and `confirmed-commit:1.0`, and `Login` says the class may commit |
| `RollsBackOnClose()` | **false**: a closed or killed session leaves the confirmed commit pending to the window's end (lab, plan N2; the 0.2.4 spike's "rolled back as the session closes" was a window of seconds, N9) |
| `Open(allow)` | `<lock-configuration/>` (the exclusive analogue; N1 refuted the private session, and `<open-configuration><exclusive/>` is a syntax error on the device), then the compare against the committed configuration must be empty (a staged change is refused and the lock released); `ModePrivate` is `<open-configuration><private/>`. Both answer with an EMPTY reply on success; the allow-list is applied to every statement as in D133 |
| `Load(line)` | one `<load-configuration action="set" format="text">` per statement, or the batch (N3); an error-severity `<rpc-error>` is a load error as the typed texts are today; a `statement not found` warning on a delete is `Loaded.NotFound` |
| `Compare` | `<get-configuration compare="rollback" rollback="0" format="text"/>`, normalised by `plan.ParseCompareFor` |
| `Check` | `<commit-configuration><check/>`; `lock-denied` is `*LockedError{Holder}` |
| `CommitConfirmed` | `<commit><confirmed/><confirm-timeout>S</confirm-timeout><log>...</log></commit>`, S in **seconds** (the window in minutes times 60: the device reads the element in seconds, N9) |
| `Confirm` | `<commit/>` on the same session, with the id as the log |
| `Cancel` | in the held session `<load-configuration rollback="1"/>`; only when the history still shows a pending commit and the compare (`compare="rollback" rollback="0"`) is exactly the inverse of the held session's last compare, `<commit><log>cancel comment</log></commit>` (lab: ends the window at once, a normal entry); otherwise `discard-changes` and nothing committed. Closing the session is not a cancel |
| `Revert` | the same load, compare and commit for a commit that something else confirmed first (any session's bare `<commit/>` or a `commit check` confirms a pending one); the history must show no pending commit after the load |
| `Discard` | `<discard-changes/>`, then `<unlock-configuration/>` (lock mode) or `<close-configuration/>` (private), then `<close-session/>`; an empty reply is success |
| `History`, `Identity`, `Login`, `Read`, `LandedCompare`, `RollbackCompare` | the `<command>` RPC with the same operational commands the CLI reader types, in a session of their own (never the held one), parsed by the CLI reader's parsers so both transports give the same typed values; `<get-commit-information/>` is not used (N5) |
| `State` | `show system commit` over `<command>`; **pending is the device's own `rollback pending` line under entry 0** (plan N5: the label `rollback in Nmins` rounds down and reads `0mins` for a one-minute window, so it decides nothing; after the confirming commit the line is gone). There is no prompt over NETCONF and so no banner (the CLI's marker) |
| `SharedDirty` | a throwaway session: `<get-configuration compare="rollback" rollback="0"/>` of the shared candidate (a staged change) and a `<lock-configuration/>` released at once with `<unlock-configuration/>` (`lock-denied` is `*LockedError`; a modified database is a staged change). Editors that changed nothing are not visible over NETCONF |

Built (WP15.3): `devapply.JunosNetconf` with `NewJunosNetconf(client,
mode)` and `DialJunosNetconf(ctx, target, mode)`; modes `ModePrivate`,
`ModeExclusive` and `ModeAuto` (the first two modes' successor: the lab
refuted the private session, so `ModeAuto` and `ModeExclusive` are the
lock, and an explicit `ModePrivate` sets `RetryExclusive()` and gives the
typed `ErrPrivateConfirmRefused` when the device refuses the confirmed
commit in a private session, with its own words `"commit confirmed" is not
supported for private configuration`, matched on `not supported for private
configuration`; the mode is never switched inside a transaction). The
confirmed commit is `<commit><confirmed/><confirm-timeout/><log/></commit>`
and the confirming one `<commit><log/></commit>` ([S] working form), the check
`<commit-configuration><check/></commit-configuration>`; `Cancel` and
`Revert` are the command line's `rollback 1`, inverse compare and commit
over `<load-configuration rollback="1"/>` (a closed session cancels
nothing). The transport's `Log()` holds the CLI's apply word where one
exists and `netconf: ...` for an RPC that has none.

Session mode, settled by N1 on the lab switch (Junos 25.4R1-S2.3): the
private session refuses `commit confirmed` over NETCONF as the command line
does, and `<open-configuration>` has no exclusive form (`<exclusive/>` is
`syntax error, expecting <invoke-on>`). The exclusive analogue is the
candidate's lock, `<lock-configuration/>`, with the shared candidate edited
under it: the lock keeps riders out for the transaction as `configure
exclusive` does over the command line (D131). What D78 of the deferred plan
refused about the shared candidate (a dirty one, `discard-changes` of
someone else's work) is met by two rules: the lock is taken only on a
candidate whose compare against the committed configuration is empty (the
gate reads it before, and `Open` reads it again under the lock), and
`discard-changes` is sent only under that lock, on a candidate that held
nothing but tacctl's own statements. The driver's gate (`SharedDirty`) is
read in a throwaway session as D131 does.

Everything the transport answers is typed; the driver never parses XML, and
no statement or reply text carrying a secret is stored or logged (the
transport's `Log()` elides values as the CLI's does).

### D150. Choosing the transport **(user: cli by default, NETCONF opt-in)**

New key `device.apply.transport` (`cli|auto|netconf`, default `cli`; the
`device.apply.*` family of 0.2.9, not `device.config.*`), `tacctl config
devices apply-transport [cli|auto|netconf]`, and a `--transport
auto|cli|netconf` on `device config apply` (the check is `--check`; the
setters' `--apply` forwards no flag and follows the setting; `shapes seed`
opens no transaction). The flag is `apply`'s own: the reads' `--transport`
(`auto|netconf|ssh`) is not accepted there, and `device.config.transport`
keeps governing reads.

- `auto`: NETCONF when the device's last probe is `hello ok` and a dialled
  NETCONF login offers the two capabilities and may commit
  (`JunosNetconf.Capable`); else the command line, and the device's result
  line says `[via cli: <reason>]` (`NETCONF port closed at the last read`,
  `NETCONF gave no hello at the last read`, `cannot confirm over NETCONF:
  <why>`, `NETCONF login failed: <why>`). A device never probed is the
  command line and the line says nothing (it would change every 0.2.9
  line); the JSON has `via_reason` always. The probe is the record's, never
  made by the selection (`devapply.Choose` is pure). A delta with `system
  services netconf` statements goes over the command line (D148): the
  planner of a NETCONF attempt returns a sentinel after its first read,
  before anything is opened, and the whole transaction runs again over the
  command line, noted `[via cli: netconf service change]`; the same rerun
  carries the exclusive-session retry. `--transport netconf` with such a
  delta is `failed` with what to run instead.
- `cli`: the 0.2.9 behaviour, whatever the probe says.
- `netconf`: never falls back; a device that cannot is `failed: ...` with
  the reason.

`onboard`, `seed` and the one-shot local login are command-line only (D136,
D148). The review and the record say which transport carried each device
(`via netconf`, `via cli`); `devconf.Applied` gains `Via` (additive,
`Records.Version` unchanged; a 0.2.9 record has none and was the command
line). A read through NETCONF also records the transport and the hello on
the pull part of the record.
`auto` changes the transport of every NETCONF-enabled device the first time
a 0.2.10 apply runs against it; that is the user's decision and is stated in
the release notes and the CHANGELOG item.

### D151. The fake device grows a NETCONF configuration model

`internal/devssh/fakedev` has a command-line configure model (D142 [V:
`junos_config*.go`]) and a NETCONF server that answers `<command>` and the
reads only [V: `netconf.go`]. The NETCONF side gains the configuration RPCs
of D149 over the **same** committed state and candidate tree
(`junos_config_tree.go`), so a statement loaded over either channel is one
configuration: `open-configuration` (private, exclusive, and the warning
when another session is exclusive), `load-configuration` (non-atomic, with
per-statement `rpc-error` from the same `load.errors` knob, `statement not
found` as a warning), `get-configuration` with `compare`, `commit-
configuration` `check`, `commit` with `confirmed`, `confirm-timeout`, `log`
and the bare confirming `commit`, `close-configuration`,
`load-configuration` `rollback="N"` (the cancel), `lock-denied`,
`get-commit-information`. A session that closes without confirming leaves the
commit pending to the window's end (the knob `netconf.close.rollback=on` is
the model of a device that rolls it back at the close). The knobs of D142
apply to both channels (`verify.fail`, `commit.drop`, `lock.held-by`, `check.errors`,
`load.errors`) and the committed configuration is written to
`committed.set` after every commit from either channel.

## 2. Changed behaviour and compatibility

- A scope with no `netconf` value reads as `leave`: no plan, no compare, no
  record change; `diff`, `plan` and `apply` output are byte-identical for
  existing installs (the diff corpus against `0.2.9` proves it; the new
  lines are marked `@known 0.2.10 item N`).
- `auto` (D150) moves NETCONF-enabled devices to the NETCONF transport. The
  command line is one flag or one setting away.
- Tiers: the two verbs and the setting are superuser (D141's rule: the apply
  verbs stay superuser, so the new transport adds no engineer path). No
  sudoers text changes unless a new command word needs a row; the TIERS
  table in the man page is generated from `deviceConfigNeeds` as always.
- `device config enable-netconf` (D93 of `apply-deferred.md`) is **not**
  built: `scope netconf <scope> enable` plus an apply covers it, and a
  device that cannot be reached by apply yet is brought up by `onboard`.
- `tacctl rollback 0.2.9` (WP15.5) replaces the 0.2.8 target of D143, as
  the release before this one and `0.2.3` are the targets: it removes
  `device.apply.transport`, the `netconf_scope` keys and the `netconf:` map
  of each device, leaves and lists the `via` field of the apply records
  (0.2.9 ignores it) and rewrites no drop-in (0.2.10 changed no sudoers
  text). `0.2.4` to `0.2.8` are refused the one-release-at-a-time way, and
  `rollback 0.2.3` removes the same settings. `TestRollbackRealOldBinary029`
  builds the 0.2.9 tag and reads the converted state with it.

## 7. Risks

1. **A transport-specific leftover.** A pending confirmed commit must not
   outlive tacctl on either transport. On both the rollback is the window's
   end, or tacctl's own cancel while it runs (D132); a dead tacctl leaves
   the commit pending for the rest of the window (default 10 minutes); the
   exit table is tested once per transport.
2. **`disable` cuts the path it runs on.** D148: the command line carries
   it and the verification is a command-line login plus a failed probe; a
   probe that cannot tell is a failed proof (fail closed), which a real
   device that closes the channel instead of refusing the subsystem would
   turn into a rollback (N6).
3. **`auto` changes devices that already work.** The setting is one word
   away (`config devices apply-transport cli`), and the release notes say
   so; the live acceptance (section 6) is what the release waits for.
4. **The absence compare** (D146) is the first of its kind: Opus reviews
   `Absent` through `diff`, `plan`, the shapes and the backout.
5. **Size.** If it grows, the order of cuts is: per-device override of the
   two limits, then the `device netconf` verb (scope only).
