# tacctl 0.2.23 plan (2026-10-30)

State: scope chosen 2026-10-30, designs mapped on the 0.2.22 code, nothing
built. Branch `feature/0.2.23` from `develop` at the 0.2.22 merge.
Decisions continue the numbering of the earlier plans (D296 and up). Items
the user did not decide are marked "default"; they stand until overruled.

## 1. Scope

The release closes the gaps the 0.2.22 work left open and adds three things
that change the stored files. Every stored-file change gets a rollback step
(`rollback 0.2.22` is new) and nothing is scheduled or automatic.

| Item | What |
|---|---|
| Rollback target | `tacctl rollback 0.2.22`; every older target also removes what this release adds; `backup recover` puts it back |
| Carry-overs | `device rename` carries the staging line; two style ratchets; the 0.1.18 corpus markers re-checked |
| Own aaa settings | A device's own leaves under tacctl's server (a source address, a timeout) are not irregularities or differences |
| Source addresses | The AAA source of a device must be an address of one of its interfaces; the pull records them |
| User changes and the sync | A user verb that changes an account on this server syncs it at once; one notice for the other hosts; INFO and WARN say different things |
| User email | An optional `email` on users, set by superusers, no mail is sent |
| SNMPv3 pool | Several v3 users per level, one default, the protocols stay per level |
| Device clone | `device clone <old> <new> --staging <ip>` and `device rename <new> <old> --replace` |
| Lockdown on hosts | `emergency lockdown` also closes SSH key logins and forwarding on enrolled hosts |

Out of the release (`backlog.md` section 3j): naming a device from its
configuration, several server addresses and failover, several addresses per
device, multiple shared secrets, the logging release, completion phase 2,
device reports.

## 2. Decisions

### Rollback and carry-overs

D296. `tacctl rollback 0.2.22` is a target (the template is the 0.2.21 one,
`rollback0221.go`). Each stored-file change of this release is a step of
every target, including the ones that return early (0.2.21, 0.2.20), in the
way the timing scale is (`rollback_timeoutscale.go`), not like the password
change flag. The plan lists what it does; `--apply` needs `--yes` when it
drops data (an email, a second SNMPv3 user).

D297. `renameDevice` carries the staging line (`staging` file, device name
in the fourth field); `hostRenameStaging` and `scopeRenameHosts` are the
precedent. Today a renamed device loses its staging /32 sweep.

D298. Style: the summary of `device list` is shortened to at most 72
characters and its line leaves `testdata/style/summary-length.txt`, lowering
the ratchet by one. `shell.Candidate.Command` is read by no code but tests
and goes. The 13 `@known` lines of `breakglass.txt` were checked (2026-10-30): they
are markers with reasons, not unexplained differences. Against 0.1.18 the
corpus has 13 known lines and 3 without a marker (lines 18, 19 and 30, whose
output 0.1.18 never had); against 0.2.22 all 16 lines are the same. Markers
record differences from 0.1.18 and are never pruned (D293), so none is
dropped and the three stay as they are: the gate compares with the previous
release.

### The device's own aaa settings

D312. Reported 2026-10-30 on a Junos device: `source-address` under tacctl's
own `tacplus-server` was listed as an irregularity ("extra ... Left alone"),
so the plan said there was something to look at and the device counted as
differing, although the ownership rows (`plan/owned.go`, the Kept column)
already leave it alone. The table of the device's own statements
(`devconf/unmanaged.go`) gains the `aaa` section for what the Kept columns
keep and that is not about who can log in: the leaves under tacctl's own
server or server block, the server options, the device's own source
interface when the scope sets none. They are counted in Own, never listed,
and do not make a device differ (plan, diff, `device list --differs`, the
CONFIG column). Another server or server block, another group and a method
or login list of another name stay findings: they decide who can
authenticate. A leaf the rendering states with another value is still a
difference.

D314. A source address that the device does not hold breaks AAA silently
(the packets leave from no such address), and D312 makes the source of the
AAA server the device's own setting. The pull therefore records the
addresses of the device's interfaces (Junos `interfaces ... family inet|inet6
address`, IOS `interface` with `ip address`), taken from the configuration
the pull already reads: no new device command, only the addresses and, for
IOS, the names of the interfaces that carry one. An AAA source that matches
none (Junos `system tacplus-server|radius-server <addr> source-address`;
IOS `ip tacacs|radius source-interface <name>`: the interface must exist
and carry an address) is an ACCESS irregularity in the plan, the diff and
the lists, worded 'source-address <a> is not an address of any interface of
this device'; it is never fixed by the paste. A device pulled before the
upgrade has no addresses recorded and is not checked until its next pull, and
the plan says so; a login that cannot see the interfaces says so too. Syslog,
NTP and SNMP sources are not checked in this release. The record gains a
key: the rollback strips it (derived data, like the other pull files) unless
older records already ignore unknown keys; the builder checks the parser.

### User changes and the sync

D313. Reported 2026-10-30: after `user add` the new user could not log in to
this server to change the password, because the account (and its UID) is
made by the next `host sync` of this server, and the two notices that said so
were nearly the same sentence at two levels. Every user verb that changes an
account on this server (add, remove, rename, group, scope, enable and
disable, `require-password-change on|off`) syncs this server's own account
at once when this server is enrolled, with the code of `host sync <this
server>`; one INFO line says what was done. A failed sync is a WARN with the
retry command. A user change reaches the devices through the restart of the
AAA service that the verb already does; nothing is pushed to a device. The
other enrolled hosts a change affects get one notice naming them and the
command (`tacctl host sync <hosts>`); on a terminal the verb offers to sync
them (`[y/N]`, the answer is never taken from `--yes`), in a script the
notice is all. INFO says what was done, WARN says something failed or the
operator must act; a fact is said once (the password-change rule of a new
user is one line, not an INFO and a WARN), and the other user verbs' hints
(`reportNeedsSync`, `reportHostsSync`) follow the same two levels.

### User email

D299. `users.<name>.email` is an optional string, a plain address
(`local@domain`, at most 254 characters, no spaces, angle brackets or
quotes), kept as typed. It is written only when set, so a store without one
stays byte-identical; the store version stays 1 and an older build refuses a
store with an email as an unknown field (the rollback removes it).

D300. Verbs: `user add --email <address>` and `user email <name>
[<address>|clear]`, both superuser. Visible to everyone who can run `user
show` (an `email` line); not in `user list`. `store show --json` carries it.
`store import` keeps an existing email like the other kept flags. A rename
carries it. An address belongs to one user, compared without regard to case:
the store validation, `user add --email` and `user email` refuse a second
user with the same address and name the first.

D301. The address is never in an audit line: `--email` is a secret flag in
its spec, the positional form has an `auditTable` row that hides it, and no
error message echoes it.

D302. Rollback: every target removes the email key from the store after a
snapshot, with a warning that names the users; `--apply` needs `--yes` when
any user has one. The snapshot is the record: the plan and the audit line
name the snapshot and say what was dropped (the users with an email, the
SNMPv3 users of each level), and nothing is deleted for good. `tacctl backup
recover <snapshot> [--only email,snmp-users]` (superuser, this release and
later) puts back only what a rollback dropped, from that snapshot into the
current state, and leaves everything else as it is. It skips a user, scope or
device that no longer exists, says which, and takes its own snapshot first;
`--dry-run` lists what it would restore. `backup restore` still restores the
whole state, and an older release's refuses a snapshot with these keys.

### SNMPv3 pool

D303. The version, the port, the timeout and the auth and priv protocols
stay one setting per level (config, scope, device). A level holds a pool of
v3 users (name and passphrases) and a default user or none. `snmp v3-user`
becomes `v3-user add|remove|default|list`; adding a user changes nothing but
the pool, and the old single-argument form is retired with no alias
(default).

D304. A device uses its own default user, else its scope's default, else the
config's. It may be told to use any user of its own pool, its scope's pool or
the config's. User names are unique across those three pools, so a scope user
cannot shadow a config user (default). A chosen user that is missing or
incomplete is an error naming the command that fixes it, never a fallback
(default). The walkthroughs and rendered blocks name only the effective
user, as now.

D305. Files: version 2 of the credential files (`snmp.yaml`,
`snmp/<scope>.yaml`, `snmp/devices/<name>.yaml`) holds `users:` and
`default:`. A version 1 file reads as a pool of one user that is the
default and is written as version 2 on the next change; there is no eager
rewrite on upgrade (default). The rollback writes version 1 again with the
default user; a level with several users keeps the default and drops the
rest (warning, `--yes`), and a level with several users and no default
refuses, naming the level. `snmpcred.ResolveDevice` is the one place that
resolves.

D306. `device snmp` JSON gains `v3_users` and `v3_default`; `v3_user` stays
the effective one. Secret reads are audited per user (`secret-read` kinds as
now, the user name added); `show --reveal <user>` reveals one user.

### Device clone and replace

D307. `device clone <old> <new> --staging <ip>` registers a copy of a
device's intent at a bench address: the plain fields, the SNMP settings and
credentials, the NETCONF settings, the timing scale and the block files with
their manifest. It does not copy the address, the name, the host keys, the
acknowledged notices, the hold or the pull record. `--staging` is required
(the registry needs a unique address); the bench /32 is added to the scope
as the existing scope staging does, before the registry write, as for the
other `--staging` verbs. The new name follows the device name rules
(lower-case). Engineers may clone within their own scopes, copied SNMP
credentials included (they can read them today); the clone is audited and the
tiers sudoers gain a row (the `device support-bundle` commit is the template,
the frozen copies in `internal/tier/rollback.go` included).

D308. `device rename <new> <old> --replace` (the flag name differs from
`device import --replace`) takes a snapshot, shows the original's hold if
it has one, and after one confirmation (`--yes`) removes the original with
its files, moves the replacement to the original's address, which ends the
staging /32, and clears the hold; the hold is never moved to the
replacement. An original with a hold needs a superuser (release is a
superuser verb and engineers get no break-glass privilege); an engineer is
refused naming the hold. The replacement keeps the scope that its
new address gives it. One shared snapshot covers the steps
(`Snapshots().Hold()`).

### Lockdown on hosts

D309. `emergency lockdown <scope> enable|disable` also reaches the enrolled
hosts of the scope. A static sshd drop-in on each host, named to sort before
`00-tacctl-engineer.conf` (default `000-tacctl-lockdown.conf`), holds
`Match Group tac-users,!tac-superuser` with `PubkeyAuthentication no`,
`AllowTcpForwarding no`, `AllowStreamLocalForwarding no`, `X11Forwarding no`
and `AllowAgentForwarding no`. It matches tiers, not store groups, so a
lockdown that does not name every lockable group of the scope locks every
non-superuser account on those hosts; the enable prompt says so before it
asks for the scope name. The provisioner login has no `tac-users` group and
is not matched; the provisioner being a tacctl user stays a warning.

D310. The hosts get it through `host sync`: the script protocol becomes 7
with one header variable for the desired state; the shell side writes or
removes the drop-in in the `--accounts-only` and the full path, checks it
with `sshd -t` and `sshd -T -C user=...`, reloads sshd and runs `restorecon`.
A host whose sshd does not include `sshd_config.d` is refused and reported
(a drop-in there would be silently inert). `client-remove.sh` removes the
drop-in. Test hooks gain a path override like the PAM and sudoers ones.

D311. `enable` and `disable` change the devices as now, then ask whether to
run the host sync (long `--yes` form only). Hosts that are unreachable, held
or refused stay on a pending list in the lockdown record that `status`
shows and a later `host sync` completes; a host enrolled or synced during a
lockdown gets the drop-in. `enable` also ends the live sessions of the
accounts the drop-in matches (members of `tac-users` that are not in
`tac-superuser`) in the same host step, after the drop-in is in place and
sshd is reloaded: `loginctl terminate-user` where systemd-logind runs, else
the account's processes are ended. The provisioner login, superusers and the
step's own session are never touched, and `disable` ends nothing. The
server's own console users are ended like any host's. The server's own
console drop-in order test learns the third file.

## 3. Series and checks

Order: (1) the 0.2.22 rollback target and the carry-overs; (2) email;
(3) the SNMPv3 pool; (4) clone and replace; (5) lockdown on hosts. Each is
separate commits with its CHANGELOG items, man page and docs in the same
change. Each series passes `make gate-go` and is reviewed by a second model.
On the combined tree before release: `make gate-ci`, bats, the corpus
against 0.2.22, the container matrix (a `lockdown` cycle in
`tests/containers/hosts`: key login refused, `sshd -T -C`, lifted) and the
usual release steps (`docs/releasing.md`).

## 4. Compatibility

A 0.2.22 build cannot read a store with an email, a version 2 credential
file or the pending list of a lockdown. `tacctl rollback 0.2.22` removes the
email, collapses the credential files to version 1 and refuses while a
lockdown stands, as every earlier target does.
