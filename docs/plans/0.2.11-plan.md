# tacctl 0.2.11 plan: one apply lock

Written 2026-10-15 on `feature/0.2.11`. Decisions continue
`0.2.10-plan.md` (D145-D151): **D152-D158**. Reviewed against the code before
any change was made (the findings are folded in below).

## 0. The defect

`StoreApply` (`internal/backend/apply.go`) copies `store.yaml` and
`tacctl.yaml` at the start and puts the copies back when its writer or its
render fails. Nothing holds the files between the copy and the restore, so a
change another command wrote in between is undone with it, and that command
printed success. Four other transactions do the same with whole files, some
with `rendered.json` too, and put the copy back after a restart:
`settingsApply` (`config listen|loglevel|metrics`, tacacs), the radius
`listenerApply`, `backend enable` with its undo, and `disableLegacy`. Putting
`rendered.json` back also removes the records another render wrote, so the
next gate refuses those artifacts as hand-edited.

## 1. Decisions

- **D152. One lock, not a key-level restore.** `<state>/.store-apply.lock`,
  root 0600, serialises every transaction that restores whole files. A
  restore of only the keys a command wrote needs a change journal in two
  storage packages and a policy for an inverse that no longer validates;
  it is not pursued unless contention becomes a problem.
- **D153. A reentrant lock object, one per process** (`internal/applylock`):
  an exclusive flock taken at depth 0 and counted above it, so a
  transaction that calls `StoreApply` or `Conf.Set` while holding the lock
  does not wait for itself. The file is opened with `os.OpenFile` (close on
  exec: `upgrade` execs the new binary) and the directory is never created
  by the lock. Waiting polls the non-blocking flock every 100 ms and gives
  up when the invocation's context ends, so Ctrl-C works; the wait prints
  one line, once: `Waiting for another tacctl command that is changing the
  configuration...`. A cancelled wait is `Nothing was changed.`, exit 1.
- **D154. The span.** `StoreApply`: `Require`, then the lock, then the gate,
  the snapshot, the copies, the writer, the render, the rollback when one is
  needed, the restart, and only then the release. A restart outside the lock
  could start a daemon on another command's half-committed render and
  misattribute the failure. `ApplyForced` (`backup restore`) and
  `ConfigRender` take the same lock through their restarts. The four
  transactions above, `store import` (with its group-tier pin), `store
  rollback` and the upgrade (after its self-update exec) hold the lock for
  their whole span.
- **D155. A change inside a change is an error, not a hang.** `Env` has an
  `inWriter` flag, set only while the writer of a `StoreApply` or
  `ApplyForced` runs; calling `StoreApply`, `ApplyForced` or `ConfigRender`
  then returns an internal error. Nesting inside an outer transaction (D154)
  is legal.
- **D156. The single writers.** `conf.Config` takes the lock around each
  write (`write`, `edit`, `UnsetMany`) through a hook set by the App, after
  the directory is made and before the directory flock; a Config without the
  hook (tests, snapshot views) does not lock. The lock order is then apply
  lock, directory flock, `.store.lock`, never the reverse.
- **D157. The guard.** After the writer returns, the files' bytes are
  remembered. A rollback that finds a file equal to its start copy renames
  nothing; one that finds it different from the post-writer bytes (a hand
  edit; under the lock nothing else can) saves it as
  `<file>.overwritten-<stamp>` (0600, in the state directory), says so, and
  restores as before.
- **D158. Not changed.** The restart staying part of the apply, the
  check-then-act of callers that load the model before `StoreApply`
  (`Mutate` validates again), and the snapshot (it takes no lock of its own).

## 3. Tests that must exist

Two instances on one state directory (flock between two descriptors works
in one process). A's writer or render fails while B waits: B ran after, B's
change is present and A's is not. B waits at the gate, not at the writer. A
restart in progress holds B. A nested apply inside a writer errors under a
deadline. Another instance holding the lock makes `settingsApply`,
`listenerApply`, `backend enable` (and its undo), `store import` and a
`Conf.Set` wait; a failed `settingsApply` or enable no longer reverts a
concurrent `user add`, and the next gate is not refused. The guard saves
`.overwritten-*`. A stale lock file and a stale `.apply.*` directory do not
block. A cancelled context while waiting changes nothing.
