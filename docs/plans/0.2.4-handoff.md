## Facts learned in the 0.2.3 acceptance (design inputs for 0.2.4 and 0.2.5)

- **Junos tests a `deny-commands` pattern against a command's keywords, with
  each argument replaced by a placeholder, not against the text typed.** A
  pattern can deny `file delete` or `request system`, but it cannot tell
  `load set terminal` from `load set /var/tmp/x`. A denied keyword vanishes
  from the parse tree, so an abbreviation resolves to what remains (`file
  delete` ran as `file delete-directory` until that was denied too). The
  engineer's set therefore does not deny `load`.
- A directory made by an engineer's `file make-directory` belongs to the
  class's template user and cannot be removed by another login; test debris
  on a switch needs `start shell user root`.
- `tacctl` runs as root under sudo, so files it writes for the invoking user's
  ssh need an explicit `chmod` (the umask closed the rotation proof's
  known_hosts file); container runs as root do not catch this, a live run
  does.
- `tests/diff/run.sh` and `gates.sh`-style scripts write a `done` marker:
  remove it at the start of a run or a watcher fires on the old one.

## Facts learned in 0.2.4 (design inputs for 0.2.5 and later)

Settled by the spike and the package reviews (`0.2.4-spike.md`, `0.2.4-plan.md`
§9):

- **A non-superuser Junos login sees secrets masked** as `/* SECRET-DATA */`,
  and the TACACS+ server's `secret` statement is not shown at all; a pull as an
  engineer can say `present` or `not visible` for a secret statement, never
  `missing`.
- **The Junos exec channel exits 0 for a CLI error**; the reader inspects the
  output for `error:` lines. NETCONF is the ssh subsystem on the ssh port; port
  830 need not be probed.
- **`show configuration | display inheritance no-comments | display set`** is
  the read: statements kept in groups are seen where they take effect.
- **Nothing reversible is stored**: sections are normalised with secret values
  elided, so the sections file, `--json` and diffs never carry a device's
  encrypted keys, communities or hashes (D65, amended).
- **A password goes to the SSH library as a string**, so the zeroisation
  promise of the cache ends at the askpass boundary.

## 0.2.5 handoff (apply and rollback on the device)

What the spike and the plan establish, and nothing beyond them:

- **Confirmed commits need one session.** A NETCONF confirmed commit that is
  not confirmed by the same session is rolled back as the session closes, within
  seconds, not after the timeout. Apply therefore holds one NETCONF session from
  the confirmed commit through the verification (the fresh login proving the
  user can still reach the device over TACACS+) to the confirming `<commit/>`;
  it must not reconnect to confirm. `persist` was not exercised and stays
  unexercised until a lab run. Over the CLI, `commit confirmed <minutes>` rolls
  back on its own at expiry (confirmed on the lab switch). The working RPC form
  is `<commit><confirmed/><confirm-timeout>N</confirm-timeout><log>text</log>
  </commit>`, minutes; `<log>` is where the change identifier goes (it shows in
  `show system commit`).
- **Pre-commit review**: `load-configuration action="set"` over NETCONF with
  `<get-configuration compare="rollback" rollback="0" format="text"/>` returns
  the `[edit ...]` diff; the candidate lock (`<lock><target><candidate/>`)
  worked and apply should hold it for the whole transaction.
- **Reuse, do not rebuild**: the batch runner (`internal/devconf/batch`: a
  generic `Job`, the canary and `--max-failures` fit its options,
  `StopOnAuthFailure`, the two-stage interrupt), the record store (the
  `applied` fields are reserved and nothing writes them), both transports, the
  password cache and the managed-section builders (`devices.Managed`), whose
  text a push can reuse as it stands (renderers are pure by rule).
- **`Confirms()`**: D61 says the transport interface carries `Confirms() bool`
  from the start so a transport that cannot confirm a change is refused for
  apply and never downgraded; the 0.2.4 code has no such method, so it is added
  with apply.
- **Secrets** are compared by presence in 0.2.4, so apply re-pushes them by
  value (`--secrets`); the SNMP section's "offer to set what is missing" is
  `apply --section snmp`.
- **Cisco is open**: the IOS-XE items of `0.2.4-spike.md` (the revert timer,
  `configure confirm`, `archive`, `netconf-yang`) are assumptions written from
  the references, to be confirmed with the paste the spike lists when a router
  is available; IOS-XE over NETCONF only if that confirms `netconf-yang`.
- **WTI is later**: WTI units are unread in 0.2.4 (D71); the run-sheet results
  decide whether the menus script at all (a later release, backlog §0).
- **Unattended pulls and drift detection** need a credential no person types;
  the never-stored rule rules out a user's password for that (a read-only
  service account is backlog §0, later).

## 0.2.4 scope (backlog §0)

Device configuration, read-only. First a lab spike that decides the design
(Junos `commit confirmed` over NETCONF or CLI on SSH; the Cisco IOS-XE
`configure terminal revert timer` and `configure confirm` behaviour; whether
the WTI SSH menus can be scripted and which firmware has the RESTful API;
scrapligo against a thin driver on `golang.org/x/crypto/ssh`). Then `device
config pull|diff` of the tacctl-managed sections, per-device records and
`device list --stale`, parallel sessions with `device.config.max_concurrency`
(default 8, at most 64) and per-device timeouts, the SNMP read of each device
against its scope's settings, and the user's password cached for the session
only (never stored). The design constraint from 0.2.3 stands: every
walkthrough renderer (`internal/devices/{cisco,juniper,wti}.go`) takes one
input struct for one device and returns text, with no CLI, terminal,
global-state or clock access, so a batch can render per device in parallel
and a push can reuse the same text.

Write `docs/plans/0.2.4-plan.md` first (decisions numbered from D60, packages,
tests), ask the open questions up front, then implement.

## Release procedure (git-flow, `docs/releasing.md`)

`git flow release start x.y.z` from `develop`; the release date in the
CHANGELOG heading, the man page `.TH` date and version, the release notes
`docs/release-notes-x.y.z.md`; `git flow release finish -m "Release x.y.z"
x.y.z`; re-tag with `git tag -f -a x.y.z -m "Release x.y.z" master`; build,
sign and verify the assets; push `develop`, `master` and the tag; `gh release
create`. Feature work happens on `feature/x.y.z` off `develop`.

## Working rules

- Model routing: Opus reviews, Sonnet and Haiku implement, Fable decides
  important design questions. Subagents never commit; the coordinator reviews,
  merges, renumbers CHANGELOG items and commits.
- Commits only when the user asks in the current turn; push only to the branch
  being worked on; merges into `develop` and `master`, tags and releases only
  when the user says so. **No Claude attribution or session URL in commit
  messages.**
- No private names (hosts, addresses, users, home paths, domains) and no
  description of any installation's state or rollout in repo files or commit
  messages: use roles ("the dev server", "the test host", "the lab switch")
  and `example.*`, `192.0.2.x`. Do not describe a release as lab-only.
- Never act against the production host and never connect to a production
  device: prepare the files and let the user apply them. Testing happens in
  the dev environment and is performed directly by Claude as far as it can be;
  ask before changing the lab switch.
- Every user-visible change gets a numbered CHANGELOG item and updates
  `man/tacctl.1` and `README.md` in the same change (`make man` rewrites the
  generated blocks of the man page).
- Tests sandbox host paths. Containers need rootless podman, Go in
  `/usr/local/go`, `/usr/local/bin/tacquito` and `python3-bcrypt`.
