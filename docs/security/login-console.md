# Login console

[Documentation](../README.md) › [Security](README.md)

**On the tacctl server itself, every tacctl user's login shell becomes the login console once the server's accounts are synced** (`tacctl install` and `tacctl upgrade` set up this machine's own login and sync them; the `user` verbs that change an account run that sync themselves; `tacctl host sync <name>` after any other change; `tacctl host enroll --local` to rebuild, move or repair it); nothing changes for anyone before that sync. A console user who logs in over ssh gets a `<host>> ` prompt (`<host>` is the host name, or the name `tacctl server name` set) that runs tacctl commands (as `sudo tacctl …`, so the [tiers](tiers.md) apply line by line) and `tacctl ssh` to the registered devices of their scopes, and nothing else: no system shell, no file transfer unless it is switched on for the account (superusers always have it), no port forwarding (superusers excepted by default: `console forwarding tiers`). `ssh <server> 'user list'` runs one tacctl line; `rsync`, `scp -O` and every program are refused, and `sftp` (and the `scp` of OpenSSH 9 or later) works only for an account that has file transfer (see File transfer settings below).

- **Who gets it.** Every tacctl user of every tier, with no switch: the next `host sync` of the server sets the console as the login shell (`usermod -s`) and the sshd drop-in forces it; `tacctl console show` lists each user's effective shell and why. Every user can log in to the server unless disabled or of tier none (a group without a priv-lvl). The engineer tier has the console or no login on this server: an account whose console cannot be provisioned (the `tacctl-console` link is missing) gets `/bin/bash` only if it has the system shell (a superuser always; others when a superuser opened it to their tier or to them) and `/usr/sbin/nologin` otherwise, an engineer included, as does an account whose tier is none. sshd's drop-in `/etc/ssh/sshd_config.d/00-tacctl-engineer.conf` (its own file, written at every sync of this server even when the console is not installed, named to be read before the console's) closes every forwarding and tunnel for the engineers whatever shell they have (agent forwarding follows `console agent-forwarding`); `console check` verifies that file on its own and also looks at the engineers: each member of `tac-engineer` has the console or a nologin shell, sshd closes forwarding for them, and every member of `tac-superuser` that is a tacctl account is a superuser-tier user (root excepted; a removed user whose UID is in tacctl's range is named red; a local administrator outside the UID range is listed as not a tacctl account and the check stays green). Lowering a tier with a group command (`group edit … tier`, `group edit … priv-lvl`, `group remove`, `group preset roles --force`, `group reset`) syncs this server's accounts at once; when that fails the command says `Members of '<group>' keep their old groups on this server until: tacctl host sync <server>`. The `user` verbs that change an account (`user add`, `remove`, `rename`, `move`, `enable`, `disable`, `scope`, `require-password-change`) sync it after every change, and a sync that fails is one warning with `tacctl host sync <server>` (exit 0). An engineer keeps this lockdown (no system shell, no forwarding) even when `tacctl.yaml` cannot be read and the gate treats them as an operator.
- **A required password change.** A user who must change the password (`tacctl user require-password-change`, which `user add` and an administrator's `user passwd` do by default; never a superuser) gets, when the console starts, the notice `A password change is required of your account.` and the password change dialog straight away: no device accepts the login until the password is changed, nor any enrolled Linux host but this server (its next `host sync` expires the account there, SSH keys included), and nothing else runs in the console. Every other line, `help` and the other words of the console included, is refused (`A password change is required: nothing runs here until it is made but 'passwd' (and 'exit').`, status 1), Tab and `?` list the change only, and Up and Ctrl-R recall no earlier line. Once the password is changed the session goes on as any other. A console that cannot read the answer (sudo refuses, the store cannot be read) cannot tell whether a change is required and holds a user who is no superuser the same way, without the dialog; a superuser, known by the system group `tac-superuser`, is never held by a read error. Ctrl-C in the dialog ends the session; a wrong current password or a rejected new one leaves the locked prompt, where `passwd` tries again and `exit` leaves. `ssh <server> 'user list'` and a batch are refused the same way, and a plain shell or `ssh <server> tacctl ...` meets the same refusal in the command line (only `passwd`, `version` and `help` run). The lock holds the console, and sshd's drop-in holds the forwarding: a forwarding (`ssh -N -L`, `-R`, `-D`, `-J`) opens no session, so it never reaches the console, which is why the drop-in lists the users who must change the password in a block of its own before the tier blocks (`Match User <names>` with `DisableForwarding yes`, see below). Whatever their tier, even one of `console forwarding tiers`, a new connection of theirs forwards no port, X11 display or agent through the server until the password is changed. sshd applies the drop-in when a connection authenticates, so a connection the user already has open keeps the forwardings it had until it closes; tacctl does not end it (the administrator can: `loginctl terminate-user <name>`). The list is rewritten by every sync of this server (the `user` verbs that change an account run it; so does `tacctl host sync <server>`), by `console install` and `upgrade`, and by the verbs that change who is held, each at once and by itself, so that it is current whether or not a sync of this server follows and gets as far as the drop-in (a server that is not enrolled, a sync that stops at its checks, a scope in which no user gets the console): `user require-password-change` in every form, `user add`, `user remove`, `user rename`, `user move`, an administrator's `user passwd`, the user's own `passwd`, a group command that lowers a tier, `store import`, `backup restore` (a snapshot or an old-style backup) and `store rollback` (legacy mode holds nobody). The list is read and installed under the apply lock, so that two commands cannot leave a user out. Any other write of the store or of `tacctl.yaml` leaves the drop-in as it is until the next of those. With nobody held there is no block, and a superuser is never listed. Only a change that lowers a group's tier syncs this server (and so lists a flagged user whose group stops being a superuser's); raising a tier leaves the list as it was until the next rewrite, which can only close forwarding: a user who has become a superuser stays listed, and his new connections stay closed, until then. `console check` reports the drop-in as differing, with the two lists, when it is not the users held now; `tacctl console install` writes it again. The user must be able to get here: a user with no login on this server is never required to change the password (see [User Commands](../cli/user.md)). The sessions and refusals are in the log (`console password-change`, `console DENY ... reason=password-change`).
- **Break-glass.** Local accounts that are not tacctl users (root, the administrators who installed the server) are never touched, so they keep their shells and their local passwords; a tacctl user has no plain shell on the server.
- **sshd's drop-in is the key line.** `Match Group tac-console` in `/etc/ssh/sshd_config.d/tacctl-console.conf` sets `ForceCommand /usr/local/bin/tacctl-console` (every login, remote command and subsystem, the sftp server included, reaches the console, which takes the client's command from `SSH_ORIGINAL_COMMAND` and lets only one tacctl line through, or the sftp subsystem for an account that has file transfer), `DisableForwarding yes` with `AllowTcpForwarding no`, `AllowStreamLocalForwarding no`, `X11Forwarding no`, `AllowAgentForwarding no` and `PermitTunnel no` (agent forwarding only with `console agent-forwarding enable`). For each tier of `console forwarding tiers` (default: superuser) a block before it, `Match Group tac-console Group tac-<tier>`, sets `DisableForwarding no`, `AllowTcpForwarding yes` and `X11Forwarding yes`: sshd takes the first value it finds, so those users can `ssh -X`, `-L`, `-R`, `-D` and `-J` through the server (still into the console, still by password) while everyone else stays closed. Before those, when anyone must change the password (see above), comes `Match User <names>` (the names sorted, only those of a Linux account, at most 50 to a block: more users make further `Match User` blocks, all before the tier blocks), which sets `DisableForwarding yes` with the `Allow...` and `X11Forwarding` switches at `no`, `PermitTunnel no` and `GatewayPorts no`: the first value wins here too, so a new connection of a user held to a password change forwards nothing in any tier, and the block is not written when nobody is held. Forwarded ports on the server listen on loopback only (`GatewayPorts no` in the console's block) unless `console forwarding gateway-ports enable` adds `GatewayPorts clientspecified` to the tier blocks: an `ssh -R 0.0.0.0:8080:host:80` to the server then listens on every address, and the console's `tacctl ssh` takes `-g` and a bind address on `-L` and `-D`; anyone who reaches the server can connect to those ports. Then `PubkeyAuthentication no` (a key login would bypass TACACS+), and `ClientAliveInterval 300` / `ClientAliveCountMax 2`. Every change is checked with `sshd -t` and undone when sshd refuses it; sshd is reloaded otherwise. `/etc/ssh/sshd_config` must include `sshd_config.d/*.conf` (Debian, Ubuntu and RHEL 9 do). `tacctl console check` (operator and up) asks `sshd -T` what it applies to a console user and warns in red when anything is off; `console show` does the same.
- **`system-shell`.** The console word `system-shell` starts the user's own system shell, logged. Superusers always have it; readonly and operator users do not until a superuser opens it for the tier (`tacctl console system-shell operator enable`) or for one user (`tacctl console system-shell user <name> enable`; a user's setting wins over the tier's, in both directions; an enable lasts only while the user stays in the tier they had when it was set, so a demotion does not leave a shell behind); engineers never have it. Only a superuser sets it; the operator tier and up read it (`tacctl console system-shell`, `... <tier>`, `... user <name>`, `... path`) and `console show` shows each user's access and why.
- **File transfer settings.** Whether a tier or a user may transfer files to and from their home through the console is a setting like `system-shell`: off for every tier but the superuser tier, which always has it; `tacctl console file-transfer <tier> enable|disable` or `... user <name> enable|disable|clear` (a user's setting wins over the tier's; an enable lasts only while the user stays in the tier it was set for); the engineer tier is not closed to it, because a transfer reaches the home only. A quota (the bytes the whole home may hold, 256M by default, none for superusers) and a rate (bytes a second, off by default) can be set per tier and per user. Only a superuser reads or sets `console file-transfer`; each user's state, quota and rate are in `console show`, which the operator tier and up can run. The console serves SFTP only, to the accounts that have it, as the user, rooted in the home the account database names, with `.ssh` out of reach and no symbolic link followed, and a file with more than one name neither opened nor changed (the size of a file can be set, within the quota, which `scp` does after an upload; the owner cannot be changed); an account without file transfer sees only `Connection closed` from `sftp` and `scp`, and the reason (`reason=file-transfer`) is in the audit log; `scp -O`, `rsync` and every program stay refused. Uploads, downloads and changes are audited with the caller's tier, and a refused request of any kind is too (`console sftp ...`, with the file names escaped and cut); a successful `stat`, listing, `readlink` or `realpath` is not. The quota counts the regular files of the home, and a directory the session cannot read makes the home count as full (see File transfer). sshd must define `Subsystem sftp ...` itself, which `console show` and `console file-transfer` check. See [Console commands](../cli/console.md#file-transfer--console-file-transfer).
- **Password cache.** `console password-cache tiers` says which tiers may keep a user's network password in the session's memory; for an allowed tier it is off until the user types `password-cache on` (`console password-cache on`) at the prompt, which saves the choice for later sessions and starts it in that one (`ssh` and `device ssh` then ask for the password themselves the first time, before they connect, and keep it). A user sets only their own choice; a superuser sees and clears the others' with `console password-cache user`. See [the shell](../cli/shell.md#password-cache).
- **Pasted lines.** A line that starts with `tacctl`, `sudo tacctl` or `/usr/local/bin/tacctl` runs as the line without it (the console takes only the rest); see [the shell](../cli/shell.md).
- **Logged.** Sessions, refused commands and system shells go to syslog (tag `tacctl-console`), every line to sudo's log, and every `tacctl ssh` session with `console=<session>`. A refused `-c` string logs its first word (`first=`) only when it is a verb of tacctl or a console word; any other word, which can be a password typed at the prompt, reads `first=- len=<n>`.
- **Undoing it.** `tacctl host unenroll <server>` gives tacctl's accounts `/bin/bash` back and removes the drop-in and the `/etc/shells` line; so does `tacctl uninstall`, which never leaves an account with a shell that is about to disappear.

The [tiers sudoers rules](tiers.md) must be installed for readonly and operator console users: without them their lines are refused by sudo.
