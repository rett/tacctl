# Tiered access

[Documentation](../README.md) › [Security](README.md)

tacctl users who have a local account on the server can be given tacctl access that follows their group:
```
tacctl config sudoers tiers show      # print the rules
tacctl config sudoers tiers install   # write /etc/sudoers.d/tacctl-tiers
```
| Local group | Tier (priv-lvl) | tacctl access |
|---|---|---|
| `tac-readonly` | read-only (below 7) | `passwd`, `status`, `version`, `help` (also `-h`, `--help`), `user list`, `user show`, `group list`, `group show`, `scope list`, `backend list`, `backend status`, `device list`, `device show`, `device notices`, `device ssh-config`, `ssh` and `device ssh` (their own scopes' devices only), `_console-policy` (the login console reads its settings with it) |
| `tac-operator` | operator (7-14) | read-only set plus `log tail/search/failures/accounting`, `config validate`, `backup list`, `device export`, `device scan`, `device discover`, `device check`, `device config list`, the CONFIG column of `device list` and the Configuration row of `device show` (and their JSON field), `console show`, `console check`, `console forget` (a word of the shell and the console), `device list --scan` and `--probe` (their own scopes' devices only; `discover` lists every unregistered address) |
| `tac-engineer` | engineer (the tier set on the group, `tier.<group>`) | operator set plus, for the devices, hosts and scopes of their own scopes only: `device add`, `remove`, `rename`, `address`, `hostname`, `vendor`, `port`, `description`, `location`, `legacy-ssh`, `config-syntax`, `hostkey`, `import -` (standard input only), `scope devices`, `config cisco|juniper|wti` (with `--staging`; `config cisco source-interface` only reads for them), `device config show <name>`, `device config pull` and `diff` (they log in to the devices as the engineer), `device config plan` (from the last pull; with `--pull` it logs in as the engineer), `host list` and `host show` (read only: another scope's host is not found, and `show --check`, which logs in to the host, is refused), `scope staging list`, and the reads of a scope of their own: `scope secret <scope> show`, `scope show <scope>` and `scope snmp <scope> show [--reveal]`, `scope block <scope> juniper list|show [--reveal]|check` and, for a device of theirs, `device snmp <name> show [--reveal]` and `device block <name> list|show [--effective] [--reveal]|check` (a secret read is logged, never the value; the SNMP settings are theirs to read only, every setter stays the superuser's, and an import of theirs neither sets nor drops a device's own settings); another scope is not found. Linux host deployment is the superuser's: `host enroll`, `sync`, `move`, `target`, `provisioner`, `unenroll` and `default-method` are not an engineer's, so an engineer changes no setting that makes a host sync necessary (a host is "not found" to the device verbs, to `device hostkey` and to `--staging`, and an engineer's change never ends a host's staging address); engineers still get accounts and sudo on the hosts of their scopes through a superuser's sync. No global setting is theirs to change |
| `tac-superuser` | superuser (15) | everything, plus full `sudo` |

**Which tier a command needs.** Every command's entry in the manual page ends with a `Requires: <tier>` line (`man tacctl`, COMMANDS), and its TIERS section lists, from the same table the gate and the sudoers rules are made from, the verbs each tier is the lowest for, with the notes for the verbs the code splits further (`scope staging`, `scope secret`, `scope snmp`, `scope block`, `device block`, `config cisco`, `host show`, `device import -`, `device config`). A tier may run what the tiers below it may; a verb on no list (users, groups, scopes, secrets, backends, backups, upgrades, every global setting) is the superuser's. The manual shows every verb whatever your tier; only the shell and the console hide what you cannot run (see [Interactive Shell](../cli/shell.md#interactive-shell--tacctl-shell)).

Lower-tier rules are plain `NOPASSWD` lines. The only things the file lets through from the caller's environment are:

- the agent socket, the console's marker, the X11 display and the colour choice (`Defaults!/usr/local/bin/tacctl env_keep += "SSH_AUTH_SOCK TACCTL_CONSOLE DISPLAY NO_COLOR TACCTL_COLOR"`): the agent socket for `tacctl host`, the login console's session marker, the display `tacctl ssh -X` hands on, and `NO_COLOR` and `TACCTL_COLOR`, which only take styling out of the output or put it back;
- `TACCTL_ASKPASS`, for the command lines that use the password cache (`device config pull|diff|plan`, `ssh`, `device ssh`, `scope|device block ... adopt`, `device config apply`, `device onboard` and `device collect`), through a `Cmnd_Alias` and its own `Defaults!` line;
- `VISUAL` and `EDITOR`, for the four command lines that open an editor (`scope block <scope> juniper edit|adopt`, `device block <name> edit|adopt`), the same way: a `Cmnd_Alias` and a `Defaults!` line of their own. tacctl removes both from its own environment at start, so no program it runs inherits them.

A caller therefore cannot hand tacctl another `SUDO_USER`; tacctl also refuses a `SUDO_USER` that is not the account of `SUDO_UID`.

Anything that prints a shared secret or a password hash (`scope secret`, `backup diff`, `config dump`, `store show`, and the walkthroughs `config cisco|juniper|wti`) is the superuser's, but for the engineer's read of the secret of a scope of their own (`scope secret <scope> show`, the walkthroughs of their scopes' devices, `scope snmp <scope> show --reveal`, `scope block <scope> juniper show <block> --reveal`; each read is logged: `secret-read kind=scope|snmp|block name=<scope> by=<user>`, never the value). `scope show` prints the scope and the secret's length only, and an engineer may run it for their own scopes. Everything that changes anything is the superuser's too, but for what an engineer does to the devices of their own scopes (`device add|remove|rename|address|hostname|vendor|port|description|location|legacy-ssh|hostkey`, `device import -`, `scope devices`, which write `devices.yaml`); `scope secret <scope> set|generate`, every `scope snmp` setter and `set`, `remove`, `edit` and `adopt` of `scope block` and `device block` stay the superuser's. An engineer also lists the [break-glass holds](../devices/break-glass.md#holding-break-glass) of the devices of their own scopes (`breakglass list`) and sees them wherever the device is shown; `breakglass hold` and `breakglass release` are the superuser's.

tacctl also checks the tier itself on every run, taking it from the user's group in the store rather than from local group membership, and logs denials to syslog. A group's tier setting that is not a tier counts as read-only. While `tacctl.yaml` cannot be read, or holds a tier setting that is not a tier (a mapping, a list, null, an empty value or a number under `tier.<group>`, or a `tier` that is not a mapping), no tacctl user is trusted above the operator tier (the denial says so, `config validate` shows the problem) and `host enroll` and `host sync` refuse, so a broken file never makes an engineer a superuser; `tacctl group edit <group> tier <tier>`, run by root, repairs it.

A group at priv-lvl 15 other than the built-in `superuser` (the built-in `readonly` and `operator` included) always has an explicit `tier.<group>`:

- `group add` and `group edit priv-lvl` record `superuser` when none is given (the band's tier).
- `tacctl upgrade` records it, once, for every such group it finds without one (one line each, after a snapshot). It leaves `/var/lib/tacctl/tier-pinned`, so a setting lost later is never silently made a superuser's by a routine upgrade.
- `store import` and `backup restore --legacy` record it for the groups the import brought, not for the ones the store already had.

A group at priv-lvl 15 with no setting (it was lost: an emptied or restored `tacctl.yaml`) is ambiguous. Its members are held at the operator tier, and a `host enroll` or `host sync` gives them the operator tier on the hosts (neither is refused, so a sync that takes rights away, as `user remove` runs, still runs) and prints one red line per group naming `tacctl group edit <group> tier <tier>`. `group show` says `NOT SET`. The members of the built-in `superuser` group and everyone else are not affected, and `tacctl group edit <group> tier <tier>` (root, or a superuser who is not a member) sets it. A legacy install (no store yet) keeps no tier settings, so it has no ambiguous groups.

Lowering a group below 15 removes a `superuser` setting, the recorded one and one chosen with `--tier superuser` alike (an `engineer`, `operator` or `readonly` setting stays): set the tier again when a superuser group below 15 is wanted. Callers who are not in the local group `tac-users` (root, local admins) are not restricted.

`tacctl upgrade` rewrites an installed `/etc/sudoers.d/tacctl-tiers` that differs from the release's rules (after `visudo -cf` accepts them), so a new release's verbs reach the tiers; the upgrade says `Updated: tiers sudoers`, or `Unchanged:`. It never creates the file, and when `visudo` refuses the new rules the old file stays and a warning says so. Until the file is current, tier users cannot run the verbs a release adds; `tacctl config sudoers tiers install` writes it.

`tacctl passwd` (no arguments) lets any tier change their own password: it acts only on the user who invoked sudo and asks for the current password first.
