# Shell, completion and manual page

[Documentation](../README.md) › [CLI reference](README.md)

## Shell Completion

`install` and `upgrade` place the bash script in `/etc/bash_completion.d/tacctl`. zsh and fish are print-only: write the script where the shell looks for it, as the user who will use it.

```bash
# zsh: any directory on fpath, then compinit
mkdir -p ~/.zfunc
tacctl completion zsh > ~/.zfunc/_tacctl
# in ~/.zshrc, before compinit:  fpath=(~/.zfunc $fpath); autoload -Uz compinit && compinit

# fish
tacctl completion fish > ~/.config/fish/completions/tacctl.fish
```

The scripts ask `tacctl __complete` for the words, so they match the installed binary; a second Tab lists each sub-command, each verb word after a name (`scope mgmt-acl lab <Tab><Tab>`) and each flag. In bash the list is the words alone, in columns, as in the shell and the console; zsh and fish show a description beside each word in their menus (at most 72 characters; a longer one ends in `...`) and, for a flag, the value it takes. Regenerate the scripts after an upgrade.

**The help key in bash.** The bash script ends with a key binding: on a line that starts with `tacctl`, the question mark prints the help of the words before the cursor (`tacctl user add ?` prints what `tacctl user add --help` prints, in colour on a terminal, as the shell's `?` does) and leaves the command line as it is. The word being typed is not part of the question (`tacctl user ad?` is the help of `user`). The key runs one thing, the hidden `tacctl __help -- <words>`, which prints the help and runs nothing else: the words are plain words to it, so a flag that waits for its value (`tacctl breakglass hold sw1 --reason ?`), a `--` earlier on the line or a hidden command is never run as a command or given `--help`; the help is what `?` shows at that place, or the usage of the last command the words name. The key types a literal `?` instead when the line does not start with `tacctl`, has a second line before the cursor, or has before the cursor anything but ASCII letters, digits, spaces, tabs and `_ @ % + = : , . / -` (so a quote, a backslash, `$ * ~ ! # [ {`, a shell operator, a carriage return or a non-ASCII character anywhere before the cursor: `ls *.?` and `echo a; tacctl user ?` type it). On a line that does start with `tacctl` and has only such words a `?` always asks for help, even inside a word (`tacctl device description sw1 why?` prints help); to type a literal one there, quote it first (`Ctrl-V` then `?`). `TACCTL_HELP_KEY`, read when the script is sourced, changes the key: unset or `?` is the question mark, a readline key spelling such as `\eh` (Alt-h) is that key instead (and does nothing outside a `tacctl` line; the question mark is then an ordinary character), and `off` binds nothing. Sourcing the script replaces whatever the key was bound to and does not restore it, and `off` only keeps the script from binding: set before the script is sourced, it unbinds nothing that an earlier source bound (start a new shell, or `bind -r '?'`). The system-wide script is sourced when bash starts, before `~/.bashrc`: to change the key, set the variable in `~/.bashrc` and source the script again after it (`source /etc/bash_completion.d/tacctl`), and start a new shell to go back to the default. `completion` is a word of the top level in the scripts and in the shell, and completes the three shells. Live names (users, groups, scopes, ...; a device or host with its vendor and scope) need root or the NOPASSWD sudoers rule; without it only fixed words are completed.

## Manual Page — `tacctl man`

```
tacctl man [--path] [word...]
```

Opens the manual page in a pager and returns when it is quit. It runs as you, with no `sudo` and no tier needed, so every tier can run it, in the shell and in the login console (where there is no `man` of your own). Without words the page opens at the top. With words it opens at that place: a section or subsection heading (`tacctl man tiers`, `tacctl man audit log`), a family (`tacctl man user` is "User management") or a command (`tacctl man device config plan` is the entry of that command). The words are matched without regard to case. The place is reached with searches in the pager (the heading or the first words of the entry, made after the searches of the entries just before it, so that a sentence earlier in the page that begins with the same word is not found; less cannot take the end of a line in a search), so `n` finds the next match; the page has no anchors. Words that name nothing open the page at the top and say so on standard error. When the output is not a terminal the page is written whole as plain text, with no pager and no bold or underline sequences (also when `groff` renders it), and the words do nothing. `--path` shows nothing and says which page is shown (below).

The page shown is always the copy the binary carries, which is the page of the version that runs, whether or not `install` and `upgrade` placed one (`/usr/share/man/man1/tacctl.1.gz`): the command works on a host where the page was never installed, and never shows an older page left there. `--path` prints `built into tacctl` and, when the installed file exists, a second line `installed: <path>` that says whether it is identical to the built-in page or differs from it. The page is rendered by `man -l` (given the page on standard input, the only page it can show), else by `groff` and shown by `less`; with neither installed the command says so and exits 1.

The pager cannot start a program, so the command is safe in the console: it is the `less` found in `/usr/local/bin:/usr/bin:/bin` (the `PATH` the programs get; `man` and `groff` are looked for there too, not in your `PATH`), started with `LESSSECURE=1` (no shell escape `!`, no editor `v`, no pipe `|`, no `s` or `:e`: they answer "Command not available") and a `LESS` of tacctl's own. `man`, `groff` and `less` get an environment made from your `TERM`, `LANG` and `LC_*` (a locale given as a path is dropped, since the C library would load the locale files of that directory) and a fixed `PATH`; `PAGER`, `MANPAGER`, `LESS`, `LESSOPEN`, `LESSCLOSE`, `MANPATH`, `MANOPT`, `MAN_*` and `GROFF_*` are ignored, and no `~/.lesskey` or `~/.manpath` is read. The page is the only file `man` is given. Without `less` the page is printed whole, with a line on standard error saying so (`more` is not used: its shell escape cannot be switched off). Inside `less`: `/` searches, `q` quits, `h` is its help.

## Interactive Shell — `tacctl shell`

```
tacctl shell

    Prompt 'tacctl> ': type commands without 'tacctl' (user list, scope show lab)

tacctl shell --no-history

    Keep this session's history in memory only

tacctl shell --idle 30

    Leave after 30 minutes at the prompt without input (0, the default: never)

tacctl shell --space-completion off

    A typed space is only a space (default on)

tacctl shell --password-cache

    Keep your network password in this shell's memory (see Password cache)

tacctl shell -c 'user list'

    Run one line and exit with its status

tacctl shell < commands.txt

    Run the lines in order; stop at the first non-zero status and exit with it
```

The shell runs as you and holds no privilege: each line runs as `sudo [-n] tacctl <words>` with the terminal attached, so sudo's rules and log, and the tier gate, apply to every line as they do from bash; prompts and password input work as usual. Tier users of the readonly and operator tiers (members of `tac-users`, who have no local password) get `sudo -n`, and a line their tier's sudoers rules do not cover is reported as not permitted; superusers (`tac-superuser`) get plain `sudo`, which asks for their network password on the terminal when a line needs it (once; sudo's cache applies), so their write verbs work from the shell. `hash`, `completion` and `man` lines run without sudo; `host` lines carry `SSH_AUTH_SOCK` as the re-exec does.

A line is split into words at blanks; single and double quotes and backslash quote as in `sh`, and nothing else is special — no variables, globbing, pipes, redirections, `;`, `$(...)`, backticks or `!`. Lines are at most 4096 bytes. A line pasted from the help or these pages may start with `tacctl`, `sudo tacctl` or `/usr/local/bin/tacctl`: that first word (and the `sudo` before it) is dropped, once, and the rest runs, completes and is explained as it would without it (`tacctl dev<Tab>` completes `device`, `tacctl ?` lists the top level); a `tacctl` anywhere else in the line is an argument. A line that is only `tacctl` prints what `tacctl` with no arguments prints, the top-level usage, and ends with status 1. The history keeps the line as typed. The shell's own words are `help` (the top-level usage), `help <command>` (that family's usage), `history`, `console forget` and `console password-cache [on|off]` (see [Password cache](#password-cache)) and `exit`/`quit` (or Ctrl-D). After a non-zero status the shell prints `[exit N]`.

**Spaces at the prompt** are handled as on a Junos device (`--space-completion on`, the default): a space is refused where it would be a second one (at the start of the line, right after a space, right before one), and where a word ends it completes the word when the word is a command, a sub-command, a fixed choice or a flag name and only one such word starts with what is typed (`de` and a space give `device `). Several matches are listed once, as `?` lists them, without a question and without paging, and nothing is inserted; more than the console's `list-max` print nothing. A word that is complete already (`user` while `user-x` exists), a name of your own (a user, a host, a file), free text and a typo get the space as typed, and so does a space inside a word and a word of dashes only (`-`, the standard input of `device import - --check`, and `--`, the end of the options). Inside quotes, after a backslash, in a Ctrl-R search, and with Tab and `?`, nothing changes. A paste is not affected: it is inserted as it is, as without the setting (a paste is one line; see Keys). That assumes the terminal sends a paste bracketed; one that does not sends its spaces as typed ones, and a paste then completes words: turn the setting off there. `-c` and batch input are not affected. `--space-completion off` turns off the refusal of repeated spaces and the completion, so every typed space is a space.

**What the lists show.** In the shell and the login console, Tab, `?`, a typed space and the top-level `help` list only the commands and sub-commands your tier can run (the rows of the [tier table](../security/tiers.md), read from the same place as the sudoers drop-in, so the two cannot differ): a readonly user does not see `store` or `install`, an operator sees `log` and `config validate` but not `host`, a superuser and a caller outside `tac-users` see everything. The verbs of `device config` are listed by the tier of each (an operator sees `list`, an engineer all but `forget` and `shapes`). A line ends with `Shown: the commands the <tier> tier can run`. The usage stays complete: `help group` describes every verb and ends with the tier each one needs (`readonly   list, show` and so on, with a note for the verbs whose sub-verbs the code splits: `scope secret`, `scope staging`, `scope snmp`, `scope block`, `device block`, `host show`, `device import`; the man page prints the same table and notes under TIERS), and `?` after a verb typed by hand names the tier it needs (`Needs the <tier> tier.`; after a command family you cannot run at all, `Needs the <tier> tier. help <family> describes it.`). The descriptions of the rows that are listed are the usage's text and can still name a verb of the family that is not listed. This is display only: the tier gate and sudo remain the check, and a command typed by hand is refused as before. The shell learns your tier from the root side (`sudo -n tacctl _console-policy`, as the console does) when it starts, in the background and within 3 seconds, so typing never waits for it; until the answer is in, or when it cannot be learned, only the read-only commands are listed, and the next Tab, `?` or space asks again once 30 seconds have passed. A disabled tacctl user (the root side answers that the account has no tier) is listed no command, as the gate refuses them all; `help`, `exit` and `quit` remain. The plain `tacctl` usage, the man page and this documentation are not filtered. **Colours.** On a colour terminal the lists are in a palette: the names of the commands (the first word at the top level: `device`, `user`, `scope`), the sub-commands, the fixed words and the options teal, the live names (users, groups, devices, hosts ...) bold, and the descriptions plain text. It applies to Tab's columns, to `?` (the sub-command list, and the `Usage:`, `Options:` and `Next:` lines) and to `-h` and `--help`. The widths never count the colour. The rule that decides colour is in [environment](exit-status.md); the console's own choice, in place of the variables its environment is scrubbed of, is `console color auto|on|off` (a superuser sets it; each console session reads it when it starts).

Keys: Tab completes commands, flags and live names (asked of `sudo -n tacctl _completion-names`, kept 5 s); a second Tab lists the matching words alone, in columns that fit the terminal. `?` inserts nothing and shows help for the cursor's position: where words can come, `Possible completions:` with each one's argument column (at most 40 characters, a longer one is cut and ends in `...`; the whole form is in the usage of the command; a name with no column, such as a long device name, is cut the same way) and description (a long one goes on under its column, with the blanks that align a device's vendor, address and scope kept; a command or sub-command has the same description as in the completion scripts above; devices and hosts with vendor, address and scope; a fixed word such as `priv-lvl` after `group edit <name>` with the description of the usage line that has it); after a command that takes arguments, the usage lines of the forms the words typed so far fit, its options and what comes next (`Next: <username> <group>`; where the forms part, the choice: `Next: <name> priv-lvl|juniper-class|wti-level|tier ...`; `Next: <Enter> to run`). `-h` or `--help` after the words of a command, in the shell and from bash, prints that same help, from the same code (a command with sub-commands lists them; another one prints its usage, options and `Next:`; see [conventions](conventions.md)). Inside quotes, or after a backslash (`\?`), `?` is typed as a character. A list of more than 40 entries (the console's `list-max`; the shell's own is 40) asks first (`Show all 45 devices? [y/N]`): `y` shows it, any other key (or Ctrl-C) prints how to narrow it and gives the line back. Help from `?` taller than the terminal is shown a screenful at a time (`-- more (Space: page, Enter: line, q: quit) --`; `q` or Ctrl-C stops). Up/Down walk the history, Ctrl-R searches it (Ctrl-R again: older; Enter runs; Ctrl-G restores the line). Esc-b/Esc-f (Alt-Left/Right) move by word; Home/End, Ctrl-A/E/K/U/W/T/L as usual. A paste is one line (newlines become blanks, at most 4096 bytes) and runs only on Enter. Ctrl-C discards the line, or ends the running command; Ctrl-Z and Ctrl-\ do nothing (no job control, inherited by the commands).

History lives in `~/.local/state/tacctl/history` (0600, newest 1000 lines). Lines are stored redacted: everything after `--secret`, `--hash`, `--password`, `--email`, `--note`, after `set` in `secret … set`, after `import` with a value, after the word of a `passwd` line, after the name in `user email <name> <address>` and from the first word with an `@` in a `user` line (an address typed in the place of a name) becomes `…(redacted)` (`scope secret lab set x` → `scope secret lab set …(redacted)`); a recalled redacted line is refused. Lines ended with Ctrl-C are not stored; batch input is never stored. In a batch (`tacctl shell < file`) the commands get no stdin, so questions cannot be answered from the file — use `--yes` where a command has it. Over ssh, ask for a terminal to get the interactive shell: `ssh -t <host> tacctl shell`; without `-t` ssh allocates none, the shell reads commands from standard input, and it says so on stderr.

### Password cache

`device config pull` (and `diff --pull`, `plan --pull`) and `tacctl ssh` log in to devices with your own network password. In a shell or console session that password can be asked once and kept **in memory, for that session only**, so a pull of sixty devices, a diff and a few `ssh` lines ask once:

```
tacctl console password-cache tiers [<csv>|none]

    the tiers allowed to use it: operator, engineer, superuser; default none (superuser sets it)

console password-cache [on|off]

    your own choice, off until you turn it on: a word of the shell and the console, see below

tacctl console password-cache idle [<min>]

    forgotten after this long without a use (1-120, default 15)

tacctl console password-cache max [<hours>]

    forgotten this long after it was cached (1-24, default 8)

console forget

    a word of the shell and the console: forget it now
```

`console password-cache tiers` is the **permission**: it names the tiers that may use the cache, and nothing changes for a tier that is not listed. For a tier that is listed the cache is not automatic: it is on in a session when your tier is allowed **and you have turned it on for yourself**, which is off until you do. Type `console password-cache on` at the prompt of the console (or of `tacctl shell`): it saves your choice for every later session and starts the cache in the running one at once (the first device login that asks for your password keeps it: the logins `tacctl` makes itself store the password after a device accepts it, and `ssh` and `device ssh` ask for it themselves the first time, before they connect, see below). `console password-cache off` saves that, forgets a cached password at once (`password forgotten (console password-cache off)`) and stops caching. With no argument the word prints the permission and limits (`tiers`, `idle`, `max`, `your tier (operator): allowed`, `your setting: on|off`) and whether a password is cached in this session now. When your tier is not allowed, `on` is refused in one sentence naming the fix (a superuser runs `console password-cache tiers ...`) and saves nothing. Each user sets only their own choice (the word takes no name, and the root side takes the user from the one `sudo` was run by); a superuser sees who turned it on with `console password-cache user` and switches a user's choice off with `console password-cache user <name> clear` (a session the user has open keeps its cache until it ends or they turn it off). A user who is renamed keeps the choice, and a removed user's is dropped. A plain `tacctl shell --password-cache` is an explicit request and stays as it was: it needs only the tier's permission (a caller outside `tac-users` asks for it themselves). It is for the interactive session only: `-c` and batch lines keep no process to hold it, and the plain CLI from bash asks per run.

How it works: the shell process itself holds the password, in a page it locked in memory (`mlock`; when memory cannot be locked, a debugger is attached, or no private directory is available for the socket, there is no cache and one line says `password cache unavailable: <why>`: `cannot lock memory`, `this process is being traced` or `no private directory for its socket`), in a process marked not dumpable, zeroed when it is forgotten. It is never written to a file, a log, an argument or the environment. The shell listens on a socket in a private directory (`$XDG_RUNTIME_DIR/tacctl`, else `/run/user/<uid>/tacctl`, else `~/.local/state/tacctl/run`, mode 0700) and is shut between lines. For a line that runs `device config pull`, `device config diff --pull`, `device config plan --pull`, `ssh`, `device ssh`, `block ... adopt`, `device config apply`, `device onboard` (for your own password after its review), `device collect` or `device enroll`, and for no other line (a `diff` without `--pull` logs in to nothing, and a line with `--login <local-user>` logs in as a device's local account, whose password never comes from or goes into the cache, so their lines leave it shut), it mints a token and puts `TACCTL_ASKPASS=<socket>:<token>` in the environment of that line's `sudo` process, never on sudo's command line; the tiers drop-ins keep that one variable for those command lines only. The token exists only for that line: the agent answers only while the line runs, only to your own user or root (`SO_PEERCRED`), only with that token, and gives the password once; after that single `get` the token is good for nothing but `forget`, and when the line ends it is dead (a value read from an earlier line is refused). A second ask on the same line is a refusal and forgets the password. What remains is the usual one for a secret handed through an environment: a process of your own user that reads the pull's or ssh's environment during the line, and gets to the socket before the single `get` of that line, is answered as the line would be. Which lines use and which store: every line named above uses a cached password. The logins `tacctl` makes itself (`device config pull`, `diff --pull`, `plan --pull`, `block ... adopt`, `device config apply`, `device onboard`, `device collect` and `device enroll`) ask the cache, and when nothing is cached they prompt on the terminal; after the first device **accepts** a password they prompted for it is stored (a password that came from the cache is never stored again, so the maximum lifetime cannot be extended by use). A device that refuses the password makes the cache forget it at once and the run stops starting new devices. `ssh` and `device ssh` ask for your password themselves the first time, before they connect, and keep it: with the cache on and empty, for a device with pinned host keys and no option of ssh's own after `--`, they prompt `Password for <you> (device login):` on the terminal (no echo; Ctrl-C ends the line with status 130 and starts nothing, an empty answer stores nothing), store the answer in the cache and then connect by the path below, so the password is typed once, before the device banner, and the next `ssh` to any device asks nothing. Their audit line ends `password=asked` for the line that prompted and `password=cached` for the lines that used the cache. The password is stored before the device has seen it, so a wrong one stays only until the first ssh that ends with status 255 (an authentication or connection failure), which forgets it: a typo costs one more typing, as with ssh itself. Only the password `ssh` asked for itself is stored, never a word a device asks for later, so a device cannot make the session keep anything. Without a terminal to prompt on, for a device with no pinned host key, with an option of ssh's own after `--`, or when the account is not in the local account database, ssh asks for the password itself, as it always did, and nothing is cached. `tacctl ssh` uses a cached password only for a device with pinned host keys: ssh is then started as you directly, without sudo (your uid, gid and groups; an explicit environment of `HOME`, `USER`, `LOGNAME`, `PATH`, the terminal and locale, and the display), so the token is never a `sudo` variable or argument and reaches no log. It asks the shell's agent for the password through `SSH_ASKPASS` (this binary, which answers a password prompt and nothing else), `SSH_ASKPASS_REQUIRE=force`, one prompt (`NumberOfPasswordPrompts=1`), no configuration file and `StrictHostKeyChecking=yes` against the pinned keys; an ssh that ends with status 255 forgets the password. An account that is not in the local account database keeps the prompt.

It is forgotten when the session ends, after the idle time, after the maximum lifetime, when you change your password (`passwd`, `user passwd`), when a device refuses it, when the clock goes backwards, and by `console forget`; the shell says `password cached for this session (console password-cache)` when it keeps one and `password forgotten (<why>)` when it lets go. The cache protects the password against other users and against its landing in files, logs, arguments or the environment; root can read any process, and hibernation can write the locked page to disk.
