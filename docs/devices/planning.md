# Planning a device's change

[Documentation](../README.md) › [Network devices](README.md)

`tacctl device config plan` turns the last pull into what a technician pastes to make a device match what tacctl renders: the report first, in plain words (what is irregular on the device and what the paste does about each item), then one region between two banners that is copied once and pasted once, then the check and the one line to type yourself afterwards. It connects to nothing (`--pull` reads the devices first, as `device config diff --pull` does) and writes to no device, ever: the paste is the technician's.

```
$ tacctl device config plan sw-lab-1
##### sw-lab-1  192.0.2.21  scope lab  juniper (TACACS+) #####
# Based on the pull of 2026-10-10 14:02 by alice over netconf (18 minutes ago; the login could see
# secrets) and the standard of 2026-10-10 14:20 (tacctl 0.2.5).
#
# What is irregular on sw-lab-1 (4 items; the paste fixes 1, leaves 3):
#  1. aaa      ACCESS     extra: a TACACS+ server 192.0.2.99 (set system tacplus-server 192.0.2.99
#                         secret <secret>). Left alone. To remove it later: delete system
#                         tacplus-server 192.0.2.99
#  2. snmp     COSMETIC   missing: the SNMP description is Core switch (set snmp description "Core
#                         switch"). Fixed by region line 3.
#  ...
# Consistent: roles, mgmt-acl. Not planned: netconf, breakglass (walkthrough Steps 6 and 7).
# Secrets: 3 present on the device, not changed (--secrets pushes them).
# The switch undoes this by itself in 5 minutes unless you type the one word after the check (see
# below).
#
# Type this first, on sw-lab-1, and check the name:   show version | match Hostname
# The region opens configure exclusive: the session holds the configuration lock until you type exit
# (after commit, to confirm). If it printed "error: configuration database modified", another session
# has uncommitted changes: have that person commit or discard them, then paste again. If it printed
# "error: configuration database locked by", another session holds the exclusive lock: wait for it to
# exit, then paste again. Either way nothing happened (every later line is an unknown command).
#
##### PASTE FROM HERE: sw-lab-1 #####
configure exclusive
# snmp: the description tacctl renders
set snmp description "Core switch"
show | compare | no-more
commit check
commit confirmed 5 comment "tacctl plan sw-lab-1 2026-10-10T14:20Z by alice"
##### PASTE TO HERE: sw-lab-1 #####
#
# Check now. In 5 minutes the switch undoes this by itself unless you type one word.
#   From the tacctl server:   tacctl device config pull sw-lab-1 --diff     (snmp: ok)
#   In a second terminal:     ssh sw-lab-1, then: show cli authorization | no-more
# When both checks are fine, type this one word yourself:  commit     (before the 5 minutes end)
# ...
```

- **One region, nothing to select.** Between `PASTE FROM HERE` and `PASTE TO HERE` there are only statements the device takes as they stand, the wrapper lines, and one label comment per section; no kept line, no warning, no alternative, nothing to uncomment. Everything else, the report, the check, the follow-up and the back-out, is a comment line outside it. Both banners carry the device's name, a file is named by the device, and the line to type first (`show version | match Hostname`, `show version | include uptime` on IOS) prints the name to check against the box.
- **Safe when pasted whole.** On Junos the region is `configure exclusive`, the statements, `show | compare | no-more`, `commit check` and ends at `commit confirmed N comment "..."`: without the follow-up the switch rolls back by itself in N minutes (`config devices confirm-timeout`, 1-60, default 5), and `commit` (the one word) is typed by hand after the check. The session holds the configuration lock until you type `exit` (after `commit`, to confirm); a private session cannot be used, because Junos refuses `commit confirmed` in one. If `configure exclusive` printed `error: configuration database modified`, nothing happened (every later line is an unknown command): another session has uncommitted changes, so have that person commit or discard them, then paste again; `error: configuration database locked by: <name>` means another session holds the exclusive lock: wait for it to exit. On IOS the region is `configure terminal`, the lines, `end`; the change is live at `end` and **nothing rolls it back by itself**: there is no revert timer, because on IOS 15.x it reverts only while the session that armed it stays open, which fails the case that matters: a paste that cuts the technician's own session. `write memory` is the follow-up after the check, never in the region; until it is typed a reload brings back the saved configuration. Keep a second terminal logged in at privilege 15 until the end.
- **The report.** One item per finding of the comparison: *missing* (a standard line the device lacks), *different*, *out of order*, *extra* (a line in a standard hierarchy the standard does not have), *secret not visible* and *not plannable for this login*; its section; the statement in plain words with the line (a secret's value elided); **what the paste does** (`Fixed by region line 3`, `Left alone`, `Not fixable by this login: EN-CLASS cannot change 'snmp' (ask a superuser)`); and its severity: `ACCESS` (anything on the login path: AAA, the authentication order, template users, the management filter, a second AAA server), `MONITORING` (SNMP communities, clients) or `COSMETIC` (order, contact, location, accounting events, privilege lines). `device config diff` is the same comparison line by line for engineers; `plan` is the explained version with the commands.
- **Extras and `--converge`.** A statement in a standard hierarchy that the standard does not have is reported with its severity and the exact line that removes it, and left alone: one paste fixes what is safe to fix, and the person who runs `plan` decides about the rest once, not the technician per line. `--converge` makes the **cleanup region** for a device that has nothing else to paste: the plan made after the paste and the pull that verified it (`tacctl device config pull <name> --diff` reads `ok` for `aaa`, and a new session as yourself works), so the paste that adds the new server is never the one that removes the old. That region is the whole output of the device, between `CLEANUP FROM HERE` and `CLEANUP TO HERE`: it is never beside a first region, because whoever copies a whole output runs every region in it (on Junos the second `commit check` would confirm the first region's pending `commit confirmed` unverified). A device that still has a first region gets that region and one report line, `cleanup comes after this region is pasted and verified: pull the device, then plan --converge again`. The cleanup holds only other servers of the scope's own protocol and their groups (IOS: the legacy `tacacs-server host` form, a `tacacs server` block, an old `aaa group server` with its entries first, then the group, then the server it names; Junos: another `system tacplus-server` (on a RADIUS scope another `system radius-server`: never the other protocol's, which may serve accounting or another login method, nor a server that a staying `system accounting destination <protocol> server <address>` names), a login class no user uses, the entries of another `snmp client-list`). Another SNMP community is never in it: its name is not known to tacctl, so it and what is under it stay (`ok (+N unmanaged)` when nothing else differs). On Junos the check pull the first region asks for is taken before its `commit`, so the cleanup's report and follow-up also ask that `show system commit` shows no pending `commit confirmed` (type the plan's `commit` first). Never a login, a line, the enable secret, a method list (a named `aaa authorization commands` list included: the pull does not say which line uses it, so the report gives the `no` line to type when you know it is not in use), another ACL, a server or group of the other protocol (the RADIUS of an 802.1X switch on a TACACS+ scope), or a server or group that a statement which stays names (a group in `aaa authentication login VTYLIST group OLD local` stays, and the servers it names; while a staying list uses `group tacacs+` or `group radius` no server of that protocol goes); never a line that holds the address given with `--from` (without `--from` no client-list entry is removed: it could be your own source); and the whole cleanup is refused while the standard's server is missing and the paste does not put it there. A section the pull's login could not see completely is not cleaned. `--converge --json` has the `cleanup` list and, for a device with a first region, `cleanup_deferred`.
- **The back-out.** `--backout` prints the back-out region alone (`BACK-OUT FROM HERE` ... `BACK-OUT TO HERE`): the statements that put back what the pull showed, for the sections the plan changed (on IOS the `no` lines in reverse order, with the console and VTY login leaves typed again, never a `no line`; a secret tacctl does not hold is a comment saying to type it again). The check the plan asks for is a pull, and a pull replaces the picture a back-out is computed from; so every plan that has changes **keeps its back-out** beside the device's record (`<name>.backout`, 0600, stamped with the pull it was computed from, the device's address and the sections it undoes; a secret's value is never in it; `device config forget` and `device rename` carry it). `--backout` prints the kept one whenever one exists, whatever pull it was made from (it is what was pasted), with a first comment line that names the sections and the pull (`This back-out undoes the plan of aaa, snmp made from the pull of <time> (UTC)`), and prints it even when the plan itself cannot be made (a stale record): with one line on standard error. A narrower plan from the same pull (`plan <name>`, then `plan <name> --section snmp`) does not replace it; a later plan with changes does, and the report then says `this plan replaces the kept back-out of the plan from the pull of <time> (UTC); print it first with 'tacctl device config plan <name> --backout'`; a plan with changes and no line tacctl can type to undo them removes it and says so, so that an earlier plan's back-out is never printed for it; a plan with nothing to paste leaves it. For a device name whose address changed since the plan it says `nothing to back out: the kept back-out is for another device address` (exit 0); with none kept it computes it from the pull, and with no plan to undo it says `nothing to back out: no plan was made from an earlier pull of <name>` (exit 0). `--backout --pull` is refused (exit 2: the pull is the picture it would replace). `--out-dir` also writes it beside the plan, as `<name>.backout.txt`.
- **Cisco: the standard block, in two steps.** The region follows the order of the standard block (`aaa new-model`, the server, the group, the method lists with `aaa authorization exec` directly after the login list, accounting, `roles`, `snmp`, `mgmt-acl`, the console and VTY login leaves). **Command authorization (`aaa authorization commands <level>`, `config-commands`) is held back** until the pulled configuration already uses the scope's server (its address in a server block or host line and a login or exec method list that names the group): once the commands list names the server, every further command of the pasting session and of its back-out is asked of the server, which answers FAIL for a user it does not know and never falls through, so a device whose TACACS+ path has not been proven could end with no session able to run a command. The report then says `command authorization is not in this paste: log in on a new session with your own account and check 'show privilege', then plan again; it is the one group of lines left`: the first plan puts everything else, the check proves the path, the second plan adds the one group of lines. A `default` list of `aaa authentication enable` on the device (the standard has none: `enable` is the local enable secret) is removed with its own `no` line, the full statement, after the added lines; the back-out types it again, and a list of another name is left alone. A device that has no local user at privilege 15 and no `aaa new-model` is refused for `aaa` (add the break-glass user first). The device's configuration syntax is the one resolution of `device config-syntax` and the pull's version line (a Cisco device that needs a pull is `cannot be planned`); the ssh flag has no part in it. The report says which release trains the standard block was checked on and that the other trains are written from the vendor's references.
- **Cisco: a restore point (`--restore-point[=<fs>]`, IOS and IOS-XE only).** The region's own way back is the back-out's `no` lines; the flag adds a file to go back to. The output gets a block of its own before the region, outside the `PASTE FROM HERE` banners, between `RESTORE POINT FROM HERE: <device>` and `RESTORE POINT TO HERE: <device>`: one `copy running-config <fs>tacctl-<device>-<yyyymmdd-hhmm>.cfg` and one empty line (it answers the `Destination filename` prompt; a paste tool that drops blank lines turns the closing banner into the file name, and `file prompt quiet` turns the prompt off). `<device>` is the device's name up to its first dot (IOS limits a file name to about 63 characters) and the time is the plan's, in UTC. The comments above the block say to paste it first and on its own at the privileged prompt, to check that `dir <fs>` lists the file, that the file holds the device's secrets in their own forms (protect it, delete it when done) and needs free space, and that it is a file and no rollback timer: IOS has no commit-confirm for a pasted plan. **The file system** is the one named (`--restore-point=disk0:`: lower case letters and digits, then a colon; a network file system such as `tftp:` is refused, since its copy asks for more than one empty line answers), or, for the bare flag, the device's own archive path, which the pull keeps in its record (the file system word only, never the host or user of a remote path): the block is then the one line `archive config`, which asks for no name. A bare flag for a device whose last pull read no archive path is refused with exit 2 and says to name a file system or to pull again. **The back-out** gains an alternative after its `no` lines, as comments: `configure replace <file> force` (for `archive config`, the newest entry of `show archive`), with the caveats: where a release lacks it, `copy <file> running-config` only merges, on IOS 12.4 a replace can skip the removal of `aaa new-model` or stop at a line it cannot remove (an `ntp server` with options): do not rely on it for AAA, use the `no` lines, and the file and any copy the replace leaves are to be deleted afterwards. The kept back-out records the file (its first comment line says `its restore point is <file>`), so the name in the back-out is the one the block made. Off by default: without the flag the IOS output has no restore point block. The flag is refused for a device of another vendor (naming it), with `--plain` and with `--backout`; the region's whole-paste check still refuses a `copy`, and the block has an allowlist of its own (exactly `archive config`, or one `copy running-config <fs>tacctl-<name>-<time>.cfg` and one empty line). The report says that the `archive config` form is not checked against a device.
- **A server entry of another name at the standard's address.** IOS silently refuses a second server entry with the same address and key, so a device that holds the standard's server as a named `tacacs server <OTHER>` block or as the legacy `tacacs-server host` line on a modern image cannot take `tacacs server TACACS` beside it. The region replaces it in an order that keeps the pasting session: (a) the command-authorization lists that name the group are taken off first (`no aaa authorization config-commands`, then each `no aaa authorization commands <level> ...`), typed while the server still answers; (b) the group's `server name <OTHER>` or `server <address>` entry, then the old block or `no tacacs-server host <address>`; (c) the standard block, the group's `server name TACACS` and the rest of the standard's order; (d) the lists again, last. A group of another name that held the old entry is pointed at the standard block by its own name, so the method lists that name it keep resolving; the report says which entry is replaced and why. The back-out is the inverse (the old block and entry back, its key a note for you to type, the lists last; it starts by taking command authorization off). A `radius server <OTHER>` block at the standard's address and ports is replaced the same way. Only a device that authorizes commands and shows no server in use (no login or exec list names a group), where nothing proves the pasting session is a TACACS+ user, is refused for `aaa`, with the steps by hand below the region. The old entry is removed by the region only when the plan types the standard block's address or key.
- **Secrets.** A secret the device lacks (a missing server key or community) is typed in its line, and the output then says `THIS OUTPUT HOLDS THE TACACS+ KEY OF SCOPE lab` (first line of the report, and on standard error so a redirected output carries it); one the device has, or one the pull's login could not see, is neither printed nor changed unless `--secrets` (then every secret statement of the planned sections is typed again, the way to rotate a key). `--no-secrets` leaves each as a comment line (`# VALUE NEEDED, then remove this mark: ...`) so a paste as it stands cannot set the literal `<SECRET>`; `--plain --no-secrets` is refused. `--json` never holds a value, and the audit line says only `secrets=none|values|placeholders`. The values are the ones `device config show` prints for the same caller, and an engineer's print logs `secret-read`.
- **Formats and files.** `--plain` is the region's statements alone, no wrapper line, no comment, no banner, for `load set terminal` / `load set <file>` on Junos (one device; with `--converge` a device that has a cleanup makes two files, the plan's and `<name>.cleanup.set`); `--json` one object per device (`name`, `scope`, `vendor`, `based_on`, `status` `consistent`, `needs-change`, `left-alone` or `cannot-plan`, `reason`, `irregularities`, `region`, `after`, `backout`, `extras`, `withheld`, `warnings`, with `--restore-point` `restore_point` (`mode`, `file`, `command`, `file_system`, `note`), and with `--converge` `cleanup`, `cleanup_after`, `cleanup_deferred`); `--out <file>` one device's output in a file; `--out-dir <dir>` one file per device (`<name>.txt`, `.set` with `--plain`, `.json` with `--json`), each plan's `<name>.backout.txt`, and for several devices `COVER.txt`. Files are 0600 and written as the user who ran sudo, with that user's own user and group alone (a directory that only a supplementary group of the user may write is refused), into a directory that is 0700 (an existing directory open to others is refused); an existing file is refused, all of them before any is written, unless `--force`; the name of a device's cleanup file and `COVER.txt` (when a cover is written) count as files of the run, and a device that cannot be planned gets no `--plain` file (an empty one would read as nothing to load). A `--plain` run that writes a device's file also removes that device's `<name>.cleanup.set` (`<out>.cleanup.set` for `--out`) of an earlier plan when it does not write one itself, and a text `--out-dir` run removes `<name>.backout.txt` when the plan has no back-out to write (each says so on standard error), so an old cleanup is never left beside new statements; `--plain --converge` says on standard error why a device has no cleanup file (deferred to after the first region, refused, nothing to remove). Several devices print the **cover page** first, one line per device (`consistent`, `needs change: 2 irregularities fixed by the paste, 1 left (1 ACCESS), 1 extra`, `NOT consistent, nothing to paste`, `cannot be planned: not pulled`), then the outputs separated by a rule; `--plain` of several devices is refused without `--out-dir` (a paste into the wrong device is the one mistake the output is built to make hard).
- **A WTI unit: steps to type and one block to paste.** A unit has no configuration to paste: its settings are the items of numbered menu pages, a value is live as soon as its Enter is accepted, the configuration is written to flash when a top-level menu is left with ESC, and the unit has no commit-confirm and no rollback. So its plan is, after the report, the check (`/H` must show `Version 8.10`; `/J` shows the Site ID the pull read), a serial console or second session to keep open and `/SN` to see that no other administrator is on the unit (the pull's count of other sessions is in the report), **a numbered checklist** between `DO THESE STEPS ON: <unit>` and `END OF STEPS`, one comment line for each setting that differs: the keys typed from the prompt (`/N  28  4`), the item as the unit prints it, what to enter after the arrow (a pick's number and its text, a number, or the text; an address item asks the protocol first, `1 (IPv4), then 192.0.2.10`) and `was:`, the value the pull showed. The order cannot take away the way in before the step that needs it: Multiple Logins first of all (`/N  31`, a pick of Off or On, rendered On: a unit with it Off refuses the second session that every check, and the pull itself, logs in from, and the report says why the step goes first), then the SNMP page, then the page of the scope's protocol (the secret word only when the pull shows it undefined, the host, the port, the service name, the Default User Access page, the account and session modules, the fallback timer, Fallback Local, Debug, and the protocol's Enable last), then `ESC ESC` (the save) and a `CHECK` step (a login as a member of the scope from a second session and `/H`). A secret step names the command that shows the value (`<the scope's TACACS+ secret: tacctl scope secret show lab>`, `tacctl scope snmp lab show --reveal`); a unit's plan types no secret unless `--secrets` is given, and then the output says so on its first line and on standard error (`--no-secrets` is the default made explicit). A step on the AAA page carries a warning that a wrong secret word, host, port or service name does not stop a login but returns every login to the unit's Default User Access level. **The IP tables list is presented, never applied.** Between `IP TABLES (replaces every entry; see the notes)` and `END OF IP TABLES` there is one `<iptables>` block, the whole rendered list followed by the unit's own tail exactly as the pull showed it (the final DROP, the OUTPUT ACCEPT and the three policies; with none shown, the plan warns that the list restricts nothing until the walkthrough's last step), which is pasted at the page's prompt (`/N`, 5) and replaces every entry; its lines are the only lines of a unit's output that are not comments, so a copy of a whole output pastes nothing else. An entry the unit lacks, an extra entry of its own or another order is one finding, fixed by the paste. The section is refused, with the reason in the report and the rest of the plan still made, when the list would hold more than 48 entries (the tail counted) or an entry the paste does not take (not printable ASCII, not `iptables -A` or `-P`, longer than 256 characters), when it does not permit the tacctl server's address to reach the unit's ssh, or when it does not permit the address given with `--from`; without `--from`, a list that ends with the final DROP, and other sessions on the unit at the pull, are warnings. A plain entry of the permit list renders as a rule for every protocol and port, so a list that pastes one carries the report note `N plain permit(s) of the rendered list allow every protocol and port from the source (...)` (the unit's telnet and web pages included; `<cidr>:tcp/22` restricts a permit to ssh); the check that the tacctl server and `--from` reach the unit's ssh reads a rule for tcp 22, a port range that holds 22, every tcp port and every protocol. A scope with no management permit list (or none that permits ssh) has no IP tables section, and one whose server address is not known is refused for it. What the standard does not render and the unit has is its own and is left alone (the SNMP system name and trap settings, the tail, the other protocol's page while it is switched off); a second host, a read/write community, the other protocol's page switched on and a local account the scope does not record are findings, each with the step that removes it (`/N 25 8`, then `<SPACE><CR>`), and `breakglass` is compared and reported, never planned (walkthrough Step 10). `--backout` prints the steps again with the pulled values as targets, last step first, a secret or community as a line that says to re-enter the one you keep, and the old list as an `<iptables>` block (an old empty list: clear the slots one by one with `<SPACE><CR>`), the list first because it is the change that can lock out; it is never part of the plan's own output. `--converge` offers only the removal of a read/write community and the other protocol's Enable set to Off, for a unit with nothing else to type. `--plain` and a `--section` of `roles` or `system` are refused for a unit (exit 2), and `--out-dir` writes `<name>.txt`, `<name>.backout.txt` and `COVER.txt`, never a `.set`.
- **Cannot be planned** (exit 1, one line on standard error): a device never pulled (`tacctl device config pull <name>`, or `--pull`), a pull older than `stale-days` (a technician must not paste from a stale picture), one whose last pull failed, a Cisco device whose syntax is not known, and a plan with nothing to paste because a section was refused: a statement that a Junos group applies (`display inheritance` against the plain view the pull also reads), the lock-out guards of the `aaa` unit, the guards of a WTI unit's IP tables list when no step is left. Exit status: 0 the outputs were made (a consistent device included), 1 a device cannot be planned, 2 wrong arguments (with `--exit-code` also: a device needs a change and none could not be planned), 130 interrupted.
- **Who.** An engineer plans the devices of their own scopes; a section their login's class cannot commit (an `EN-CLASS` login: the server, accounting, `login`, `snmp`) is not in the region and the report says so in one line (`Not fixable by this login`), the class being the one of the caller's group as the rendering gives it. An operator may not plan (`device config list` only). The audit line is `device config plan user= device= status= sections= converge= secrets= out=`.
- **What it never emits**, whatever flag is given: `breakglass` (a walkthrough step), `netconf` unless the scope's or the device's NETCONF setting enables or disables the service (then exactly `set system services netconf ssh`, its two limits with a value of 1 to 250, or `delete system services netconf`: a trace option, the port or a limit the setting states none of is the device's own and is kept), the application of the management filter on `lo0` and the `access-class` binding, `system root-authentication`, `system services ssh`, groups and `apply-groups`, `username`, `enable secret`, a `line` header or `no line`, a plain `commit`, `exit`, `rollback`, `write memory`, `configure confirm`, `copy`, `delete /force`, `reload`. Everything in a region is checked to be printable ASCII and of an owned shape before it is printed; a region that fails the check is not printed.

## Applying a plan

`tacctl device config apply` is the step after `plan` for a Junos device, and the superuser's: it types the same statements into the device itself, under a confirmed commit, and proves the result, where `plan` prints them for a person to paste.

```
$ tacctl device config apply --scope lab
Password for alice (device login):
  sw-lab-1  checked: shape 3f2a1b9c0d4e (new) (aaa, snmp: 5 set, 1 delete); kept 1; check ok
  sw-lab-2  checked: shape 3f2a1b9c0d4e (new) (aaa, snmp: 5 set, 1 delete); kept 1; check ok
  sw-lab-3  no change

Shape 3f2a1b9c0d4e, 2 devices (sw-lab-1, sw-lab-2), not confirmed yet:
  aaa      the authentication order tacctl renders; tacctl's TACACS+ server
    set system tacplus-server 192.0.2.10 secret <secret>
    ...

Apply to 2 devices (sw-lab-1, sw-lab-2), one shape's first device at a time, each under commit confirmed 10 and kept only after a fresh login as alice works and what landed is what the check showed?
  Type 2 to go on: 2
  sw-lab-1  committed, verifying ...
  sw-lab-1  confirming ...
  sw-lab-1  applied (aaa,snmp: 5 set, 1 delete) [tacctl-20261013T141201Z-3f2a]
  sw-lab-2  applied (aaa,snmp: 5 set, 1 delete) [tacctl-20261013T141233Z-81c0]

  2 applied, 1 no change
```

- **Two phases, one question.** Every selected device is checked first, in the pool of `pull`: tacctl reads it, plans from that read, loads the statements in an exclusive configure session (`configure exclusive`: a private session does not take `commit confirmed` on the devices of the lab, so there is no other mode), runs the device's own `commit check` and discards the candidate. `--check` ends there: nothing is committed, the device's shape and result are recorded. The devices that need a change are then shown grouped by shape and by what the review shows of each (two devices of one shape whose warnings, sections left out, kept statements or not-found deletes differ are two headings), every secret elided, a statement whose per-device value differs printed for each device after its name, with what the plan keeps and what it leaves out, and ONE question is asked: type the device's name (one device) or the number of devices back. A device whose plan refuses a section (what makes `device config plan` exit 1) is not applied: its row is `failed: the plan refuses <section> (<why>)`. A terminal is needed; without one the only way through is `--confirmed --yes`. `--yes` without `--confirmed` is a usage error: a batch of shapes nobody reviewed is not run blind.
- **What an apply proves.** The device is committed under `commit confirmed N` (`config devices apply-confirm-timeout`, default 10), then a second connection logs in as you through the device's own login path, `show system commit` must show tacctl's commit and the device's banner must say a confirmed commit is pending, `show configuration | compare rollback 1` must be the change the check showed, and a read of the planned sections must lack nothing. Only then, with a minute of the window left, the confirming `commit` is typed in the session that committed (no other session ever confirms for it). A proof that fails cancels the commit (`rollback 1` and `commit` in the held session) and the device is `rolled back`; a window that ran short is left to the device's own expiry. `--hold` adds the one proof a machine cannot make: after the fresh login you log in with one account of each class in another terminal and type `OK`; anything else, or no answer while a minute of the window is left, rolls the change back. A line typed before a device's question is not its answer. `--hold` needs a terminal and is refused with `--json` (exit 2).
- **Pending.** Over the command line a device undoes a confirmed commit only when its window ends, not when tacctl's session dies, and any `commit` or `commit check` typed on it confirms the change. A device whose state could not be read after the confirmed commit is therefore reported `PENDING until <time>` (and said in red on standard error): type nothing on it before then. The record says `pending` with the identifier and the window's end from the moment the confirmed commit is typed, so a tacctl killed during the verification leaves a record the next run settles (a record that cannot be written then is said at once in red on standard error, and the transaction goes on); `device config list` and `device show` say it, and the next `apply` or `--check` of that device first reads its commit history, records what happened (`applied`, `rolled-back`) and only then goes on; while the window stands it sends nothing. Where the history alone does not say (the commit after tacctl's is `by root via other`, the device's own rollback or a commit of the system, or someone else's), the device's rollbacks do: with tacctl's commit at history entry N, `show configuration | compare rollback N` empty is `applied` and `compare rollback N+1` empty is `rolled-back`, both read in one operational session; anything else is `unknown`, never applied, whatever the rendering is now. The settled result is printed above the device's line (`the earlier apply <id> by <user> was rolled back by the device at <time>`; JSON `settled`) and logged (`device config apply settle user= device= id= result=`). If the history can no longer say, the refusal names `device config forget <name>` for after the device was looked at by hand.
- **Shapes and the batch.** Two devices that need the same change have one shape: a hash of the statements with every secret elided and every per-device value (a location, a contact, a name) masked, so it is known before any device is dialled. The first device of each shape goes alone and the others of its shape follow only when it applied (`--no-canary`: together); `--concurrency` applies several at a time (default one), `--pause <seconds>` (default `config devices apply-pause`, 60) waits between devices, `--max <n>` (default 5) caps the devices of every apply run, and `--max-failures` defaults to 1. At the start of each device's apply the break-glass hold, the registry entry (name, address, vendor, hostname, port, host keys) and the scope that covers it are read again: a device held, changed or no longer yours since the review fails with the reason, and nothing is sent to it. `--confirmed` runs only the devices whose shape an earlier apply confirmed and skips the rest (`unknown shape <hash>: review and apply it by hand first`). `tacctl device config shapes` lists the shapes seen and which are confirmed, `--show <hash>` prints one; `shapes seed <name>` files the shape of a device's last check or apply as confirmed on your word, for a device that was applied and verified by hand (one question, `-y` answers it). One reviewed apply per shape confirms it for the rest.
- **The transport.** A device is reached over the Junos command line or over NETCONF, as `--transport` of the run (or `config devices apply-transport`, default `auto`) says. `auto` uses NETCONF for a device whose last read found the service answering and whose login may commit, and otherwise the command line; the line says why when it fell back (`[via cli: NETCONF port closed at the last read]`; a device never read says nothing, the JSON has `via` and `via_reason` always). `cli` is what 0.2.9 did. `netconf` never falls back: a device that does not answer, or cannot confirm, is `failed`. Over NETCONF the change is loaded under the candidate's lock (a Junos device refuses a confirmed commit in a private session), checked, committed under a confirmed commit and confirmed by the session that made it; a session that ends without confirming is rolled back by the device within seconds, and the same fresh login proves the device. A candidate that holds another editor's staged change is refused, never committed with the change. A change to the NETCONF service itself (`scope netconf`, `device netconf`) is always made over the command line, because its verification depends on the service; `--transport netconf` refuses it. Its proof, before the confirming commit, is a NETCONF probe on a fresh login: enabling the service must be answered by a hello as you, disabling it must find the hello no longer answered (`port closed` or `no hello`); a probe that cannot tell fails the proof and rolls the change back. The line says `[NETCONF verified: hello ok]` or `[NETCONF verified: not answering]` (the JSON's `service_proof`), and the record's NETCONF probe becomes what was proved; a rolled-back change leaves it as it was. The record's `applied.via` and the JSON's `via` say which transport.
- **What it never writes.** `breakglass` (a walkthrough step), `system root-authentication`, `system services` (but for the exact statements of the NETCONF setting), `netconf` otherwise, `interfaces`, groups and `apply-groups`, any local user's credentials, the root user, the account that is running it, the login class that account belongs to, and the deletion of a whole hierarchy tacctl renders. The statements are held against the planner's own ownership tables before the first is typed, whatever the flags: a statement outside them stops the device with nothing sent. A statement that a group supplies is never changed; the section that would have to is left out and the review says so. `--section` limits the sections (`aaa`, `roles`, `mgmt-acl`, `snmp`, `system`, `netconf`); `--converge` is not offered: the cleanup is a second reviewed run after the first is verified.
- **Refusals before any login.** A caller below the superuser; root (the login is the invoking user's); a device held for break-glass (the server does not answer it); a device no scope covers or whose scope is not yours; a Cisco device or a WTI unit (a selector leaves them out and counts them; a named one is a failed row). A device that reports another name than the registry's name or hostname is `failed: calls itself '<x>'`, one with another editor's staged or open configuration is `failed: other editors or staged changes`, and an exclusive session someone else holds names the holder.
- **Interrupts, exit and audit.** The first Ctrl-C starts no more devices and lets the running one finish (a transaction is never cut by it); the second cancels: before the commit the candidate is discarded, after it the commit is cancelled where the window allows and otherwise left `PENDING`. Exit status: 0 every device applied, was checked or had no change; 1 a device failed, was rolled back or is pending, the review was not answered, or devices were selected and none was applied or found already applied (`--confirmed --yes` that skipped them all: `Nothing was applied: every device was skipped.`, JSON `"stop":"nothing-applied"`); 2 wrong arguments (`--check --exit-code`: a device needs a change); 130 interrupted. `--json` prints one object per device and phase, then the summary; the review goes to standard error. The audit lines are `device config apply user= device= id= shape= result= duration=` (each check), `user= approved=<n> shapes= canary=` (the review's answer; `canary=` names the first device of each shape, or `none` with `--no-canary`), `user= device= id= shape= sections= result= commit= until=` (each apply), `device config apply settle user= device= id= result=` (an earlier apply's pending record settled) and `device config shapes seed user= device= shape=`; none holds a value.
- **The records.** `/var/lib/tacctl/device-apply/shapes.json` (0600) holds each shape's elided lines and who confirmed it, `locks/` a lock per device (`another apply is running on <name>`); the `applied` part of the device's record is described under *Records* in [Device configuration](configuration.md). No raw device output and no password is kept anywhere.

## Onboarding a blank device

`tacctl device onboard <address> --login <local-user>` brings a Junos device that has no TACACS+ or RADIUS server yet, reached with one of its local accounts, under tacctl in one run. It is the superuser's. Any local account may be named, a break-glass account included; only `root` is handled apart (its csh wrapper, below).

```
$ tacctl device onboard 192.0.2.31 --login admin --name sw-lab-5
  192.0.2.31 offers:
    ED25519  SHA256:...
  A blank device has no other proof: compare one with its console (...).
Trust these keys and send the local password of 'admin' to 192.0.2.31? [y/N] y
Password of admin on 192.0.2.31 (a local account; asked once, never kept):
  192.0.2.31  Junos 25.4R1  ex4300-48mp  device reports host name sw-lab-5; no TACACS+ or RADIUS server
[INFO] Device 'sw-lab-5' registered: 192.0.2.31, juniper.
  ...
  From the device: location "Lab rack 2"
  sw-lab-5  read as local:admin: aaa, roles differ from what tacctl renders
  sw-lab-5  checked: shape ee791d20ded1 (new) (roles, aaa: 17 set, 0 delete); check ok

Shape ee791d20ded1, 1 device (sw-lab-5), first-time plan:
  ...
Apply to sw-lab-5 under commit confirmed 10, as 'admin', kept only after a TACACS+ login as alice works and what landed is what the check showed?
  Type the device name to go on: sw-lab-5
Password for alice (device login):
  sw-lab-5  committing as admin, verifying as alice ...
  sw-lab-5  applied (roles,aaa: 17 set, 0 delete) [tacctl-20261013T141201Z-71be]
  The local account 'admin' was not probed: a login would send its password to the TACACS+ server.
```

- **Identity first.** The host keys the address offers are shown, and one question is asked before any login. `--host-key SHA256:<fp>` (the fingerprint read on the device's console) answers it instead and pins that key alone. Without a terminal and without `--host-key` the run is refused, and without a terminal only `--check` runs.
- **Pre-flight as the local account.** Its password is asked once on the terminal and never kept or cached. `show version`, no pending confirmed commit, a login class that may commit, no TACACS+ or RADIUS server (`system tacplus-server`, `radius-server` or `accounting destination tacplus|radius server`, also in a group: a device that has one is reached by the normal flow, `device add`, `device config pull`), and no local account of your own name (a login as you could be that account's, not TACACS+). `--login` may not name your own login, and `--section` must include `aaa`. What the device reports is shown with its control characters replaced.
- **Registration.** The name is `--name`, else the host name the device reports, else asked for at the terminal (a generic or taken one). The device is registered through `device add` with the keys of the first step; its own `snmp location` and `snmp description` fill the registry's empty location and description. Its host name is only shown (`device reports host name`): it never fills the registry's hostname, which ssh would dial instead of the address. A device an earlier onboard registered, and that was never read as your own login, is taken again under its name and pinned keys.
- **Read, plan, check.** The read is recorded as a pull made as the local account (`login=local:<account>`); the plan is the ordinary planner's first-time plan, checked on the device with its own `commit check` as `device config apply --check` does. `--check` stops here: the device is registered and nothing is committed. The plan never holds the break-glass accounts, root, the local account, system services or interfaces.
- **Commit as the local account, proven by your login.** After the review (the device's name typed back) your own password is asked (the password cache may answer it). The change is committed as the local account under `commit confirmed`; every session after the commit is your own TACACS+ login: the fresh login, the landed change and the reads of the planned sections. Its `show cli authorization` must name, as the current user, the template user your group's Juniper class renders, with that class; a local account is not a proof. The confirm is typed in the held local session. A fresh login that is refused or is not that template user rolls the change back and leaves the local account as it was. The local account is never tried again after the commit, `root` included: with `authentication-order tacplus` Junos sends a local account's password to the TACACS+ server, so the run says `was not probed` (`--json` has `"probe": "not-probed"`).
- **Audit.** `device onboard user= device= approved=1 shape= login=` at the answer and `device onboard user= device= addr= login=local:<account> result=` at the end; never a password.

### One read as a local account

`device config pull <name> --login <local-user>` (and `diff --pull`, `plan --pull`) logs in to one registered Junos device with a pinned host key as one of its local accounts instead of you, for a device the server does not answer yet. It is the superuser's (an engineer is refused by the tier gate), takes one device by name (a list, `--all`, `--scope`, `--vendor` or `--stale` is a usage error) and needs a scope that answers the address; a device on which break-glass is held is refused (release it first), as for every pull. Any local account may be named, a break-glass account included; only `root` is handled apart. The password travels as above: asked on the terminal, sent to the one connection, never stored in or asked of the password cache. `root` is accepted only for a device never read as your own login; its csh is left at once by the remote command `sh -c 'PATH=$PATH:/usr/sbin:/usr/bin:/sbin:/bin; exec cli'`, and it reads over the ssh command line only. The audit line is `device config pull user= device= login=local:<account>`.

## Collecting from addresses nobody registered

`tacctl device collect <address>... | --discovered` reads what an address is before it is registered, with one login. It is the superuser's and is for Junos devices; the registry forbids a login without a pinned key, so this is the verb that makes one first. `--discovered` takes the addresses `device discover` lists (the seen cache: unregistered and authenticated; run `device discover` first to refresh it).

```
$ tacctl device collect 192.0.2.31 192.0.2.32 --register
  192.0.2.31 offers:
    ED25519  SHA256:...
  192.0.2.32 offers:
    ED25519  SHA256:...
  Nobody registered these 2 addresses, one attempt at each: compare the keys with each device's console (...).
Trust these keys and send the password of 'alice' (your tacctl password) to these 2 addresses, one attempt at each? [y/N] y
Password for alice (device login):

Collected from 2 address(es)
------------------------------
  ADDRESS      HOSTNAME  MODEL        RELEASE      AUTH-ORDER        SERVERS    EN-CLASS  NETCONF  LO0-FILTER  LEGACY  RESULT
  192.0.2.31   sw-lab-5  ex4300-48mp  25.4R1-S2.3  tacplus,password  tacplus:2  yes       yes      MGMT-ACL    -       collected
  192.0.2.32   -         -            -            -                 -          -         -        -           -       not-junos

  192.0.2.32: not a Junos device (...); the session was closed
  tacctl device add sw-lab-5 192.0.2.31 --vendor juniper

Register 1 device(s), pinning the host keys shown: sw-lab-5 (192.0.2.31)? [y/N] y
```

- **Admitted first.** Before anything is scanned or sent, an address a registry entry holds (it is reached by the normal flow, `device config pull`), an address no scope answers, one on which break-glass is held and, for your own login, a caller who is not an active member of the scope are refused, and the run stops: nothing was sent.
- **Identity.** The host keys are read (nothing is authenticated) and shown with fingerprints, and one question is asked before any login. `--host-key SHA256:<fp>` (read on the device's console) answers it for one address and pins that key alone; without a terminal and without `--host-key` the run is refused. A device that offers only the legacy algorithms is found by the scan and registered `--legacy-ssh`.
- **One login, once per address.** Your own login (your tacctl password; the password cache may answer it) or, with `--login <local-user>`, one local account of the devices for the whole run: its password is asked once on the terminal, never kept or cached, and goes to each address once; `root` is reached through its csh wrapper. The first refusal of the password ends the run (`auth-failed`; the addresses after it are `not-tried`), so a wrong password reaches one address only. A device whose authentication order is `tacplus` only refuses local accounts while the server answers.
- **Nothing else.** In that session `show version` and the pull's read command are typed, and nothing more. An address whose `show version` is not a Junos answer is listed `not-junos`, its session closed and never registered.
- **The table.** One table with the device's own host name, model and release, its `authentication-order`, the number of TACACS+ and RADIUS servers, whether tacctl's engineer class `EN-CLASS` is configured, NETCONF over ssh and the filter applied on `lo0`; `--json` prints one object (the progress goes to standard error). Each collected device is followed by the `device add` line it would run; one that reports no name the registry accepts (generic, taken, or the same as another address of the run) says so.
- **`--register`.** After the table, one question; then each device is registered through `device add`, the same code as every registration, with `--vendor juniper`, every key shown pinned (the login was made against exactly those keys) and `--legacy-ssh` when the handshake needed it. The read is kept as the device's first pull record, as a pull makes it (`login=local:<account>` for a local login), so `device sync` and `device config plan` have one at once; no plain view was read, so a plan says the groups' inheritance was not checked until a pull reads it. `-y` answers the question (without a terminal it is needed). Without `--register` nothing is kept.
- **Audit and exit.** `device collect user= addr= login=own|local:<account> result=` per address, never a password or a device's text. Exit status: 0 every address collected, 1 one was refused, failed or not Junos, 2 wrong arguments, 130 interrupted.

## Filling the registry from the records

`tacctl device sync <name>[,<name>...] | --all | --scope <scope> | --vendor <vendor>` fills a device's empty `hostname`, `location` and `description` in the registry from what the device said of itself in its last pull record: its `system host-name` (with `domain-name`), `snmp location` and `snmp description`. The `hostname` is filled only when the name resolves, with the system resolver, to the device's registered address and to no other. It is the superuser's, reads only Junos records and logs in to nothing (it does look the name up); a device with no pull record is named with the command that makes one (`device config pull`, or `device collect --register`).

```
$ tacctl device sync sw-lab-5
  DEVICE    FIELD        REGISTRY  DEVICE SAYS           ACTION
  sw-lab-5  hostname     -         sw-lab-5.lab.example.net  fill: resolves to the address
  sw-lab-5  location     -         Lab rack 2            fill
  sw-lab-5  description  -         Lab switch five       fill
  ...
  3 field(s) on 1 device(s) would be written. Write them with --apply.
$ tacctl device sync sw-lab-5 --apply
```

- **Preview first.** The table shows, per field, what the registry has, what the device says and the action: `fill` (empty in the registry), `same`, `keep` (set, and different: `--overwrite` replaces it), `replace` (`--overwrite`, with the old value shown), `none` (the device states none) or `refused`. A second table gives the record's facts (login, model, release, serial number), which are the record's and never written to the registry.
- **`--apply`.** After one question (`-y` answers it; without a terminal it is needed), one registry write under the registry's own lock, with a snapshot first; each field is checked again against the live file, so a value set since the preview is left as it is and said. The file is never re-imported. The name, address, vendor and scope are never touched.
- **What a device reports is checked.** A value with control characters (a newline, a terminal escape), invalid UTF-8, one the registry would not accept from a person (more than 120 characters, a `?` in a location or description) and a host name that is not a DNS name (the device states no `domain-name`: a bare label) are listed `refused` and never written. Text a device reports is shown with control characters as `?` and cut at 64 characters.
- **A host name must resolve to the address.** The registry's `hostname` is where tacctl connects (it is dialled instead of the address, with your password), so a name the device reports is filled only when the system resolver answers it with the registered address and no other. A lookup that fails, an answer without the address and an answer with any other address are listed `refused: does not resolve: not filled`; the hostname stays empty and logins keep using the address. `--overwrite` follows the same rule: it never replaces a hostname with a name that does not resolve to the address (a filled row reads `fill: resolves to the address`). `location` and `description` are not looked up.
- **Audit and exit.** `device sync user= devices= fields=` when fields were written. Exit status: 0, 1 refused, 2 wrong arguments.
