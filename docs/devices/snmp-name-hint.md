# The SNMP name hint

[Documentation](../README.md) › [Network devices](README.md)

`device add <name> <address>` reads the device's own name, `sysName.0`, next to the host-key scan and compares it with the name given:

```
$ tacctl device add core-sw1 192.0.2.10 --vendor juniper
[INFO] Device 'core-sw1' registered: 192.0.2.10, juniper.
  The device calls itself 'sw1.site-a.example' (SNMP sysName).
  ! That is not the name given or its --hostname: add --hostname sw1.site-a.example, or register
    it as sw1.site-a.example.
```

A match (the name, the `--hostname`, or the first label of either, in any case) prints the first line only; a mismatch is a warning, never a refusal. A device that does not answer within the timeout (`snmp.timeout`, 2 s by default, one retry), an empty sysName, or no SNMP set up is one info line (`No SNMP answer from 192.0.2.10; no name hint.`), and the add goes ahead; when a scan recorded a NAS-Identifier for the address, that is shown instead, labelled `(NAS-Identifier seen by a scan)`. `--no-lookup` skips it. `device add <address>` with no name offers the sysName, lowercased, and takes it only after a `y` at a terminal; without an answer, with no SNMP set up, or when the sysName is no valid device name or a generic one (a WTI unit's Site ID `WTI`), a terminal is asked for the name (Enter registers nothing; the typed name passes the add's name rules), and without a terminal it is refused with the usage line. `device check` shows the sysName in a `SNMP name` row (`match` or `differs`), and `--json` as `sysname`. Nothing of it is stored.

**The device's own location.** Unless `--snmp-location` or `--no-lookup` is given, `device add` also reads `sysLocation.0` next to the name and, when the device reports one, stores it as the device's location and says so (`  Location: Site A, rack 4 (read from the device)`); a value the registry does not accept (`?`, control characters, more than 120 characters) is shown and not stored. A device that reports none gets one line, `  Location not set: tacctl device location core-sw1 '<text>'`; at a terminal the add offers instead to enter one (blank skips). No answer is not mentioned again: the name hint has said so. The add never fails because of the location. `device check` shows the device's reading next to the registry's in a `Location` row (`match`, `differs: device '...', registry '...'`, `registry only`, `device only`) and writes nothing. `device location <name> --from-device` reads it now and stores it: an empty answer is refused with the reason, and a different registered location is shown beside the device's and replaced after a `y` at a terminal, or with `--yes`.

**The device's vendor.** Beside the name, `device add` reads `sysObjectID.0`
and `sysDescr.0` in one request of their own (the same credentials, timeout
and retry) and says which vendor they name:

```
$ tacctl device add sw1 192.0.2.10
[INFO] Device 'sw1' registered: 192.0.2.10, other.
  The device calls itself 'sw1' (SNMP sysName).
  The device says it is Cisco IOS Software, vendor cisco (SNMP sysObjectID
    1.3.6.1.4.1.9.1.1, sysDescr 'Cisco IOS Software, ...').
  ! It is registered as other: tacctl device vendor sw1 cisco
```

A sysObjectID under enterprise 9 (`1.3.6.1.4.1.9.`) with a sysDescr that
starts `Cisco IOS Software` or `Cisco IOS XE Software` is `cisco`; one under
enterprise 2636 with a sysDescr that names Junos is `juniper`; one under
enterprise 2634 is `wti` (a WTI unit's sysDescr is generic Linux text, so the
enterprise is the only evidence). Enterprise 9 also covers ASA, NX-OS and IOS
XR, which tacctl does not read as `cisco`: any other enterprise 9 sysDescr, an
enterprise 2636 sysDescr that does not name Junos, an unknown enterprise, and
a missing sysObjectID (or, for Cisco and Juniper, sysDescr) name no vendor,
and the line says what was read (`The device names no vendor tacctl reads:
Cisco device, sysDescr not recognised as IOS or IOS-XE (...)`). A `--vendor`
that disagrees is a warning with the `device vendor` command, never a
refusal. Without `--vendor`, a terminal is asked one
`y/N` (default no) to register with the vendor named, folded into the
question of `device add <address>` (`Register 192.0.2.10 as 'sw1' (cisco)?
[y/N]`); without a terminal it is only printed. `--pull` without `--vendor` uses the vendor the answer takes.
`device check` shows a `Vendor` row (`match`, `differs: device says ...`, or
`unknown: ...` with what was read; `vendor_detected` in `--json`), and
`device check --all` ends with the devices registered as `other` that name a
vendor. `device vendor <name> --from-device` reads it now and sets it after a
`y` at a terminal, or with `--yes`; a read that names no vendor is refused with
the reason. `device discover --snmp` reads the sysName and the vendor of each
listed address and puts them in its `device add` line. The vendor read last
for an address is kept in the seen cache, and one that is not the registered
vendor is the notice `vendor-differs`. Nothing is written to a device.

SNMP is v2c (a community) or v3 at authPriv (HMAC-SHA-96 or HMAC-SHA-256-192, AES-128), read by tacctl itself (no net-snmp): `tacctl config snmp community` asks for the community, and `tacctl config snmp v3-user add <user> [--auth sha256] [--default]` for the user's two passphrases, twice without echo (`--stdin` reads them, one per line); they are stored in `/etc/tacctl/snmp.yaml` (0600, never printed). `community` sets `snmp.version` to v2c; adding a v3 user changes nothing but the pool, so `config snmp version v3` makes the lookups use v3 and `v3-user default <user>` (or `--default` on the add) chooses the user they read with; `config snmp test <address>` tries one device (`no answer` is also what a wrong community, or a wrong v3 privacy passphrase, looks like; v3 names `unknownUserName` and `wrongDigest`). `config snmp` is for administrators only: the credentials reach every device. These settings are the **default**: a scope sets its own with `tacctl scope snmp <scope> ...` (version, community, v3-user, port, timeout), and what it does not set comes from the default, then the built-in; `scope snmp <scope> show` says which one each value is. **The v3 user pool.** The version, the port, the timeout and the two protocols are one setting for a level (the config, a scope, a device); the v3 users are a pool of names with their passphrases and a default user or none: `v3-user add|remove|default|list` of `config snmp`, `scope snmp <scope>` and `device snmp <name>`. A device reads with its own default user, else its scope's, else the config's, and may be told to use a user of its own pool, its scope's or the config's (`device snmp <name> v3-user default <user>`). A name stands for one user across the pools a device can see, so a scope's user cannot shadow the config's: adding a name another pool holds is refused, naming the level (two scopes may use the same name for different users), and a user that a device's default names cannot be removed. A chosen user that is missing, or has no passphrase, is an error that names the command that fixes it, never a fallback to another user; the walkthroughs and the rendered blocks name only the user in force. `show --reveal <user>` prints one user's passphrases. In the files, version 2 holds `users:` (a name and the two passphrases each) and `default:`; a version 1 file (one v3 user, 0.2.22 and before) reads as a pool of one user that is the default, and is saved as version 1 again while it fits version 1 (a community and at most one v3 user that is the default); version 2 is written only for what version 1 cannot hold (a second or non-default user, a default naming another level's user, a device's file without an `snmp:` entry). A device's file follows its entry: version 2 while the device has none (it counts all the same), version 1 once any setting gives it one when the content fits (a pool of two stays version 2), version 2 again if the entry is emptied; the command says so when it rewrites a file that way, and a file it cannot write is a warning that names the command that writes it again (exit status 1 when the file is then ignored). The scope's secrets are the file `/etc/tacctl/snmp/<scope>.yaml` (0600, in a 0700 directory, the format of `snmp.yaml`), its other settings `snmp_scope.<scope>.*` in `tacctl.yaml`, both written only when set. The name lookup of `device add` and `device check` uses the credentials of the device's scope, the one that answers its address (a device in no scope uses the default); `scope snmp <scope> test <address>` tries the scope's; `config snmp test` follows a registered device (its own settings, else its scope's, else the default's, and the answer says which it tried) and is the default's for an address that is no device.

**A device's own SNMP settings.** A device that its scope's (or the default's) settings do not fit, a different community, a non-standard port, its own list of allowed clients, has them of its own: `tacctl device snmp <name> version|port|timeout|clients|community|v3-user` (superusers; an engineer reads the devices of their own scopes with `show [--reveal]`, each reveal logged as `secret-read kind=snmp-device`). The order is **the device's value, then its scope's, then the default's, then the built-in**, one setting at a time (the v3 user and both passphrases come together from one level); `device snmp <name> show`, `device show` and `device check` print the resolved values and say where each comes from, `scope snmp <scope> show` lists the devices that have their own. The non-secret settings are an optional `snmp:` map of the device in `devices.yaml` (`version`, `port`, `timeout`, `clients`; written only when set), the credentials `/etc/tacctl/snmp/devices/<name>.yaml` (0600, in a 0700 directory, the format of `snmp.yaml`). The name and location lookups of `device add`, `device check` and `device location --from-device`, the SNMP step of `config <vendor> --name <device>` and `device config show` (which says `Credentials: this device's own`), and the SNMP and management-ACL sections of `device config pull|diff|plan` use the device's resolved values. A device's own list of allowed clients replaces its scope's for that device (the tacctl server's /32 stays first, `0.0.0.0/0` refused last). A credentials file of version 1 counts only while the device has an `snmp:` map of its own (`community` set the version, so a map always existed in use); one with none, such as a rollback to 0.2.3 left, is ignored by every reader, is not parsed, is said once by `device show` and `device snmp <name> show`, and comes into force again when the device is given settings (the verb says so) or is removed by `device snmp <name> clear`. A file of version 2 (a pool and a default, which choose no version) counts without a map. `device remove` deletes the device's credentials file and `device rename` moves it; a new device, or a rename onto a name whose file is already there (an earlier device's, kept by a rollback), is refused with the file's path. A credentials file that cannot be parsed is named, with the way out, by every read that meets it and listed by `scope snmp <scope> show`; `device snmp <name> clear` removes it without reading it, and `community` or `v3-user add` replace it and say so. Every change of a credential takes the snapshot first, so it holds the old one, and `backup restore` makes `snmp/devices/` match the registry it restores (a snapshot without it, one with a registry, leaves no device file behind). The SNMPv3 user's name is shown to the engineer tier and above; a read-only or operator user of `device show` and `device check` (and their `--json`) is told only that a user is set (`v3 user set`, `v3_user_set`). An engineer's `--reveal` is logged as `secret-read kind=snmp-device name=<device>`, `kind=snmp name=<scope>` and `kind=snmp-default name=default`, one line for each level a printed secret comes from, never the value; the line of a v3 user's passphrases adds `user=<name>`. `device show --json` carries `v3_users` (the names in the device's own pool, empty for a caller below the engineer tier) and `v3_default` (its own default) beside `v3_user`, the user in force.
