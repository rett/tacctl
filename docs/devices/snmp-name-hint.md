# The SNMP name hint

[Documentation](../README.md) › [Network devices](README.md)

`device add <name> <address>` reads the device's own name, `sysName.0`, next to the host-key scan and compares it with the name given:

```
$ tacctl device add core-sw1 192.0.2.10 --vendor juniper
[INFO] Device 'core-sw1' registered: 192.0.2.10, juniper.
  The device calls itself 'sw1.site-a.example' (SNMP sysName).
  ! That is not the name given or its --hostname: add --hostname sw1.site-a.example, or register it as sw1.site-a.example.
```

A match (the name, the `--hostname`, or the first label of either, in any case) prints the first line only; a mismatch is a warning, never a refusal. A device that does not answer within the timeout (`snmp.timeout`, 2 s by default, one retry), an empty sysName, or no SNMP set up is one info line (`No SNMP answer from 192.0.2.10; no name hint.`), and the add goes ahead; when a scan recorded a NAS-Identifier for the address, that is shown instead, labelled `(NAS-Identifier seen by a scan)`. `--no-lookup` skips it. `device add <address>` with no name offers the sysName, lowercased, and takes it only after a `y` at a terminal; without a terminal, without an answer, or when the sysName is no valid device name or a generic one (a WTI unit's Site ID `WTI`), it is refused with the usage line. `device check` shows the sysName in a `SNMP name` row (`match` or `differs`), and `--json` as `sysname`. Nothing of it is stored.

**The device's own location.** Unless `--snmp-location` or `--no-lookup` is given, `device add` also reads `sysLocation.0` next to the name and, when the device reports one, stores it as the device's location and says so (`  Location: Site A, rack 4 (read from the device)`); a value the registry does not accept (`?`, control characters, more than 120 characters) is shown and not stored. A device that reports none gets one line, `  Location not set: tacctl device location core-sw1 '<text>'`; at a terminal the add offers instead to enter one (blank skips). No answer is not mentioned again: the name hint has said so. The add never fails because of the location. `device check` shows the device's reading next to the registry's in a `Location` row (`match`, `differs: device '...', registry '...'`, `registry only`, `device only`) and writes nothing. `device location <name> --from-device` reads it now and stores it: an empty answer is refused with the reason, and a different registered location is shown beside the device's and replaced after a `y` at a terminal, or with `-y`.

SNMP is v2c (a community) or v3 at authPriv (HMAC-SHA-96 or HMAC-SHA-256-192, AES-128), read by tacctl itself (no net-snmp): `tacctl config snmp community` or `tacctl config snmp v3-user <user> [--auth sha256]` asks for the secrets twice without echo (`--stdin` reads them, one per line), stores them in `/etc/tacctl/snmp.yaml` (0600, never printed) and sets `snmp.version`; `config snmp test <address>` tries one device (`no answer` is also what a wrong community, or a wrong v3 privacy passphrase, looks like; v3 names `unknownUserName` and `wrongDigest`). `config snmp` is for administrators only: the credentials reach every device. These settings are the **default**: a scope sets its own with `tacctl scope snmp <scope> ...` (version, community, v3-user, port, timeout), and what it does not set comes from the default, then the built-in; `scope snmp <scope> show` says which one each value is. The scope's secrets are the file `/etc/tacctl/snmp/<scope>.yaml` (0600, in a 0700 directory, the format of `snmp.yaml`), its other settings `snmp_scope.<scope>.*` in `tacctl.yaml`, both written only when set. The name lookup of `device add` and `device check` uses the credentials of the device's scope, the one that answers its address (a device in no scope uses the default); `scope snmp <scope> test <address>` tries the scope's; `config snmp test` follows a registered device (its own settings, else its scope's, else the default's, and the answer says which it tried) and is the default's for an address that is no device.

**A device's own SNMP settings.** A device that its scope's (or the default's) settings do not fit, a different community, a non-standard port, its own list of allowed clients, has them of its own: `tacctl device snmp <name> version|port|timeout|clients|community|v3-user` (superusers; an engineer reads the devices of their own scopes with `show [--reveal]`, each reveal logged as `secret-read kind=snmp-device`). The order is **the device's value, then its scope's, then the default's, then the built-in**, one setting at a time (the v3 user and both passphrases come together from one level); `device snmp <name> show`, `device show` and `device check` print the resolved values and say where each comes from, `scope snmp <scope> show` lists the devices that have their own. The non-secret settings are an optional `snmp:` map of the device in `devices.yaml` (`version`, `port`, `timeout`, `clients`; written only when set), the credentials `/etc/tacctl/snmp/devices/<name>.yaml` (0600, in a 0700 directory, the format of `snmp.yaml`). The name and location lookups of `device add`, `device check` and `device location --from-device`, the SNMP step of `config <vendor> --name <device>` and `device config show` (which says `Credentials: this device's own`), and the SNMP and management-ACL sections of `device config pull|diff|plan` use the device's resolved values. A device's own list of allowed clients replaces its scope's for that device (the tacctl server's /32 stays first, `0.0.0.0/0` refused last). A device's credentials file counts only while the device has an `snmp:` map of its own (`community` and `v3-user` set the version, so a map always exists in use); a file with none, such as one a rollback left, is ignored by every reader, is not parsed, is said once by `device show` and `device snmp <name> show`, and comes into force again when the device is given settings (the verb says so) or is removed by `device snmp <name> clear`. `device remove` deletes the device's credentials file and `device rename` moves it; a new device, or a rename onto a name whose file is already there (an earlier device's, kept by a rollback), is refused with the file's path. A credentials file that cannot be parsed is named, with the way out, by every read that meets it and listed by `scope snmp <scope> show`; `device snmp <name> clear` removes it without reading it, and `community` or `v3-user` replace it and say so. Every change of a credential takes the snapshot first, so it holds the old one, and `backup restore` makes `snmp/devices/` match the registry it restores (a snapshot without it, one with a registry, leaves no device file behind). The SNMPv3 user's name is shown to the engineer tier and above; a read-only or operator user of `device show` and `device check` (and their `--json`) is told only that a user is set (`v3 user set`, `v3_user_set`). An engineer's `--reveal` is logged as `secret-read kind=snmp-device name=<device>`, `kind=snmp name=<scope>` and `kind=snmp-default name=default`, one line for each level a printed secret comes from, never the value.
