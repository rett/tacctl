# SNMP and NETCONF in the walkthroughs

[Documentation](../README.md) › [Network devices](README.md)

`tacctl config cisco|juniper|wti` end with an SNMP step that lets the device answer the tacctl server's reads and nobody else's. It is built from the scope's settings with the default beneath them (see [The SNMP name hint](snmp-name-hint.md)):

- **Allowed clients**, in this order: the tacctl server's own address as a /32 (always; the address its route to the devices uses, or `--source`), the scope's ranges in the order given (`tacctl scope snmp <scope> clients add 192.0.2.0/24,198.51.100.7`), or, for a device that lists its own (`tacctl device snmp <name> clients add <cidr>`), those instead, then `0.0.0.0/0` refused, always rendered and never stored. A scope without ranges allows the server only, and the output says so. Ranges are IPv4, at most 32, never `0.0.0.0/0`; an overlap is a note.
- **The Cisco and Junos steps are live lines, not a comment.** Pasted on a device that already has SNMP, they bind an existing community to an access list or client list that allows only the server and the scope's ranges, and overwrite the location and contact: pollers and NCM using that community lose access. Before pasting the SNMP step, add your pollers with `tacctl scope snmp <scope> clients add <cidr>`, or leave the step out.
- **Cisco:** the standard access list `TACCTL-SNMP` (a /32 as `permit host`, the others with wildcard masks, ending in `deny any`), `snmp-server community <community> RO TACCTL-SNMP`, or for v3 `snmp-server group TACCTL-GROUP v3 priv read TACCTL-VIEW access TACCTL-SNMP` and `snmp-server user ... v3 auth sha|sha256 ... priv aes 128 ...`; `snmp-server location` and `contact`.
- **Junos:** `set snmp client-list TACCTL-SNMP <cidr>` per client and `0.0.0.0/0 restrict`, the community `authorization read-only` with `client-list-name`, or the v3 `usm local-engine` user with its `vacm` group and view; `set snmp location|contact|description`. A client list restricts communities only: it does not restrict a v3 user; when the management filter of Step 4 is rendered it carries `permit-snmp` and `deny-snmp` terms for udp port 161 from the same clients (ahead of its `default-accept`), which restrict v3 once the filter is applied to `lo0`, and the step says so. In a scope whose management filter mode is `strict` (`scope mgmt-acl <scope> mode`) the sources of the permit list reach udp port 161 as well, and the step says that instead.
- **WTI:** the unit's SNMP menu in the walkthrough's style (version, community or v3 user, location, contact) as Step 6 (Save, Test and Debug are Steps 7 to 9); the client restriction is the udp port 161 lines of the unit's IP Tables list (Step 5, see [Management ACL](../security/management-acl.md)), unless the unit has an SNMP access menu of its own.
- The community or the v3 passphrases are **printed** for superusers and for engineers (of their own scopes; the reveal is logged as `secret-read kind=snmp`), with a line saying whether they are the device's own, the scope's own or inherited from the default.
- A **value that is not set**, the scope's contact (`scope snmp <scope> contact '<text>'`) or a device's location (`device location <name> '<text>'`), is a commented placeholder, never text a paste would apply, and the output ends with `Unfilled SNMP values: contact (tacctl scope snmp <scope> contact '<text>'), location (tacctl device location <name> '<text>')`. With no SNMP version in the scope or the default, the step is a comment saying SNMP is not configured in tacctl.
- `tacctl device config show <name>` is `--scope <the device's scope> --name <name>` with the device looked up for you: it prints the device's data, then this walkthrough (`--protocol`, `--legacy`, `--server` and `--source` as for `config <vendor>`; a Cisco device is walked through in its configuration syntax, `--legacy` being the explicit IOS 12.x override).
- `--name <device>` takes the location, description and sysName of a registered device of the scope; `--snmp-location <text>` gives the location for one paste (not stored). `device add --snmp-location` and `device location` store it.
- **NETCONF** (by default nothing is enabled by tacctl): the Junos walkthrough has a commented `set system services netconf ssh` step (with the optional `connection-limit` and `rate-limit`, and the check `ssh -p 830 -s <user>@<device> netconf`, which should answer a `<hello>`); its management filter already permits tcp port 830 next to ssh, and says so (in `strict` mode it accepts every protocol from a source without services, and tcp port 830 from a source with services only when they include `tcp/830`). The Cisco walkthrough has a commented `netconf-yang` step with its prerequisite (exec authorization) for superusers, and an engineer's says to ask one; IOS 12.x has none. A WTI unit has no NETCONF. A Junos device whose scope or own setting (`scope netconf`, `device netconf`) says `enable` has the statement live instead (with the limits when set, as `set system services netconf ssh connection-limit <n>`: a limit's statement enables the service by itself), and `disable` has a live `delete system services netconf`.
- **`--server <address|name>`** is the address the devices are told to authenticate against (the TACACS+ or RADIUS server lines), for devices that reach this server through a translating firewall; a host name must resolve to an IPv4 address. **`--source <address>`** is the address tacctl itself reaches the devices from: the first SNMP client, the address the ssh permit of the Cisco VTY-ACL and of the Junos management filter allows in addition to the scope's ranges, and the server's /32 of the WTI IP Tables list. The default of `--source` is the address the route to the Internet uses; the default of `--server` is the server address recorded in `server.addresses` (`tacctl server addresses`), else that detected address (a RADIUS listener bound to an address keeps that address in a RADIUS walkthrough, and `--server` wins for that run). Neither is stored, they combine with `--staging`, and when they differ the output says which address plays which role. In a scope whose Junos management filter mode is `strict`, the address the device authenticates against is accepted for the server's answers only, as a term of its own, when it differs from the address tacctl reaches the device from and no plain source of the permit list holds it (a plain source accepts everything, as any source of the list does); an entry with services for it keeps its services, and the term adds the answers (see [Management ACL](../security/management-acl.md#strict-mode-for-junos)).
- The output marks the SHA-256 keyword lines, the Junos v3 restriction and the WTI client restriction as not verified on a device, and the WTI step says its item names are those of one firmware release and may differ on others. Review the step before pasting it.

**Notices** are computed when shown (only acknowledgements are stored) and appear in `scan`/`discover` output, a `Device notices` section of `tacctl status` (count and the first five), `device list` and `host list` (NOTICES), `device notice list`, and `device show` (which counts the acknowledged ones; `--all` on either lists them, marked). Besides `generic-name`, `hostkey-unpinned` and, for an enrolled host whose address changed between two enrolments or syncs, `address-changed` (the only notice an enrolled host acknowledges), a scan raises `ambiguous-nas-id` (one NAS-Identifier from several addresses; a fully qualified host name on each device tells them apart), `generic-nas-id`, `name-mismatch` (a NAS-Identifier other than the registry name or the hostname, in full or by its first label, as `sw1` for `sw1.site-a.example`; informational), `duplicate-address` (two entries at one address, or an address identifying as another entry), `identity-changed` (an address's NAS-Identifier changed: replaced or reset?), and from the host-key re-scan `hostkey-changed` (cannot be acknowledged; only `device hostkey <name> accept|set` clears it), `hostkey-added` and `hostkey-unreachable`; `vendor-differs` is a vendor a device named by SNMP (`device add`, `device check`, `device vendor --from-device`, `device discover --snmp`) that is not its registered one (cannot be acknowledged; setting the vendor clears it). Each line ends with the command that fixes or acknowledges it.

**Host keys.** `device add` reads the keys the device offers (`ssh-keyscan -T 5 -p <port> -t ed25519,ecdsa,rsa <address>`, as root; `legacy-ssh` devices are asked for `ssh-rsa` by name too; a device that accepts the connection but gives no key to that, because it limits the simultaneous connections `ssh-keyscan` opens per key type or drops its long offer, is asked again one key type at a time, `-t ed25519`, then `ecdsa`, `rsa` (and `ssh-rsa`), each with `-T 3`, and every key that answers is pinned; a device whose name `ssh-keyscan` reports as not resolving is not asked again; `ssh-keyscan` cannot do the SHA-1 key exchange and CBC ciphers a `legacy-ssh` device needs, so for a `legacy-ssh` device that it reads nothing from, for any device that accepted the connection but gave no key even one type at a time, and for a device it reads nothing from and prints nothing about (a server slow to greet, which plain `ssh` waits longer for, or a refused or filtered address; no one-type retry then, and a 3-second connect), tacctl's built-in ssh client reads the keys instead, stopping at the host key, before authentication, so no password is sent; it starts with ed25519 alone and the library's short algorithm offer, the legacy algorithms only when that reads nothing), pins them in `devices.yaml` and prints each `SHA256:` fingerprint with the command that shows it on the device console (Cisco `show ip ssh`, Junos `file show /etc/ssh/ssh_host_ed25519_key.pub` from the CLI, or `ssh-keygen -lf` on the same file from `start shell`, Linux `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`); compare them before connecting (`tacctl device hostkey <name> show` prints each pinned key as an `ssh-ed25519 AAAA…` line as well, so a `file show` output can be compared by eye). A device that does not answer either read is refused unless `--no-host-key` is given. `host enroll` and `host sync` pin an enrolled host's keys the first time from two independent reads: the host's own public key files (`cat /etc/ssh/ssh_host_*_key.pub`, read-only, over the enrolment's ssh connection, which your own ssh checked against your known_hosts) and an `ssh-keyscan` of the target. Only keys both reads hold are pinned; a key type they disagree on refuses the pin (both sets are shown and `host hostkey-mismatch` is logged), a type only one of them has is reported and not pinned, and key files that cannot be read pin nothing. The enrolment or sync succeeds either way. A sync of a pinned host compares the session's keys with the pin, reports a difference and keeps the pin. The same connection gives the host's address: enroll and sync record the address the connection reached (the host's side of `SSH_CONNECTION`; `--local` records 127.0.0.1) in `devices.yaml`'s `hosts:` section, and warn when it differs from what the target's name resolves to. `device add` and `device address` refuse that address, `device show <address>` finds the host, sightings from it are the host's, and `device discover` does not list it; a sync that finds another address records it and raises `address-changed`. Only `device hostkey <name> accept|set` changes a pin. Every registry write regenerates `/var/lib/tacctl/ssh/known_hosts` (0644), one `<name> <type> <key>` line per pinned key, for `ssh -o UserKnownHostsFile=/var/lib/tacctl/ssh/known_hosts -o GlobalKnownHostsFile=none -o HostKeyAlias=<name> -o StrictHostKeyChecking=yes`.

**`tacctl ssh <name|address>`** opens an ssh session to a registered device or an enrolled host, as you: the name is resolved as root (the registry is root's), and only an active tacctl user (in the store, not disabled) whose scopes include the entry's may connect, at every tier, superusers included (`'jdoe' has no access to scope 'prod' (device core-sw1)`; a local account that is not a tacctl user, and an entry in no configured scope, are refused to everyone; each refusal is logged as `ssh DENY … reason=`). The session is logged (`ssh user=<you> device=<name> addr=<address> from=<where you logged in from>`, syslog auth.info; `from=` is omitted when it cannot be told), and ssh runs as the invoking user (`sudo -u <you> -H ssh …`), logging in as you by password: your tacctl password, checked by the device against this server; no agent, no key, no other login. An enrolled host's enrolment account and identity are never used. Its exit status is passed back. `-X`/`-Y` forward X11 to this server's display (the `DISPLAY` of an `ssh -X` login here, which sudo keeps for tacctl), and `-L`, `-R` and `-D` (repeatable) are ssh's port forwardings; the log line then carries `forward=x11,local,…`. In the login console they are for the tiers of `console forwarding tiers` only (default superuser; others get `ssh DENY … reason=forward`), and `-L` and `-D` listen on loopback only: `-g` and a bind address other than loopback (`0.0.0.0:8443:localhost:443`, `*:1080`, or an empty one, which ssh binds on every address even without `-g`) are refused (`ssh DENY … reason=gateway`) unless `console forwarding gateway-ports` is enabled. Run as root itself it refuses (`tacctl ssh runs ssh as the user who invoked it; run it from your own account, not as root`); it needs a terminal. An unregistered address is refused with the `device add` command that registers it. The options per device:

| Device | ssh options |
|---|---|
| every one | `-o ConnectTimeout=10 -o PubkeyAuthentication=no -o PreferredAuthentications=keyboard-interactive,password`; your username as the login; the device's hostname, else its address; its port (`-p`) unless given |
| `wti` | `PreferredAuthentications=password` instead (see [WTI console servers](wti.md)) |
| `legacy-ssh` | `-o KexAlgorithms=+diffie-hellman-group14-sha1,diffie-hellman-group1-sha1 -o Ciphers=+aes128-cbc,aes192-cbc,aes256-cbc,3des-cbc -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa` (a device that offers only those; OpenSSH 8.5 or later; the CBC ciphers are appended, so the strong ones stay first) |
| pinned keys | `-o UserKnownHostsFile=/var/lib/tacctl/ssh/known_hosts -o GlobalKnownHostsFile=none -o StrictHostKeyChecking=yes -o HostKeyAlias=<name> -o UpdateHostKeys=no` |
| enrolled host | its target's host and its port |

An unpinned device is checked against your own known_hosts, after its `hostkey-unpinned` notice. Arguments after `--` follow the target, so ssh takes them as the remote command (`tacctl ssh core-sw1 -- show version`); they cannot replace an option. Each session is logged when it starts (`ssh user= device= addr=`) and when it ends (`ssh end user= device= status= duration=`).

From a login console session (each of its lines carries `TACCTL_CONSOLE=<session>`), `tacctl ssh` reads no ssh configuration file and opens nothing but the session: it adds `-F /dev/null -o PermitLocalCommand=no -o ControlMaster=no -o ClearAllForwardings=yes -o ForwardAgent=no`, `-o EscapeChar=none` unless `tacctl console ssh-escape enable`, and puts the target after `--`, so the words after the name's `--` are only ever the remote command (a first word starting with `-` is refused). A device or host with no pinned host key is refused: `'<name>' has no pinned host key, so the console does not connect to it; an administrator pins it: tacctl device hostkey <name> accept`. Its log lines end with `console=<session>`. When ssh fails with 255 on a pinned device whose key changed, tacctl prints the pinned and offered fingerprints, the console command that shows the key, and `tacctl device hostkey <name> accept|set`.

`tacctl device client-config > ~/.ssh/tacctl.conf`, with `Include ~/.ssh/tacctl.conf` at the top of `~/.ssh/config`, gives a plain `ssh <name>` the same options and pin (one `Host` block per device you may see, with `PubkeyAuthentication no` and the password methods and no `User` line: ssh logs in with your local username, which for a tacctl user is the tacctl name; print-only, re-run after registry changes).

## The server's port

The walkthroughs name the port the server listens on where the device's configuration takes one. It is the configured listener (`tacctl config listen`; see [Listeners](../server/backends.md#listeners)): the `default` TACACS+ listener, and for RADIUS the `auth` and `acct` listeners. Where a port is not written when it is the default, it is written only for a listener that moved, so a server on the default listeners renders what it always did:

| Device | TACACS+ listener on tcp `:4949` |
|---|---|
| Cisco, IOS 15.2 and later, IOS-XE | `port 4949` under `tacacs server TACACS`, after `address ipv4` |
| Cisco, `--legacy` (IOS 12.x) | `tacacs-server host <address> single-connection port 4949 timeout 5 key <secret>` |
| Junos | `set system tacplus-server <address> port 4949` |
| WTI | item 7, Authentication Port: `4949` (always written; 49 by default), and the Step 4 note that a ping does not prove `TCP/4949` |
| Junos, management filter mode `strict` | the term `permit-auth-replies` accepts source port `4949` (the name `tacacs` when it is 49) |

RADIUS walkthroughs write both ports as they always did (`auth-port`/`acct-port` on Cisco, `port` and `accounting-port` on Junos, the two WTI items) and name the TACACS+ port where they contrast the protocols (`UDP, not TCP/4949`).

What a pull is compared with and what a plan types is the same rendering, so a device that still has the old port is a difference with the fix in its plan: after `tacctl config listen tcp :4949`, a Cisco device with `port 49` under its server block shows `- tacacs server TACACS > port 4949` and `+ tacacs server TACACS > port 49` in `device config diff`, and `device config plan` types `port 4949` under `tacacs server TACACS`; a Junos device with `port 49` gets `set system tacplus-server <address> port 4949`; a WTI unit gets its Authentication Port item changed. A device that carries a port the listener no longer has (the listener is back on 49, the device says `port 4949`) is an extra statement, which a plan leaves alone and names with the line that removes it (`no port 4949` under `tacacs server TACACS`). A template you changed before 0.2.22 has no port line and keeps the literal 49 on WTI: merge the new default (see [Custom templates](templates.md)).
