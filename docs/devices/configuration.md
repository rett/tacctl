# Device configuration

[Documentation](../README.md) › [Network devices](README.md)

`tacctl device config pull` reads what the devices run, as you, and compares the sections tacctl manages with what tacctl would render for each device. Nothing is written to a device.

```
$ tacctl device config pull --scope lab
  core-sw1  ok via netconf
  core-sw2  ok, differs in aaa,snmp via netconf
  edge-r1   ok via ssh (netconf: port closed)
  edge-r2   failed: timed out

  2 ok, 1 differ, 1 failed
$ tacctl device config diff core-sw2
Device core-sw2 (lab, juniper): pulled 2026-10-09 14:02 by alice over netconf
  aaa         differs
      - set system accounting destination tacplus
      + set system tacplus-server 192.0.2.99 secret (present, not compared)
  roles       ok
  ...
```

- **Who and how.** The login is the user who invoked tacctl (`SUDO_USER`; root is refused), with that user's tacctl password, asked for once on the terminal without echo and never stored, written to a file, put in an argument or the environment, or logged. A device needs a pinned host key (`device hostkey <name> accept`): an unpinned device is refused with that command, a key that is not the pinned one is `host-key-mismatch` (and raises the hostkey notice), and nothing is ever trusted on first use. You must be an active tacctl user and the device's scope must be one of yours (the device login is your account), whatever your tier; an engineer's selection is their own scopes' devices, and `--all` means all of those. A device of vendor `other`, a device in no scope and a device in a scope you are not in are refused when named and left out, with a note that names them, by `--all`, `--scope`, `--vendor`, `--stale`, `--differs`, `--name` and `--ip`. Those filters combine (`--differs` keeps the devices whose last pull differs from what tacctl renders now, decided from the records with no login; `--name <text>` and `--ip <addr|cidr|text>` take comma lists, as `device list` does; see [device](../cli/device.md)); names and `--all` stand alone. Every device is logged (`auth.info device config pull user= device= transport= result= duration=`, never a credential).
- **What is read.** Junos: `show configuration | display inheritance no-comments | display set` over NETCONF (the ssh subsystem `netconf`, a `<command>` RPC) where the device answers, else the same command over an ssh exec channel (`--transport auto`, the default; `netconf` and `ssh` never fall back); then, in the same session, `show configuration | display set` (the plain view, without the groups' inheritance applied, which `device config plan` needs to tell a group's statements from the device's own; best effort, a device that does not answer it is still pulled). IOS and IOS-XE: `terminal length 0`, `show version | include Version` (the image's version line, kept on the record with the configuration syntax it says), then `show running-config` over the ssh command line (a Cisco device is not read over NETCONF: `--transport netconf` refuses it before any login, as a failed line that leaves its record alone, or, when every selected device is Cisco, as a wrong argument). A WTI console server has no command that prints its configuration, so it is read as its menus show it, over ssh as you (`--transport auto` and `ssh`; `--transport netconf` is refused for a unit as for a Cisco device): the pages the tables of command menu version 8.10 name are opened one after the other (the login's help, the network status, the Site ID, and under `/N` the SNMP access and trap pages, the TACACS+ and RADIUS pages, the IP tables list), with only the keys a page lists, never a prompt that takes a value, and never the final ESC that would make the unit save its configuration; the one prompt it opens is read-only: the SNMP access page prints the system name, the contact and the SNMP location cut at about 16 characters with `...`, so for each one the page shows cut that way, the item's text prompt is opened with its number and a CR (`/N`, 25, then 4, 5 or 6), which prints the whole value, and left with ESC, which keeps it. Nothing is typed at a prompt (no text, no CR, no `<SPACE><CR>`, which would clear the field), a value the page shows whole is not opened, the prompts of the communities and secret words are never visited, and the three whole values are what the pull extracts and compares, exactly; a record that holds the cut value is compared by its beginning, with a note, until the unit is pulled again; the user directory (`/F`) is read in a second connection with the same password, because a top-level menu is left only by a save. Both connections end on a page, which writes nothing. The pages are never kept: the extraction is, as for any device, and a community the unit prints in clear is compared against what tacctl renders and kept as a label. `device config pull`, `list`, `diff` and `device show` treat a unit like any device (`--all`, `--scope`, `--vendor wti`, `--stale` select units too; a hold refuses it; one job and one login per unit, plus the second connection), and add: how many other sessions the unit had (`1 other session on the unit`, a count only; no name is read into any output), its command menu version (`device show`: `command menu 8.10`, and `os` in `--json`) and its Site ID (`device show`, `--json` `unit.site_id`). Three results belong to the unit: **`denied`**, the login's WTI level cannot configure it (`the login's WTI level is User; SuperUser or Administrator is needed`, with `tacctl group edit <group> wti-level superuser` for the login's group; none of the tables' pages was opened; it counts as a failed pull, exit 1, and does not stop a batch, because the password was accepted); **`unsupported`**, the command menu is not version 8.10 (`command menu version 7.4; tables are verified for 8.10`), checked before any page; and **`parse-failed`**, a page the tables do not know, or laid out otherwise (`WTI unit, page /N > 28 (title "..."): ...`: the page's path and title line, never its text). A user directory that cannot be read (the second connection is refused, or the list is longer than a pull reads) is not a failure: the pull is `ok` with a warning on its line, and `breakglass` reads `n/a` with a note.
- **The six sections** (and a seventh, `system`, for a scope that has a Junos `system` block: the login message, domain name and search, time zone, name servers and NTP servers the block states, compared additively, the device's other ones kept and listed as unmanaged, an NTP key set only where its number is missing, a login message kept in the record as its size and a digest, never as text) are `aaa` (the server and its key, the method lines, accounting and per-level authorization; on Cisco also the login method of the console and VTY lines, which the walkthrough sets to `login authentication CONSOLE` and `login authentication default`), `roles` (the login classes and their template users, the privilege lines), `mgmt-acl` (the management filter or access list and its application), `snmp`, `netconf` (compared only where the scope's or the device's NETCONF setting enables or disables the service: `enable` expects its statements and keeps the device's other ones under `system services netconf` as unmanaged, `disable` expects nothing there; a scope that leaves it alone compares nothing) and `breakglass` (the accounts by name, never the hash; for a scope that records `root`, a Junos device is also checked for its root password, by presence, under `system root-authentication`, and for `system services ssh root-login allow`, see [Junos root](break-glass.md#junos-root); a device's login user that differs from the scope's only in case, `netengineer` against `NetEngineer`, counts as the same account and the section reads ok with a note that says so, because the names are case-sensitive on the device and a login by the scope's spelling is refused there: record the device's spelling with `tacctl scope breakglass <scope> add <name>`). A section is the statements tacctl renders plus anything the device holds in the same hierarchy, so a stray server shows as `+`; in `snmp` the device's own statements that the plan keeps by rule show as `+` too and do not make the section differ (see **SNMP: communities, and the device's own statements**). Statements compare as sets, except the order of Junos `authentication-order` and of firewall filter terms and of Cisco ACL entries (`!`). A secret (a server key, a community, a hash) is compared by presence only: the record, the sections file, the diff and `--json` never hold its value. A login that cannot see the device's secrets (a Junos class without the secret permission masks them and omits a server's `secret`) is told so: a masked one is present, an omitted one is `?`, never `-`. A section tacctl renders nothing for is `n/a`, with the device's statements listed as `~`. A WTI unit has four of them: `aaa` (the TACACS+ or RADIUS page of the scope's protocol, the other protocol's page being the unit's own and listed as `+` and kept), `mgmt-acl` (the IP tables list, in order; the walkthrough's final DROP and the policies are the unit's own tail, kept and noted), `snmp` (the access and trap pages; an SNMP v3 scope is not compared and the section says so) and `breakglass` (the local users of the user directory, by name and level, never a password); `roles`, `netconf` and `system` do not exist on a unit and are not listed as `n/a`.
- **SNMP: communities, and the device's own statements.** A community's name is its secret, so a compared section never holds it: it holds a label that says whose the name is, `<secret:N>` for the N-th community tacctl renders for the scope (in the order of the rendering) and `<other:N>` for the N-th other string on the device (by first appearance). One string has one label throughout a pull, a Junos `trap-group` name (the community its traps are sent with) and the community word of an IOS `snmp-server host` included, so `diff`, the plan's report, `--json` and the stored sections tell tacctl's community from another one and never hold the string. The labels are relative to the rendering the pull was compared with: after a scope's community is changed, pull the device again. A stored record that holds the bare `<secret>` for every name is compared by presence, a note says so, and `plan` leaves every statement under a community of it alone (`the community's name is not visible`) and says to pull the device again. The `snmp` section reads `ok (+N unmanaged)` when nothing tacctl renders is missing or different and every extra statement is one the plan keeps by rule: another community and its client lists and leaves, a client list, view or SNMPv3 object tacctl does not render, a location, contact or description when tacctl renders none, and the statements no row covers (`snmp name`, `engine-id`, trap groups and options, on IOS `snmp-server host`, `enable traps` and the rest of `snmp-server`). `diff` and `pull --diff` still list them as `+` with the note `N statements of the device's own, kept on purpose`; `device show` and `diff` show `ok (+N unmanaged)`; `device config list` keeps the state `ok` and its DETAIL says `snmp +N unmanaged`; such a device is not in `--differs` or `--stale` and does not make `--exit-code` of `diff` or `plan` exit 2 (the plan still lists the extras, as left alone). Only `snmp` reads this way: an extra server, login class, filter or user in `aaa`, `roles` or `mgmt-acl` is an access finding and the section `differs`, as is any deactivated statement, any statement under a community of such a record, and an extra of the rendered community itself (a stray `clients` entry), which the plan deletes under its real name. In `--json` the `state` string stays `ok` and each section has the integer `unmanaged` (omitted when 0); `device config list --json` has the `unmanaged` map and the record `sections.<name>.unmanaged`.
- **What a scope's block may state.** A scope's block (and the default) holds only what is the same for every device of the scope. A value that names the device itself, an address it holds or an interface it has (`set snmp trap-options source-address <address>`, `set system ntp source-address <address>`, `snmp-server trap-source <interface>`, and the `source <interface>` of an IOS `ntp server`), is an error there: it is stated in the device's own block (`tacctl device block <name> ...`). The loopback by its convention name, `lo0` on Junos and `Loopback0` on IOS, is the one exception, with a note that a device without it cannot take it. A scope block that states one fails its check and is not rendered for any device (`tacctl scope block <scope> <vendor> check <block>` names the line); `adopt` into a scope leaves such statements out and says so.
- **The Junos `system` block: syslog, the login announcement, the retry options and the password policy.** Beside the login message, domain, time zone, name servers and NTP, the block states `set system login announcement <<'EOF'` (the text shown before the login, a heredoc like the message); `set system syslog host <address|name> <facility> <level>`, `host <h> facility-override <authorization|daemon|ftp|kernel|local0-local7|user>`, `host <h> log-prefix <word>`, `host <h> explicit-priority` and `syslog time-format year|millisecond`; `set system login retry-options` with `tries-before-disconnect` (1 to 10), `backoff-threshold` (1 to 3), `backoff-factor` (5 to 10), `minimum-time` (20 to 60), `maximum-time` (20 to 300) and `lockout-period` (1 to 43200 minutes); and `set system login password` with `minimum-length` (6 to 20), `minimum-changes` (1 to 128), `change-type character-sets|set-transitions` and `format md5|sha1|sha256|sha512`. The list is closed: another leaf under `syslog` or `login` (a file, the console, a user, a class) is an error, as is `maximum-time` below `minimum-time`. `syslog source-address <address>` names an address of the device and is the device's own block's only. A statement is identified by its host and facility, or its leaf; a more specific layer's replaces the less specific one's, and `delete system <the words of the identity>` says it is not managed on this device. The plan sets what is missing, replaces a differing level or value in place and never deletes (the device's syslog files and users are no business of the block and are left alone). `lockout-period` locks an account after its failed logins: the check says so.
- **Which block a statement comes from.** In the region of `device config plan` every statement that a block states has a comment before it that names the block in the words of the verb that edits it: `# from scope block lab juniper system` (`tacctl scope block lab juniper edit system`) or `# from device block sw1 system` (`tacctl device block sw1 edit system`); on IOS the comment starts with `!`. It changes where the layer does, so a device's own block laid over the scope's shows both. The reason above the section and the findings name the layers too (`the system block of scope 'lab' with the block of device 'sw1' over it`); a community or trap group is named for the layer that wrote it, and the scope's and the device's are two findings. The walkthrough (`device config show`, `config juniper|cisco --name`) has the same comments where the two layers are laid together; a block of one layer is named by its heading. `--plain` stays statements only, for `load set`.
- **Configuration blocks in the walkthrough, the compare and the plan.** A scope with a Junos `snmp` block in force has the block's communities (with their `authorization`, `clients` and `client-list-name`), trap groups and trap options (`agent-address outgoing-interface`, and one `source-address <address>|lo0`, replaced in place when the device's differs) appended to the SNMP step of `device config show` and `config juniper` (under a comment that names the scope's block, never a string), rendered even when the scope's own SNMP settings are not configured, compared as whole objects (a `clients` entry or a trap-group target the block does not state is an extra, which the plan deletes under its real name; the device's other communities stay `<other:N>`, kept and listed), and planned and backed out like the structured community. The management filter's `permit-snmp` term also permits the block's unrestricted IPv4 clients (a `restrict` entry is no permit; a community that uses a `client-list-name` gets a comment, because the list's addresses live on the device). A block with an error is never rendered in part: every Junos device of the scope is refused, with the line numbers and the verb that checks it. A community in the block that is the scope's own community is refused without printing it. A Cisco device takes the IOS `snmp` block (see **Configuration blocks: the IOS `snmp` block**) and never a Junos block. A scope with a `system` block has the `system` section (see **The six sections**), rendered as the last lines of the same SNMP step; the plan sets what is missing, replaces a single value (the login message, domain name, time zone, boot server, source address) in place, adds list entries and never deletes (the report says `the system block only adds`), warns when the one-line login message statement is over 1,000 characters (a line over 1,023 pasted into an interactive terminal is truncated: use `plan <name> --plain`), and the back-out puts a replaced value back (a replaced message cannot be typed back, since only its digest is kept: it names the rollback). A record that has no `system` section is not compared on it until the next pull, and the plan says to pull again.
- **Configuration blocks: the verbs.** `tacctl scope block <scope> {juniper|cisco} list|show|check|set|remove` and `tacctl device block <name> list|show|check|set|remove` keep the files and the lists in `tacctl.yaml` that put them in force. A block is its vendor's own syntax and nothing else: Junos `set` lines (a `delete` line says the object is not managed on this device and is kept, never rendered) or, for `cisco`, IOS configuration lines (a `no` line says the same); `<block>` is `snmp` or `system` (a WTI unit has no blocks); a scope with both Junos and IOS devices has a file per vendor. `set` takes the text from `--file <path>` (read as you) or `-`, runs the check, shows the objects that become owned and the diff against the file in force (elided), asks (`-y`), takes the configuration snapshot (which holds the block directory) and writes the file once, then names it in `tacctl.yaml`; nothing is restarted, because a block reaches a device only through `device config plan`. `check` and `show` never print a string: a community string, a trap group's name, an NTP key's value and the login message are marks (`<secret:N>`, `<group:N>`, `<secret>`, `<message: N lines, M characters>`), a comment line is never shown, and the check says a block community that is the scope's own community is refused. A device's block is laid over its scope's per object (a community the device states replaces the scope's of the same string whole, one it adds is added, the scope's others stay; likewise a trap group by name, a trap-options leaf, and in the system block a single value or an entry of a list), and the device's `delete` line takes the scope's object out for that device; `device block <name> show <block> --effective` prints the result with the layer of each object. The walkthrough, `device config show|pull|diff|plan` and the management filter's `permit-snmp` term use the resolved block, and a device whose own block has an error is the only device refused (the refusal names the device and `tacctl device block <name> check <block>`). `config validate` reports a name with no file (error), a file no list names (warning), a device's orphans (warning) and a block in force that has errors (error). An engineer reads the blocks of their own scopes and of the devices there (`list`, `show`, `check`; every `show --reveal`, the superuser's too, is logged as `secret-read kind=block name=<scope>/<vendor>/<block>` or `name=_devices/<device>/<vendor>/<block>`, never a value); `set` and `remove` are the superuser's, and each logs `block-set` or `block-remove`.
- **Configuration blocks: editing and adopting.** `tacctl scope block <scope> juniper edit <block>` and `tacctl device block <name> edit <block>` open a block in your editor, as `visudo` and `sudoedit` do: `VISUAL`, else `EDITOR`, else `editor`, else `vi` (a value may carry arguments; a path must be absolute), run as you, never as root, on a private copy (0600, named for the block) in a private directory (0700, under `/var/tmp`, handed to you) that is removed afterwards on every path, with your `HOME`, `TERM`, `LANG` and `LC_*` and nothing of sudo's or tacctl's. They are the superuser's and need a terminal on standard input and output; in the login console they are open only to those who have the system shell (`console system-shell`), since an editor can start one. The seed is the file in force, or for a new block its grammar and an example as `#` lines (a device's new block also has the scope's objects as `# set ...` lines to uncomment where the device differs). What the editor leaves is read back as you (a regular file of at most 256 KiB that is yours; a link or anything else is ignored), checked as `set` checks it, and installed as `set` installs it (objects, diff, question, snapshot, one atomic write, the entry in `tacctl.yaml`, logged `block-edit`). A text that fails the check is offered back, up to five times, with the errors as `# tacctl:` lines at the top (numbered as the editor's window is, removed before the text is read); an editor that exits non-zero, an empty text, one that states nothing and one that changes nothing write nothing. `adopt <device> <block>` (at the device level, `adopt <block>`) reads the device's own statements of the block's hierarchy (`show configuration snmp | display set`, or `system`) live with your login, as `device config pull` reads it (the password cache and prompt, the pull's transport and timeout, the pinned host key, its words for a failure), and opens them as the draft to prune; nothing of the device's text is stored, and the read is logged `secret-read kind=block-adopt name=<scope>/juniper/<block>` (or `_devices/<device>/...`). The draft is the statements the block's grammar takes minus the scope's own community, client list and v3 settings, the device's identity (`snmp name`, `engine-id`) and, at the device level, what the scope's block already states with the same statements; a community string or trap group name the login sees masked or as the device's ciphertext, and an NTP authentication key, are named as `# left out:` lines with their shape and no value, and the system block's login message is converted to its heredoc. An existing block of that name is opened first, whole, with the adopted statements beneath it under a `# adopted from <device> at <time>` comment. Both are `check`ed, shown as a diff, asked and snapshotted as `set` is, and log `block-edit` or `block-adopt`. The editor has to stay in the foreground until the text is saved (a graphical editor needs its wait option, such as `code --wait` or `gvim -f`: one that returns at once leaves tacctl an unchanged text). An editor may write swap or backup files beside its working copy: they land in the private directory and are removed with it; a block holds community strings, which are a poller's credential on this host and in the snapshots.
- **Configuration blocks: the IOS `snmp` block.** `tacctl scope block <scope> cisco ...` and `tacctl device block <name> ...` for an IOS or IOS-XE device keep an `snmp` block of IOS configuration lines, one per line, with `#` and `!` comment lines: `snmp-server community <string> RO|RW [<acl-name>]`, `snmp-server host <address> [vrf <name>] [informs|traps] [version 1|2c] <community> [udp-port <n>] [<type> ...]`, `snmp-server enable traps [<type> [<subtype> ...]]`, `snmp-server trap-source <interface>`, `ip access-list standard <NAME>` with `permit <address> [<wildcard>]`, `permit host <address>` or `permit any` under it, and `no ...` lines for what is not managed on the device. `check` refuses a name tacctl renders itself (the structured community, `TACCTL-SNMP`, the v3 names, the scope's management access list), a numbered access list, a read-write community with no access list or one that permits `any`, a placeholder, a tab, `snmp-server contact|location|source-interface|engineID|user|group|view`, an abbreviated interface (`Lo0` for `Loopback0`), SNMPv3 hosts, `informs` without `version 2c`, a `vrf` with no name or a name outside letters, digits, `.`, `_` and `-`, and any token off the grammar, with the line number and never a string. A community and a list the block defines are objects tacctl owns: the plan retypes a community whose access or list differs (in place, never removed), sets the entries a list lacks and removes with a `no` line each entry the block does not state; a list a community only names is the device's own and is kept. A trap host (an entry as IOS keeps it: one object per address, vrf, kind (`traps` is the default, `informs` needs `version 2c`), `udp-port` (162 is the default) and community, so one address as traps and as informs, on two ports or in two vrfs is several hosts, which a block states one line each and a device may hold side by side; the version and the notification types are attributes, replaced in place when they differ, compared as a set since IOS leaves out the default version, kind and port; the device's hosts of another vrf, kind or port are its own and are kept and listed) and an `enable traps` line (present when the device enables it in the expanded form it prints; a line with no type is present when the device has any `enable traps` line) are only ever added; the trap source is one value, retyped in place when the device's differs (compared without case, since a device stores `Lo0` as `Loopback0`), and the device's own is kept while the block states none. The device's other communities, hosts and lines are kept and listed (`ok (+N unmanaged)`), and `--converge` removes none of them. The block's lines follow the structured SNMP step of the walkthrough, also when the scope's own SNMP is not configured, under a comment that names the block and never a string. IOS has no confirmed commit: the plan is pasted line by line and its back-out is `no` lines (a replaced community or host is typed again by value; a trap host is undone with `no` and its line up to its `udp-port`, without the types, since IOS keeps a host of another kind or port as an entry of its own and a `no` that names the types removes only them). tacctl does not create a vrf: a host that names one the device lacks is refused by the device when the plan is pasted. `adopt` for IOS reads `show running-config | include ^snmp-server` and the section of each list a community names (the whole configuration once when the image does not know `| section`), drops tacctl's own community and list, v3 and the device's identity, takes each host line of a device as it is (a traps and an informs host of one address are two lines), and names what a block cannot hold (a numbered list, a view, an IPv6 list, a deny entry, a string shown as ciphertext, a host line that is the same entry as an earlier one) as `# left out:` lines; the device's own `snmp-server trap-source` is taken into the draft.
- **Configuration blocks: the IOS `system` block.** `tacctl scope block <scope> cisco ... system` and `tacctl device block <name> ... system` keep, for IOS and IOS-XE, the device's own system settings as IOS configuration lines with `#` and `!` comments, and the banners as heredocs so that they are easy to read and edit: `banner login <<'EOF'`, the text lines, `EOF` (and `banner motd`, `banner exec`, one of each at most); `ip domain name [vrf <name>] <name>`; `ip domain list [vrf <name>] <name>`; `clock timezone <zone> <hours> [<minutes>]`; `ip name-server [vrf <name>] <address> [<address> ...]`; `ntp server [vrf <name>] <address-or-name> [prefer] [version <1-4>] [key <n>] [source <interface>]`; `ntp authentication-key <n> md5 <string>`; `ntp trusted-key <n>`; `ntp authenticate`; the statements of a closed table (below); and `no ...` lines for what is not managed on the device. The block is additive, as the Junos system block is: a statement is set when the device lacks it, a single value that differs (the banner, the domain name, the time zone, an NTP server's options) is replaced in place, a list entry is only added, and what the device holds beside is kept and listed (`ok (+N unmanaged)`); a device's block is laid over its scope's per object and its `no` line takes the scope's object out for that device. A banner is typed as IOS's multi-line banner, `banner login|motd|exec <d>`, the text, `<d>` alone on a line, with `<d>` the first of `^ ~ % # @ $ &` that the text does not contain (a text of at most 20 lines of 80 characters, ASCII, no tab or control character; one that holds every candidate is refused). An `ntp authentication-key` string is a secret: it is typed only where the device has no key of that number (a device shows it as ciphertext, so a key is compared by its number alone), it is `<secret>` in `show`, `check` and every report, and `ntp authenticate` is one boolean. The plan types the NTP lines in the order IOS needs: the keys, the trusted keys, the servers, and `ntp authenticate` last. A statement that names a vrf is another object than the same statement without it: the vrf is part of its identity, a line without the vrf does not satisfy it and the other way round, `ip domain name` is one per vrf (and one without), and a block's `no` line names the vrf it takes out (`no ntp server vrf <name> <host>`, `no ip name-server vrf <name> <address>`, `no ip domain name vrf <name>`, `no ip domain list vrf <name> <name>`). The device's lines of a vrf the block does not state are its own and are kept (`ok (+N unmanaged)`), and the plan's undo of an added vrf statement is the line as the device takes it away (`no ntp server vrf <name> <host>`, `no ip name-server vrf <name> <address>`, `no ip domain name vrf <name>`, `no ip domain list vrf <name> <name>`). tacctl does not create a vrf: the block must name one the device has, or the device refuses the line when the plan is pasted (`check` notes each vrf the block names). The vrf forms are written for IOS 15.6 and IOS-XE 16.7 and later; IOS 12.4 was not tried. `check` refuses a placeholder, a key with no number or of another algorithm, an abbreviated interface, an IPv6 NTP server, a `vrf` with no name or a name outside letters, digits, `.`, `_` and `-`, with the line number and never a word of the banner or a key; `ip domain-name` and `ip domain-list` are read as the current spellings. The device's own `banner motd` and `banner exec` are the section's only where the block states one of that kind (the login banner always is); otherwise they are nobody's business. The comparison reads both sides alike: a banner is its size and a short digest (`banner login <message: 22 lines, 1300 characters, id 3fa9c2d1>`; no text of it is stored or reported), `clock timezone CET 1` and `CET 1 0` are one statement, `ip name-server [vrf <name>] A B` is one statement per address (IOS 15.6 stores a vrf's list one address a line, IOS-XE 16.7 on one), an NTP server's keywords are compared as a set, host names and interfaces are compared without case, and a banner printed with `^C` or one printable delimiter is read as the text between them. The block's lines follow the SNMP step of the walkthrough under a comment that names the block (and the delimiter used), the Step 0 comment for the domain name names the block's value, the managed section `system` and `--section system` exist only for a scope that has the block, and the plan's back-out types a replaced single value again, takes an added statement away as the device takes it, and, for a replaced banner (only its digest is kept), names the way back (`configure replace` with the archived or the startup configuration). The whole-paste check treats the banner's text as text up to its closing delimiter, a line that starts with `!` included. `--converge` removes none of the device's own lines. `adopt` reads `show running-config | include ^(banner|ip domain|ip name-server|clock |ntp |logging |service timestamps|login |security |ip ssh)` and the banners' lines with `show running-config | section ^banner` (the whole configuration once when the image does not know `| section`), takes the vrf forms in as the block's statements, and leaves each `ntp authentication-key` out with a `# left out:` line. `clock timezone UTC 0` is IOS's default zone, which it does not print: it reads as present on a device with no `clock timezone` statement. IOS 12.4 stores an `ntp server <host> version 3` without the option, so a device in the IOS 12.x syntax is rendered and compared without it (the walkthrough, the managed section and the plan type `ntp server <host>`; every other option and version stays, and the block's text, `show`, `check` and `adopt` keep `version 3`). The report says beside the plan when the block has NTP key lines, which are not checked against a device.
- **The IOS `system` block: logging, timestamps, login and password policy, ssh and summer time.** Beside the banner, domain, time zone, name servers and NTP, the block states `logging host <address|name> [vrf <vrf>]` (one line per host), `logging trap <severity>`, `logging buffered <4096-2147483647> [<severity>]`, `logging origin-id hostname`, `service timestamps log|debug datetime msec [localtime] [show-timezone]`, `login on-failure log [every <1-65535>]`, `login on-success log [every <1-65535>]`, `login delay <1-10>`, `security passwords min-length <1-16>`, `security authentication failure rate <2-1024> log`, `ip ssh version 2`, `ip ssh time-out <1-120>`, `ip ssh authentication-retries <0-5>` and `clock summer-time <zone> [recurring [<week> <day> <month> <hh:mm> <week> <day> <month> <hh:mm> [<offset-minutes>]]]`. The list is closed: another `logging`, `service`, `login`, `security` or `ip ssh` statement (`logging console`, `logging source-interface`, `service password-encryption`, `login block-for`, `ip ssh source-interface`, `ip ssh version 1`) is an error, as is anything outside the block. A statement is identified by its words up to the value (a `logging host` by its host and vrf, a `service timestamps` by `log` or `debug`), a more specific layer's replaces the less specific one's, and a `no` line names the same words. The plan sets what is missing, replaces a differing value in place and never removes (the device's other logging hosts and the rest of its configuration are kept and listed); the three `ip ssh` settings are the only `ip ssh` statements the plan ever types. `login delay` makes every login wait after a failed one, the server's own included: the check says so.
- **Services a block requires to be absent.** Both `system` blocks take `absent` lines, the hardening that no `set` line can state: Junos `absent system services telnet|ftp|finger|xnm-clear-text|web-management`, IOS `absent ip http server|ip http secure-server|service tcp-small-servers|service udp-small-servers|ip finger|service finger` (only a statement the running configuration prints while the feature is on, so that its absence can be compared; `ssh`, `netconf` and the rest are not in the list, and a `set system services ...` line is an error). The device that holds the service, or any statement under it (`telnet connection-limit 5`), differs from the block; the plan deletes the whole statement once (`delete system services telnet`, `no ip http server`) under a comment that names the block, and the back-out types it again. A `delete` (Junos) or `no` (IOS) line of the same words in a device's own block takes the scope's marker out for that device. The deletes are the only ones under `system services`, besides the NETCONF setting's, that `device config apply` admits, and only when the rendering states the marker. A block of `absent` lines alone is a block: nothing else of the device is compared with it. The check notes that a way in by the service goes with it. The walkthrough lists the commands after the block's statements, and `device block ... show` prints the lines as written.
- **Cisco: login method and `enable`.** The line a statement belongs to is read by range: with `aaa new-model` on the device, a console or VTY line that has no `login` statement is on the default method list (IOS does not print it) and counts as `login authentication default`, as does one that prints `login authentication default`; the rendered `line vty 0 15` is satisfied when the device's ranges (`line vty 0 4`, `line vty 5 15`) with that method cover it. The console is the exception: it is on the default list, which is not the standard's own `CONSOLE` list, so a console that prints no leaf shows `- line con 0 > login authentication CONSOLE` and `+ line con 0 > login authentication default`. `aaa authentication login CONSOLE local`, `aaa session-id common` and, where the scope sets one, `ip tacacs source-interface <interface>` are statements like any other. The standard has no `aaa authentication enable` list (see **The `enable` design** in [Cisco IOS / IOS-XE](cisco.md)), for TACACS+ and RADIUS alike: a device's `default` list of that kind (`default group <G> enable`, `default group tacacs+ ...`, `default enable group <G>`, `default line`, `default none`, any other) is an extra (`+`, severity ACCESS), and only `aaa authentication enable default enable`, which is what IOS does with no list, is neither missing nor extra; a list of another name is an extra of that name and is kept. A source interface the device has where the scope sets none is nobody's and not listed. A line that says `login local`, `login`, `no login` or another list shows `+ line vty 0 4 > login local` and `- line vty 0 15 > login authentication default` in `aaa`, and the ranges that are in order are not listed. Without `aaa new-model` a line with no `login` statement has no method, so the rendered line is `-`, and a router that has nothing of AAA but `login local` on its lines is `missing`, the lines listed all the same. Whether the device holds an `enable` secret or password (for level 15) is recorded, never its value, and a device with none gets a note under `aaa` when the rendering turns AAA on: with the server unreachable, a local user of privilege 15 is then the only way to level 15. A stored record that holds nothing about the lines or about `enable` is not compared on the lines (a note says so) and gets no `enable` note until the next pull.
- **What it compares with** is the same text the walkthroughs render (`tacctl config <vendor>`), built per device from its scope: a Cisco device is compared in its configuration syntax (see **Cisco: the configuration syntax**), whatever its ssh flag says. `--server` and `--source` render for a device behind a translating firewall, as for `config <vendor>`. The expected configuration is the complete one whoever asks, so the recorded states do not depend on the caller's tier.
- **Cisco: the configuration syntax.** A device is compared, and walked through by `device config show` and `config cisco --name`, in one syntax: the explicit setting of `tacctl device ios-syntax` (`ios12` or `modern`), else the syntax the last pull derived from the device's version line (`Version 12.` is `ios12`; `Version 15.2` to `15.9`, `16.`, `17.` and `IOS-XE` are `modern`; any other line is unknown and is never guessed: IOS 11.x, IOS 15.0 and 15.1, an ASA, IOS XR, a boot-ROM line alone), else, in the walkthrough only, the modern syntax with one line (`# syntax: modern (no pull yet; ...)`, or `the last pull holds no image line: run device config pull` for a device whose record has none). `legacy-ssh` is the ssh algorithms and has no part in it; `--legacy` of `config cisco` and `device config show` stays an explicit IOS 12.x syntax for that run. A scope served over RADIUS has one syntax. A pull compares in the syntax the device says now (so an upgraded device is not compared in the syntax it had) unless the setting says otherwise; a pull that reads no image line (a boot-ROM `ROM:` or `BOOTLDR:` line is none), or one that no row maps, and has no setting is refused with the command to set it; such a pull is not recorded, so `device config list` is unchanged and the pull's own output is where the reason is. A setting that the pull's image contradicts wins and is shown by `pull` (text and `--json`: `syntax_conflict`, `image_syntax`, `os`), `device show`, `device config list` and the walkthrough. A Cisco device whose setting is `auto` and whose record has no version line (a record made by an older release, or by a pull under a setting that read none) is not compared as either: `device config list` shows `pull` with `needs pull (syntax unknown)`, `--stale` selects it, and `tacctl device config pull --vendor cisco` makes it known; set `ios12` or `modern` to compare it without that pull.
- **Device facts.** A good pull records what the device reports about itself, as read-only facts in the record (never in `devices.yaml`) that every good pull replaces: the **release**, the **model** and the **serial number**. The release of a Junos device is the `Junos:` line of `show version | no-more` (an older Junos prints none: its `JUNOS Base OS boot [...]` line; else the `set version` statement of the configuration the pull read, which is the release it was last committed under), the version of the `Cisco IOS Software ... Version X,` line of the version output a Cisco pull reads (`15.6(2)T`, `12.4(15)SW`, `16.7.1`; else the first image line's number), and a WTI unit's command menu version. The model and the serial number are read with more commands in the same session, run after the configuration is read: Junos `show chassis hardware | no-more` (the `Chassis` row: its description is the model and its serial number the serial; `Model:` of `show version` is the model when the chassis row gave none) and IOS and IOS-XE `show inventory` (the first entry's `PID:` and `SN:`), over NETCONF the same commands without the `| no-more`, through the `<command>` RPC. A device that refuses a command, a class that may not run it, an old release that does not know it and an answer that holds none of it leave the field empty: the pull does not fail and its result is unchanged, no extra login is made, and a command that stalls takes the pull at most 15 seconds more. A WTI unit has a release only (its menu prints no model or serial number). `device show` has `Release:`, `Model:` and `Serial:` rows after the Configuration row (a row is left out when empty), `device config list` a `RELEASE` column, and `--json` the fields `release`, `model` and `serial` (`release` only in `device config list --json`); a failed pull keeps those of the last good one, and all of it is shown to whoever is shown the Configuration row.
- **Records.** `/var/lib/tacctl/devices-config.json` holds, per device, when it was pulled, by whom, over which transport, the NETCONF probe, for a Cisco device the version line and the syntax derived from it, the release, model and serial number (device facts, above) and the file system word of its `archive` / `path` statement (`flash:`; for the plan's `--restore-point`), and the state of each section (with the number of the device's own statements of an `ok` one); `/var/lib/tacctl/device-config/<name>.yaml` the managed sections of the last successful pull (secret values elided), and, for a Junos device, `<name>.plain` the same read without the groups' inheritance applied (`device config plan` tells a group's statement from the device's own by the two; the view is read only for the pull it was made with), and `<name>.backout` the back-out of the last plan that had changes. A failed pull changes the record's result and keeps the sections of the last good pull, which `diff` still compares. `device list` shows the recorded state; `device config list` computes it against today's rendering, so a change of the store or `tacctl.yaml` makes a device `differs` without a new pull. `device config forget` deletes the records.
- **Apply records.** A check or an apply of a device (`device config apply`, see [Planning a device's change](planning.md#applying-a-plan)) keeps in its record, beside the pull's fields, the `applied` part: `at`, `by`, `id` (the change identifier in the commit comments), `kind` (`check`, `apply`, or `onboard` for the commit of [`device onboard`](planning.md#onboarding-a-blank-device)), `result` (`checked`, `applied`, `rolled-back`, `pending`, `failed`, `unknown`; a device with nothing to change leaves the last one), `reason`, `via` (`cli` or `netconf`: the transport the run wrote through; a record of 0.2.9 has none), `until` (the end of a pending window), `shape`, `sections`, `set`, `delete`, `insert`, `commit` and `pre` (the fingerprint of each planned section before the change). `device config list` shows it in the `APPLIED` column once a listed device has one, `device show` in the Configuration row (`apply: applied 2026-10-13 14:12 by alice (<id>, shape <hash>)`, or `PENDING until 14:22:00` in red), and the `--json` of both as `applied`. `device config forget` removes it with the pull record.
- **Local logins.** A pull made as a device's local account (`--login`, `device onboard`) says so in the record: `login` is `local:<account>`; `user_pulled` stays set once any good pull was made as the invoking user's own login, which is what `--login root` and a second `device onboard` of the address look at.
- **After a setting changes.** A registry setting the configuration is rendered from (`device location`, `description`, `address`, `ios-syntax`, `vendor`) says, in one line, when the device has a stored pull that `device config plan` would now change: `The configuration of <name> would change: tacctl device config apply <name> --check` (`device config plan <name>` for a device that is not Junos or a caller who is not a superuser). The line is made from the stored pull alone: no login, no network, and nothing for a device that was never pulled or whose pull is stale. `--apply` on `location`, `description`, `address` and `ios-syntax` runs [`device config apply`](planning.md#applying-a-plan) for that device right after the value is stored, in the same command: the same review and confirmed commit, never skipped; a superuser, a Junos device and a terminal are needed, and without them nothing is changed. `device rename`, `port`, `legacy-ssh` and `hostname` do not change the rendered configuration (a rename says the device's own host name is unchanged and not planned by tacctl). A change that writes what a scope's devices are rendered from (`scope prefixes`, `secret`, `mgmt-acl`, `snmp`, `block`) says the same for the scope when at least one of its devices has a stored pull that would change: `tacctl device config apply --scope <name> --check`.
- **Apply settings.** `device.apply.confirm_timeout` (`config devices apply-confirm-timeout`, 3 to 60 minutes, default 10) is the N of the `commit confirmed N` of every `device config apply`: the device undoes the change by itself after N minutes unless the run confirms it, and a window under three minutes cannot hold the verification. `device.apply.pause` (`config devices apply-pause`, 0 to 3600 seconds, default 60; 0 is none) is the wait between the devices of a batch after the canary; `--pause` of one run replaces it. Both are the superuser's, are written to `tacctl.yaml` only when set, and `config devices` shows them with the others. `device.apply.transport` (`config devices apply-transport`, `cli`, `auto` or `netconf`, default `cli`) is how `device config apply` reaches a Junos device; see "Applying a plan" in the planning page.
- **Many devices.** At most `device.config.max_concurrency` (default 8, at most 64, `config devices max-concurrency`) devices are read at once; `--concurrency` lowers it for one run and is refused above it. Each device has `--timeout` (default `device.config.timeout`, 90 s, connect included). A progress line per device is rewritten in place on a terminal and appended otherwise; `--json` prints one line per device and a summary line. The first rejected password stops the batch (one wrong password must not lock an account out on many devices); `--max-failures <n>` stops after n failures. The first Ctrl-C stops starting devices and lets the running ones finish (the rest are `not started`); a second cuts the running ones off. The status is 130 either way.
- **How IOS stores typed lines.** IOS stores some typed lines in another form, which the comparison takes as the typed ones: `permit host A` and `permit A 0.0.0.0` are stored as `permit A`, trailing blanks and the order of the aaa lines do not count, and the `privilege exec level N <words>` lines IOS adds for the words that lead to a command the rendering carries are not extra (one left under a command that nothing renders any more is). An IOS 15.x or IOS-XE image does not remove a privilege line that is negated: `no privilege exec level 7 clear counters` leaves `privilege exec level 15 clear counters`, and `no privilege exec all level 7 ping` leaves `privilege exec level 1 ping`, with the words leading to them (`level 15 clear ip`, `level 15 monitor`, `level 1 clear`, `level 1 show`) at their own levels; that line is the image's own and nobody can remove it, so it is neither compared nor reported when the command is one tacctl lowers or has lowered (`ping`, `traceroute`, `monitor capture`, `clear counters`, `clear line`, `clear ip arp`, `clear arp-cache`, `clear mac address-table dynamic`, `undebug all`, `show running-config`, and the words leading to them), the level is that command's own, it has no `all`, and the rendering has no line for the command (a line at another level is extra, and a rendered line that the device lacks is still missing). An image that does not know the last words of a privilege command (IOS 12.4 has no `monitor capture`, and stores `privilege exec level 7 monitor` for it) shows that command as missing, with a note naming the line the device holds instead (a device on which the command was removed and its parent left looks the same, so it is not read as equal), and the stored line is not extra; a privilege line that the image accepts and does not store at all shows as missing on every pull; `snmp-server queue-length 100`, which IOS 12.4 prints beside the first community, is not extra when tacctl renders a community. `snmp-server user` lines, which `show running-config` does not print, are not compared.

```yaml
# /etc/tacctl/devices.yaml
version: 1
settings: {stale_days: 30}
devices:
  core-sw1: {address: 10.99.0.1, vendor: cisco, legacy_ssh: true, ios_syntax: modern,
    description: DC1 core}
  lab-rtr2: {address: 192.0.2.7, vendor: juniper, hostname: lab-rtr2.lab.example.net,
    snmp: {version: v3, port: 1161, clients: [192.0.2.0/24]}}
```

The optional `snmp:` map of a device (`version`, `port`, `timeout`, `clients`) is written only for a device that sets its own SNMP settings (`tacctl device snmp`); its credentials are not in this file.
