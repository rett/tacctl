# Cisco IOS / IOS-XE

[Documentation](../README.md) › [Network devices](README.md)

The generated config is the **standard Cisco block**: the same lines, in one order, for every Cisco device, so that a device configured by it needs no explanation and a pull can say exactly what differs (see [Device configuration](configuration.md#device-configuration)). It has two steps:

- **Step 0, a commented checklist** (never compared, never part of the managed sections): `hostname`, `ip domain name`, `no ip domain lookup`, `service password-encryption`, `service timestamps debug|log datetime msec localtime`, `no service pad`, `no ip source-route`, `no ip http server`, `no ip http secure-server`, `ip ssh version 2`, `ip ssh time-out 60`, `ip ssh authentication-retries 3`, `transport input ssh`, `exec-timeout` and `logging synchronous` on the lines, and the local enable secret (`no enable password`, `enable algorithm-type scrypt secret <PASSWORD>`; `enable secret <PASSWORD>` with `--legacy`), followed by the scope's [break-glass accounts](break-glass.md#break-glass-local-users) and one commented line that names `tacctl breakglass hold <device>` as the way to use them while the server is up ([Holding break-glass](break-glass.md#holding-break-glass)). Site policy differs, so tacctl prints these and keeps no value for them; type what your site uses before Step 1.
- **Step 1, the AAA standard**, in the order that keeps the session you paste from alive: `aaa new-model` first (nothing under `aaa` exists on IOS until it is set, so a group and its `server` leaf typed before it are rejected); the server block and its group; `ip tacacs source-interface <interface>` when the scope sets one; `aaa authentication login default <methods>` and `aaa authentication login CONSOLE local`; `aaa authorization exec default <methods>` (no `aaa authentication enable` line: one comment says `enable` is the local enable secret); `aaa accounting exec ...` and `aaa accounting commands <level> ...` per level in use; `aaa session-id common`; the `privilege exec level` mappings; SNMP; the VTY access list; NETCONF (commented); `line con 0` with `login authentication CONSOLE` and `line vty 0 15` with `login authentication default`. From `aaa new-model` until the login lists are typed a new TACACS+ login would fail (a local user still gets in): paste the block in one go and keep the session you paste from.
- **The check, then Step 2, the command authorization** (`aaa authorization commands <level> ...` per level in use, then `aaa authorization config-commands`), which is not in Step 1. The session that pastes was opened before AAA, as a local user the server does not know, and a server that answers `fail` for a name it does not know is final and never falls through to `local`: from the first command authorization line every command of that session (and of a break-glass local user, while a server answers) would be denied, and a device whose TACACS+ path is not proven could end with no session able to run a command. So open a new session with your own TACACS+ account, run `show privilege` (it must say the level the server gives your group), and type Step 2 from that session with a second one kept logged in.

The names are the plain ones tacctl renders and none is a setting: the server block `TACACS`, its group `TACACS-GROUP` (`scope tacacs-group` sets another), `VTY-ACL`, `TACCTL-SNMP`, and the console's login list `CONSOLE`. The console has a list of its own, local only, so that a local user can always log in there: the `default` list asks the server first, and a reject from the server does not fall through to local. With the server up, a local user on `line con 0` lands at privilege 1 (the standard does not set `aaa authorization console`, and must not: it would put the console under the `default` lists, server first, and defeat `CONSOLE`), and `enable` with the local enable secret takes it to privilege 15, with the server up or not (the standard has no enable list); so the local console works while the server answers. A vty is the other way round: a local name there is refused by the server while it answers, and `tacctl breakglass hold <device>` makes the server stop answering one device on purpose for that (see [Holding break-glass](break-glass.md#holding-break-glass)).

**The `enable` design.** Nobody needs `enable` in normal operation: a TACACS+ user lands at the level the server's `priv-lvl` gives (`aaa authorization exec`), a superuser at 15 at once and an operator at 7. The standard has no `aaa authentication enable` line, so `enable` uses the local enable secret and nothing else (Step 0 sets it; the walkthrough carries one comment that says so). A list that asks the server (`aaa authentication enable default group <G> enable`) is not part of it: tacquito answers an enable request as a login with the user's own password, so an operator who typed `enable` and their own password would reach privilege 15 and could read `show running-config`, with the TACACS+ key, the enable secret's hash and the local users' hashes in it. RADIUS has no enable list either, by the same rule. The cost: the local enable secret is the one shared secret of the way up, on the vty and on the console alike, while the server is up, and who holds it is site policy (Step 0: tacctl prints the line and keeps no value for it). Command authorization at level 15 still asks the server with the user's group rules, so an operator who knows the secret still cannot configure, debug or clear, and can read the running configuration. A device with no enable secret has no `enable`: `device config plan` warns about it. `tacctl breakglass hold <device>` is for a vty local login and for Junos and WTI; see [Holding break-glass](break-glass.md#holding-break-glass).

**Key points:**
- `local` fallback ensures access if TACACS+ is unreachable. A group at priv-lvl 15 is kept apart from the superusers only by the server's rules, so with the server unreachable the fallback lets it run everything
- Per-command authorization and command accounting: `aaa accounting commands <level>` for every privilege level a group uses, always; once any group has command rules also `aaa authorization commands <level>` per level (commented out, with the group named, for a level where a group has no rules) and `aaa authorization config-commands`; commands typed on the console line are not authorized by the server, and `aaa authorization console` is not to be set (the walkthrough says so)
- `ip tacacs source-interface` is the one policy value the standard needs from you: set it once per scope with `tacctl config cisco source-interface <scope> <interface>` (the server then sees one stable address per device, which must be inside a prefix of the scope). Give the full interface name as IOS prints it (`Loopback0`, `GigabitEthernet0/0/1`; not `lo0` or `gi0/1`, which IOS stores in the long form). Unset, the walkthrough prints the line commented with that command and nothing is rendered or compared A source interface typed inside `aaa group server` is an older per-group form: the plan and the diff name it as such, and the standard sets one for the device.
- Custom privilege levels (2-14) require `privilege exec level` command mappings (or another mode: see [Cisco priv-exec mappings](../security/cisco-priv-exec.md#cisco-priv-exec-mappings))
- The server's port is the configured listener's (`tacctl config listen`; 49 by default): a listener that moved adds `port <n>` under `tacacs server TACACS` (after `address ipv4`; in `--legacy`, after `single-connection` on the `tacacs-server host` line), and a default one adds nothing. `device config diff` and `plan` follow it (see [The server's port](walkthroughs.md#the-servers-port)).
- Use `config cisco` to regenerate after adding groups, and re-paste the AAA block after a group's level changes
- By default the output uses the modern `tacacs server <name>` block (IOS 15.2 and later, IOS-XE). For older devices (e.g. IOS 12.4), add `--legacy` to emit the global `tacacs-server host` / `aaa group server ... / server <ip>` syntax instead. What differs from the modern output is the server-definition block (the global `tacacs-server host ... single-connection timeout 5 key ...` line and `server <ip>` under the group, in place of `tacacs server TACACS` and `server name TACACS`), the local enable secret line (`enable secret <PASSWORD>` in place of `enable algorithm-type scrypt secret <PASSWORD>`), the hashes of the break-glass accounts (type 5 instead of type 9), the NETCONF step (IOS 12.x has none: one comment line) and the Type 6 note (not available on IOS 12.x); the AAA lines, `roles`, SNMP and the access list are identical.

**A device configured from an earlier walkthrough.** The block adds lines an earlier walkthrough did not have (`aaa authentication login CONSOLE local`, `aaa session-id common`, `login authentication CONSOLE` under `line con 0`, and the source interface when set). `device config pull --diff` reads them as missing (`-` lines); the console, which was on the default list, reads as `login authentication default` where the standard has `CONSOLE`. The old forms a device may still carry (`tacacs-server host` on a modern image, `radius-server host` beside a `radius server` block, a server group of another name) are listed as extras (`+` lines), never as satisfied lines, and the walkthrough removes none of them: `tacctl device config plan` replaces an entry at the standard server's address in its region and `--converge` removes the others (see [Device configuration](configuration.md#device-configuration)), and what neither does stays on the device until you remove it there. An old `tacacs-server host` entry at the standard server's address on a modern image, on a device that `plan` refuses (command authorization on and no server in use), is replaced from the console, as a user that reaches privilege 15 there, in four steps: `no tacacs-server host <address>`; the standard's `tacacs server TACACS` block (Step 1); in each `aaa group server tacacs+ <group>` that held `server <address>`, `server name TACACS` and then `no server <address>`; then open a new session and check one command. (Whether IOS takes the named block beside the old entry is not known, so remove the old entry first; with command authorization on, a TACACS+ session that removes it would be denied its own commands, so do not paste Step 1 over it from such a session. The groups keep their names, and the method lists that name them keep resolving; when no group holds the old address, because the method lists use `group tacacs+`, the standard group is created and pointed at the named block and the lists keep using `group tacacs+`.) A device that also has `aaa authorization console` cannot take the four steps as they are: after the old entry goes the group has no server, command authorization falls to `local`, and a TACACS+ user is not in the local database. A step 0 comes first, typed while the TACACS+ user's commands still pass: `configure terminal`, `no aaa authorization console`, `end` (the standard never sets it and it is not put back). If the console session is refused after it, type steps 1 to 4 from a new session as a user that reaches privilege 15. A device with no local user at privilege 15 needs the break-glass account of Step 0 before `aaa new-model` is typed: that is why Step 0 comes first.
